## 论文概要：大禹水利记忆网络

**问题背景。** 当前 Agent 记忆系统的主流范式是“存储 + 检索”：把对话蒸馏成事实或摘要，需要时用向量、BM25 或图遍历把相关条目拉回上下文。这套范式有三个结构性局限：其一，检索是一次性的、无状态的查询，无法表达“想起 A 导致想起 B”的路径依赖；其二，遗忘是条目级的状态判定（删除、失效、衰减阈值），无法表达“记忆一直在、只是这次线索不够强”的舌尖现象；其三，记忆注入通常不把“前缀缓存字节稳定性”当作一等约束，长会话高频召回时成本失控。

**核心思想。** 大禹治水，疏而不堵。记忆系统里没有“删除”这道堤坝，只有球的大小、管道的粗细、水量与阻力这组水文参数。记忆不是被清理，是被调度：纠正靠放水缩球，遗忘靠自然沉底，唤醒靠强线索突破细管。没有被删除的记忆，只有还没等到足够强水压的记忆。

**模型。** 图上的点是大小不同的球，大小表示记忆强度；边是粗细不同的管道，粗细表示关联强度；一次对话触发一次激活，给定总水量（`total_water_budget`）从起始球注入，水沿管道传播，每跳扣损失，到达球时按相关性决定是否补充，水量耗尽或触达安全阀时停止。流动只点亮球、不写入；结算同步立刻执行，用流动加权语境算相关性、按路径相关性强化路径上的球和管道、决定本轮注入哪些球。损失是试探的成本，补充是球当前状态的兑现，补充大于损失当且仅当球大、新鲜、强相关。

**关键机制。** 球分 `ball_stored_size`（累积强度，不衰减）和 `ball_effective_size`（读取时现算，含时间衰减），衰减只算一次；管道是无向权重，同时决定阻力与损耗，阻力有上限、强线索可突破；分配按 `1 + pipe_effective_thickness` 加权，先分配后判断、损失不回收；资格看 `semantic_similarity`、幅度和排序用 `semantic_similarity × 路径折扣`，每种信号只负责一件事；短期记忆永不删除、只降可提取性，强线索可唤醒；纠正审计先行、软删默认、强度守恒、可逆。

**与前缀缓存的兼容。** 所有动态记忆只追加在 messages 尾部，不回写 system prompt、工具 schema 或历史中段；前缀只做只读冻结，动态性全部赶到尾部。这不是“完全兼容”，是“有条件兼容”，条件是接受“注入位置只能在尾部”。

**可观测性与证伪。** 可观测性在这个项目里不是监控面板，是证伪工具——它让“动力学扩散是否优于查询检索”“阻力上限是否制造假阳性唤醒”“路径级强化是否导致联想僵化”这些概念赌注能被数据回答。在线只保留激活快照（`activation_log`），激活性价比的判定和“不遗漏”的调参在离线完成，由用户用 AI 从 DB 检索判定，不在线加规则。

**结论。** 大禹水利记忆网络是一个概念上自洽、工程上可实现、可被数据证伪的异类提案。它的价值不在于“比 Mem0 更好”，而在于它提出了一个主流方案没有认真回答的问题：如果记忆提取不是查询，而是一个有阻力、有竞争、有路径依赖的过程，记忆系统的结构应该长什么样？

## 一、初始水量（注水入口）

### 总水量预算（`total_water_budget`，原 W₀）

**起因**：每次激活需要一个预算上限，否则多义输入会自动获得更强扩散力——命中三个起始球就是三倍水，一个“多义”的输入自动获得更强扩散力，这是无意的放大，破坏了预算守恒的前提。

**理念**：预算是本次激活的硬约束，命中几个球、几个源，都不改变总量。单源时严格守恒，多源时受控放大——多线索共同指向同一批球本身就是强信号，值得比单源略强的扩散力，但不该线性叠加，否则“多塞一个输入源”会变成无成本的扩散放大器。

**解释**：`total_water_budget` 是本次激活的总注水量，是一个固定值，不随命中球数变化。起始球之间按余弦占比分配，不是每个球各拿一份。单源时总水量严格等于预算，按 `water_i = total_water_budget × cosine_i / Σcosine_j` 分配到起始球；多源时总水量按 `total_water_budget × min(1 + source_bonus × (n_sources − 1), source_cap)` 次线性放大并封顶，`source_bonus` 默认 0.3、`source_cap` 默认 1.5。

**方案**：`source_bonus = 0` 时倍率恒为 1.0，退化为严格守恒，用于验证“多源放大”是否带来实质收益；“命中几个球不改变总量”仍然成立——那是起始球之间的分配，与源数量无关；变的是“源数量可以适度放大总预算”，但这部分放大有上限、不随源数量线性增长。

**结论**：单源严格守恒、多源受控放大，命中几个球不改变总量、只改变“往哪浇、各浇多少”。这是所有注水相关条目的预算前提，任何“总量随命中数膨胀”的实现都是 bug。

**关联**：起始球选择、注水分配、强线索放大、多输入源汇合、除零防御。

### 起始球选择（`start_ball_threshold`，原 start_threshold）

**起因**：每次激活需要确定从哪些球开始注水。如果没有下限，任何球都能成为起始球，哪怕余弦只有 0.05——总水量是固定的，弱相关球分走一份水，强相关球就少一份，水被摊薄到突破不了任何管道。

**理念**：只有语义上足够相关的球才值得被浇。阈值的作用是保证“水不被摊薄”，Top-N 的作用是保证“多线索不被遗漏”。没有球超阈值时本轮不注水，这是正常状态、不是故障——用户说“今天天气不错”，图上可能没有任何球和它相关，这时候不注入记忆是对的，强行注入只会引入噪声。

**解释**：当前输入嵌入与所有 `active` 状态球算余弦，过滤低于 `start_ball_threshold`（默认 0.3）的球，按余弦降序取 Top-N（默认 3）。执行顺序是“先过滤、再取 Top-N”，不是“先取 Top-N、再过滤”——否则可能取到 3 个但其中两个低于阈值，实际起始球不足。

**方案**：`start_ball_threshold` 太低（如 0.1）会让什么球都成为起始球、水被摊薄；太高（如 0.6）会让很多该想起的记忆想不起来；0.3 是“弱相关但可能有用”和“基本不相关”之间的经验分界，需要根据真实对话调。`start_top_n` 太大则水分散、每个球突破不了管道，太小则漏掉多线索。

**结论**：阈值保证水不被摊薄、Top-N 保证多线索不被遗漏，无球超阈值是合法的“这次没有相关记忆”，不是故障。三个阈值（`start_ball_threshold` 0.3、`flow_continuation_threshold` 0.3、`strong_cue_threshold` 0.85）语义不同、作用位置不同，可以独立调、不要求相等。

**关联**：总水量预算、强线索放大、多输入源汇合、除零防御。

### 注水分配

**起因**：多个起始球之间需要分配总水量。原实现每个起始球都拿满 `base_water_amount × significance`，命中 3 个球就是 3 倍水——一个“多义”的输入自动获得更强扩散力，这是无意的放大。

**理念**：总水量守恒，按余弦占比分配，不是每个球各拿满一份。余弦越高的起始球分到的水越多，这符合直觉——当前输入和某个球越相关，水压越大，越可能突破它的管道、流向更深层的联想。

**解释**：`water_i = total_water_budget × cosine_i / Σcosine_j`，余弦越高的起始球分到的水越多。起始注水量只由“当前输入与球的余弦”决定，和球本身大小无关——一个很小的球如果和当前输入高度相关，照样分到很多起始水；但起始球被注水后，它释放的补充量 = `ball_effective_size × 归一化相关性`，球大、新鲜的起始球补充多、水流更容易继续，球小、陈旧的起始球补充少、水流可能在第一跳就衰减。起始水决定“能不能启动”，球的大小和新鲜度决定“能不能持续”。

**方案**：单起始球时占比 100%、退化为拿满 `total_water_budget`；`Σcosine` 做除零防御，小于极小阈值（如 `1e-9`）时跳过本轮注水、返回空注入块、记 `start_allocation_zero_denominator` 指标；不设“给所有起始球平均分”之类的兜底，因为分母异常说明起始球选择本身出了问题，静默兜底会掩盖上游 bug。

**结论**：总量守恒、按相关度分配，除零防御保证异常时不产生 `inf`/`NaN`、不静默兜底。这是修正“每球各拿满预算”bug 后的正确行为。

**关联**：总水量预算、起始球选择、多输入源汇合、除零防御。

### 强线索放大（`strong_cue_threshold`、`strong_cue_multiplier`）

**起因**：强线索需要足够水压突破细管道、唤醒沉睡大球——这就是“闻到某种气味突然想起儿时记忆”的工程对应。自然衰减理论上会让水停下，但强线索如果水量不够，再细的管道也突破不了。

**理念**：极度相关的线索值得比常规线索更强的扩散力。`strong_cue_threshold` 是 `start_ball_threshold` 之上的一个更高档位，不是替代关系——一个球余弦 0.5，过了 `start_ball_threshold` 成为起始球，但没过 `strong_cue_threshold`，不触发水量放大。

**解释**：某起始球余弦 > `strong_cue_threshold`（默认 0.85）时，`total_water_budget` 先放大 `strong_cue_multiplier`（默认 3.0）再分配。放大作用在分配之前，按放大后的预算分配。

**方案**：强线索放大起始水量、放大可释放水量、降低被阻挡管道的有效阻力——三条规则叠加，任何管道在足够强线索下都能被突破，不是靠给细管开特例，是靠权重下限保住基础水量、让“强线索突破细管”在分配层面成为可能。

**结论**：强线索放大水量，与“阻力有上限、强线索可突破”配套，让沉睡记忆可被唤醒。5 跳的深度阀是保守兜底、不是常规限制，强线索唤醒通常 1–2 跳就够。

**关联**：总水量预算、起始球选择、阻力、通过条件、安全阀 max_flow_depth。

### 多输入源汇合（`source_bonus`、`source_cap`、`multi_source_merge_cap`）

**起因**：一轮对话里用户消息、工具结果、模型自己的话可能各自产生查询嵌入。如果每个源都独立按 `total_water_budget` 分配起始球水量，总注水量会随源数量线性膨胀，让“多塞一个输入源”变成无成本的扩散放大器，破坏注水守恒的预算前提。

**理念**：多个线索共同指向同一批球本身就是强信号，值得比单源略强的扩散力，但不该线性叠加。多源放大要次线性、有上限，否则“多源”会变成一种无成本的注水放大器。

**解释**：各源独立选起始球后，先按**扩散区域重叠度**做连通分组——重叠度 = |A∩B| / |A∪B|，A/B 为各源在子图上的可达球集合（纯图可达，不含水量判断）；重叠度 ≥ `multi_source_overlap_threshold`（默认 0.3）的源并成一组共享一次流动，不重叠的各自独立流动，不扩散的源（可达集 ≤ 1）不构成独立区域、与任何源视为同组。分组后组内合并去重、同一球取最大余弦；总水量按 `total_water_budget × min(1 + source_bonus × (n_sources − 1), source_cap)` 次线性放大并封顶（单源退化为严格守恒）；子预算按各源最高余弦占比分配，再在子预算内按余弦占比分配到各起始球；同一球被多源命中时，注水量 = `min(各源分配之和, 最大单源分配 × multi_source_merge_cap)`（默认 1.5）。

**方案**：`source_cap` 管全局总水量的上限、`multi_source_merge_cap` 管同一球被多源命中时该球注水量的上限，两者正交——前者防止全局预算膨胀，后者防止单个球被过度注水；一个场景可能触发前者但不触发后者，也可能反过来；单源时不触发汇合逻辑，退化为普通 Top-N 分配；`source_bonus = 0` 时倍率恒为 1.0，退化为严格守恒，用于验证“多源放大”是否带来实质收益。

**结论**：多源受控放大、不线性膨胀，与“总水量预算”的单源守恒构成完整规则。“命中几个球不改变总量”仍成立（起始球之间的分配与源数量无关），变的是“源数量可以适度放大总预算”。

**关联**：总水量预算、注水分配、起始球选择。

### 除零防御

**起因**：分配公式的分母 `Σcosine` 理论上 >0（起始球已过滤阈值），但实现不能依赖“理论上”——浮点误差、多源汇合后去重导致候选集为空、配置被误改成 0 阈值、上游嵌入返回全零向量，都可能让 `Σcosine` 变成 0 或极小值，此时除法会产生 `inf` 或 `NaN`，污染注水量并沿流动传播到所有下游计算。

**理念**：防御性编程不能假设上游不变量永远成立，尤其是这个分母直接进入水量分配，一旦污染会让整轮流动失效且难以定位。

**解释**：分配前检查 `Σcosine`，若小于一个极小阈值（如 `1e-9`）则跳过本轮注水、返回空注入块，并记一次 `start_allocation_zero_denominator` 指标用于诊断。

**方案**：不设“给所有起始球平均分”之类的兜底，因为分母异常说明起始球选择本身出了问题，静默兜底会掩盖上游 bug；指标记录让运维能定位“什么时候、因为什么原因触发了除零防御”。

**结论**：分母异常时明确跳过并记录，不产生 `inf`/`NaN`、不静默兜底。这是“防御性编程”在预算分配上的具体落地。

**关联**：注水分配、起始球选择。

## 二、水球（Ball）

### 球存储大小（`ball_stored_size`，原 size_stored）

**起因**：需要区分“球被强化了多少”和“球现在还有多活”。早期设计里把衰减直接乘进存储值（`size *= exp(-Δt/S)`），导致存储值每秒都在变、无法增量更新，且和“读取时算衰减”的消费方重复计权。

**理念**：存储层只存稳定量，衰减是时间的函数、读取时现算、不落库。账面余额不变、购买力随时间下降——`ball_stored_size` 是账面、`ball_effective_size` 是购买力。

**解释**：`ball_stored_size` 是球在存储中的固有大小，代表这个球历史上累积了多少强化。它只在球被结算强化时增加、被纠正时扣减，存储层不做任何时间衰减——今天存进去多大，明天读出来还是多大。DB 里与它一起存的还有 `last_watered_at`（上次注水时间）和 `ball_stability`（稳定性，随注水次数增长），三者共同构成球的完整状态；`ball_stability` 必须独立存、不能从 `ball_stored_size` 推导，因为它承载的是“这个球抗衰减的能力有多强”这一独立信息——两个 `ball_stored_size` 相同的球，注水 20 次和注水 2 次的稳定性不同，衰减速度不同，这就是间隔效应。

**方案**：写入时机只有结算事务（`ball_stored_size += 含边际递减的有效增量`、`last_watered_at = now`、`ball_stability` 按注水次数增长）和纠正操作（按贡献扣减），饱和时 clamp 到 `[0, ball_size_ceiling]`。它不直接进入任何消费计算——不直接决定补充量、不直接进入注入排序、不直接进入相关性，这些都用 `ball_effective_size`。

**结论**：账面余额不变、购买力随时间下降。`ball_stored_size` 是“这个球被强化了多少”的账本，`ball_effective_size` 是“这个球现在还有多活”的现算值，两者分工明确、不混用。

**关联**：球有效大小、球稳定性、边际递减、饱和后行为。

---

### 球有效大小（`ball_effective_size`，原 size_effective）

**起因**：消费方需要“当前这一刻这个球有多可用”，而不是“历史上被强化了多少”。早期设计里衰减因子被乘了三次——球自身衰减一次、补充规则乘一次新鲜度、注入排序再乘一次，同一个衰减被重复计算，陈旧球被平方甚至立方地过度沉底。

**理念**：衰减只在读取时算一次，所有消费方共用同一个有效值。任何消费方需要“陈旧就弱一点”时，都应该直接读 `ball_effective_size`，而不是在它之上再乘一个新鲜度因子——后者就是重复计权。

**解释**：`ball_effective_size = ball_stored_size × exp(-Δt / ball_effective_stability)`，`Δt = now - last_watered_at`，`ball_effective_stability` 是稳定性的有效值（已含自身衰减），读取时现算、**永不落库**——因为它是时间的函数，存了明天就过时，还得定时刷新；而存 `ball_stored_size + last_watered_at + ball_stability` 三个稳定量，任何时刻都能算出正确值，且 `ball_stored_size` 可增量更新。所有消费方统一使用它：起始球选择用 `余弦 × ball_effective_size`、补充规则用 `ball_effective_size × 归一化相关性` 作为可释放水量、注入排序用 `ball_effective_size / ball_size_ceiling` 归一化、归档触发用“`ball_effective_size` 低 + 久未注水”判断。

**方案**：结算时也不写回它，写回的是 `ball_stored_size`、刷新 `last_watered_at`、增长 `ball_stability`。管道遵循完全同构的模式：存 `pipe_base_thickness`、`last_flowed_at`、`pipe_stability`，读取时算 `pipe_effective_thickness = pipe_base_thickness × exp(-Δt / pipe_effective_stability)`，但 `pipe_stability` 独立演化，管的是“这条联想通不通”，与球的“记忆牢不牢”是两套独立的衰减。

**结论**：衰减只算一次，修正了此前“球自身衰减一次、补充规则乘一次、排序再乘一次”的重复计权。同一次激活内，衰减基准点固定在流动开始读快照的那一刻，流动和结算共用同一个 `ball_effective_size`，结算不重新调 `now()` 再算一遍。

**关联**：球存储大小、新鲜度只算一次、球稳定性、可释放水量、注入排序。

---

### 新鲜度只算一次（`freshness_factor`，原 R(t)）

**起因**：衰减因子 `freshness_factor = exp(-Δt / ball_effective_stability)` 曾在前面的设计里被乘了三次——球自身衰减一次（`size *= exp(-Δt/S)` 直接改存储值）、补充规则乘一次新鲜度（`可释放水量 = 球大小 × freshness_factor`）、注入排序再乘一次（`排序 = 相关性 × 球大小 × 新鲜度`），同一个衰减被重复计算，陈旧球被平方甚至立方地过度沉底。

**理念**：`freshness_factor` 本身不能删——它的稳定性随注水次数增长，编码了“这个球被巩固过多少次”的间隔效应，两个 `ball_stored_size` 相同的球，注水 20 次和注水 2 次的衰减速度不同，这个差异只能由 `ball_stability` 承载；但它在多个环节重复出现，说明“衰减到底在哪里算”没有收敛。

**解释**：把衰减收敛到**读取时算一次**：存储层只存 `ball_stored_size`（固有大小，不衰减）、`last_watered_at`、`ball_stability`，读取时统一计算 `ball_effective_size = ball_stored_size × exp(-Δt / ball_effective_stability)`，所有消费方——起始球选择、补充规则、注入排序、归档触发——统一使用 `ball_effective_size`，**不再额外乘任何新鲜度**；结算时只写回 `ball_stored_size`、刷新 `last_watered_at`、增长 `ball_stability`，**永不写回 `ball_effective_size`**。

**方案**：关键在于“对齐”——同一次激活内，衰减基准点固定在流动开始读快照的那一刻，流动和结算共用同一个 `ball_effective_size`，结算不重新调 `now()` 再算一遍——否则流动跑几十毫秒后结算时 `Δt` 又变了，同一个球在流动里和结算时算出的有效大小不一致，“只算一次”就破了；跨激活时每次激活各自算一次，不跨激活累积乘法；版本冲突时旧计算作废、基于最新状态重算一次，这不算重复计权，因为旧的那次结果已经因冲突失效。管道的 `pipe_effective_thickness = pipe_base_thickness × exp(-Δt / pipe_effective_stability)` 遵循同构但完全独立的模式，`pipe_stability` 随流动次数增长，管的是“这条联想通不通”，与球的“记忆牢不牢”是两套衰减，不混用。

**结论**：任何消费方需要“陈旧就弱一点”时直接读 `ball_effective_size`，不在它之上再乘 `freshness_factor`——后者就是重复计权。这条原则是“每种信号只负责一件事”在衰减上的具体落地。

**关联**：球存储大小、球有效大小、球稳定性、管道有效粗细。

---

### 球稳定性（`ball_stability`，原 S）

**起因**：`ball_stored_size` 单独表达不了“这个球抗衰减的能力有多强”——两个 `ball_stored_size` 相同的球，注水 20 次和注水 2 次的衰减速度不同，这就是间隔效应，必须由独立状态量承载，不能从 `ball_stored_size` 推导。原设计里稳定性只增不减，会让年轻时反复强化、之后多年不用的球稳定性永远保值、几乎不淡忘。

**理念**：稳定性与 `ball_stored_size` 正交——前者回答“衰减得有多慢”、后者回答“被强化了多少”。稳定性采用“饱和增长 + 长期不活动衰减”双重规则：既保留间隔效应，又避免“年轻时攒了一辈子、永久保值”。

**解释**：`ball_stability` 决定 `exp(-Δt / ball_effective_stability)` 的衰减速度。每次结算强化时按注水次数或强化增量增长、有上限 `ball_stability_ceiling`（如 730 天）、增长速率随稳定性增大而递减；同时随时间按曲线速减，存储 `ball_stability_stored` 和 `last_watered_at`，读取时算 `ball_effective_stability = ball_stability_stored × exp(-Δt / ball_stability_decay)`，`ball_stability_decay` 建议 180–365 天（比 `blocked_pass_count` 的衰减慢得多，因为“记忆本身淡化”比“差点通过的痕迹淡化”慢）。

**方案**：结算时先算 `ball_stability_decayed = ball_stability_stored × exp(-Δt / ball_stability_decay)`，再叠加增长增量、封顶 `ball_stability_ceiling`，写回 `ball_stability_stored` 并刷新 `last_watered_at`——写回的是“已衰减到当前时刻的值 + 增长量”，不是原始累积值。纠正不重置 `ball_stability_stored`，但 `ball_stability_stored` 会随时间自然衰减；稳定性不参与流动和结算的任何直接计算，唯一用途是进入 `freshness_factor` 间接影响 `ball_effective_size`。管道的 `pipe_stability` 遵循完全同构的模式（饱和增长 + 长期不流动衰减，读取时算 `pipe_effective_stability`，结算时先衰减再叠加），管“联想通不通”，与球的“记忆牢不牢”是两套独立状态。

**结论**：长期不活动的球有效稳定性自然下降、新鲜度衰减加速，符合“长期不用、稳定性本身也会流失”的直觉，不会出现“年轻时反复强化、之后多年不用、稳定性永远保值、永不淡忘”的问题。

**关联**：球存储大小、球有效大小、新鲜度只算一次、新球初始大小、管道稳定性。

---

### 球大小上限（`ball_size_ceiling`，原 size_max）

**起因**：没有上限，一个被反复强化的球会无限变大，最终压过一切，注入排序里“大小”这个因子会失控。

**理念**：强化边际递减、有天花板，“一件事想太多次就不会再加深”。上限全局统一、不按球分类型——长期/短期的差异靠稳定性表达，不靠不同的大小上限。

**解释**：`ball_size_ceiling` 是 `ball_stored_size` 的硬天花板，默认 10.0、可配。它出现在两个地方：一是结算强化的边际递减公式 `有效增量 = 强化值 × (1 - ball_stored_size/ball_size_ceiling)^γ`（γ 默认 1.0），球越接近上限增量越小，饱和后 `ball_stored_size` 不再增长，但 `last_watered_at` 仍刷新、管道照常变粗、内容仍可追加，长时间不注水衰减到上限以下后可以重新增长；二是注入排序的归一化分母 `ball_effective_size / ball_size_ceiling`，把球大小映射到 `[0,1]`，与相关性、巩固度因子同量纲相乘。

**方案**：写入时 `ball_stored_size = min(ball_stored_size + 有效增量, ball_size_ceiling)` 且 clamp 到 `[0, ball_size_ceiling]`，防止浮点误差越界；配置校验拒绝 0 和负数，避免归一化除零。它和 `ball_stability_ceiling` 是两套独立的上限——`ball_size_ceiling` 管“球能变多大”、`ball_stability_ceiling` 管“衰减能变多慢”，两者不混用。

**结论**：有了上限，“强化边际递减”和“一件事想太多次就不会再加深”的直觉才能落地；注入排序里的大小因子不会被少数大球主导。

**关联**：边际递减、饱和后行为、注入排序、球稳定性。

---

### 边际递减（`size_saturation_gamma`，原 γ）

**起因**：没有边际递减，一个被反复强化的球会线性膨胀到上限然后突然停住，“从 9.9 到 10.0”和“从 1.0 到 1.1”的强化效果一样，不符合“越强越难更强”的直觉。

**理念**：饱和不是一个突兀的开关，而是一个平滑的、可配置的逼近过程。有了它，同时避免注入排序里 `ball_effective_size / ball_size_ceiling` 这个因子被少数大球主导。

**解释**：球被结算强化时，写入 `ball_stored_size` 的不是原始强化值，而是乘上一个随 `ball_stored_size` 接近 `ball_size_ceiling` 而递减的系数：`有效增量 = 强化值 × (1 - ball_stored_size/ball_size_ceiling)^γ`，γ 默认 1.0、可配。γ=0 退化为纯线性硬饱和，γ 越大边际递减越强。球越接近上限，同样强度的路径强化带来的增量越小；严格达到 `ball_size_ceiling` 后有效增量为 0，`ball_stored_size` 不再增长，但 `last_watered_at` 仍刷新、管道照常变粗、内容仍可追加。

**方案**：它只作用于结算写入侧，`ball_effective_size` 是读取时现算的派生值，不参与边际递减计算；它和稳定性的饱和增长是两套独立的机制——边际递减管“球能变多大”，稳定性饱和增长管“衰减能变多慢”，两者公式同构（都是趋近上限、增量递减）但作用对象不同，不混用。

**结论**：越强越难更强，饱和平滑逼近。这是“边际递减”在球大小上的具体落地，与稳定性饱和增长公式同构但语义不同。

**关联**：球大小上限、饱和后行为、球稳定性。

---

### 饱和后行为

**起因**：球达到 `ball_size_ceiling` 后，其他状态是否继续演化需要明确。如果饱和把整只球都冻住，球会变成僵死状态、无法承载新经验；如果饱和只封住大小，其他维度继续演化，球仍是一个活的记忆节点。

**理念**：饱和只封住“大小”这一个维度，不封住“最近注水时间”“稳定性”“管道强度”“内容容量”这些维度，球不会因为饱和而变成僵死的状态。饱和不是永久状态——长时间不注水、`ball_effective_size` 衰减到 `ball_size_ceiling` 以下后，下次强化时有效增量恢复为正，球可重新增长，记忆会淡化、淡化后可再次被强化。

**解释**：球达到 `ball_size_ceiling` 后，**只有 `ball_stored_size` 这一个量停止增长**（有效增量为 0），其余状态照常演化：`last_watered_at` 仍刷新为本次结算时间——因为“我刚想起过它”这个事实必须记录，否则衰减计时会错、球会被误判为“很久没注水”而被归档；`ball_stability` 仍按饱和增长规则继续演化——强化次数仍在累积，只是稳定性自身也有 `ball_stability_ceiling` 上限；路径上的管道照常变粗——球饱和不等于它和邻居的关联饱和，“一起被想起”这个信号仍要写进管道；内容列表仍可追加（去重后）——球的大小到顶了，但它仍可以承载新的经验，只是这些新内容不再让它变大。

**方案**：长时间不注水，`ball_effective_size` 随衰减降到 `ball_size_ceiling` 以下，下次被强化时有效增量恢复为正，球可以重新增长。这与“疏而不堵、不删除”的理念一致——记忆会淡化，淡化后可以再次被强化，饱和不是永久状态。

**结论**：饱和只封住“大小”一个维度，不封住其他维度，球不会因为饱和而变成僵死的状态。这是“疏而不堵”在球状态上的具体落地。

**关联**：球大小上限、边际递减、球稳定性、内容列表。

---

### 新球初始大小（`size_init_min`、`size_init_factor`）

**起因**：新球不能太小——如果初始 `ball_stored_size` 接近零，它释放的可释放水量 `ball_effective_size × 归一化相关性` 不足以突破任何中等阻力管道，就会变成永远扩散不出去的“死球”；新球也不能与显著性无关——一个在高度显著片段上起念的球，初始就应该比弱显著片段上的球更大，这样它在下一轮流动里有更高的 `ball_effective_size`、更容易被起始球选中和补充，符合“强烈的念刚产生时就更有分量”的直觉。

**理念**：新球至少能释放一次足以通过中等管道的补充（`size_init_min` 是保底值，全局统一、不随球变）；初始大小与触发它的显著性相关（`size_init_factor` 是敏感度系数）。原设计只定义了 `size_init_min` 这个保底值、没有定义稳定性的初始值，导致“保底可扩散”是一个没有兑现条件的承诺——新球创建后第一轮如果没被注水，`Δt` 增大，`ball_effective_size` 按稳定性衰减；如果稳定性初始值很小，新球可能在第一次被注水之前就已经衰减到不足以扩散。

**解释**：`ball_stored_size = size_init_min + 显著性 × size_init_factor`，`size_init_min` 默认 0.1、`size_init_factor` 默认 0.5，两者均可配——显著性 0.8 的球初始约 0.5，显著性 0.5 的球初始约 0.35。稳定性的初始值必须与 `size_init_min` 联合校验——保证“第一次被注水时 `ball_effective_size` 仍足以通过中等管道”。

**方案**：联合约束为 `size_init_min × exp(-Δt_first / ball_stability_init) ≥ 最小可扩散阈值`，其中 `Δt_first` 是新球创建到第一次被注水的最大预期间隔；实现上可以反过来——先定 `ball_stability_init` 的默认值（如 30 天），再校验 `size_init_min × exp(-Δt_first / ball_stability_init)` 是否仍大于最小可扩散阈值，不满足则配置校验拒绝。`size_init_min` 和 `size_init_factor` 只作用于新球创建那一刻，之后球的增长完全由结算强化和边际递减决定；新球创建走独立事务、与流动/结算解耦，判别器异步产出新球时不影响本轮注入、只影响下一轮流动。兜底合并命中已有球时不创建新球，而是给已有球 `ball_stored_size += 显著性 × size_init_factor` 的强化，不叠加 `size_init_min`——因为已有球不需要“保底可扩散”，它已经在线上了。

**结论**：`size_init_min` 的保底在第一次注水时仍成立，不是“创建瞬间成立”的空头承诺。这是“保底可扩散”从口号变成可校验约束的具体落地。

**关联**：球稳定性、新球接图、兜底合并、通过条件。

---

### 新球接图（`new_pipe_threshold`、`new_pipe_initial_factor`）

**起因**：新球没有管道就是孤岛，下次流动永远到不了它；但也不能乱连——阈值太低会让新球连上一堆弱相关球、图变成乱麻，太高会让大多数新球成为孤岛。

**理念**：能连就弱连、连不上就等，不给孤岛强行接边。新球刚创建时只有一条内容、语义身份还不稳定，连太多球会让它过早绑定到多个方向、后续强化时水流分散。初始 `pipe_base_thickness` 刻意做细——新球刚建立、关联强度还没被验证，细管道让常规水流不容易通过、但强线索可以突破，后续共激活或结算强化会让它自然变粗。

**解释**：用嵌入与已有 `active` 球算余弦，过滤低于 `new_pipe_threshold`（默认 0.5）的球，取 Top-K（默认 2）建弱管道，初始 `pipe_base_thickness = 余弦 × new_pipe_initial_factor`（默认 0.5），来源标记 `new_ball`。阈值 0.5 是“语义上有明确关联”的保守分界，Top-2 而非 Top-5 是因为新球刚创建、语义身份还不稳定。

**方案**：没有球超阈值时新球就是孤岛，这是**正常状态不是故障**——新概念、新话题刚出现时图上确实没有相关节点，强行接一条弱管道反而破坏结构；孤岛球的后续路径是强线索直接命中（成为起始球、注水后释放补充）、离线巩固补边（余弦 > `offline_pipe_threshold` 时建管道）、或永远孤岛（仍然可以被强线索直接命中而激活，只是不参与多跳扩散）。新球创建、建内容、建初始管道在同一事务内完成，要么完整存在要么不存在，不会出现“球建了但管道没建”的半完成状态；`graph_version` 随之递增，正在流动的其他进程会在结算时检测到版本变化并重算。

**结论**：新球接图是“弱连”不是“强连”，初始做细、后续流动和结算自然变粗。孤岛是正常状态，靠强线索直接命中或离线补边接入。

**关联**：兜底合并、管道创建来源、离线相似补边、结算变粗。

---

### 兜底合并（`merge_cosine_threshold`）

**起因**：判别器判定“产生新球”后，系统层在真正建球之前需要先做一次兜底检查——判别器的职责是“是否起念”、不是“是否是新球”，它可能在 prompt 里看到 top-5 候选球后仍误判“新球”，系统层需要兜底拦截“几乎完全相同”的情况，否则同一个记忆会被反复创建成多个球、产生碎片化。

**理念**：只拦截“几乎完全相同”，不拦截“语义相近但确实不同”——语义相近但不同的球应该作为两个球存在、靠管道连接，而不是合并。阈值必须很高（0.95），只拦截“几乎完全相同”。

**解释**：建球前用候选片段嵌入与已有 `active` 球算余弦，若与某个球的余弦超过 `merge_cosine_threshold`（默认 0.95），不创建新球，而是把触发片段追加到该已有球的内容列表，并给已有球一次强化 `ball_stored_size += 显著性 × size_init_factor`（不叠加 `size_init_min`——已有球不需要“保底可扩散”，它已经在线上了）。

**方案**：兜底合并和新球创建走同一个事务：要么建新球 + 建内容 + 建初始管道，要么追加内容 + 强化已有球，不会出现半完成状态；`graph_version` 递增。它和离线巩固里的“相似合并”是两层不同的机制——兜底合并是**写入时**拦截“几乎完全相同”的重复创建，离线合并是**巩固时**合并“语义相近且管道很粗”的已有球，前者防碎片化于未然，后者收敛历史遗留的冗余。

**结论**：兜底合并是写入时的“几乎相同”拦截，不是语义归并。这是“防碎片化”在写入路径上的第一道防线。

**关联**：新球接图、新球初始大小、合并。

---

### 内容列表（`content_list_max`）

**起因**：球需要挂载可渲染为文本的记忆本体，但不能无限增长——内容列表如果无限增长，球的 Payload 会膨胀、读取和序列化成本上升；但直接删除旧内容又违背“不删除、只降可提取性”的理念。

**理念**：淘汰不是删除，是转入冷层，热层只保留最常用的。分层是“降级”而非“删除”，热层最常用、温层完整保留、冷层按需回源。

**解释**：每个球挂载一个内容列表，存放可渲染为文本的记忆本体——触发片段原文、后续被强化时追加的语境片段、离线巩固生成的摘要或抽象，默认上限 5 条、可配（`content_list_max`）。新球创建时挂触发片段原文作为第一条内容；球被强化时，本次流动中经过该球且产生补充的语境片段在去重后追加；离线巩固时，同一球下多条内容聚类生成摘要或抽象，作为新内容追加。超出上限时按“被注入次数”淘汰最不常用的那条，淘汰**不是删除**，而是转入冷存储表、带球 ID 索引，强线索需要回源时才读取。

**方案**：内容本身可被纠正——用户否定某条内容时标记 `archived`，不再参与渲染，但不删除；每条内容带编码标记（`rmw-utf8` 或 `raw`），中文短文本压缩存储、不膨胀则回退原文；单条内容长度有上限（默认 4000 字符），超出截断为“前 N 字符 + 摘要”、原文转冷存储。内容列表的长度和总字节数也是“这个球承载多少信息”的度量，未来若要做“内容丰富度调制衰减”，用的是这个维度而不是 `ball_stored_size`。

**结论**：内容列表和 `ball_stored_size` 正交——一个是“装了什么”、一个是“被强化了多少”；一个球可以很大但内容列表很短（反复强化同一条内容），也可以很小但内容列表很长（刚创建、多条不同语境被追加），两者互不替代。

**关联**：冷热分层、原文压缩、嵌入、纠正。

### 嵌入（`embedding_ema_beta`）

**起因**：所有相似度计算需要球的语义向量。一个球可以挂多条内容，但只有一个嵌入——如果对内容列表重新嵌入取平均，每次追加内容都要重算全部内容、且球的语义身份会突变。

**理念**：一个球挂多条内容、但只有一个嵌入，它是内容列表的“语义重心”、不是某一条内容的复制。EMA 更新让球的语义身份缓慢漂移、不会因为追加一条内容就突变；引入 EMA 而非“对内容列表重新嵌入取平均”的理由是：EMA 是增量的、不需要每次重算全部内容，且它让球的语义身份稳定。

**解释**：每个球持有一条语义向量，用于计算相似度——起始球选择、流动相关性、结算路径相关性、新球接图、离线补边、归档召回，全部依赖它。球被强化时，若本次语境片段被追加为内容，嵌入做一次 EMA 更新 `新嵌入 = 旧嵌入 × (1 − embedding_ema_beta) + 本次内容嵌入 × embedding_ema_beta`，`embedding_ema_beta` 默认 0.1。内容被纠正标记 `archived` 后，嵌入不立即重算、由后续 EMA 自然稀释。

**方案**：嵌入存储用 TriviumDB 原生 Vector 字段，f32 存储、内部可 f16 量化，存储体积随维度线性变化——维度不是固定常量、由具体嵌入后端决定：`pizza-embed-zh-small-v1` 是 512 维、`piccolo-large-zh` 是 1024 维、`bge-small-zh-v1.5` 是 512 维、`bge-m3` 是 1024 维。QuIVer ANN 在向量数超过阈值时自动激活、无需额外向量库。嵌入不承担检索职责——它只提供向量，余弦计算、阈值判断、归属判定都由规则层完成；不直接出现在注入文本里——注入渲染的是内容列表里的文本。维度一致性是启动时的硬校验：`DayuCore` 初始化时校验 `EmbeddingBackend::dimension()` 与球存储的向量维度一致，不匹配则启动失败而不是运行时静默错乱；换嵌入模型（如从 pizza 的 512 维切到 piccolo 的 1024 维）时，需要一次显式的迁移——要么全库重算嵌入、要么新建球表旧球按需回填，不能在同一张表里混存不同维度的向量。

**结论**：嵌入是“语义重心”不是“某条内容的复制”，EMA 让语义身份稳定、纠正由后续 EMA 稀释。嵌入不参与检索决策、不参与注入渲染、不经过文本压缩。

**关联**：球有效大小、起始球选择、补充规则、相关性定义、嵌入存储。

### 可释放水量（`supplement_threshold`、`max_supplement_ratio`）

**起因**：球释放补充不能是 `ball_effective_size × 相关性系数` 的线性乘积，否则一个勉强过 `flow_continuation_threshold`（0.3）的弱相关大球，如果 `ball_effective_size` 很大（比如 8.0），补充量仍有 2.48——它靠历史强度而非当前相关性放大了水流，和“大球赢家通吃”是同一个结构问题。

**理念**：资格 + 幅度两段式——相关性管“有没有资格补充”，大小和新鲜度管“有资格时补充多少”。弱相关的大球无法靠历史强度放大水流：相关性没过资格阈值时补充为零；过了之后，球大、新鲜才在幅度里起作用。

**解释**：先看相关性是否过补充资格阈值 `supplement_threshold`（默认建议 0.4–0.5，高于 `flow_continuation_threshold`），低于它时补充量为零——球不贡献任何水，防止一个勉强过流动阈值的弱相关大球靠历史强度放大水流；高于它时补充按归一化相关性增长，`补充量 = ball_effective_size × (相关性 - supplement_threshold) / (1 - supplement_threshold)`，相关性刚好过阈值时补充接近零、接近 1 时才拿满 `ball_effective_size`。`ball_effective_size`（当前有效大小，已含时间衰减）是“潜力”、归一化相关性是“兑现比例”。

**方案**：补充量受 `max_supplement_ratio`（默认 2.0）截断，`补充量 = min(可释放水量, 当前水量 × max_supplement_ratio)`，防止一个大球让水流指数爆炸。关键语义是：球释放补充后**自身不变**——可释放水量是计算值、不是从球里扣水，球的大小变化只在结算时发生（被路径强化则变大、久不注水则惰性衰减），流动过程中球只是贡献了一个由当前状态决定的水量。补充加在**扣损之后**：`下一跳水量 = 扣损后水量 + 补充量`，细管道上的补充需要更大力才能让水流维持甚至增长。

**结论**：可释放水量 > 当前损失时水流可能被放大、继续扩散，可释放水量 < 当前损失时水流衰减、联想链更早终止——这就是“补充 > 损失当且仅当球大、新鲜、强相关”的工程对应，但“强相关”现在有了明确的资格阈值，不是线性乘一个小的相关性系数。

**关联**：球有效大小、补充规则、补充 > 损失条件、supplement_threshold。

### 状态（`ball_status`）

**起因**：球需要区分“正常”“有争议”“休眠”“永久删除”四种生命周期。原设计里“删除”和“休眠”混在一起，无法表达“球还在、只是不参与常规流动”和“球真的被永久删除”的区别。

**理念**：除了 `deleted`，没有任何状态是“删除”，球始终在存储里、只是“能不能被这次水流想起”不同。`contested` 只是标注不确定、`archived` 只是休眠可唤醒。状态管“这个球现在参不参与”，和 `ball_stored_size`、`ball_stability`、内容列表是正交的——一个球可以 `active` 但很小、可以 `archived` 但内容很多，状态不替代其他维度、只回答“此刻它是否可被召回”。

**解释**：球有四种状态：`active`、`contested`、`archived`、`deleted`，状态决定它是否参与流动、是否可被注入、是否可被纠正。`active` 是正常运行状态，参与起始球选择、流动、结算、注入排序；`contested` 是“有争议”状态，由隐式纠正（用户话与注入记忆矛盾）或离线矛盾检测触发，仍可参与流动，但注入时带“我之前的理解可能不准确”的标注，不直接删除是因为单次矛盾可能误判，等离线巩固再确认——确认正确则回 `active`，确认错误则转 `archived`；`archived` 是“休眠”状态，不参与常规流动和起始球选择，但存储保留、嵌入保留、内容保留，仍参与检索，被余弦 ≥ `start_ball_threshold` 的线索命中即直接翻回 `active`（无临时态、无 TTL）；`deleted` 是唯一不可逆状态，只能由用户显式“永远忘掉”并二次确认触发，执行硬删或加密归档，纠正审计保留但球本身不再可召回。

**方案**：状态转换的路径是：新建 → `active`；`active` → `contested`（隐式纠正/矛盾检测）；`contested` → `active`（确认正确）或 `archived`（确认错误/显式纠正）；`active` → `archived`（规模管理触发）；`archived` → `active`（强线索唤醒且被强化）；`archived` → `deleted`（显式永久删除 + 二次确认）。状态转换全部走纠正审计，`correction_log` 记录原状态、新状态、触发来源、时间、可逆性，保证每一次状态变化都可追溯、可回退（`deleted` 除外）。

**结论**：状态管“此刻是否可被召回”，与球存储大小、球稳定性、内容列表正交。这套状态设计的核心理由是“疏而不堵”——除了 `deleted`，没有任何状态是“删除”。

**关联**：归档触发、归档唤醒、纠正机制、软删默认。

### 归档触发（`archive_inactive_days`、`archive_size_threshold`、`max_active_balls`）

**起因**：球数无限增长会拖慢起始球选择的扫描成本。归档的目标不是省存储，是控制扫描成本。

**理念**：只针对“又小又旧”的球，不误伤有价值的记忆。判定只看两个与球本身相关的量——多久没被想起、现在还剩多少；规模超限作为独立的兜底，不与前者耦合。

**解释**：归档由离线扫描执行（`DayuCore::archive_sweep`），定时任务与 `dayu archive` CLI 共用这一个入口。判定是**时间与大小两条同时满足**：距 `last_watered` 超过 `archive_inactive_days`（默认 90 天），且 `size_effective` 低于 `archive_size_threshold`（默认 0.2）。**不要求“球数超过 max_balls × 0.8”**——旧设计把规模条件也塞进归档判定，结果是球数没超时归档永不发生，小旧球一直占着扫描成本；而“球数超了”本身就是另一个问题，应该由另一条规则回答。规模超限单独处理：活跃球数超过 `max_active_balls`（默认 1 万）时，按 `size_effective` 升序（同分按 id，保证可复现）强制归档最弱的球，直到回落到上限。这条是兜底，不是常规路径。归档只改 `status` 字段，`size_stored`、`S`、`last_watered`、`embedding`、内容列表全部保留；归档球不删除、不进独立表，仍留在同一张球表里、与主图共用同一份索引——“归档区也建索引”不是另建一套，而是归档不摘索引。

**方案**：两条规则叠加的效果是——平时只归档“又小又旧”的，规模真的超了才动还没衰减透的球。每次扫描记指标（归档球数、扫描前活跃球数、扫描后活跃球数），用于判断 `max_active_balls` 是否设得太小。

**结论**：归档不是删除，是休眠；休眠的判据是“多久没被想起”和“现在还剩多少”，不是“库有多大”。

**关联**：状态、归档唤醒、规模管理、管道归档。

---

### 归档唤醒（无独立阈值）

**起因**：归档如果不可唤醒，就等于变相删除，违背“不删除、只降可提取性”的理念。

**理念**：既然归档球必须能被检索到，那么“是否值得唤醒”就该由相似度本身回答，不该再叠一个与状态相关的阈值。

**解释**：`search_by_embedding` 只过滤 `deleted`、不过滤 `archived`，归档球与活跃球在同一索引里按余弦排序，共用同一个 `start_ball_threshold`（默认 0.3）。旧设计给归档球设 0.9 的独立门槛，等于让它几乎不可召回——这与“必须能被检索到”直接冲突。唤醒**不做临时加载**：归档球一旦被选为起始球，直接持久化翻回 `active`，没有临时态、没有 TTL、没有“流动后未强化则回归 archived”。理由是临时态需要在每次流动后做一次判定和写回，多一个状态机分支、多一次写事务；而“被问到”本身就是足够强的唤醒信号——它已经进入起始球，说明线索够了。

**方案**：唤醒发生在结算之前（`DayuCore::recall` 取 `depth == 0` 的球调 `wake_archived`），本次流动它已按普通球参与，下一次检索它就是活跃球。代价是归档球会因一次偶然的高相似输入永久回到主图——这与“不删除、只降可提取性”一致：既然被想起，就该留在主图。

**结论**：唤醒是“被想起”的必然结果，不是需要额外审批的动作。

**关联**：状态、归档触发、规模管理、管道归档。

### 点亮次数（`lit_count`）

**起因**：需要记录“球被水流到达过多少次”，但不能刷新衰减计时——如果点亮就刷新 `last_watered_at`，那经常被路过但从未被真正激活的球会“永葆青春”，衰减机制失效。这正是之前“路过与注入必须区分”那条修正的核心。

**理念**：点亮是“到达”不是“注入”，两者必须分开记账；一个被多次点亮但从未被强化（相关性没过 `supplement_threshold` 或没过 `strengthen_eligibility_threshold`）的球，说明它“反复差点被想起”，下次流动时值得一次轻量补偿。

**解释**：`lit_count` 是球被水流点亮时累加的轻量计数，与 `ball_stored_size`、`ball_stability`、`last_watered_at` 完全解耦——点亮不刷新衰减计时、不触发 `ball_stored_size` 增长、不改变 `ball_stability`，它只记录“这个球被水流到达过多少次”、不记录“它被强化了多少次”。

**方案**：写入时机在流动阶段点亮球时 `+1`、与结算解耦、不需要事务；封顶（如 100）防止无限增长，封顶后不再增加但不清零；它不参与任何消费计算——不进入起始球选择、不进入补充规则、不进入注入排序、不进入相关性，唯一消费方是“下次流动时判断是否给予轻微阻力折扣”，且这个折扣**默认关闭**、作为对照实验的可选增强，开启时也远小于 `blocked_pass_count` 的折扣幅度。它和 `blocked_pass_count` 是两套独立的轻量计数：`blocked_pass_count` 记“水到了但过不去”、`lit_count` 记“水到了且点亮了”，前者补偿“差点通过”、后者补偿“反复被到达”，两者都不刷新衰减计时、都不改变球的大小。

**结论**：`lit_count` 当前是一个**可观测性字段**、不是功能机制——默认配置下它只写不读；要让它产生行为影响，必须显式开启折扣并做对照实验。这是“自觉的取舍”，不是逻辑漏洞。

**关联**：blocked_pass_count、阻力、全失败、可观测性。

## 三、水管（Pipe）

### 无向权重（`pipe_base_thickness`，原 w）

**起因**：管道是否需要区分方向？原设计里管道存储 `w_ab` 和 `w_ba` 两个方向的粗细，A→B 和 B→A 可以不同。有向权重是过度设计，增加存储和逻辑复杂度（两条权重、两套阻塞计数、各自独立衰减），却没有对应的人脑直觉——“A 让 B 想起”和“B 让 A 想起”在大多数情况下强度相当。

**理念**：水利模型里管子就是管子、不分上下游，水从哪边流过来阻力都一样。方向性如果需要表达，应由内容或额外的边类型承载、不塞进 `pipe_base_thickness`。

**解释**：一根管子只有一个 `pipe_base_thickness`、一个 `blocked_pass_count`、一个 `last_flowed_at`，A↔B 共享，不分上下游；水从 A 流向 B 和从 B 流向 A 遇到同一个阻力、同一个损耗、同一个阻塞记忆，不会因为方向不同而不同。

**方案**：唯一性约束用 `(min(a_id, b_id), max(a_id, b_id))` 防止重复建边；管道的无向权重和球的有向无关——球本身没有方向，管道也不应该有。

**结论**：无向权重简化了流动、衰减、强化、阻塞、合并重定向的全部逻辑——流动直接取 `pipe_base_thickness` 算有效粗细、衰减一个值一个稳定性、强化一个增量、阻塞一个计数、合并时取 `max` 而不是“两个方向分别取 max”。

**关联**：唯一性约束、阻力、合并、归档。

---

### 唯一性约束

**起因**：无向管道需要防止 A-B 和 B-A 重复建边——如果同一个关联被建两条记录，流动时随机走其中一条，会导致阻力、损耗、阻塞记忆不一致。

**理念**：因为管道无向，两端 ID 顺序没有语义，必须规范化后才能做唯一性判断。

**解释**：存储层用 `(min(a_id, b_id), max(a_id, b_id))` 作为唯一键，保证 A-B 和 B-A 不会重复建边。

**方案**：建边前规范化两端 ID，重复建边被拒绝；唯一性约束是无向权重的存储层落地。

**结论**：唯一性约束保证“一根管子只有一个 `pipe_base_thickness`、一个 `blocked_pass_count`、一个 `last_flowed_at`”在存储层被强制。

**关联**：无向权重、创建来源、合并。

---

### 粗细范围（`pipe_base_thickness` 范围）

**起因**：管道粗细的取值域需要明确。如果允许归零，“归零”语义上等于删除管道，违背“不删除、只降可提取性”的理念。

**理念**：管道永不封死，只是变细到“几乎断流”——`pipe_base_thickness` 可衰减到极接近 0，但不会等于 0。

**解释**：`pipe_base_thickness ∈ (0, 1]`，永不归零。下界开区间保证管道不会完全消失，上界 1.0 是粗细归一化天花板。阻力有上限（`pipe_effective_thickness → 0` 时 `resistance → 1`），即使最细的管道，强线索水量足够大时仍能突破。

**方案**：存储层不强制 `pipe_base_thickness` 的精确范围，但结算变粗时 clamp 到 `[0, pipe_thickness_ceiling]`、惰性衰减时保证 `pipe_effective_thickness` 不为零；配置校验拒绝 `pipe_thickness_ceiling ≤ 0`。

**结论**：管道永不封死，只是变细到“几乎断流”。这是“疏而不堵”在管道粗细上的具体落地。

**关联**：阻力、通过条件、细管保底非零。

---

### 阻力（`pipe_resistance`）

**起因**：水能否通过一条管道需要判据。原设计里管道粗细低于阈值时“流不过去”，相当于永久封死，违背“不能清理短期记忆、确实有可能突然想到”的理念——儿时记忆平时想不起来，是因为管道很细、常规水流过不去，但闻到某种气味时能突然想起，说明强线索的水流可以突破细管道。

**理念**：管道是阻力不是开关，阻力有上限、强线索可突破。`pipe_effective_thickness → 0` 时 `resistance → 1`，不是无穷大——这意味着任何管道在足够大的水量下都能被突破。

**解释**：`pipe_resistance = 1 / (1 + pipe_effective_thickness) × 阻挡记忆折扣`。`pipe_effective_thickness` 越大阻力越小，水越容易通过；越小阻力越大，水更容易在这一跳停住。阻挡记忆折扣让被阻挡过的管道下次有效阻力略降，是舌尖效应的载体。

**方案**：强线索放大起始水量、放大可释放水量、降低被阻挡管道的有效阻力——三条规则叠加，任何管道在足够强线索下都能被突破，不是靠给细管开特例，是靠权重下限保住基础水量、让“强线索突破细管”在分配层面成为可能。

**结论**：任何管道在足够大水量下都能被突破，这是“阻力不是开关”的物理依据。这是“疏而不堵”在通过条件上的具体落地。

**关联**：管道有效粗细、通过条件、阻挡记忆折扣、强线索放大。

---

### 管道有效粗细（`pipe_effective_thickness`，原 w_eff）

**起因**：管道粗细需要区分“账面粗细”和“当前有效粗细”——与球的 `ball_stored_size`/`ball_effective_size` 同构，存储基础值、读取时算衰减。如果分配用 `pipe_base_thickness` 而通过用 `pipe_effective_thickness`，一条 `pipe_base_thickness` 很大但 `pipe_effective_thickness` 很小的管道（长期不流动、稳定性衰减了），在分配时会因为 `pipe_base_thickness` 大而分到很多水；但到了通过判断时，`pipe_effective_thickness` 小导致阻力大、水过不去，分到的那份水按“损失不回收”消失——水被系统性地分配给“账面粗但实际细”的管道，然后浪费掉。

**理念**：分配、阻力、损耗三条路径统一用同一个 `pipe_effective_thickness` 的不同侧面——粗管“分得多、好通过、损耗小”，细管“分得少、难通过、损耗大”，三者一致。

**解释**：`pipe_effective_thickness = pipe_base_thickness × exp(-Δt / pipe_effective_stability)`，`Δt = now - last_flowed_at`，`pipe_effective_stability` 是管道稳定性的有效值（已含自身衰减），`pipe_base_thickness` 是存储里的基础粗细、不随时间变。它回答的是“这条联想现在还有多通”，和球的 `ball_effective_size` 完全同构但独立演化——球管“记忆牢不牢”，管道管“联想通不通”。在流动中承担两个角色：先算阻力 `pipe_resistance = 1 / (1 + pipe_effective_thickness) × 阻挡记忆折扣` 判断能不能过，过了之后用同一个 `pipe_effective_thickness` 算这一跳损失 `loss = min(base_loss × (1 + loss_pipe_factor × (1 - pipe_effective_thickness)), loss_max)`——阻力和损耗是同一属性的两个正相关侧面，共用同一个 `pipe_effective_thickness`，不是两个独立参数。

**方案**：**永不落库**——流动时用 `pipe_effective_thickness` 算阻力和损耗，不写回存储；只有结算强化时才写回 `pipe_base_thickness`，衰减是读取时现算的。`pipe_effective_stability` 本身也遵循“饱和增长 + 长期不流动衰减”的双重规则（读取时算 `pipe_effective_stability = pipe_stability_stored × exp(-Δt / pipe_stability_decay)`，结算时先衰减再叠加增长量），所以 `pipe_effective_thickness` 实际是“基础粗细 × 管道稳定性的有效衰减”，长期不流动的管道 `pipe_effective_stability` 下降、`pipe_effective_thickness` 加速变细，符合“长期不通的联想应该越来越难走”的直觉。`pipe_effective_thickness` 不进入相关性计算、不进入注入排序、不进入球的任何计算——它只活在流动阶段的阻力和损耗里，不污染其他维度。

**结论**：分配权重用 `pipe_effective_thickness` 而不是 `pipe_base_thickness`，避免水被分到“账面粗但实际细”的管道上浪费。阻力和损耗是同一属性的两个正相关侧面，共用同一个 `pipe_effective_thickness`。

**关联**：阻力、损失函数、管道稳定性、分配权重、管道粗细双重角色。

---

### 管道粗细双重角色

**起因**：管道粗细原设计只决定阻力、损耗是全局常数 `base_loss`。但管道粗细的语义是“关联强度”——粗管不仅好过、过了之后也应该损耗小；细管不仅难通过、通过了也应该剩不下多少。

**理念**：把损失从“全局常数”改成“`pipe_effective_thickness` 的确定性函数”，让管道粗细在流动中承担完整的物理角色：阻力决定能不能过、损耗决定过了之后剩多少，两者共用同一个 `pipe_effective_thickness`、正相关但机制不同。

**解释**：`pipe_effective_thickness` 在流动中同时决定阻力和损耗，两者共用同一个 `pipe_effective_thickness`、正相关但机制不同。

**方案**：先算阻力判断能不能过，过了之后用同一个 `pipe_effective_thickness` 算损失；两者不是两个独立参数。

**结论**：管道粗细在流动中承担完整的物理角色。这是“管道粗细双重角色”修正的具体落地。

**关联**：阻力、损失函数、管道有效粗细。

---

### 损失函数（`base_loss`、`loss_pipe_factor`、`loss_max`）

**起因**：每跳损失需要从“全局常数”改为“管道状态的确定性函数”。原设计里损失是全局常数 `L`、与管道无关，但管道粗细的语义是“关联强度”，应该同时影响阻力和损耗。

**理念**：损失是试探本身的成本，不是随机噪声，同一 `pipe_effective_thickness` 永远算出同一损失。损失单调递减于 `pipe_effective_thickness`（管道越细损失越大）、损失有界（永不低于 `base_loss`、永不超过 `loss_max`）。

**解释**：`loss = min(base_loss × (1 + loss_pipe_factor × (1 - pipe_effective_thickness)), loss_max)`，其中 `base_loss` 是粗管基准损失（默认 0.2）、`loss_pipe_factor` 是细管额外损耗系数（默认 0.8）、`loss_max` 是损失率上限（默认 0.8，必须 <1.0）。`pipe_effective_thickness = 1`（最粗）时损失等于 `base_loss`、只有基准损失；`pipe_effective_thickness → 0`（最细）时损失趋近 `base_loss × (1 + loss_pipe_factor)`、被 `loss_max` 截断，防止细管把水全部吃掉、导致永远流不动。

**方案**：损失发生在通过判断之前——水到达管道先扣损、再判断剩余水量能否通过阻力，不管最终是否通过，这一跳的损失都已经发生；过不去的管道损失不回收，符合“想不起来就是白费力气”的直觉。`base_loss`、`loss_pipe_factor`、`loss_max` 全部进配置、可调参；**配置校验 `base_loss + base_loss × loss_pipe_factor < 1.0`**（否则 `loss_max` 形同虚设），并**可选地校验 `base_loss × (1 + loss_pipe_factor) ≤ loss_max`** 以保证严格单调（否则截断区间内只成立非严格单调）。`LossModel` 做成可替换 trait，`PipeWeightLossModel` 是默认实现，`ConstantLossModel` 精确复现旧规则（损失恒等于 `base_loss`）、用于对照实验——如果两种损失模型跑出来的召回质量没有差异，说明“管道决定损耗”这个修正在当前参数下不产生实质影响、需要检查是不是被其他机制掩盖了。

**结论**：损失是 `pipe_effective_thickness` 的确定性函数，粗管损失小、细管损失大、永不超过 `loss_max`。这是“管道粗细双重角色”在损失上的具体落地。

**关联**：损失单调性、每跳损失先扣、管道粗细双重角色、LossModel。

---

### 损失单调性

**起因**：损失函数必须满足“管道越细损失越大”的物理直觉。这是物理法则层面的不变量，不是靠某个参数值恰好满足——如果单调性被破坏，说明损失函数实现有误（比如把 `1 - pipe_effective_thickness` 写成了 `pipe_effective_thickness`、或 `loss_pipe_factor` 符号错了），它会让“细管损耗大”的整个设计意图失效，比业务逻辑错误更严重。

**理念**：用属性测试覆盖，随机生成 `pipe_effective_thickness` 对和参数组合；手写用例只能覆盖有限几个点，属性测试能覆盖整个输入空间。

**解释**：对任意 `pipe_effective_thickness_1 < pipe_effective_thickness_2`，有 `loss(pipe_effective_thickness_1) ≥ loss(pipe_effective_thickness_2)`——这是**非严格单调递减**（允许 `loss_max` 截断后的平台）；如果配置校验强制 `base_loss × (1 + loss_pipe_factor) ≤ loss_max`，则严格单调 `>` 也成立。损失有界 `loss ∈ [base_loss, loss_max]`——`pipe_effective_thickness = 1` 时取下界 `base_loss`，`pipe_effective_thickness → 0` 时趋近上界 `base_loss × (1 + loss_pipe_factor)` 但被 `loss_max` 截断。

**方案**：属性测试断言非严格单调 `≥`；配置校验可选地强制未截断损失 ≤ `loss_max` 以保证严格单调；测试用例覆盖三个关键点——`pipe_effective_thickness = 1` 时损失恰好等于 `base_loss`、`pipe_effective_thickness → 0` 时损失被 `loss_max` 截断、中间任意两点满足非严格单调递减。

**结论**：严格/非严格取决于配置校验是否强制未截断损失 ≤ `loss_max`；属性测试断言非严格单调，配置校验可选地保证严格单调。这是“损失单调性”从口号变成可测试不变量后的准确表述。

**关联**：损失函数、属性测试、配置化。

---

### 创建来源（四条：`new_ball`、`co_activation`、`offline_similarity`、`manual`）

**起因**：不同场景产生的关联，可信度和初始强度不同。新球接图是“语义相似但未验证”的弱关联，共激活是“被水流一起走通过”的关联但单次共现不足以建立强关联，离线补边是“事后发现的相似”比新球接图更保守，手动建边是“用户确认的关联”可信度最高。四条来源用 `source` 字段标记，便于审计和指标归因。

**理念**：新建立的关联强度还没被验证，初始做细——四条来源的初始 `pipe_base_thickness` 刻意都做细，因为新建立的关联强度还没被验证，需要后续流动和结算自然变粗。这和“结算变粗”是配套的：创建时细、走通后粗、久不走则惰性衰减，形成完整的生命周期。

**解释**：① 新球接图——新球创建时，用其嵌入与已有 `active` 球算余弦，过滤低于 `new_pipe_threshold`（默认 0.5）的球，取 Top-K（默认 2）建弱管道，初始 `pipe_base_thickness = 余弦 × new_pipe_initial_factor`（默认 0.5），来源标记 `new_ball`；这是新球进入图的主要路径，没有它新球就是孤岛。② 共激活建边——同一次激活中，两个球都产生补充且都进入注入 Top-K，在它们之间建弱管道，初始 `pipe_base_thickness = co_activation_initial`（默认 0.1），来源标记 `co_activation`；语义是“它们一起被想起过”，初始权重极低、需要多次共激活才能变粗，**默认关闭**（`enable_co_activation_pipe = false`），因为会增加图密度，MVP 阶段先不开，Phase 3 再评估。③ 离线相似补边——离线巩固时，孤岛球或图稀疏区域，余弦 > `offline_pipe_threshold`（默认 0.7）且当前无管道 → 建管道 `pipe_base_thickness = 余弦 × 0.3`；已有管道但 `pipe_effective_thickness` 低于 `offline_pipe_min`（默认 0.05）且余弦 > 0.8 → 适度加粗，防止本该连接的球因长期不流动而断开；来源标记 `offline_similarity`。④ 手动建边——纠正或用户显式操作时直接建管道或调粗，来源标记 `manual`，走纠正审计、记录原值、新值、原因、操作者。

**方案**：四条来源都遵守无向权重和唯一性约束、不会重复建边；来源标记进入指标 `pipe_creation_by_source`，用于判断图生长是否过度依赖某一条来源——如果 90% 的管道都来自 `new_ball`、`co_activation` 和 `offline_similarity` 几乎不触发，说明图结构在“新建时一次性定型”、缺少后续演化，需要检查共激活和离线补边是否被正确启用。

**结论**：创建时细、走通后粗、久不走则惰性衰减，形成完整生命周期。这是“关联强度需要被验证”在图结构上的具体落地。

**关联**：新球接图、离线相似补边、结算变粗、管道惰性衰减。

---

### 结算变粗（`pipe_strengthen_factor`、`pipe_thickness_ceiling`）

**起因**：路径被走通后，管道应该变粗，把“这条联想路径被走通过”这个事实写进结构。不只是被点亮的球变大，路径上的管道也变粗——“一起被想起的东西一起变强”。

**理念**：强化值随路径相关性缩放，强相关路径的管道加粗更多；有饱和上限 `pipe_thickness_ceiling`，防止单条管道无限变粗、形成正反馈；只强化路径上的管道，不是所有被点亮球之间的管道、也不是全图管道。

**解释**：结算时，水流走通的**路径上的每一条管道**按路径相关性强化：`pipe_base_thickness += 路径相关性 × pipe_strengthen_factor`（默认 0.05），饱和 `pipe_thickness_ceiling`（默认 1.0），写入时 clamp 到 `[0, pipe_thickness_ceiling]` 防浮点越界。

**方案**：同一结算中管道出现在多条路径上时，取最大路径相关性强化一次、不累加——这和球的多路径取最大值是同一个原则，防止一条管道被多条弱路径“刷”成过强、导致流动时越来越倾向于走这条管道、联想僵化。它和“创建来源”的初始 `pipe_base_thickness` 是配套的：创建时初始做细（新建立的关联强度还没被验证）、走通后结算变粗（关联被验证了）、久不走则惰性衰减变细（关联淡化了），形成“创建细 → 走通粗 → 不走细”的完整生命周期。它和“管道衰减”是两套独立的写入路径：结算变粗写的是基础 `pipe_base_thickness`（存储值），惰性衰减算的是 `pipe_effective_thickness`（读取时的派生值），两者不在同一时刻发生——变粗只在结算事务里写回，衰减只在读取时现算、不落库。强化走原子增量、不用读-改-写、并发安全；写入与球大小更新在同一结算事务内，要么全成功要么全回滚。

**结论**：结算变粗写的是基础 `pipe_base_thickness`（存储值），惰性衰减算的是 `pipe_effective_thickness`（读取时派生值），两者不在同一时刻发生。这是“一起被想起的东西一起变强”在管道上的具体落地。

**关联**：创建来源、多路径取最大、管道有效粗细、结算同步立刻执行。

---

### 多路径取最大

**起因**：同一球或管道可能出现在多条路径上。如果累加，一条被三条 0.3 相关性路径经过的管道会得到 `0.3 + 0.3 + 0.3 = 0.9` 的强化，比一条被单条 0.8 相关性路径经过的管道还强，这违背“强相关路径应该主导强化”的直觉，也会让被多条弱路径反复经过的管道突然变得极粗、流动时形成正反馈、越来越倾向于走这条管道、导致联想僵化。

**理念**：强度取最强、不叠加——与“管道合并取最大值”是同一类守恒逻辑，两者都遵循“强度取最强、不叠加”的守恒逻辑。

**解释**：同一结算中，一个球或一条管道出现在多条路径上时，取最大路径相关性强化一次、不累加。取最大值后，同一结算中每条路径的贡献独立、不叠加，最强的路径决定强化幅度、弱路径不因为“数量多”而补偿。

**方案**：球和管道都遵守这条规则；最低强化球不走这条规则（它不按路径相关性算幅度、只强化一次）；不改变单条路径内的 `semantic_similarity × 路径折扣` 计算。

**结论**：最强路径决定强化幅度、弱路径不因“数量多”而补偿。这是“防止联想僵化”在强化规则上的具体落地。

**关联**：结算变粗、强化球/最低强化球、合并。

### 阻塞记忆折扣（`blocked_pass_count`、`blocked_discount`、`blocked_cap`）

**起因**：被阻挡过的管道，下次同类线索到达时应该更容易通过——“差点想起”的补偿。这是舌尖效应的工程对应：人“差点想起”某件事之后，下次再遇到相关线索，往往更容易想起来。工程上需要一个机制记录“这条管道曾经被水流试探过但没通过”，并在下次给一点补偿，否则每次都是从零开始，试探永远只是白费损失、不留下任何痕迹。

**理念**：折扣最多 50%、不会降到零——它只是“更容易通过”、不是“必然通过”，如果折扣能降到零阻力，那等于“被阻挡过几次的管道自动变成开关”，违背“阻力不是开关”的理念。

**解释**：每次水流因阻力不足无法通过某条管道，`blocked_pass_count_stored += 1`（封顶 `blocked_cap`，默认 5），并刷新 `last_blocked_at`；下次水流到达同一条管道时，有效阻力 `pipe_resistance × (1 - blocked_discount × min(blocked_pass_count_effective, blocked_cap))`，`blocked_discount` 默认 0.1、最多降低 50% 阻力。

**方案**：`blocked_pass_count` **随时间间隔按曲线速减**——读取时算 `blocked_pass_count_effective = blocked_pass_count_stored × exp(-Δt / blocked_decay)`，`Δt = now - last_blocked_at`，`blocked_decay` 建议 30–90 天；结算时先算 `blocked_pass_count_decayed = blocked_pass_count_stored × exp(-Δt / blocked_decay)`、再叠加本次新增阻挡次数、封顶 `blocked_cap`、写回 `blocked_pass_count_stored` 并刷新 `last_blocked_at`——写回的是“已衰减到当前时刻的值 + 新增量”，不是原始累积值。成功通过后 `blocked_pass_count_stored` 不清零、不再增长——已通的管道不需要继续降阻，但“曾被阻挡过”是历史事实、清零会丢失信息，它只是停止增长并随时间自然衰减。`blocked_decay`、`blocked_discount`、`blocked_cap` 全部进配置可调。

**结论**：被阻挡时增长、通过后停止增长、长期不活动自然衰减，形成“差点想起 → 更容易通过 → 通过了就不再累积 → 久了痕迹淡化”的完整生命周期。它和 `lit_count` 是两套独立计数：`blocked_pass_count` 记“水到了但过不去”、`lit_count` 记“水到了且点亮了”。

**关联**：blocked_pass_count 随时间衰减、成功通过后、阻力、lit_count。

---

### blocked_pass_count 随时间衰减（`blocked_decay`）

**起因**：原设计里 `blocked_pass_count` 是永久累积计数、不随时间变化，会让“年轻时差点通过”的痕迹永久保值——一个管道十年前被阻挡 5 次和昨天被阻挡 5 次不应享受同样折扣。

**理念**：历史痕迹随时间淡化，与 `pipe_base_thickness` 的惰性衰减遵循同一套“存储原始值、读取时算有效值、不落库”的模式，但写回策略不同——`pipe_base_thickness` 只在结算变粗时写回、不衰减写回；`blocked_pass_count` 在每次结算时先衰减再叠加写回，因为前者是“质量”、后者是“痕迹”。

**解释**：存储 `blocked_pass_count_stored` 和 `last_blocked_at`；读取时算 `blocked_pass_count_effective = blocked_pass_count_stored × exp(-Δt / blocked_decay)`，`blocked_decay` 建议 30–90 天，只用于计算阻力折扣；结算时先算 `blocked_pass_count_decayed = blocked_pass_count_stored × exp(-Δt / blocked_decay)`、再叠加本次激活中该管道被阻挡的次数、封顶 `blocked_cap`（默认 5）、写回 `blocked_pass_count_stored` 并刷新 `last_blocked_at`——写回的是“已衰减到当前时刻的值 + 新增量”，不是原始累积值。

**方案**：引入衰减的理由是：不衰减会让“年轻时差点通过”的痕迹永久保值；衰减后长期未被试探的管道折扣自然失效、重新活动时从低基线重新增长，符合“历史痕迹随时间淡化”的直觉。

**结论**：长期未被试探的管道折扣自然失效、重新活动从低基线增长。这是“历史痕迹随时间淡化”在阻塞记忆上的具体落地。

**关联**：阻塞记忆折扣、成功通过后、阻力。

---

### 成功通过后

**起因**：管道成功通过后，`blocked_pass_count` 如何处置需要明确。如果清零，“曾被阻挡过”这个历史事实就丢失了；如果继续增长，已通的管道不需要继续降阻，增长没有意义。

**理念**：已通的管道不需要继续降阻，但“曾被阻挡过”是历史事实、清零会丢失信息——它只是停止增长、并随时间自然衰减。

**解释**：管道被水流成功通过后，`blocked_pass_count_stored` **不清零、不再增长**——已通的管道不需要继续降阻，但“曾经被阻挡过”是历史事实、清零会丢失信息；同时 `blocked_pass_count_stored` 仍会随时间自然衰减，读取时算 `blocked_pass_count_effective = blocked_pass_count_stored × exp(-Δt / blocked_decay)`，长期不再被试探的管道折扣自然失效、重新被阻挡时从低基线重新增长。`last_blocked_at` 不在“成功通过”时刷新——它记的是“上次被阻挡”的时间，不是“上次流动”的时间，成功通过不改变这个时间戳、衰减计时继续从上次阻挡时刻算起。

**方案**：这条规则和“阻塞记忆”的衰减机制配套：被阻挡时增长、成功通过后停止增长、长期不活动自然衰减，形成“差点想起 → 更容易通过 → 通过了就不再累积 → 久了痕迹淡化”的完整生命周期。它和管道粗细的 `pipe_base_thickness` 是两套独立状态：`pipe_base_thickness` 在成功通过后会因结算强化而变粗（路径级强化），`blocked_pass_count` 在成功通过后不会增长——前者记“这条联想被走通了”、后者记“这条联想差点走不通”，两者语义不同、更新时机不同、互不替代。

**结论**：成功通过后停止增长、但仍随时间衰减。这是“阻塞记忆生命周期”在通过后的具体处置。

**关联**：阻塞记忆折扣、blocked_pass_count 随时间衰减、结算变粗。

### 合并（`merge_cosine_threshold`、`merge_edge_threshold`）

**起因**：两个球可能事实上是同一个，需要合并。合并有两个触发时机——离线巩固时的相似合并、用户手动合并。

**理念**：语义几乎相同且管道很粗才合并——两个条件同时满足才合并，语义几乎相同但管道很细的球不合并（它们只是相似、还没被水流反复验证为同一个），管道很粗但语义不同的球也不合并（它们是被频繁一起想起的不同记忆、不是同一个）。用户显式判断优先于离线相似度。

**解释**：① 离线巩固时的相似合并——离线巩固阶段扫描球对，当两个球的内容嵌入余弦超过 `merge_cosine_threshold`（默认 0.95）且它们之间的 `pipe_effective_thickness` 超过 `merge_edge_threshold`（默认 0.9）时触发合并。② 用户手动合并——用户显式说“这两个是同一件事”或通过纠正操作指定合并，走纠正审计、不受阈值约束。合并时大球吸收小球，`ball_stored_size` 取合并后重新计算（不简单相加、按内容贡献加权），`ball_stability_stored` 取最大值，内容列表合并去重。

**方案**：管道处理规则——另一端就是吸收方 → 删除自环；另一端是 C 且吸收方与 C 已有管道 → 取 `pipe_base_thickness = max(...)`、`blocked_pass_count_stored = max(...)`、`pipe_stability_stored = max(...)`、时间戳取最大值，删除被吸收方的管道；另一端是 C 且吸收方与 C 无管道 → 重定向保留原值。核心约束是**不叠加权重**（取最大值不相加，否则合并让管道突然变粗）、时间戳取最大值（反映最活跃那条管道的历史，取最小值会让衰减计时错乱）。合并是分裂的逆操作，走纠正审计，反向执行分裂时按审计记录恢复原管道。离线相似合并在离线巩固时执行、不在线触发，用户手动合并可随时触发但走同步事务。

**结论**：合并是分裂的逆操作，离线相似合并不在线触发、用户手动可随时触发。这是“语义归并”在纠正机制下的具体落地。

**关联**：分裂、兜底合并、多路径取最大、可逆性。

### 分裂（`split_cohesion_threshold`、`split_min_contents`）

**起因**：一个球里可能混了多个语义方向的内容，需要分裂。分裂有两个触发时机——离线巩固时的内聚度分裂、用户手动分裂。

**理念**：内聚度低且内容足够多才分裂——内容条数太少不分裂（样本不足、可能是噪声），内聚度还高不分裂（语义还集中、没到该拆的时候）。用户显式判断优先于离线内聚度。

**解释**：① 离线巩固时的内聚度分裂——离线巩固阶段扫描球的内容列表，计算该球下所有内容嵌入的两两平均余弦（内聚度），当内聚度低于 `split_cohesion_threshold`（默认建议 0.6）且内容条数 ≥ `split_min_contents`（默认 5）时触发分裂。分裂时用嵌入聚类把内容分成若干组（组数由聚类结果决定、不预设），每组创建一个新球，原球保留其中一组、其余组成为新球。② 用户手动分裂——用户显式说“这两件事不是一回事”或通过纠正操作指定分裂，走纠正审计、不受阈值约束。

**方案**：分裂的具体处理规则——`ball_stored_size` 按各组内容的贡献比例（如内容条数或显著性总和）拆到新球，不复制、不重复计数、拆完总和守恒；`ball_stability_stored` 按各组独立演化，新球从基础值开始、不继承原球的高稳定性（因为“被反复强化过”是原球整体的历史、不是某个内容组的历史）；内容列表按分组迁移，每条内容只属于一个球；管道按内容组的归属重定向——与组内球相连的管道复制 `pipe_base_thickness`/`blocked_pass_count_stored`/`pipe_stability_stored` 到新球，跨组的管道按“该管道另一端属于哪个组”重定向到对应新球，原球与自身新球之间不建管道（它们是分裂出来的、不是独立关联的）。分裂走纠正审计，`correction_log` 记录原球的内容列表、聚类分组结果、每组的新球 ID、`ball_stored_size` 拆分比例、每条管道的重定向去向，保证可追溯、可回退——反向执行合并时按审计记录恢复原球和原管道。

**结论**：分裂是合并的逆操作，强度按比例拆分、新球不继承历史稳定性。这是“内聚度低才分裂”在纠正机制下的具体落地。

**关联**：合并、可逆性、强度守恒、球稳定性。

### 归档

**起因**：球归档时管道如何处置需要明确。如果管道独立归档，`pipe_effective_thickness` 低只说明“这条联想现在很细”，不代表“这条联想没价值”，两端球都还活跃时强线索仍可能用到它；如果把低 `pipe_effective_thickness` 的管道独立归档，等于变相删除细管道，违背“阻力不是开关、永不封死”的理念。

**理念**：管道跟随球归档、不独立触发。`pipe_effective_thickness` 低不等于“没价值”。

**解释**：当球被归档（距上次注水超 `archive_inactive_days` + `ball_effective_size` 低于 `archive_size_threshold`，或活跃球数超 `max_active_balls` 被强制归档）时，与它相连的所有管道一起转入归档表、状态置为 `archived`，**不删除**——`pipe_base_thickness`、`blocked_pass_count_stored`、`pipe_stability_stored`、时间戳全部保留，只是不参与常规流动。归档球被检索命中翻回 `active` 时，管道随之恢复 `active`。

**方案**：管道不因 `pipe_effective_thickness` 低而独立归档——只有球归档才带管道归档，因为“管道很细”不等于“这条联想没价值”，两端球还活跃时强线索仍可能用到它。管道独立归档只在一种情况下发生：两端球都已被归档，管道无处附着，随最后一个归档球一起归档——这不是“管道主动归档”，是“球归档的连带结果”。归档不改变管道的任何状态值、只改变 `status` 字段；归档管道的 `blocked_pass_count` 和 `pipe_stability` 仍随时间衰减，但读取时不参与主图流动、只在临时加载时算 `pipe_effective_thickness` 和折扣。归档表的管道同样做嵌入分桶索引，强线索加载归档球时按球 ID 直接查关联管道、不做全量扫描。 **结论补充**：管道不归档。管道是球之间的关系，球醒了路就该能用；单独归档管道会制造“球活着但路断了”的怪状态。`archive_sweep` 只改球状态，管道保持 `active`。

**结论**：管道归档是球归档的连带结果，不是“管道主动归档”。这是“疏而不堵”在管道归档上的具体落地。

**关联**：归档触发、归档唤醒、状态、管道有效粗细。

### 管道健康因子

**状态**：**已废弃**。

**起因**：曾是“管道粗细也决定损耗”修正时提出的可选增强——在结算的路径折扣里，除了按跳数打折，再乘一个“路径上 `pipe_effective_thickness` 均值”的健康因子，公式形如 `路径相关性 × 长度折扣 × (pipe_health_floor + (1 - pipe_health_floor) × avg_pipe_effective_thickness)`，默认 `pipe_health_floor = 0.5`，意图是让“管道都很粗的长路径”少打折、“管道很细的短路径”多打折，让路径折扣“更物理”。

**理念**：废弃——`pipe_effective_thickness` 已经在流动阶段决定了阻力和损耗，再乘进相关性是同一个信号第二次计权。这和“水量乘进相关性”“`ball_stored_size` 塞进衰减函数”是同一类错误，一个量在它不该出现的地方被当成了另一个量的乘数；更严重的是它会形成“粗管 → 更受偏爱 → 强化更多 → 变得更粗”的正反馈，细管和孤岛记忆永远等不到水流，违背“疏而不堵”的理念。

**解释**：修正后路径折扣只含跳数折扣 `max(min_discount, 1 - discount_per_hop × 跳数)`、不含任何 `pipe_effective_thickness` 相关因子；管道的粗细信息只活在流动阶段的阻力和损耗里，不进入结算的相关性计算、不进入注入排序。

**方案**：当时曾建议“MVP 阶段先只保留跳数折扣，等对照实验数据显示管道粗细对路径质量有独立解释力再开启”，但后续在“相关性与水量解耦”的修正中，它被识别为与水量乘进相关性同构的二次计权错误，**正式废弃、不再作为可选项保留、连默认关闭的开关都不留**。

**结论**：一个量在它不该出现的地方被当成了另一个量的乘数——这是“二次计权”在管道健康因子上的具体反例。

**关联**：相关性定义、路径折扣、水量乘进相关性。

## 四、流动动力学

### 流动只点亮、不写入

**起因**：流动过程中每跳写入会把持久化塞进传播路径，复杂且容易竞态——同一轮多路径同时到达同一个球、dsh 和 pi 两个客户端同时流动时，会出现“读-改-写”竞态，需要复杂的锁。

**理念**：流动回答“哪些球被点亮、沿什么路径”，结算回答“强化多少、注入哪些”，两者混在一起会让流动逻辑被写入逻辑污染，也让“流动可以纯粹用内存子图跑”这个性能优势丧失。结算必须同步立刻执行、基于刚强化后的球状态决定注入排序，如果流动过程中已经写入了部分强化值，结算时的“强化前状态”就不存在了、注入排序会基于被污染的状态。

**解释**：流动阶段是**纯内存计算**、不产生任何持久化写入。水从起始球出发、沿管道传播、逐跳扣损失、判断阻力、释放补充、点亮球——全程在内存子图上完成，点亮集合和路径集合是临时状态，**不落库、不开启写事务、不持有数据库写锁**。写入只发生在结算阶段，且是**一次激活一次事务**、不是每跳一次。

**方案**：流动开始时开短读事务加载起点子图、记录全局版本号 `graph_version_start`、立刻结束读事务，流动在内存子图上纯计算；结算时开写事务、校验版本号（无冲突直接写、有冲突重读涉及球/管道重算增量）、写入球大小增量、管道粗细增量、`last_watered_at`/`last_flowed_at` 刷新、`blocked_pass_count` 和 `ball_stability` 先衰减再叠加，提交后落库。流动阶段被阻挡的管道，`blocked_pass_count` 的本次新增只记在内存里、结算时才写回——如果本次结算因版本冲突失败或进程崩溃，这次阻挡记录丢失、下一轮重新开始，丢失一次阻挡记录可接受（只影响下次阻力折扣、不影响记忆内容）。

**结论**：写入从“每跳一次”变成“一次激活一次”，竞态被压缩到结算那一次事务里。这是“流动只点亮、结算才强化”在写入时机上的具体落地。

**关联**：结算同步立刻执行、快照隔离、版本冲突重算。

### 每跳损失先扣

**起因**：损失发生在通过判断之前还是之后？如果先判断能否通过、通过才扣损，那失败的试探零成本，系统会倾向于广撒网、失去“选择方向”的意义，也不符合物理直觉——水流过一段管子，不管最后有没有流出去，摩擦损耗都已经发生了。

**理念**：损失是**试探本身的成本**，不是“通过才付的代价”。水被分散到一条管道上，不管最终能不能通过，这一跳的试探已经发生了，“想不起来就是白费力气”的直觉要求试探有成本。

**解释**：水到达一条管道时，**先按 `loss(pipe_effective_thickness)` 扣掉这一跳的损失、再判断能否通过阻力**，顺序不能反。扣损后的剩余水量才拿去和阻力比较：通过则用扣损后的水量加补充继续流向下一跳，不通过则这部分水损失掉、不回收给其他管道。

**方案**：损失函数是 `pipe_effective_thickness` 的确定性函数——粗管损失小、细管损失大，损失永不超过 `loss_max`、保证再细的管道也不会把水全部吃掉。它和“通过条件”是严格的两步顺序：先扣损（不管通过与否、损失都发生）→ 再判断（扣损后的水量 > 阻力才能通过）。它和“分配权重”“损失不回收”一起构成完整的流动成本模型：分配时按 `1 + pipe_effective_thickness` 加权把水分到各条未访问出边，每条管道先扣自己的损失、再判断能否通过，过不去的损失不回流——三步合起来保证“每条管道的试探成本独立、失败不拖累其他方向、成功与否都不退还已付出的成本”。

**结论**：损失是试探本身的成本，不是“通过才付的代价”。这是“每跳损失先扣”在流动成本模型上的具体落地。

**关联**：通过条件、损失函数、损失不回收、分配权重。

### 通过条件

**起因**：水能否通过一条管道需要唯一判据。如果判据是语义判断或阈值开关，那“语义无关但水压足够的球能通过并继续流向远处”就无法实现。

**理念**：纯物理量比较，不是语义判断、不是阈值开关。语义相关性只在“是否补充”和“是否强化”里起作用，不直接决定“能不能过”——一个球语义上完全无关，只要水压足够大、管道足够粗，水照样能通过它继续流向远处，这正是“水流不按语义预判方向、让水自己找路”的体现。

**解释**：水能否通过一条管道，唯一判据是**扣损后的剩余水量 > 阻力**：`water_after_loss > pipe_resistance`，其中 `water_after_loss = current_water × (1 - loss(pipe_effective_thickness))`，`pipe_resistance = 1 / (1 + pipe_effective_thickness) × 阻挡记忆折扣`。满足则通过——目标球被点亮、扣损后的水量加上目标球释放的补充继续流向下一跳；不满足则不通过——这部分水按损失规则损失掉、不回收，该方向尝试结束，改试该球的其他未访问出边。

**方案**：阻力有上限，所以通过永远可能——`pipe_effective_thickness → 0` 时 `pipe_resistance → 1`、不是无穷大，这意味着任何管道在水量足够大时都能被突破；强线索放大起始水量、放大可释放水量、降低被阻挡管道的有效阻力，三条规则叠加，让“沉睡记忆被强线索唤醒”在通过条件上成为可能，而不是靠给细管开特例。它和“每跳损失先扣”是严格的两步顺序：先扣损、再用扣损后的水量判断，不能反。边界情况：`pipe_effective_thickness` 极小时阻力接近上限 1，常规水量过不去、但强线索放大后水量可超过 1 而通过；`blocked_pass_count_effective` 高时阻力被折扣到最低 50%、让“差点通过”的管道更容易通过，但不会到零阻力、不会变成必然通过。

**结论**：语义无关但水压足够的球能通过并继续流向远处。这是“水流不按语义预判方向”在通过条件上的具体落地。

**关联**：每跳损失先扣、阻力、分配权重、损失不回收。

### 回边排除

**起因**：原设计里回边（来路，目标已访问）和去路（目标未访问）同等参与 `1 + pipe_effective_thickness` 加权分配，导致每经过一个中间球水量腰斩——ball1 的出边有来路（ball0，已访问）和去路（ball2，未访问），两条各拿 50%，回边那 50% 按“第二次到达只损失”白费，5 球链只能点亮深度 0、改造前能到深度 3。

**理念**：回边不是“待探索的方向”、是“已经走过的路”，排除它不违背“不按语义预判方向”的本意。用拓扑事实（已访问标记）排除确定性浪费，和用语义判断（相关性）预判方向，是两回事——前者不扼杀探索、后者会。

**解释**：水从球出发流向它的出边时，**只流向目标未被访问过的出边**，目标已访问的出边不参与水量分配。规则表述从“水球流向所有连接它的水管”**精确化为**“水球流向所有未访问的连接水管”。修正后 ball1 的出边只有 ball2 参与分配、水 100% 流向去路，传播能力恢复。

**方案**：它和“第二次到达只损失”是两条独立规则——回边排除在**分配前**就生效（目标已访问的出边不分配水），“第二次到达只损失”只在**分配后**的多路径汇聚场景生效（两条不同路径同时指向一个未访问球，先到者变已访问、后到者全损）。边界情况：球的所有出边都已访问时，没有未访问出边、水全部损失、该球成为死路、**无特例回流**——实现时不能加“如果没有未访问出边就回流”的特例，那会重新引入回边浪费。

**结论**：用拓扑事实排除确定性浪费，和用语义判断预判方向是两回事。这是“回边排除”在分配规则上的具体落地。

**关联**：分配权重、同一次激活每球只注一次、第二次到达只损失、所有出边已访问。

### 分配权重

**起因**：多条未访问出边之间如何分水？平均分让粗管和细管拿到一样的水，违背“粗管是强关联”的语义，`pipe_base_thickness = 0.9` 和 `0.1` 两条管道各拿 50%，等于告诉系统“这两条关联一样强”；直接按 `pipe_base_thickness` 分会让 `pipe_base_thickness → 0` 的管道分到趋近于零的水，等于用分配规则把路封死、和“阻力不是开关、强线索可突破”的理念直接冲突。

**理念**：让管道粗细在**流量分配**上也有语义，而不只是在阻力判断和损耗计算上有语义——三条路径（分配、阻力、损耗）都用同一个 `pipe_effective_thickness` 的不同侧面，粗管“分得多、好通过、损耗小”，细管“分得少、难通过、损耗大”，三者一致。

**解释**：水从球流向多条未访问出边时，按 `1 + pipe_effective_thickness` 加权分配，每条出边分到的水量 `= 球可分配水量 × (1 + pipe_effective_thickness_i) / Σ(1 + pipe_effective_thickness_j)`，其中 `j` 遍历所有未访问出边。**用 `pipe_effective_thickness` 而不是 `pipe_base_thickness`**——分配、阻力、损耗三条路径统一用同一个 `pipe_effective_thickness` 的不同侧面，避免水被分到“账面粗但实际细”的管道上浪费。`1 + pipe_effective_thickness` 的权重下限是 1，保证细管分到的水最少但**非零**、粗管分到最多；`pipe_effective_thickness = 1` 的管道权重 2、`pipe_effective_thickness = 0.1` 的管道权重 1.1，粗管拿约 64.5%、细管拿约 35.5%，比例合理但不极端。

**方案**：它和“细管保底非零”是同一件事的两面：`1 + pipe_effective_thickness` 加权既保证了粗管多分（语义正确），又保证了细管非零（不封死）。它和“先分配后判断”配套：分配是一次性完成的，每条管道拿到自己的那份水后独立判断能否通过、过不去的损失不回收。分配权重做成可配置：`split_mode = "weighted"`（默认，`1 + pipe_effective_thickness`）或 `"equal"`（对照实验用，平均分）；`equal` 不是为了生产使用，是为了验证“按粗细加权分配”是否真的带来召回质量差异——如果两种模式跑出来没有差异，说明分配规则在当前场景下不产生实质影响；如果有差异，方向是否符合预期也需要数据判断。

**结论**：分配用 `pipe_effective_thickness`，避免水被分到“账面粗但实际细”的管道上浪费。这是“管道粗细在流量分配上也有语义”的具体落地。

**关联**：细管保底非零、先分配后判断、管道有效粗细、回边排除。

### 细管保底非零

**起因**：直接按 `pipe_base_thickness` 分会让 `pipe_base_thickness → 0` 的管道分到趋近于零的水，等于用分配规则把路封死、违背“不删除、只降可提取性”的理念。

**理念**：`1 + pipe_effective_thickness` 的权重下限是 1，保证细管分到的水最少但**非零**。有了非零保底，细管在常规水量下确实过不去（分到的水太少、低于阻力），但当总水量因强线索放大时，细管的绝对水量也随之放大、可能超过阻力上限而被突破——不是靠给细管开特例，是靠权重下限保住基础水量、让“强线索突破细管”在分配层面成为可能。

**解释**：`1 + pipe_effective_thickness` 加权保证每条未访问出边**至少分到严格大于零的水量**，即使 `pipe_effective_thickness` 极接近 0。`pipe_effective_thickness → 0` 时权重趋近 1、不是 0——细管分到的是“最少但非零”的那一份、而不是零。

**方案**：它和“通过条件”是配套的：分配保证非零、通过条件保证“水量 > 阻力才通过”，两者叠加的效果是“细管平时过不去、强线索下可能过去”。它和“直接按 `pipe_base_thickness` 分”是两条对立的设计：直接按 `pipe_base_thickness` 分会让 `pipe_effective_thickness → 0` 的管道分到趋近于零的水、等于用分配规则封死；`1 + pipe_effective_thickness` 加权则保留了非零下限。

**结论**：细管平时过不去、强线索下可能过去。这是“阻力不是开关”在分配规则上的具体落地。

**关联**：分配权重、通过条件、强线索放大。

### 先分配后判断

**起因**：逐条尝试、失败了把水还给其他管道，会让**判断顺序**影响结果——先试的管道如果失败、把水还回来，后面的管道就能拿到更多水，这意味着“哪条管道先被尝试”成了一个有语义影响的决策，而管道之间本应平等、没有“谁先谁后”的语义。

**理念**：先分配后判断让每条管道的成败**互不影响**，结果与尝试顺序无关、可复现、可审计。

**解释**：水到达一个球后，**先把球的可分配水量按 `1 + pipe_effective_thickness` 加权一次性分到所有未访问出边**，然后**每条管道用自己分到的那份水量独立判断能否通过**——顺序不能反，也不能改成“逐条尝试、失败了把水还给其他管道”。可分配水量 = 流入该球的水量 + 该球释放的补充；分配是一次性完成的、各条出边拿到的水量之和等于可分配总量（分配守恒）；分配完成后，每条管道先扣自己的损失、再用扣损后的水量和阻力比较，通过则继续流向下一跳，不通过则这部分水损失掉、**不回收给其他管道**。

**方案**：它和“分配权重”“损失不回收”一起构成完整的流动成本模型：分配按 `1 + pipe_effective_thickness` 把水分到各条未访问出边（粗管多分、细管少分但非零），每条管道先扣自己的损失、再用扣损后的水量独立判断能否通过，过不去的损失不回流——三步合起来保证“每条管道的试探成本独立、失败不拖累其他方向、成功与否都不退还已付出的成本”。它和“回边排除”配套：分配前先排除已访问出边、只对未访问出边分配，避免把水分到注定白费的回边上。边界情况：球只有一条未访问出边时分配退化为 100% 给这条边；球没有未访问出边时不分配、水全部损失、球成为死路；多条出边时按 `1 + pipe_effective_thickness` 加权比例分配、不是平均分。

**结论**：结果与尝试顺序无关、可复现、可审计。这是“管道之间本应平等”在分配顺序上的具体落地。

**关联**：分配权重、损失不回收、回边排除。

### 损失不回收

**起因**：如果回收，等于“试探无成本”——失败的方向把水还给成功的方向，系统就会倾向于广撒网、每个方向都试一遍，因为试错没有代价；这会让“选择方向”失去意义，也让水流变成“穷举所有路径”而非“有成本地探索”。

**理念**：每次分配是一次**有代价的承诺**：水一旦分出去，不管走不走得通，都已经消耗在试探里，“想不起来就是白费力气”的直觉正是这条规则的工程对应。

**解释**：一条管道判断不通过后，它分到的那份水按损失规则扣掉后**直接消失，不回流给其他管道、不重新分配、不退还**。水被分散到多条出边后，每条管道的成败独立——某条走不通，那部分水就白流了，其他管道该拿多少还是多少、不会因为这条失败而多拿。

**方案**：它和“每跳损失先扣”配套——损失先扣、不管通过与否都发生；和“先分配后判断”配套——分配是一次性的、判断独立、失败不退还；和“回边排除”配套——回边在分配前就被排除、不产生“分了水又退回”的情况。边界情况：球的所有出边都失败时，可分配水量全部损失、球成为死路、水耗尽、不回流到上游；上游球不会因为下游失败而重新获得水量，上游那一步的分配已经完成、不可逆。它和“结算”是两件事：流动阶段的损失是**水量**的消失（不落库、只影响本次激活能传多远），结算阶段的强化是**球和管道状态**的写入（落库、影响后续激活）——损失不回收说的是水量、不是强化值。

**结论**：“想不起来就是白费力气”的工程对应。这是“有成本地探索”在损失规则上的具体落地。

**关联**：每跳损失先扣、先分配后判断、全失败。

### 同一次激活每球只注一次

**起因**：A→B→C→A 的循环会无限注水。如果不禁，A 被反复注水变大、B 和 C 也是，系统会在一个局部循环里反复强化、把水全部消耗在环上。

**理念**：循环不是被禁止，而是循环的那一段不产生收益、只有损失——水可以沿着环路流回去，但回流到已访问球时既不加注、也不补充，还要付这一跳的损失，水流自然会在几次循环后衰减到零，不需要显式检测环、不需要给循环设特例。

**解释**：水第一次到达一个球时，正常注水、释放补充、继续流向它的下游；**第二次到达同一个球时，不注水、不释放补充、只扣损失**。这条规则的作用是防止 A→B→C→A 的循环无限注水，也保证“点亮集合”天然是去重的球 ID 集合——`max_lit_ball_count` 约束的就是这个集合的大小、不是“点亮动作发生的次数”。

**方案**：它和“回边排除”是两条独立但配套的规则：回边排除在**分配前**生效（目标已访问的出边不参与水量分配，水 100% 流向未访问去路），“第二次到达只损失”在**分配后**的多路径汇聚场景生效（两条不同路径同时指向一个未访问球，先到者把它变已访问、后到者到达时水已经分好、无法回收、只能全损）。两条规则分工明确：回边排除防的是“同一球沿来路原样退回”，第二次到达只损失防的是“多路径汇聚时后到者的浪费”。边界情况：一个球第一次被到达时注水释放补充，之后无论通过哪条路径再次到达都不再注水、不再释放、只扣损失——所以一个球在一次激活中最多贡献一次补充、不会因为被多条路径到达而贡献多次。

**结论**：循环自然衰减、点亮集合天然去重。这是“循环不是被禁止、而是不产生收益”在流动规则上的具体落地。

**关联**：回边排除、第二次到达只损失、max_lit_ball_count。

---

### 第二次到达只损失

**起因**：多路径汇聚是拓扑事实——两条路径在分配时都指向同一个未访问球，分配已经完成、水已经分好，等到第一条到达后该球变已访问，第二条的水无法回收（回收就违背“损失不回收”），只能全损；如果不做这条规则，第二条到达时会重复注水、重复释放补充，一个球在一次激活中贡献多次补充、破坏“每球只注一次”的守恒。

**理念**：与“同一次激活每球只注一次”是同一件事的两面——后者是规则表述（每球只注一次），前者是到达时的处置方式（第二次到达只损失）。

**解释**：水**第二次到达同一个球**时，不注水、不释放补充、只扣这一跳的损失。这条规则现在**只用于多路径汇聚场景**——两条不同路径在分配后同时指向一个未访问球，第一条到达后该球变已访问，第二条到达时水已经分好、无法回收、只能全损。

**方案**：它和“回边排除”是两条独立规则、分工明确：回边排除在**分配前**生效（目标已访问的出边不参与水量分配，水 100% 流向未访问去路）、防的是“同一球沿来路原样退回”；第二次到达只损失在**分配后**生效、防的是“多路径汇聚时后到者的浪费”。边界情况：一个球第一次被到达时注水释放补充，之后无论通过哪条路径再次到达都不再注水、不再释放、只扣损失——所以一个球在一次激活中最多贡献一次补充；如果第二次到达时该球已经通过某条路径继续向下游流动，第二次到达的水不影响已发生的下游流动、只是自己损失掉。

**结论**：一个球在一次激活中最多贡献一次补充。这是“每球只注一次”在到达处置上的具体落地。

**关联**：回边排除、同一次激活每球只注一次、损失不回收。

---

### 所有出边已访问

**起因**：球的所有出边都已访问时，没有未访问出边可分配。如果加“回流”特例，等于重新引入回边浪费——水退回上游、上游再重新分配，本质上还是把水送回了已经走过的路、和“回边排除”的初衷冲突；而且回流会让“损失不回收”失效、试探变成无成本、系统倾向于穷举而非有成本地探索。

**理念**：所有方向都走过了，水在这里耗尽，这个球对本次激活的贡献到此为止——它可能已经在第一次被到达时贡献过补充，现在作为路径终点自然终止。

**解释**：水到达一个球后，如果它的**所有出边目标都已经是已访问状态**，则没有未访问出边可分配——水全部损失、该球成为**拓扑死路**、本方向流动终止、**无任何特例回流**。

**方案**：这是“回边排除”的边界情况：回边排除在分配前过滤掉目标已访问的出边，正常情况下至少还有去路可分配；但当球处于图的末端、或所有下游都已被本次激活走过时，过滤后剩余出边为零、分配无从进行、水只能全部损失。它和“同一次激活每球只注一次”配套：一个球第一次到达时注水释放补充，之后无论从哪条路径再次到达都不再注水；当它作为当前球、所有出边又都已访问时，水在这里损失、不会因为“没有去路”而获得任何补偿。边界情况：起始球本身如果所有出边都已访问（极端情况，比如图上只有两个球且互相连接），水在起始球处全损、本轮激活点亮集合只含起始球自身、结算时按最低强化值或正常资格判断；球只有一条出边且该出边目标已访问时，等同于所有出边已访问、水全损。

**结论**：所有方向都走过了，水在这里耗尽。这是“回边排除”在拓扑死路边界上的具体处置。

**关联**：回边排除、全失败、损失不回收。

### 补充规则（`supplement_threshold`）

**起因**：球释放补充不能是 `ball_effective_size × 相关性系数` 的线性乘积，弱相关的大球会靠历史强度放大水流。早期公式会让一个勉强过 `flow_continuation_threshold`（0.3）的弱相关大球靠历史强度释放大量补充、主导流动方向，和“大球赢家通吃”是同一个结构问题。

**理念**：资格 + 幅度两段式——相关性管“有没有资格补充”、大小和新鲜度管“有资格时补充多少”。**这里的“相关性”是流动阶段用原始查询嵌入算的余弦，不是结算阶段的流动加权语境**；两个阶段用不同语境，这是“流动加权语境”条目里明确的分工。

**解释**：水到达一个球并完成扣损后，若该球满足补充资格，会释放补充水量汇入水流、用于继续流向下一跳。**资格**：先看相关性是否过补充资格阈值 `supplement_threshold`（默认建议 0.4–0.5，高于 `flow_continuation_threshold`），**低于它时补充量为零**——球不贡献任何水，防止一个勉强过流动阈值的弱相关大球靠历史强度放大水流；过了资格阈值，水流仍可继续探索（靠剩余水量），但球不补充。**幅度**：高于资格阈值时补充按归一化相关性增长，`补充量 = ball_effective_size × (相关性 - supplement_threshold) / (1 - supplement_threshold)`，相关性刚好过阈值时补充接近零、接近 1 时才拿满 `ball_effective_size`。**上限**：补充量受 `max_supplement_ratio`（默认 2.0）截断，`补充量 = min(可释放水量, 当前水量 × max_supplement_ratio)`，防止一个大球让水流指数爆炸。

**方案**：球释放补充后**自身不变**——可释放水量是计算值、不是从球里扣水，球的大小变化只在结算时发生（被路径强化则变大、久不注水则惰性衰减），流动过程中球只是贡献了一个由当前状态决定的水量。补充加在**扣损之后**：`下一跳水量 = 扣损后水量 + 补充量`，细管道上的补充需要更大力才能让水流维持甚至增长、粗管道上的补充更容易让水越流越猛。补充量 > 当前损失时水流可能被放大、继续扩散，补充量 < 当前损失时水流衰减、联想链更早终止。`supplement_threshold = flow_continuation_threshold` 时退化为“过流动阈值就补充”的旧行为、可作为对照基线；`supplement_threshold` 不能设太高，否则中等相关球都不补充、水流衰减太快、多跳联想被扼杀。

**结论**：补充 > 损失当且仅当球大、新鲜、强相关，但“强相关”现在有了明确的资格阈值、不是线性乘一个小的相关性系数。这是“弱相关大球无法靠历史强度放大水流”的具体落地。

**关联**：可释放水量、补充 > 损失条件、流动加权语境、supplement_threshold。

---

### 补充 > 损失条件

**起因**：水在一个球处能否被放大、继续扩散，取决于补充是否大于这一跳的损失。早期公式 `ball_effective_size × 相关性系数` 会让一个勉强过 `flow_continuation_threshold`（0.3）的弱相关大球靠历史强度释放大量补充、主导流动方向，和“大球赢家通吃”是同一个结构问题。

**理念**：从“三个因子平权的乘法关系”改成“资格 + 幅度两段式”——**强相关**（过 `supplement_threshold`）决定“有没有资格补充”，**球大、新鲜**（`ball_effective_size` 高）决定“有资格时补充多少”；三者不再平权相乘，而是“相关性管资格、大小和新鲜度管幅度”。

**解释**：`补充量 > 当前水量 × loss(pipe_effective_thickness)` 时，`下一跳水量 = 扣损后水量 + 补充量` 大于流入水量、水流被放大、联想链继续延伸；`补充量 < 损失` 时下一跳水量小于流入水量、水流衰减、联想链更早终止；`补充量 ≈ 损失` 时水流勉强维持、传几跳后自然停下。资格是相关性过 `supplement_threshold`（默认 0.4–0.5），低于它时补充为零、无论球多大都**不可能**补充 > 损失；幅度是过了资格后 `补充量 = ball_effective_size × (相关性 - supplement_threshold) / (1 - supplement_threshold)`，此时“球大、新鲜”才通过 `ball_effective_size` 在幅度里起作用。

**方案**：边界情况——相关性刚好等于 `supplement_threshold` 时补充为零（归一化分子为零）；相关性接近 1 时补充接近 `ball_effective_size`、但仍受 `max_supplement_ratio`（默认 2.0）截断、防止水流指数爆炸；`supplement_threshold = flow_continuation_threshold` 时退化为“过流动阈值就补充”的旧行为、可作为对照基线。

**结论**：补充 > 损失当且仅当球大、新鲜、强相关，但“强相关”有了明确的资格阈值。这是“资格 + 幅度两段式”在补充条件上的具体落地。

**关联**：补充规则、可释放水量、每跳损失先扣、ball_effective_size。

---

### 安全阀 max_flow_depth（`max_flow_depth`）

**起因**：自然衰减理论上会让水停下，但强相关链可能越流越猛（补充 > 损失），一条 A→B→C→D→… 的强相关链如果每跳都满足补充条件，水可以流几十跳不衰减、延迟不可控、点亮球数爆炸。深度阀是防“单链极深”的兜底。

**理念**：深度阀防延迟、球数阀防内存和结算成本，两个阀都设是因为只设一个挡不住另一种爆炸。强线索唤醒通常 1–2 跳就够（起始球直接命中沉睡大球），5 跳是保守兜底、不是常规限制。

**解释**：`max_flow_depth` 默认 5，单条路径的最大跳数，是流动的两个硬安全阀之一（另一个是 `max_lit_ball_count`）。深度从起始球算起、起始球深度 0、每经过一条管道 +1，达到上限时**该方向停止向下游流动**，已点亮的球照常进入结算、不丢弃。深度按 **BFS 首次到达**算、不是最长路径——同一次激活每球只注一次，首次到达后就标记为已访问，后续再到达不注水，所以深度天然是“最短路径深度”；`depth_count_mode` 保留 `longest_path` 作为逃生舱、但默认且推荐 `bfs_first`，因为 `longest_path` 需要额外记录每条路径的深度、复杂度高且没有明显收益。

**方案**：它和 `max_lit_ball_count` 是“或”的关系：任一触发，触发阀的那个方向停止流动、其他方向继续，直到所有方向都停或都触阀。安全阀触发时记一次 `safety_valve_triggered` 指标、标签区分深度/球数，用于调参；频繁触发说明默认值太小或图太密、该调配置而不是机制有问题。边界情况：起始球深度 0 不触阀；深度恰好等于 `max_flow_depth` 时该方向停止、但不影响该球本身被点亮和结算；多个方向同时触阀时各自停止、互不影响。

**结论**：强线索唤醒通常 1–2 跳就够，5 跳是保守兜底、不是常规限制。这是“深度阀防延迟”的具体落地。

**关联**：安全阀 max_lit_ball_count、安全阀触发后、深度计算。

---

### 安全阀 max_lit_ball_count（原 max_lit_balls）

**起因**：一个球可能有几十条出边，5 跳就可能触及几千个球，自然衰减挡不住分支爆炸——点亮球数爆炸会让延迟不可控、点亮集合过大、结算成本飙升、水量被摊薄到每个球都不够结算。球数阀是防“分支太多”的兜底。

**理念**：约束的是“不同球数”而不是“点亮次数”，因为每球只注一次、点亮集合天然去重，同一个球被多条路径到达只算一个、不重复计数。球数阀通常先触发、深度阀是防单链极深的兜底。

**解释**：`max_lit_ball_count` 默认 50，单次激活最多点亮的**不同球数**。达到上限时**不再点亮新球**，但水流仍可以在已点亮的球之间尝试管道——尝试会消耗损失、但不会产生新点亮，已点亮的球照常进入结算、该强化的照常强化，安全阀只阻止“继续扩散”、不撤销“已经发生的点亮”。

**方案**：它和 `max_flow_depth` 是“或”的关系：任一触发，触发阀的那个方向停止流动、其他方向继续，直到所有方向都停或都触阀。计数时机是球第一次被点亮时 `+1`，后续路径再到达同一球不增加计数；去重键是球 ID、不是路径 ID；结算范围以点亮集合为准、集合大小不超过 `max_lit_ball_count`。安全阀触发时记一次 `safety_valve_triggered` 指标、标签区分球数/深度，用于调参——频繁触发说明默认值太小或图太密、该调配置而不是机制有问题。边界情况：恰好第 50 个球被点亮时触发，该球本身正常点亮、正常结算，只是之后不再点亮新球；已点亮球之间的管道尝试不增加球数、不触阀；多个方向同时触阀时各自停止、互不影响。

**结论**：球数阀通常先触发、深度阀是防单链极深的兜底。这是“球数阀防内存和结算成本”的具体落地。

**关联**：安全阀 max_flow_depth、安全阀触发后、同一次激活每球只注一次。

---

### 安全阀触发后

**起因**：触发安全阀后，整个流动是否立刻停止？如果“整个流动立刻停止”，已点亮球可能没有被充分结算；如果“触发阀的那条路径停止、其余分支不受影响”，流动的完整性得以保留。

**理念**：触发阀的那个**方向**停止流动、其他方向继续，直到所有方向都停或都触阀——不是“整个流动立刻停止”，而是“触发阀的那条路径/那个分支停止、其余分支不受影响”。已点亮的球**照常进入结算、不丢弃**、该强化的照常强化——安全阀只阻止“继续扩散”、不撤销“已经发生的点亮”。

**解释**：`max_flow_depth` 触发时该方向不再向下游流动、但水流仍可在当前球尝试其他未访问出边（如果还有）；`max_lit_ball_count` 触发时不再点亮新球、但水流仍可以在已点亮的球之间尝试管道——尝试会消耗损失、但不会产生新点亮，已点亮球之间的管道尝试仍可能产生结算强化（因为管道被走通了）。触发时记一次 `safety_valve_triggered` 指标、标签区分“深度”和“球数”、用于调参。

**方案**：安全阀触发**不影响结算的正确性**：点亮集合是触发前已经确定的，结算按点亮集合和路径集合正常进行、强化值、注入排序、渲染都不因触发而改变。边界情况：两个阀同时触发时、两个方向各自停止、互不影响；触发后仍有未访问出边但水量已不足以通过时、水自然损失、无需额外处理；触发后已点亮球之间的管道尝试如果全部失败、水耗尽、流动自然结束。

**结论**：偶发触发说明安全阀在正常工作、兜住了极端情况；频繁触发说明该调配置。这是“安全阀只阻止继续扩散、不撤销已发生点亮”的具体落地。

**关联**：安全阀 max_flow_depth、安全阀 max_lit_ball_count、深度计算。

---

### 深度计算

**起因**：深度按什么口径算需要明确。最长路径需要记录每条路径的深度、在球被多路径到达时比较并更新，复杂度高且没有明显收益——深度的唯一用途是触达 `max_flow_depth` 安全阀，而“最短路径深度”已经能回答“这个球离起始球最近有多远”。

**理念**：按 BFS 首次到达算，因为每球只注一次、首次到达后标记为已访问，后续再到达不注水、不释放、只损失，所以每个球的深度天然是“从起始球到它的最短路径深度”。最长路径深度在“每球只注一次”的规则下没有语义——第二次到达不注水，长路径的那次到达不产生任何效果。

**解释**：深度从起始球算起、起始球深度为 0、每经过一条管道 +1；深度按 **BFS 首次到达**计算。`depth_count_mode` 保留 `longest_path` 作为逃生舱、但默认且推荐 `bfs_first`、切换只改配置不改代码。

**方案**：它与“回边排除”和“第二次到达只损失”配套：回边在分配前被排除、不产生“沿来路退回”的深度计算；第二次到达只损失，多路径汇聚时后到者不注水、不更新深度——首次到达者决定该球的深度。边界情况：起始球深度 0、不触任何深度阀；深度恰好等于 `max_flow_depth` 的球被正常点亮、正常结算，只是它的下游不再被流动；多个起始球时每个球从各自的起始球算深度，同一球被不同起始球到达时取首次到达的深度（先到者决定）。

**结论**：深度的唯一用途是触达 `max_flow_depth`，最短路径深度已经够用。这是“BFS 首次到达”在深度计算上的具体落地。

**关联**：安全阀 max_flow_depth、回边排除、第二次到达只损失。

---

### 全失败

**起因**：球有未访问出边、水也分了，但每条都因水量不足过不去——这是动力学死路，与“所有出边已访问”的拓扑死路不同。

**理念**：全失败发生后，该球被“润湿”——不是“什么都没发生”，而是留下两层痕迹：“差点通过”的补偿（`blocked_pass_count` 增加）、“反复被到达”的补偿（`lit_count` 增加）。润湿的语义是“这次没想起来，但留下了痕迹，下次更容易”。

**解释**：水到达一个球、该球**有未访问出边**，但按 `1 + pipe_effective_thickness` 分配后，每条未访问出边先扣损失、再用扣损后水量和阻力比较，**全部不通过**——此时该球的可分配水量全部损失、没有下游被点亮、该球成为本次激活的动力学死路。它和“所有出边已访问”是两种不同的死路：后者是**拓扑死路**（没有未访问出边可分配、分配阶段就为零），前者是**动力学死路**（有未访问出边、水也分了、但每条都因水量不足过不去），两者都让水在该球处耗尽、不回流，但触发原因不同。

**方案**：全失败发生后，该球被“润湿”——每条失败的管道 `blocked_pass_count_stored += 1`、刷新 `last_blocked_at`，下次同类线索到达时有效阻力打折、这是“差点通过”的补偿；该球本身记一次 `lit_count`（它已经被点亮过、只是没能继续传播）、用于舌尖效应的轻量计数。它和“流动只点亮、不写入”不冲突：`blocked_pass_count` 和 `lit_count` 的本次新增只记在内存里、结算时才按“先衰减再叠加”写回，流动阶段仍然纯内存、不落库。全失败的水量损失**不回收给上游**——上游那一步的分配已经完成、不可逆，失败的那份水按“损失不回收”消失，上游球不会因为下游全失败而重新获得水量。边界情况：球只有一条未访问出边且该出边失败时等同于全失败；球有未访问出边但分配后每条分到的水量都为零（极端情况、`1 + pipe_effective_thickness` 保底非零使这几乎不可能）时也按全失败处理；全失败后该球不尝试回边（回边已在分配前排除）、直接结束该方向。

**结论**：“这次没想起来，但留下了痕迹，下次更容易”。这是“润湿”在动力学死路上的具体落地。

**关联**：所有出边已访问、阻塞记忆折扣、lit_count、损失不回收。

## 五、结算决策

### 结算同步立刻执行

**起因**：结算异步会引入“注入基于旧状态、结算基于新状态”的窗口，同一个球在注入时和写入时的 `ball_stored_size` 不一致，虽然差异微小但“只算一次”就破了；而且注入排序需要基于刚强化后的球状态，异步会让排序结果过时。

**理念**：结算 = 注入决策，不可异步。结算不是“事后写库”，是“决定这轮想起什么”，写入和注入是同一个步骤的前后两半、中间没有异步间隙。结算延迟直接叠加到注入延迟上、必须控制在毫秒级，这也是为什么相关性判定只能用嵌入、不能用 LLM——LLM 延迟是百毫秒到秒级、同步结算里放不下。

**解释**：流动结束后**立刻结算**、结算与注入在同一同步步骤内完成、不可异步。流动纯内存计算、只点亮不写入；流动结束后立刻进入结算，计算流动加权语境（α ≤ 0.3）、对每个点亮球算相关性（语义相似度 × 路径折扣、不含水量）、多路径取最大值、划分强化球/最低强化球、计算路径相关性和强化增量、开写事务校验版本号（无冲突直接写、有冲突重读涉及球/管道重算增量）、写入球大小增量、管道粗细增量、`last_watered_at`/`last_flowed_at` 刷新、`blocked_pass_count` 和 `ball_stability` 先衰减再叠加、提交事务、按刚强化后的状态做注入排序、渲染注入块、返回给宿主拼装尾部消息。

**方案**：**失败降级**——结算写入失败或版本冲突重算失败时注入照常进行（用流动阶段已确定的点亮集合和路径），只是本轮强化没写入、下一轮重试；记忆系统可以降级、但不能让主对话卡住。它和“流动只点亮、不写入”是严格配套的两步：流动只回答“哪些球被点亮、沿什么路径”，结算回答“强化多少、注入哪些”，两者职责分离但同步衔接、中间不能插入异步。

**结论**：结算即注入决策、同步衔接、不可拆分。这是“结算同步立刻执行”在职责分离上的具体落地。

**关联**：流动只点亮、不写入、版本冲突重算、注入排序。

---

### 流动加权语境（`flow_context_blend_alpha`，原 α）

**起因**：水流经过中间球后语境会“被带偏”——用户说“上次那个 bug”，水流经过“上次的报错球”后，语境里已经混入了报错的内容，用这个“被染色”的语境去算后续球的相关性，比用原始语境更贴近“顺着联想往下想”的真实过程；但 α 不能高，否则语境会被中间球带跑偏到无关方向、一个语义上只和原始问题相关的球会被错误判为不相关。

**理念**：原始查询嵌入占主导、路径只做轻微染色，`flow_context_blend_alpha ≤ 0.3` 是硬约束、原始查询占至少 70%。**“原始语境”和“原始查询”是同一个东西，统一叫“原始查询嵌入”**——系统里只有这一个“原始”概念，它是触发本次激活的那条输入（用户消息/工具结果/模型的话）经过嵌入模型得到的向量，也是起始球选择时用来和所有球算余弦的那个向量。

**解释**：结算时用于计算相关性的语境嵌入，是 `原始查询嵌入 × (1 - flow_context_blend_alpha) + 流动路径上各球嵌入的加权平均 × flow_context_blend_alpha`，`flow_context_blend_alpha` 默认 0.2、上限 0.3。**流动阶段不用流动加权语境**——水到达一个球时，用原始查询嵌入和球嵌入算相关性、判断是否补充，逐跳不做语境更新；**结算时才做一次性的路径加权**，把整条路径的信息汇总后重新算语境、用于结算的相关性计算（语义相似度 × 路径折扣中的“语义相似度”就是用这个加权语境算出的余弦）。加权平均的权重是各球在路径上获得的水量占比——路径越长、水量越分散、染色越弱，符合“想得越远，越不确定自己在想什么”的直觉。

**方案**：它只影响**结算阶段的相关性计算**，不影响起始球选择（起始球选择用原始查询嵌入）、不影响流动阶段的逐跳相关性判定、不影响注入排序之外的其他计算；它和“相关性定义”配套——相关性 = 语义相似度 × 路径折扣，水量本身仍不进入相关性，流动加权语境是“语境被染色”、不是“水量乘进相关性”，两者是不同的事。边界情况：流动路径为空（只有起始球被点亮、没有传播）时加权平均项为零、退化为原始查询嵌入；`flow_context_blend_alpha = 0` 时完全退化为原始查询嵌入、可作为对照基线；超过 0.3 时配置校验拒绝。

**结论**：语境被染色、但不是被水量乘进相关性——两者是不同的事。这是“顺着联想往下想”在语境计算上的具体落地。

**关联**：相关性定义、补充规则、原始查询嵌入、path_supplement_loss_ratio。

### 相关性定义

**起因**：原定义把水量乘进了相关性（`water × sim × 路径折扣`），混淆了两个正交维度——语义相关性应由嵌入相似度和路径位置决定，水量反映的是路径通畅度、不是语义相关性。一个球语义上很相关但水勉强够到，它的相关性不应因“路难走”被打折；一个球语义一般但水很充足，也不应因“路好走”被抬高。

**理念**：相关性只由语义相似度和路径位置决定，水量和 `pipe_effective_thickness` 都不参与。`pipe_effective_thickness` 同样不进入相关性——它已在流动阶段决定了阻力和损耗，再乘进相关性是同一个信号第二次计权、会形成“粗管 → 更受偏爱 → 更粗”的正反馈，管道健康因子因此被废弃。

**解释**：**相关性 = 语义相似度 × 路径折扣**，**不含水量、不含 `pipe_effective_thickness`**。语义相似度是“当前语境嵌入与该球嵌入的余弦”——结算时用流动加权语境（原始查询嵌入 × (1 - α) + 路径上各球嵌入的加权平均 × α，α ≤ 0.3、默认 0.2），流动逐跳时用原始查询嵌入；路径折扣是 `max(min_discount, 1 - discount_per_hop × 跳数)`，默认每跳 0.1、最低 0.5、触底不再降。

**方案**：相关性和“资格与幅度分离”配套——**资格看 `semantic_similarity`**（判断是否值得强化，与路径折扣无关），**幅度和排序用 `semantic_similarity × 路径折扣`**（判断强化多少、排序多靠前）；资格不该被路径长度惩罚，深度 5、`semantic_similarity = 0.95` 的球语义上完全匹配、应该被强化，幅度是 `0.95 × 0.5 = 0.475`、被强化但幅度较小、而不是被否定。相关性不进入流动阶段的通过判断（通过条件只看水量 > 阻力），只进入结算的强化幅度；注入排序用 `semantic_similarity`（资格口径、不含路径折扣）、不乘 `ball_effective_size`——`ball_effective_size` 是相关性的历史累积结果、不是独立信号，在排序里再乘一次是重复计权。边界情况：路径折扣触底后不再随深度下降；多路径取最大值时同一球取最大路径相关性强化一次、不累加；`semantic_similarity ≥ 0.7` 为强化球，0.3–0.7 为印象球（拿最低强化值但注入），< 0.3 为最低强化球（拿最低强化值且不注入）；流动路径为空时流动加权语境退化为原始查询嵌入。

**结论**：相关性不含水量、不含 `pipe_effective_thickness`，语义相关和路径通畅是两个正交维度。这是“每种信号只负责一件事”在相关性定义上的具体落地。

**关联**：路径折扣、资格与幅度分离、注入排序、流动加权语境。

---

### 路径折扣（`discount_per_hop`、`min_discount`）

**起因**：结算时按路径长度打折强化值，防止“一条长路径上的所有球都被大幅强化”导致远处球被误强化——路径越长，终点球即使语义相关，也因为“绕了远路”而获得较少强化，这是“想得越远越不确定”在强化幅度上的体现。

**理念**：用跳数作为“这次激活有多强”的**粗糙代理**——确定、可复现、不依赖水量，但不如直接用水量精确。强线索可能在 5 跳后水量仍充足、弱线索可能在 2 跳后就衰减殆尽，跳数和水量的关系不是线性的、这是它作为代理的已知不精确之处，当前设计接受这个取舍。

**解释**：路径折扣是相关性的第二个因子，公式 `max(min_discount, 1 - discount_per_hop × 跳数)`，默认每跳 0.1、最低 0.5——跳数 0（起始球本身）折扣 1.0、跳数 3 折扣 0.7、跳数 5 折扣 0.5，触底后不再随深度下降（深度 10 也是 0.5）。跳数按 BFS 首次到达深度算、不是最长路径——同一次激活每球只注一次，首次到达后标记为已访问、后续再到达不注水，所以深度天然是“最短路径深度”。

**方案**：**管道健康因子已废弃**、不再作为路径折扣的因子——`pipe_effective_thickness` 已在流动阶段决定阻力和损耗，再乘进相关性是二次计权、会形成“粗管 → 更受偏爱 → 更粗”的正反馈，细管和孤岛永远等不到水流；这和“水量乘进相关性”“`ball_stored_size` 塞进衰减函数”是同一类错误、一个量在它不该出现的地方被当成了另一个量的乘数。路径折扣和“资格与幅度分离”配套——资格看 `semantic_similarity`（判断是否值得强化、与路径折扣无关），幅度和排序用 `semantic_similarity × 路径折扣`（判断强化多少、排序多靠前）；资格不该被路径长度惩罚，深度 5、`semantic_similarity = 0.95` 的球应该被强化、幅度是 `0.95 × 0.5 = 0.475`、被强化但幅度较小、而不是被否定。旧公式下路径折扣作用在 `semantic_similarity × 折扣` 上时存在**死区**：`strengthen_eligibility_threshold = 0.6`、深度 3 折扣 0.7 需要 `semantic_similarity = 1.0` 才能过线、深度 4 折扣 0.6 需要 `semantic_similarity = 1.17`、深度 5 折扣 0.5 需要 `semantic_similarity = 1.4`——不可能，`max_flow_depth` 默认就是 5，第 4、5 跳的球永远无法成为强化球；旧公式乘 `water` 时被掩盖（强线索 `water = 3` 能把 0.5 抬到 1.5）、移除 `water` 后暴露、方案 A 修复。多路径取最大值时同一球取最大路径相关性强化一次、不累加；`discount_per_hop` 和 `min_discount` 全部进配置可调，`min_discount` 触底后不再降是显式确认的行为、实现时不能把 `max` 写成 `min` 或漏掉触底逻辑。

**结论**：跳数代理水量的粗糙之处是已知不精确——强线索下“远 = 弱”的假设不成立，但当前设计接受这个取舍。这是“路径折扣用跳数代理激活强度”的具体落地。

**关联**：折扣触底、资格与幅度分离、相关性定义、死区问题。

---

### 折扣触底（`min_discount`）

**起因**：没有下限，无限长路径的折扣会趋近于零、强化幅度也趋近于零，等于“路径越长越不可能被强化”，这会让多跳联想在强化层面被系统性扼杀。

**理念**：远处球至少能拿到 `min_discount` 比例的强化、虽然少但不会归零，“想得越远越不确定”有下限、不是“想得越远越等于没想”。触底**不是死区问题的原因**，死区是“资格判断作用在含折扣的值上”导致的——`strengthen_eligibility_threshold` 如果判断 `semantic_similarity × 折扣`，深度 4 需要 `semantic_similarity = 1.0`、深度 5 需要 `semantic_similarity = 1.2` 才能过线、这是资格被折扣惩罚；触底只是让折扣停在一个非零下限、不改变“资格该不该看折扣”这个问题。

**解释**：路径折扣降到 `min_discount`（默认 0.5）后**不再随深度继续下降**——深度 5 折扣 0.5、深度 10 还是 0.5、深度 100 也是 0.5。公式 `max(min_discount, 1 - discount_per_hop × 跳数)` 里的 `max` 就是触底逻辑：当 `1 - discount_per_hop × 跳数` 低于 `min_discount` 时取 `min_discount`、不再继续降。

**方案**：方案 A 修复死区的方式是**资格看 `semantic_similarity`（不含折扣）**，触底仍然保留在幅度计算里——资格不被折扣惩罚、幅度仍随深度递减到下限，两者分工明确。触底后深度 5 和深度 10 的球拿同样的幅度、这是可接受的——它们都是“很远的球”，再区分 5 跳和 10 跳的差异没有语义价值、反而增加不必要的复杂度。实现时有一个容易犯的错误：把 `max` 写成 `min`、或者漏掉触底逻辑直接让折扣线性递减到零甚至负数；测试要显式覆盖“深度 5 折扣 0.5、深度 10 折扣仍是 0.5、深度 100 折扣仍是 0.5”，以及“`min_discount` 配置为 0.3 时触底值相应变化”。`min_discount` 进配置可调、但配置校验要拒绝 `min_discount > 1.0`（触底值不能比不折扣还高）和 `min_discount < 0`（不能为负）；`discount_per_hop` 也要拒绝负数。触底和“多路径取最大值”独立——触底决定单条路径的折扣下限，多路径取最大值决定同一球在多条路径上取哪条的值，两者不冲突。

**结论**：触底不是死区问题的原因，死区是“资格判断作用在含折扣的值上”导致的。这是“折扣触底”与“死区问题”分工的具体落地。

**关联**：路径折扣、死区问题、资格与幅度分离。

---

### 资格与幅度分离（方案 A）

**起因**：旧设计里 `strengthen_eligibility_threshold` 作用在 `semantic_similarity × 折扣` 上，深度 3 折扣 0.7 需要 `semantic_similarity = 1.0` 才能过线、深度 4 折扣 0.6 需要 `semantic_similarity = 1.17`、深度 5 折扣 0.5 需要 `semantic_similarity = 1.4`——不可能，`max_flow_depth` 默认就是 5，第 4、5 跳的球即使内容完全匹配也永远无法成为强化球、只能拿 `min_strengthen_value`；旧公式乘 `water` 时被掩盖（强线索 `water = 3` 能把 0.5 抬到 1.5）、移除 `water` 后暴露。

**理念**：每种信号只负责一件事——**资格**回答“这个球语义上够不够相关、值不值得强化”，不该被路径长度惩罚；**幅度**回答“强化多少、排序多靠前”，路径长度应该在这里起作用——远处球被强化得少、但不会被否定。深度 5、`semantic_similarity = 0.95` 的球语义上完全匹配，它“值得强化”这个判断不应该因为它离起始球远而被否定。

**解释**：**资格看 `semantic_similarity`**（纯语义相似度、不含路径折扣、不含水量、不含 `pipe_effective_thickness`），**幅度和排序用 `semantic_similarity × 路径折扣`**。具体规则：按语义相似度分三档——`semantic_similarity ≥ strengthen_eligibility_threshold`（默认 0.7）→ **强化球**，按 `路径相关性 = semantic_similarity × 路径折扣` 计算幅度；`impression_threshold ≤ semantic_similarity < strengthen_eligibility_threshold`（默认 0.3–0.7）→ **印象球**，拿统一最低强化值、但参与注入；`semantic_similarity < impression_threshold` → **最低强化球**，拿最低强化值、且不注入。注入排序用 `semantic_similarity × 折扣`（幅度口径）、不是 `semantic_similarity`（资格口径）——排序要考虑“多相关”和“离起始球多远”，远处高相关球排序靠后是合理的、但这不影响它被强化。

**方案**：连带影响——`strengthen_eligibility_threshold` 的语义从“路径相关性阈值”改为“语义相似度阈值”、所有文档表述和测试注释同步改；死区消失，深度 5、`semantic_similarity = 0.95` 的球幅度是 `0.95 × 0.5 = 0.475`、被强化但幅度较小、而不是拿最低值；现有手算测试中深度 0 的数值不变（折扣 1.0），涉及阈值的测试要改判断对象。边界情况：`semantic_similarity` 恰好等于 `strengthen_eligibility_threshold` 时按“严格大于”判断、等于不算通过；`semantic_similarity` 过阈值但路径相关性极低（深度触底、`semantic_similarity` 刚过线）时幅度很小但仍按幅度强化、不退回最低值——最低值只给资格未通过的球。

**结论**：远处球被强化得少、但不会被否定。这是“每种信号只负责一件事”在资格与幅度上的具体落地。

**关联**：strengthen_eligibility_threshold 语义、死区问题、强化球/最低强化球、注入排序。

### strengthen_eligibility_threshold 语义（原 strengthen_threshold_X）

**起因**：阈值判断的对象从 `semantic_similarity × 折扣` 改为 `semantic_similarity`。原语义是“路径相关性阈值”，判断的是 `semantic_similarity × 折扣`、导致死区问题。

**理念**：它回答“这个球语义上够不够相关、值不值得强化”，不是“路径相关性多高才值得强化”。语义修正的理由是“每种信号只负责一件事”——资格回答“值不值得强化”、不该被路径长度惩罚；幅度和排序才用 `semantic_similarity × 折扣`、路径长度在那里起作用。

**解释**：`strengthen_eligibility_threshold`（默认 0.7）是**语义相似度阈值**、判断的是 `semantic_similarity`——纯语义相似度、不含路径折扣、不含水量、不含 `pipe_effective_thickness`。判断规则是大于等于——`semantic_similarity ≥ strengthen_eligibility_threshold` 归入强化球、按 `路径相关性 = semantic_similarity × 路径折扣` 计算幅度；介于 `impression_threshold`（默认 0.3）与它之间的归入印象球、拿统一最低强化值（`base_reinforcement × min_strengthen_value`，默认 0.005）但参与注入；低于 `impression_threshold` 的归入最低强化球、拿最低强化值且不注入。

**方案**：它和 `supplement_threshold`（补充资格阈值、默认 0.4–0.5）是两个不同的阈值：前者管“是否值得强化”、作用在结算阶段；后者管“是否释放补充”、作用在流动阶段；两者独立配置、不要求相等，但都遵循“资格严格、幅度宽容”的分工。连带影响——所有涉及 `strengthen_eligibility_threshold` 的文档表述和测试注释要同步改为“语义相似度阈值”，测试判断对象从 `semantic_similarity × 折扣` 改为 `semantic_similarity`；现有手算测试中深度 0 的数值不变（折扣 1.0），涉及阈值的测试要改判断对象。边界情况：`semantic_similarity` 恰好等于阈值时按大于等于判断、归入强化球；`semantic_similarity` 过阈值但路径相关性极低（深度触底、`semantic_similarity` 刚过线）时仍按幅度强化、不退回最低值——最低值只给印象球与最低强化球；阈值配置校验拒绝 `> 1.0` 或 `< 0`。

**结论**：所有涉及它的文档表述和测试注释同步改为“语义相似度阈值”。这是“资格与幅度分离”在参数语义上的具体落地。

**关联**：资格与幅度分离、supplement_threshold、死区问题。

### 死区问题

**起因**：旧公式下 `strengthen_eligibility_threshold`（默认 0.7）作用在 `semantic_similarity × 折扣` 上时，深度 3 折扣 0.7 需要 `semantic_similarity = 1.0` 才能过线、深度 4 折扣 0.6 需要 `semantic_similarity = 1.17`、深度 5 折扣 0.5 需要 `semantic_similarity = 1.4`——而余弦相似度上限是 1.0、后者**在数学上不可能**。`max_flow_depth` 默认就是 5，这意味着第 4 跳的球只有语义完全匹配（`semantic_similarity = 1.0`）才能成为强化球，第 5 跳的球**永远无法成为强化球**、即使内容完全匹配也只能拿 `min_strengthen_value`（默认 0.05）。

**理念**：死区的本质是**资格判断被路径长度惩罚**——一个球“值不值得强化”应该由它的语义相关性决定、不应该因为它离起始球远而被否定；旧设计把资格和幅度混在同一个量 `semantic_similarity × 折扣` 上，路径折扣本来只该影响“强化多少”、却越权影响了“是否强化”。

**解释**：旧公式乘 `water` 时被掩盖——强线索 `water = 3` 能把 `0.5` 的路径相关性抬到 `1.5`、越过 0.6 的阈值，看起来“远处球也能被强化”；移除 `water` 后，路径相关性回到 `semantic_similarity × 折扣` 的纯语义量纲、死区立刻暴露。

**方案**：修复方案是**资格与幅度分离（方案 A）**——`strengthen_eligibility_threshold` 改为判断 `semantic_similarity`（不含折扣）、资格不再被路径长度惩罚；幅度和排序仍用 `semantic_similarity × 折扣`、远处球被强化得少但不会被否定。修复后深度 5、`semantic_similarity = 0.95` 的球资格通过、幅度是 `0.95 × 0.5 = 0.475`、被强化但幅度较小、而不是拿最低值。连带影响——`strengthen_eligibility_threshold` 的语义从“路径相关性阈值”改为“语义相似度阈值”、所有文档表述和测试注释同步改；现有手算测试中深度 0 的数值不变（折扣 1.0），涉及阈值的测试要改判断对象。边界情况：`semantic_similarity` 恰好等于阈值时按严格大于判断、不算通过；资格通过但幅度极低的球仍按幅度强化、不退回最低值——最低值只给资格未通过的球。

**结论**：当前系统只有方案 A 一套公式，旧公式已废弃、不参与任何运行时计算。这是“资格判断被路径长度惩罚”的具体反例。

**关联**：资格与幅度分离、strengthen_eligibility_threshold 语义、路径折扣。

### 多路径取最大值

**起因**：同一球或管道被多条弱路径经过，累加会让它被“刷”成过强——如果累加，一条被三条 0.3 相关性路径经过的管道会得到 `0.3 + 0.3 + 0.3 = 0.9` 的强化、比一条被单条 0.8 相关性路径经过的管道还强，这违背“强相关路径应该主导强化”的直觉，也会让被多条弱路径反复经过的管道突然变得极粗、流动时形成正反馈、越来越倾向于走这条管道、导致联想僵化。

**理念**：强度取最强、不叠加——与“管道合并取最大值”是同一类守恒逻辑，两者都遵循“强度取最强、不叠加”的守恒逻辑。它和“路径级强化”是配套的——路径级强化让“一起被想起的东西一起变强”，多路径取最大值防止“被反复想起但每次都不够强”的东西被过度强化。

**解释**：同一结算中，一个球或一条管道出现在多条路径上时，**取最大路径相关性强化一次、不累加**。取最大值后，同一结算中每条路径的贡献独立、不叠加，最强的路径决定强化幅度、弱路径不因为“数量多”而补偿。

**方案**：球和管道都遵守这条规则；最低强化球不走这条规则（它不按路径相关性算幅度、只强化一次）；不改变单条路径内的 `semantic_similarity × 折扣` 计算。边界情况：同一球出现在两条路径上、相关性分别是 0.8 和 0.3，只按 0.8 算强化值、不按 1.1 算；同一管道出现在三条路径上、取最大不累加；同一球和同一管道同时出现在多路径上、两者各自独立取最大、互不影响；两条路径相关性相同时取哪条都一样、只强化一次。

**结论**：最强路径决定强化幅度、弱路径不因“数量多”而补偿。这是“强度取最强、不叠加”在多路径强化上的具体落地。

**关联**：结算变粗、强化球/最低强化球、合并。

### 强化球 / 印象球 / 最低强化球（`strengthen_eligibility_threshold`、`impression_threshold`、`min_strengthen_value`）

**起因**：资格未通过的球是否完全不该强化？如果完全不强化，就失去了“多次弱相关点亮累积起来也能变强”的可能——最低强化值远小于正常强化值、保留一条极慢的累积路径，又不会让无关球被过度强化。

**理念**：资格未通过不代表“完全不该强化”。最低强化值给资格未通过的球、保留极慢的累积路径；资格通过但幅度极低的球仍按幅度强化、不退回最低值——最低值只给资格未通过的球，否则“过阈值”就没有意义。

**解释**：结算时，每个被点亮的球按 `semantic_similarity` 分三档：**强化球**（`semantic_similarity ≥ strengthen_eligibility_threshold`，默认 0.7）、按 `路径相关性 = semantic_similarity × 路径折扣` 计算幅度、乘 `size_strengthen_factor` 后经边际递减写入 `ball_stored_size`、并参与注入；**印象球**（`impression_threshold ≤ semantic_similarity < strengthen_eligibility_threshold`，默认 0.3–0.7）、不参与路径相关性计算、直接拿统一最低强化值（`base_reinforcement × min_strengthen_value`，默认 `0.1 × 0.05 = 0.005`）、但**参与注入**；**最低强化球**（`semantic_similarity < impression_threshold`）、同样拿最低强化值、但**不注入**。三者都受 `ball_size_ceiling` 饱和约束。

**方案**：关键边界——强化球但幅度极低的仍按幅度强化、不退回最低值，最低值只给印象球与最低强化球、否则“过阈值”就没有意义；`semantic_similarity` 恰好等于 0.7 时归入强化球（≥）、恰好等于 0.3 时归入印象球（≥）；印象球与最低强化球多路径命中时也只给一次最低值、不累加、不取最大（因为它们不按路径相关性算幅度、多路径规则对它们无意义）；最低强化值用**相对量**（`base_reinforcement × min_strengthen_value`）而不是绝对量——绝对量会与强化幅度量级倒挂（达标球最差情况 `0.1 × 0.6 × 0.5 = 0.03`，反而小于绝对最低值 0.05），相对量保证“最低强化值 < 任何达标球的强化值”恒成立。它和“资格与幅度分离”配套——强化球是“资格通过 + 按幅度强化”，最低强化球是“资格未通过 + 按固定最低值强化”；它和“多路径取最大值”的关系是——强化球走多路径取最大值，最低强化球不走这条规则、只强化一次。

**结论**：最低强化值远小于正常强化值、保留极慢的累积路径。这是“资格未通过不代表完全不该强化”的具体落地。

**关联**：资格与幅度分离、多路径取最大、ball_size_ceiling。

### 注入排序（`sort_exponent_a`、`sort_exponent_b`）

**起因**：结算后、注入前需要决定装哪几个球。原文档默认 `b = 1`（相关性和巩固度平权），但论证不充分——`ball_effective_size` 是“相关性 → 强化 → `ball_stored_size` 增长”这条链的历史累积结果、是相关性的滞后代理，不是独立信号；决策时已经能算当前相关性，再乘一次历史累积值就是把同一个信号算两遍，和“新鲜度被乘三次”“水量乘进相关性”是同一类错误。类比图书馆推荐位：读者要找什么取决于他此刻的检索词，不取决于这本书在馆藏里有多厚。

**理念**：水量和球大小都不出现在排序公式里——它们已通过“谁被点亮、谁被强化得多”间接影响结果。排序只回答“这条记忆和用户当前说的话有多像”，历史强度不应该 1:1 补偿当前相关性。`sort_exponent_b = 0` 是正确默认行为，`b > 0` 保留为对照实验的可选配置、如果数据显示“巩固度确实该参与排序”再调默认值、但那时要有数据支撑。

**解释**：结算后、注入前，对**强化球**按 `semantic_similarity` 降序排序、取 Top-K 装预算。**排序量是 `semantic_similarity`（资格口径），不是 `semantic_similarity × 路径折扣`**——注入要回答的是“这条记忆和用户当前说的话有多像”，路径走了多远不影响这条记忆的回答价值；折扣已经在强化幅度里起作用（远处球被强化得少），不该在注入排序里第二次惩罚它。**不乘 `ball_effective_size`**——它是相关性的历史累积结果，不是独立信号。保留 `sort_exponent_a`（默认 1.0）作为可调指数；`sort_exponent_b` 默认 0、仅保留为对照实验入口，不作为推荐配置。

**方案**：同等语义相关性不区分水量强弱——两个球相关性相同、一个被强水量点亮、一个被弱水量勉强点亮，排序不区分，语义相关性相同意味着回答价值相同、水量差异反映的是路径通畅度、不是回答价值；如果未来数据显示“同等相关性下强激活的球确实更该被注入”，应作为显式的第三因子（激活强度）加入排序、可配置、默认关闭、有对照实验支撑，而不是藏在相关性定义里的隐式乘数。排序结果配合“注入预算两种模式”和“不切割完整球”使用——排序决定候选顺序、预算决定装几个完整球。

**结论**：当前相关性主导注入排序、历史强度不 1:1 补偿当前相关性。这是“`size` 退出所有‘谁更重要’的决策”的具体落地——`size` 只保留两个物理角色：补充释放的活性（含时间衰减）、渲染长度的估算（不衰减）。

**关联**：同等语义相关性不区分水量强弱、注入预算两种模式、不切割完整球。

### 同等语义相关性不区分水量强弱

**起因**：两个球相关性相同、一个被强水量点亮、一个被弱水量勉强点亮，排序是否区分？语义相关性相同意味着对当前问题的回答价值相同、水量差异反映的是路径通畅度（水从粗管顺畅流来还是从细管勉强挤过来）、不是回答价值；把水量作为隐式区分因子、等于让“路好走”冒充“更相关”、混淆了两个正交维度。

**理念**：排序不区分、排序分相同，按预算装谁都可以。如果未来要区分，应该作为一个显式的、有名字的第三因子（如“激活强度” `activation_strength = 到达该球时的水量 / 起始水量`）加入排序、公式形如 `semantic_similarity × 激活强度^c`、`c` 默认 0（关闭）、可配置、有对照实验支撑——而不是藏在相关性定义里的隐式乘数、也不是在排序后偷偷按水量二次排序。

**解释**：排序公式只用 `semantic_similarity`、不含水量、不含 `ball_effective_size`，同等相关性下排序分相同。

**方案**：这样做的好处是——区分是显式的、可审计的、可关闭的；如果数据显示“同等相关性下强激活的球确实更该被注入”，打开 `c` 即可、不需要改相关性定义；如果数据显示不必要、`c = 0` 保持当前行为。边界情况：同等相关性、不同水量、同预算下两个球只能装一个时，按排序分相同、取任意一个、结果可复现（按球 ID 排序兜底）；如果开了激活强度因子、强激活的球优先，但这是显式配置的结果、不是默认行为。

**结论**：区分是显式的、可审计的、可关闭的。这是“水量不冒充相关性”的具体落地。

**关联**：注入排序、相关性定义、激活强度。

### 注入预算两种模式（`injection_mode`、`token_budget`、`tokens_per_size`、`max_balls_per_inject`、`token_hard_cap`）

**起因**：注入需要预算约束，但“token 预算”和“球数预算”对应不同偏好——token 是外部约束单位、球数是行为稳定性单位，两种模式对应不同场景。为什么用 token 作为预算单位——模型上下文窗口、API 成本、推理延迟全部按 token 计，水量是内部调度单位、token 是外部约束单位，语义相关性决定优先级、token 决定截断点、两者解耦；用球数作预算单位是因为某些场景希望“每次注入固定条数、行为稳定”。

**理念**：模式 A 适合成本敏感、上下文窗口紧张的场景，模式 B 适合行为一致性优先、球内容长度相对均匀的场景；`injection_mode` 配置切换、默认 `token`。

**解释**：注入预算有两种可配置模式，统一遵守“不切割完整球”的底线。**模式 A：token 映射**——按注入排序逐个加入完整球，对每个球估算 token（`estimated_tokens_i = ball_stored_size_i × tokens_per_size`，默认 20）——**用 `ball_stored_size` 而不是 `ball_effective_size`**，因为估算的是“这条记忆渲染出来占多少 token”，内容长度不会因为放久了变短；用衰减后的值估算会导致预算必然超支（衰减到 0.1 的球估 2 token、实际渲染仍要 20 token），累加估算值直到 `estimate_sum + estimate_{i+1} > token_budget`（默认 500）时停止、得到候选球数 K；渲染前 K 个完整球，用真实 tokenizer 对渲染结果计数——若 `real_sum > token_budget` 则从 K 开始逐个减球直到不超，若 `real_sum < token_budget` 则尝试加入第 K+1 个球直到下一个会超；估算系数 `tokens_per_size` 是保守值、宁可估高不估低，最终截断由真实 tokenizer 兜底。**模式 B：球数映射**——配置固定球数上限 `max_balls_per_inject`（默认 5），直接取排序前 K_max 个完整球，渲染后用真实 tokenizer 校验，若超过 `token_hard_cap`（默认 800）则减球直到不超，token 只作硬上限兜底、不参与主排序。**统一停止规则**：从排序后的候选球开始逐个加入完整球，加入下一个完整球后会超预算（模式 A）或超球数（模式 B）时停止、返回已加入的完整球——不切割、不截断、不部分渲染，一个球内容 800 token、预算只剩 500 token 时整个球不注入、而不是注入前 500 token。

**方案**：`allow_partial_ball` 保留为配置项、但默认且推荐永远为 false，只在极端场景（单个球内容远超预算且必须注入）才考虑、属于逃生舱不是常规路径。

**结论**：模式 A 适合成本敏感场景、模式 B 适合行为一致性优先场景。这是“token 是外部约束单位”在预算模式上的具体落地。

**关联**：不切割完整球、注入排序、`tokens_per_size`。

### 不切割完整球（`allow_partial_ball`）

**起因**：注入时一个球内容超预算，是截断还是跳过？半个球意味着模型看到的是“半句话的记忆”，它可能误解语义、可能基于残缺内容做出错误判断，而且这种误解无法被审计——模型不知道这条记忆被截断了，它以为自己看到的就是全部。

**理念**：模型看到的每条记忆都必须是完整的。`allow_partial_ball` 默认且推荐永远为 false，只在极端场景（单个球内容远超预算且必须注入）才考虑、属于逃生舱不是常规路径；即使打开，也要在注入块里显式标注“这条记忆被截断”、让模型知道它看到的不完整。

**解释**：注入时，一个球的内容**要么完整注入、要么完全不注入**，永不注入半个球——一个球内容 800 token、预算只剩 500 token 时，这个球整个不注入、而不是注入前 500 token、丢掉后 300 token。

**方案**：它和“注入预算两种模式”配套——模式 A 的“估算粗筛 + 真实 tokenizer 整球增减”、模式 B 的“取前 K 个完整球 + token 硬上限兜底”，统一停止规则都是“下一个完整球会超预算时停止、返回已累加的完整球”，不切割是两种模式共同的底线。它和“冷热分层”配套——内容列表超出上限时淘汰最不常用的内容转冷存储，是“球内的内容条目级淘汰”、不是“单条内容被截断”；单条内容长度上限（默认 4000 字符）超出时截断为“前 N 字符 + 摘要”、原文转冷存储，这是**写入时**的处理、不是注入时的切割；注入时球的内容列表已经是“可渲染的完整内容”、不再切割。边界情况：预算只够装 0 个完整球时返回空注入块、不注入任何记忆——这是正常状态、不是故障；排序第一的球就超预算时整个跳过它、尝试下一个能装下的球、而不是截断它；所有球都超预算时返回空注入块。

**结论**：不切割是两种预算模式共同的底线。这是“记忆完整性”在注入规则上的具体落地。

**关联**：注入预算两种模式、冷热分层、渲染档位。

---

### 渲染档位（清晰档 + 印象档三档措辞）

**起因**：所有注入都用同一种确定性语气，模型无法区分“高置信召回”和“低置信召回”、会把模糊记忆当事实用、产生“过度自信”的幻觉。渲染分档把“系统对这条记忆有多确定”显式传递给模型、让模型自己决定怎么用；同时，相似度太低的球根本不注入——它们只贡献噪声。

**理念**：清晰档对应“内容明确、可放心引用”，印象档对应“大致方向对、但细节可能不精确”；四档对应不同的置信度、不是“装饰性文案”、是**给模型的可靠性信号**。它和“元记忆”是同一件事的工程落地——系统知道自己“记得清”还是“只记得大概”。而低于注入下限的球不进入注入块——`docs/01` 曾有的“模糊档（我好像有关于X的印象）”已废弃，因为“想不起来具体内容”对回答没有价值，只增加噪声。

**解释**：注入块按 `semantic_similarity` 分四档渲染：**清晰档**（`semantic_similarity ≥ 0.7`）→ `[记忆] 关于"X"，我记得：Y`；**印象档·深**（`0.6 ≤ semantic_similarity < 0.7`）→ `我对"X"有比较深的印象……`；**印象档·中**（`0.5 ≤ semantic_similarity < 0.6`）→ `我对"X"有印象……`；**印象档·浅**（`0.3 ≤ semantic_similarity < 0.5`）→ `我对"X"有模糊的印象……`。`semantic_similarity < impression_threshold`（默认 0.3）的球属于最低强化球、**不注入**——因为“想不起具体内容”对回答没有价值、只增加噪声。四个分界值全部进配置（`render_clear_threshold` 0.7、`render_deep_impression_threshold` 0.6、`render_impression_threshold` 0.5、`impression_threshold` 0.3），可独立调。

**方案**：渲染发生在**尾部注入组装阶段**、不触碰前缀缓存；每一级的文本模板可配置、但语义分工不变。边界情况：清晰档的球内容必须完整（受“不切割完整球”约束）；印象档可以是完整内容但相关性中等、也可以是高相关但内容列表里只有摘要；同一轮注入可以同时出现四档、按各自相关性分别渲染。它和“注入排序”独立——排序决定“装哪几个球”，渲染决定“每个球用什么语气写出来”，排序靠前的球不一定都是清晰档、排序靠后的球也不一定都是印象档、两者按各自维度独立判断。

**结论**：四档渲染是“元记忆”的工程落地——系统知道自己记得清还是只记得大概；低于 0.3 的记忆直接不注入，不贡献噪声。这是“把系统对记忆有多确定显式传递给模型”的具体落地。

**关联**：不切割完整球、注入排序、强化球/印象球/最低强化球、元记忆、可观测性。

### 版本冲突重算（`conflict_strategy`、`graph_version`）

**起因**：结算的强化增量基于流动时读到的球大小、管道粗细、`ball_stability`、`blocked_pass_count` 等状态算出，如果这些状态在流动期间被改过，直接用旧增量写入会基于过时数据——比如球已经被另一个进程强化过，再按旧 `ball_stored_size` 算边际递减会算错。

**理念**：重算**不是重复计权**——旧的那次计算结果因版本冲突已经作废、从未写入，重算是基于新状态的一次全新计算、和“新鲜度被乘三次”“水量乘进相关性”是不同性质的问题，后者是在同一份数据上重复乘同一个因子、前者是旧结果失效后重新算一次。

**解释**：结算写入前校验**全局版本号** `graph_version`——流动开始时读快照记录 `graph_version_start`，结算开写事务时读当前版本 `graph_version_now`；`graph_version_now == graph_version_start` 说明流动之后图没被其他进程改过、直接按流动结果写入增量；`graph_version_now != graph_version_start` 说明流动期间有其他进程（dsh/pi 同时结算、或离线巩固并发写入）改过图，**旧的计算结果作废**、重读本次结算涉及的球和管道、用最新状态重算路径相关性和强化增量再写入。

**方案**：**版本号存 DB，且必须与子图加载在同一个读事务里读**——`BEGIN DEFERRED → 读子图 → 读 graph_version → COMMIT`，三者同一个快照，否则可能读到“子图是旧版本、版本号是新版本”；重算范围限于本次结算涉及的球和管道、最多 `max_lit_ball_count`（默认 50）个球 + 对应管道、毫秒级；单用户场景下冲突概率极低（两个客户端同时结算的概率很小），重算不是常态、是兜底。**冲突策略可配**——`conflict_strategy = "recompute"`（默认，重算增量后写入）或 `"abort"`（放弃本次强化，注入照常进行、下一轮重试）；`abort` 是逃生舱、如果重算逻辑出问题可以切到“冲突即放弃”、保证不写错数据、代价是丢失本次强化。**注入不依赖结算成败**——重算失败或选择 `abort` 时注入仍照常进行（用流动阶段已确定的点亮集合和路径），只是本轮强化没写入、下一轮重试；记忆系统可以降级、但不能让主对话卡住。它和“快照隔离”配套——流动开短读事务加载子图、记录 `graph_version_start`、立刻结束读事务，流动在内存子图上纯计算；结算写事务校验版本号、版本一致直接写、不一致重算。它和“非原子结算”的关系——原子模式下冲突重算后在同一事务内写入、要么全成功要么全回滚；非原子模式下重算后逐条写入、失败项进 `pending_retry`、下一轮或启动时重试。边界情况：多个进程同时结算时，后到的进程检测到版本冲突、重算、写入，两次结算的强化都保留、不丢更新；冲突重算时如果涉及的球已被归档、按归档球处理、不强行加载；版本号递增在结算事务提交时完成、与写入同一事务，不会出现“版本号加了但写入没成功”的情况。

**结论**：版本号与子图同读事务，保证快照隔离真正落地；冲突重算保证增量总是基于最新状态。这是“写入不基于过时数据”的具体落地。

**关联**：快照隔离、并发、流动只点亮、结算同步立刻执行。

## 六、存储与持久化

### 存储内核（TriviumDB）

**起因**：需要一个原生承接向量、图、文档三件事的嵌入式存储。如果选 SQLite，需要缝合向量库、图查询、文档存储，多库拼接带来数据同步和延迟问题。

**理念**：避免多库拼接、单文件、拷贝即备份。TriviumDB 的定位是“AI 应用领域的 SQLite”：服务单机环境下的 Agent 复杂上下文和多模态记忆编织，而非分布式高并发后端。

**解释**：选用 **TriviumDB**——一个用纯 Rust 编写的嵌入式三模数据库引擎，将向量检索（Vector）、属性图谱（Graph）和文档型元数据（Document）原生融合在同一个存储内核里。它原生承接了系统最吃重的三件事——向量检索（QuIVer ANN，高维 768/1024/1536 维上同召回吞吐约为 HNSW 类的 1.4–5.0×）、图遍历（TQL MATCH，类 Cypher 模式匹配，支持多跳遍历和可变长路径）、文档查询（TQL FIND，类 MongoDB 过滤语法，10 万节点内单查询亚毫秒）。存储形态上，Rom 模式保持单个 `*.tdb` 文件的便携性、拷贝即完整备份；默认 Mmap 模式将向量和已发布 Payload 分离到 sidecar 文件、按需映射。持久化与并发方面，TriviumDB 提供 WAL 日志 + 原子替换 + 事务干跑验证（Dry-Run）+ Mmap COW 隔离四层保障，`.flush_ok v3` 绑定主文件和 sidecar、发布前旧代备份与撤销日志支持中断恢复；共享只读打开支持多进程 Reader 并发查询已完成代际、Writer 保持排他锁与 WAL 安全边界。

**方案**：0.9.0 是正式版（2026-10-30 发布），汇总了 beta.1–beta.4 的嵌入式资源管理、事务与恢复、类型化存储、统一查询及跨语言契约；Rust crate、Python、Node 均有正式版分发，Server 和 WebUI 仍处于 nightly 预览、不建议生产依赖。**需要接受的代价**——TriviumDB 生态早期、版本节奏快（从 0.4.x 到 0.9.0 约五个月），长期维护风险、API 稳定性、社区支持规模都无法与 SQLite 相比；因此 `dayu-core` 通过 `StorageBackend` trait 抽象保留回退可能——如果 TriviumDB 在生产验证中出现不可接受的问题，存储层可替换回 SQLite + sqlite-vec、业务逻辑不改、只改存储适配层。**选型时的关键约束**——QuIVer ANN 的优势随维度增大而扩大，128 维仅 0.21×、384 维 0.82×、768 维 1.4–2.9×、1024 维 3.4×、1536 维 3.6–5.0×——系统的嵌入维度（pizza 512 维、piccolo/bge-m3 1024 维）落在 QuIVer 的优势区间，这是选它而非 HNSW 类方案的重要理由；低维场景下 TriviumDB 并不占优、如果未来嵌入模型降到 384 维以下需要重新评估。

**结论**：TriviumDB 是当前技术栈下最匹配的选择，接受其生态早期的代价。这是“避免多库拼接”在存储选型上的具体落地。

**关联**：持久化、并发、快照隔离、崩溃恢复、嵌入存储。

### 持久化（`synchronous`）

**起因**：程序随时可能停机，已提交的记忆不能丢。每个写入单元必须是一个原子事务，要么全成功要么全回滚，不存在“球变大了但管道没变粗”“审计写了但状态没改”的半完成状态。

**理念**：WAL 模式下 `COMMIT` 返回即已持久化到 WAL，`kill -9` 不丢已提交事务；`synchronous = NORMAL` 断电可能丢最后几秒、但数据库不损坏，`FULL` 可配成不丢。

**解释**：持久化由 TriviumDB 的 **WAL（预写日志）+ 原子事务 + Dry-Run 预检 + COW 隔离** 四层机制共同保证。事务提交时先写 WAL，`COMMIT` 返回即表示已持久化——进程被 `kill -9`、panic 或客户端闪退，已提交事务不丢，下次打开数据库时自动重放 WAL 恢复到崩溃前最后一个已提交事务、未提交事务自动回滚；断电场景下 `synchronous = NORMAL` 可能丢最后几秒未 checkpoint 的事务、但数据库不会损坏，`synchronous = FULL` 可配成不丢任何已提交事务。**每个写入单元是一个原子事务**——结算写入（球大小增量、管道粗细增量、`last_watered_at`/`last_flowed_at` 刷新、`ball_stability`/`pipe_stability`/`blocked_pass_count` 先衰减再叠加）、新球创建（建球 + 建内容 + 建初始管道）、归档、纠正（审计日志 + 状态变更 + 强度扣减/迁移）各自在一个事务内完成，要么全成功要么全回滚。

**方案**：**启动恢复流程**——打开数据库自动重放 WAL、回滚未提交事务；检查 `pending_retry` 表重试非原子结算模式下失败的写入；检查未完成结算标记（有则丢弃本次结算、下一轮重新计算）；执行 schema 版本迁移；可选 `integrity_check` 快速校验关键页。**备份**——启动时距上次快照超过 `backup_interval_hours`（默认 24 小时）则用 `VACUUM INTO` 生成一致性快照到 `backup/` 目录、保留最近 N 份（默认 7）、旧的自动删除；快照是热备份、不阻塞读写，用户也可以直接拷贝 `store.tdb` 文件做完整备份。**多进程并发**——WAL 支持多读单写，dsh 和 pi 可同时打开同一 `.tdb`，结算用 `BEGIN IMMEDIATE` 获取写锁、流动用 `BEGIN DEFERRED` 读快照，`busy_timeout` 控制等锁上限、写冲突串行化、不丢更新。**原文压缩**——`rmw-utf8` 压缩后的内容以 BLOB 存储、带编码标记，读取时按标记决定是否解压；压缩后不更小则回退 `raw`、不膨胀。边界情况：TriviumDB 的 Dry-Run 预检在事务提交前完成所有验证、验证失败不写 WAL；COW 隔离保证未提交的修改不影响正在读的快照；版本号递增与写入在同一事务内，不会出现“版本号加了但写入没成功”。

**结论**：进程随时停机不丢已提交记忆，恢复不需要人工干预。这是“每个写入单元是一个原子事务”在持久化上的具体落地。

**关联**：并发、崩溃恢复、快照隔离。

### 并发

**起因**：dsh 和 pi 可能同时打开同一 `store.tdb`。原文档假设“单用户场景下冲突概率极低”，但 dsh 和 pi 是两个独立进程、各自有独立的流动和结算节奏；如果用户同时用两个客户端高频对话，两个进程的结算可能频繁交错，版本冲突频率不是“极低”、而是“与两个客户端的结算频率成正比”。

**理念**：进程级文件锁 + 线程级 `RwLock`，多读单写、写冲突串行化。冲突频率需要指标监控、不假设永远极低。

**解释**：并发控制分**进程级**和**线程级**两层。进程级由 TriviumDB 的文件锁保证——Writer 排他、Reader 共享，dsh 和 pi 可同时打开同一 `store.tdb`，WAL 支持多读单写、多个流动可并行读快照、结算写入串行化；`busy_timeout`（默认 5000ms）控制等锁上限、写冲突时等待而非立即报错、单用户场景下冲突概率极低、等待通常在毫秒级。线程级由内核内部的 `RwLock`/`Mutex` 保护共享状态，napi 的异步调用在 Tokio 运行时上执行、不阻塞 JS 事件循环。**流动与结算的并发边界**——流动开始时开短读事务加载起点子图、记录全局版本号 `graph_version_start`、立刻结束读事务，流动在内存子图上纯计算、不持有数据库锁；结算时开 `BEGIN IMMEDIATE` 写事务、校验版本号——`graph_version_now == graph_version_start` 直接写入增量，`graph_version_now != graph_version_start` 则重读涉及球/管道、用最新状态重算增量再写（版本冲突重算），重算范围限于本次结算涉及的球和管道、最多 `max_lit_ball_count` 个、毫秒级。

**方案**：强度更新用原子增量、不用读-改-写，即使两个进程同时结算同一球也不会丢更新；版本号递增与写入在同一事务内，不会出现“版本号加了但写入没成功”。**非原子结算模式**（`atomistic_settle = false`）下逐条写入、失败项进 `pending_retry` 表，下一轮结算或启动时重试、最终一致；原子模式（默认）下所有写入在一个事务内、要么全成功要么全回滚、不需要 `pending_retry`。**未完成结算标记**只在非原子模式下使用——结算前写入、成功后清除，启动时发现标记还在则丢弃本次结算、下一轮重算，避免“半结算”状态污染图。**冲突策略可配**——`conflict_strategy = "recompute"`（默认，重算后写入）或 `"abort"`（放弃本次强化、注入照常、下一轮重试）。**注入不依赖结算成败**——结算失败或选择 `abort` 时注入仍照常进行，记忆系统可以降级但不能让主对话卡住。**需要监控 `settle_version_conflict_rate`**——两个客户端高频对话时冲突频率与结算频率成正比、不是永远“极低”，超过阈值时考虑常驻守护或退避策略。边界情况：两个进程同时结算同一球时后到者检测到版本冲突、重算、写入，两次强化都保留；流动读快照不阻塞写、写不阻塞读；`busy_timeout` 超时后返回错误而非无限等待、由上层决定重试或降级。

**结论**：多客户端共享单文件可行，冲突频率需要指标监控、不假设永远极低。这是“进程级文件锁 + 线程级 `RwLock`”在并发控制上的具体落地。

**关联**：快照隔离、版本冲突重算、持久化。

### 快照隔离

**起因**：流动读子图时需要一致性子图快照，不能读到撕裂状态——不能出现“球 A 的旧大小 + 管道 A-B 的新粗细”。原文档没有定义版本号的存储位置和读取时机，导致“快照隔离”是一个实现契约缺口。

**理念**：读不阻塞写、写不阻塞读；流动在内存子图上纯计算、不持有数据库锁；**版本号存 DB，且必须与子图加载在同一个读事务里读**——否则可能读到“子图是旧版本、版本号是新版本”。

**解释**：流动开始时打开一个**短读事务**，从 TriviumDB 加载起点球及其 N 跳邻居子图到内存、同时记录全局版本号 `graph_version_start`，然后立刻结束读事务——读事务只持续到子图加载完成、不持有到流动结束，避免长读事务阻止 WAL checkpoint、让 `-wal` 文件膨胀。子图加载完成后，流动全程在内存里纯计算、不再读数据库，因此流动看到的是一份**一致性子图快照**。TriviumDB 的快照隔离由 **WAL + Mmap COW（写时复制）** 支撑：读事务看到的是事务开始那一刻的已发布代际，写事务在 COW 隔离的副本上修改、提交后才原子替换发布，读不阻塞写、写不阻塞读。结算时打开 `BEGIN IMMEDIATE` 写事务、读当前版本号 `graph_version_now` 与 `graph_version_start` 比较——`graph_version_now == graph_version_start` 说明流动之后图没被改过、直接按流动结果写入增量；`graph_version_now != graph_version_start` 说明流动期间有其他进程改过图、旧的计算结果作废，重读本次结算涉及的球和管道、用最新状态重算路径相关性和强化增量再写入。

**方案**：版本号与子图同读事务，保证快照隔离真正落地——`BEGIN DEFERRED → 读子图 → 读 graph_version → COMMIT`，三者同一个快照。快照隔离与“流动只点亮、不写入”配套——流动不持有写锁、不产生任何写入、只在内存子图上算；与“结算同步立刻执行”配套——结算必须在同一同步步骤内完成版本校验和写入、不能异步，异步会让版本窗口变大、冲突概率上升。边界情况：读事务加载子图期间如果有写事务提交，读事务看到的是写事务提交前的代际、不会读到未提交的修改；版本号递增在结算事务提交时完成、与写入同一事务，不会出现“版本号加了但写入没成功”；冲突重算时如果涉及的球已被归档、按归档球处理、不强行加载回主图。

**结论**：流动读到一致性子图、结算写入不基于过时数据。这是“版本号与子图同读事务”在快照隔离上的具体落地。

**关联**：版本冲突重算、并发、流动只点亮。

### 崩溃恢复

**起因**：`kill -9`、panic、客户端闪退或系统断电后需要自动恢复。已提交的不丢、未提交的回滚、半完成的丢弃、schema 向前兼容。

**理念**：恢复流程分四步——WAL 重放、`pending_retry` 重试、未完成结算标记丢弃、schema 迁移 + `integrity_check`；TriviumDB 自身的 `.flush_ok v3`、旧代备份与撤销日志、Dry-Run 预检提供额外保障。

**解释**：① **WAL 重放**——TriviumDB 打开数据库时自动重放 WAL，把崩溃前最后一个已提交事务恢复到主库、未提交事务自动回滚；已提交的结算写入（球大小增量、管道粗细增量、时间戳刷新、`ball_stability`/`pipe_stability`/`blocked_pass_count` 先衰减再叠加）、新球创建（球 + 内容 + 初始管道）、纠正（审计日志 + 状态变更 + 强度扣减/迁移）、归档全部不丢；断电场景下 `synchronous = NORMAL` 可能丢最后几秒未 checkpoint 的事务、但数据库不会损坏，`synchronous = FULL` 可配成不丢任何已提交事务。② **`pending_retry` 重试**——仅非原子结算模式下使用，结算逐条写入、失败项进 `pending_retry` 表，崩溃后重启时检查该表、重试失败项、保证最终一致；原子模式下这张表永远为空。③ **未完成结算标记**——非原子结算前写入 `settle_in_progress` 标记、成功后清除，崩溃后启动时发现标记还在、说明上次结算中途崩溃——丢弃本次结算（注入已经发生过了、强化值丢失可接受）、清除标记、下一轮正常结算，避免“半结算”状态污染图。④ **schema 版本迁移 + `integrity_check`**——启动时检查 schema 版本、低于当前则执行迁移脚本、向前兼容；可选 `integrity_check` 快速校验关键页，失败则从最近的 `backup/` 快照恢复，快照也损坏时用 TriviumDB 的 `.recover` 工具抢救可读数据。

**方案**：TriviumDB 自身的恢复机制包括 `.flush_ok v3` 绑定主文件和 sidecar、旧代备份与撤销日志、Dry-Run 预检——发布前完成所有验证、验证失败不写 WAL，COW 隔离保证未提交修改不影响正在读的快照。备份策略——启动时距上次快照超过 `backup_interval_hours`（默认 24 小时）则用 `VACUUM INTO` 生成一致性快照到 `backup/`、保留最近 N 份（默认 7），快照是热备份、不阻塞读写。边界情况：崩溃发生在结算事务提交前、事务回滚、球和管道回到结算前状态、下一轮重新计算；崩溃发生在提交后、WAL 已持久化、重放恢复；崩溃发生在 `pending_retry` 写入过程中、该条重试记录可能丢失、但只影响一次强化、不影响记忆内容；崩溃发生在归档或纠正事务中、事务回滚、状态不变。

**结论**：崩溃发生在结算不同阶段时数据一致性正确。这是“WAL 重放 + `pending_retry` + 未完成结算标记 + schema 迁移”在崩溃恢复上的具体落地。

**关联**：持久化、快照隔离、并发。

### 原文压缩（`rmw-utf8`）

**起因**：中文短文本直接存储体积大。通用算法（zstd/gzip）为长文本设计，在几十到几百字节的短文本上反而膨胀——zstd 对 12 字节中文文本反而膨胀到 175%、gzip 膨胀到 275%。

**理念**：通用算法是为大文件和网络流设计的、在几十到几百字节的短文本上“帮倒忙”；`rmw-utf8` 专门为中文短文本优化，是当前技术栈（Rust）下最匹配的选择、可直接作为 crate 依赖、无跨语言开销。

**解释**：球的内容原文写入存储前用 `rmw-utf8` 压缩——这是专门针对中文 UTF-8 短文本优化的压缩算法，对 12–120 字节的中文文本压缩率 **21%–39%**，远优于 zstd/gzip 在同等短文本上的表现。**写入时**——先按 `rmw-utf8` 压缩，压缩后长度**严格小于**原始长度才存压缩版、编码标记 `rmw-utf8`，否则回退存原始字节、编码标记 `raw`——永远不存“膨胀”的结果，这是短文本场景的必要兜底；单条内容长度上限（默认 4000 字符）超出时截断为“前 N 字符 + 摘要”、原文转冷存储。**读取时**——按编码标记决定是否解压，`rmw-utf8` 的解压发生在注入渲染或冷存储回源时、不触碰前缀缓存。

**方案**：**只压缩文本内容、不压缩嵌入向量**——嵌入是浮点 BLOB，`rmw-utf8` 是为文本设计的、对向量无效；向量用 f16 量化省空间、是另一个独立话题。**存储格式**——内容以 BLOB 存储、带 `encoding` 字段（`rmw-utf8` 或 `raw`），行内标记让读取路径知道该不该解压、不需要全库重写就能逐行切换编解码器。边界情况：内容极短（字节数小于 `MIN_COMPRESS_BYTES`，默认 8）时直接存 `raw`、减少无意义压缩调用；非中文内容（纯英文、代码、JSON）压缩率可能不高、但“严格小于才压缩”的兜底保证不会膨胀；压缩后长度恰好等于原始长度时回退 `raw`（“严格小于”才压缩）；编解码 round-trip 必须 100% 一致。

**结论**：不膨胀是底线，压缩只对文本有效。这是“通用算法对短文本帮倒忙”在压缩选型上的具体落地。

**关联**：冷热分层、内容列表、嵌入存储。

### 冷热分层（`cold_content_max_gb`）

**起因**：内容列表无限增长会让球的 Payload 膨胀、读取和序列化成本上升；但直接删除旧内容又违背“不删除、只降可提取性”的理念——分层是“降级”而非“删除”。

**理念**：热层最常用、温层完整保留、冷层按需回源，三层合起来既控制热数据的体积、又保留全部内容。三层都是**保留、不删除**，只是访问频率和读取时机不同。

**解释**：内容按访问频率和读取时机分三层。**热层**是注入时渲染的代表性内容——球内容列表里被选中渲染进注入块的那条（或几条）内容，读取时直接解压、拼进尾部消息、是访问最频繁的一层。**温层**是球内容列表里的完整原文——每条内容以 `rmw-utf8` 压缩后存于球的 Payload 中、带编码标记，注入渲染时按需解压、是“这个球里装了什么”的完整记录、默认上限 5 条、可配。**冷层**是被淘汰出内容列表的旧内容和归档球的内容，单独存 `cold_content` 表、带球 ID 索引，注入回源时才读取——内容列表超出上限时按“被注入次数”淘汰最不常用的那条，淘汰**不是删除**、是转入冷层；归档球的内容也整体转入冷层，归档球被唤醒时按球 ID 直接查关联内容、不做全量扫描。

**方案**：它和“原文压缩”配套——三层都经过 `rmw-utf8` 压缩、不膨胀则回退 `raw`；它和“内容列表”配套——列表上限触发淘汰、淘汰转入冷层；它和“归档”配套——球归档时内容一起转冷层、唤醒时按需回源。冷层有软上限（`cold_content_max_gb`，默认 10 GB），超出时把更早的冷内容转入**离线备份文件**——单独的文件、不参与在线查询、但保留可恢复性，这不是删除、是“移到另一个存储介质”。边界情况：内容被纠正标记 `archived` 时不转入冷层、而是留在温层但不再参与渲染（保留审计追溯）；内容列表为空但冷层有内容时，按球 ID 回源后正常渲染；冷层回源失败时该球跳过注入、不阻塞其余球（不渲染“只记得有这件事”这类空壳内容）。

**结论**：三层都是保留、不删除，只是访问频率和读取时机不同。这是“分层是降级而非删除”在内容管理上的具体落地。

**关联**：内容列表、原文压缩、不切割完整球、渲染档位。

### 嵌入存储

**起因**：每个球需要持有一条语义向量；如果分离到独立的向量表，需要额外的向量库、多库拼接。存在 TriviumDB 原生 Vector 字段中、与 Payload 同属一个 Node，不需要分离的向量表。

**理念**：维度不是固定常量、由具体嵌入后端决定——pizza 512 维、piccolo/bge-m3 1024 维，存储体积随维度线性变化；维度一致性是启动时硬校验、换模型需显式迁移、不能混存不同维度。

**解释**：每个球在 TriviumDB 的 Node 里持有一条语义向量，存在原生 Vector 字段中、与 Payload（内容列表、`ball_stored_size`、`ball_stability`、状态等元数据）同属一个 Node——不是分离的向量表、不需要额外的向量库。存储用 f32、内部可 f16 量化，f16 每维 2 字节、384 维约 768 字节、1 万球约 7.5 MB。**QuIVer ANN 在向量数超过阈值时自动激活**（约 209–834 视版本），无需额外配置、无需建索引语句；球数少时退化为全量扫描、球数多时自动走索引——起始球选择、新球接图、离线补边、归档召回全部受益。

**方案**：**维度一致性是启动时的硬校验**——`DayuCore` 初始化时校验 `EmbeddingBackend::dimension()` 与球存储的向量维度一致，不匹配则启动失败而不是运行时静默错乱，这是防止“换模型后新旧球维度混存、余弦计算出错”的最后一道防线。**换嵌入模型需要显式迁移**——从 pizza 的 512 维切到 piccolo 的 1024 维时，要么全库重算嵌入（离线批量执行）、要么新建球表旧球按需回填，不能在同一张表里混存不同维度的向量——混存会让余弦计算无法进行、QuIVer 索引失效。**嵌入的更新走 EMA**——球被强化时若本次语境片段被追加为内容，嵌入做一次 `新嵌入 = 旧嵌入 × (1 − β) + 本次内容嵌入 × β`（β 默认 0.1），让球的语义身份缓慢漂移、不会因为追加一条内容就突变；内容被纠正标记 `archived` 后嵌入不立即重算、由后续 EMA 自然稀释。**嵌入不承担检索职责**——它只提供向量，余弦计算、阈值判断、归属判定都由规则层完成；**不直接出现在注入文本里**——注入渲染的是内容列表里的文本，嵌入只参与“选哪个球、强化多少”的计算。**嵌入向量不经过 `rmw-utf8` 压缩**——它是浮点 BLOB，文本压缩算法对它无效；省空间靠 f16 量化、是独立于原文压缩的另一条路径。边界情况：球创建时嵌入来自触发片段原文；球的内容列表被淘汰、纠正、归档时嵌入不立即重算；归档球的嵌入保留在归档表、强线索唤醒时直接使用、不重新嵌入。

**结论**：嵌入存储与原文压缩是两条独立路径。这是“维度不是固定常量、由嵌入后端决定”在存储上的具体落地。

**关联**：嵌入、原文压缩、存储内核、维度一致性。

## 七、纠正机制

### 审计先行

**起因**：纠正需要可追溯、可回退。如果状态改了但日志没写，就无法追溯“曾经想改什么”；如果日志写了但状态没改，也无法验证“纠正是否真的生效”。

**理念**：任何纠正**先写 `correction_log`、再改状态**——顺序不能反；日志与状态变更在**同一事务内**，要么全成功要么全回滚，不会出现“状态改了但日志没写”或“日志写了但状态没改”的半完成状态。日志本身不删除——即使球被硬删、`deleted` 状态不可逆，`correction_log` 仍保留，作为“这个球曾经存在过、曾经被纠正过”的审计记录。

**解释**：日志记录目标类型与 ID、纠正类型（删除内容/球、重新归属、更新描述、合并、分裂、删除管道、忘记球、拒绝召回）、原值快照、新值、来源（用户显式/用户隐式/离线巩固/判别器回滚/拒绝召回）、原因、时间戳、操作者、可逆性。引入这条规则的理由有三层：**① 纠正意图必须留痕**——即使纠正中途失败、事务回滚，纠正的“意图”也已经通过日志尝试记录，失败后重试时能追溯到“曾经想改什么”；**② 可逆性依赖原值快照**——软删的球要通过反向操作恢复，必须知道删除前的完整状态，原值快照是恢复的唯一依据；**③ 强度守恒可审计**——删除或重新归属时强度按贡献扣减或迁移，日志记录扣减前后的值，能验证“不为负、不重复计数”是否被遵守。

**方案**：它和“软删默认”配套——审计日志记录原值、软删保留可恢复性，两者合起来保证“误触纠正不会永久丢失记忆”；和“可逆性”配套——日志记录原值、新值、原因、时间，反向操作按日志恢复；和“隐式纠正”配套——隐式纠正标记 `contested` 时也写日志、来源标记 `user_implicit`，离线巩固确认正确/错误时再写一条日志，形成完整的纠正链。硬删时日志额外记录“不可逆删除”标记、二次确认的操作者、时间。它和“参数变更审计”**同构**——`param_change_log` 记录配置变更的原值、新值、触发信号、操作者，和 `correction_log` 遵循同一套“审计先行、原值快照、可追溯、可回滚”的模式——系统对“自身状态的修改”和“记忆的修改”都保持可审计。边界情况：纠正目标已不存在时、日志仍写入、状态变更跳过、标记“目标不存在”；纠正类型非法时、日志写入、事务回滚、返回错误；批量纠正时每条独立写日志、同一事务提交。

**结论**：纠正意图必须留痕、可逆性依赖原值快照、强度守恒可审计。这是“审计先行”在纠正机制上的具体落地。

**关联**：软删默认、可逆性、强度守恒、隐式纠正、参数变更审计。

### 软删默认

**起因**：误触纠正的代价不对称——软删误触可以恢复，硬删误触永久丢失记忆，违背“疏而不堵、不删除”的理念。默认选代价低的那一侧，把“永久删除”变成需要刻意确认的例外，而不是随手可得的默认。

**理念**：默认软删、保留可恢复性；硬删需要用户显式确认、二次确认。硬删是系统里唯一不可逆的操作。

**解释**：纠正操作默认执行**软删**——球、内容或管道不被物理删除，而是状态置为 `archived` 或 `deleted`（软删标记），原值保留、原因记录、支持反向操作恢复；**硬删**需要用户显式确认、二次确认，才执行物理删除或加密归档。

**方案**：它和“审计先行”配套——`correction_log` 记录原值快照，软删的球通过反向操作按日志恢复，两者合起来保证“纠正可逆”；和“状态”配套——软删的球状态变为 `archived`（休眠，强线索可唤醒）或 `deleted` 软删标记（不参与流动但保留数据），物理删除只发生在硬删；和“强度守恒”配套——软删时强度按贡献扣减但不归零、恢复时按日志回补。**硬删的约束**——用户必须显式说“永远忘掉”并二次确认，执行物理删除或加密归档，`correction_log` 保留但标记“不可逆删除”、记录操作者和时间；硬删不可回退、是系统里唯一不可逆的操作。边界情况：软删的球仍在存储中、嵌入保留、内容保留，只是状态变了、不参与常规流动；软删的球可以通过反向操作恢复为 `active`、恢复时按日志回补强度；软删的内容标记 `archived`、留在温层但不参与渲染、保留审计追溯；软删的管道跟随球的状态、球恢复时管道一起恢复。**与隐式纠正的区别**——隐式纠正只标记 `contested`、不软删，等离线巩固确认；软删是用户显式纠正或离线巩固确认错误后的操作，两者层级不同。

**结论**：硬删是系统里唯一不可逆的操作。这是“误触纠正的代价不对称”在默认值选择上的具体落地。

**关联**：审计先行、可逆性、状态、隐式纠正。

### 强度守恒

**起因**：强度是“这个球被强化了多少”的账本，纠正只应改变“这份强化归属于谁”、不应凭空创造或销毁强化——如果删除时不扣减，球的强度会虚高、后续注入排序和补充规则被污染；如果扣减过头，球可能变成负数、破坏 `ball_effective_size` 和衰减计算；如果重新归属时只加不减，同一份强化会被两个球各算一次、总量膨胀。

**理念**：纠正操作涉及删除或重新归属内容/球时，**强度按贡献扣减或迁移、不为负、不重复计数、总量守恒**。

**解释**：删除一条内容时，从球的 `ball_stored_size` 中扣减该内容贡献的强度——扣减量不超过该内容的贡献、扣减后 `max(0, ...)`、不会因扣减过头变成负数；重新归属时，从旧球扣减、向新球累加、两边总量守恒，不会出现“旧球没扣、新球加了”导致强度凭空多出一份。**贡献比例的确定**——删除一条内容时，该内容的贡献按“这条内容在球的内容列表中的占比”或“这条内容被注入次数占该球总注入次数的比例”估算，具体口径可配；重新归属时，按新球和旧球各自应得的比例拆分、不简单对半分。

**方案**：它和“审计先行”配套——`correction_log` 记录扣减前后的值、扣减量、贡献比例，能验证守恒是否被遵守；和“软删默认”配套——软删时强度按贡献扣减但不归零、恢复时按日志回补、扣减和回补对称；和“多路径取最大值”是不同层面的守恒——后者防止同一结算内多条路径重复强化、前者防止纠正时强度重复计数或凭空消失。边界情况：扣减后 `ball_stored_size` 变为 0 时球不删除、只是极小、仍可被强线索唤醒；扣减量超过当前 `ball_stored_size` 时按当前值扣到 0、不产生负数；重新归属的目标球已有强度时累加、不覆盖；批量删除多条内容时逐条扣减、总量不超过球当前强度。它和 `ball_stability` 的关系——纠正不重置 `ball_stability_stored`，但 `ball_stability_stored` 会随时间自然衰减；强度守恒管的是 `ball_stored_size`、不是 `ball_stability`；`ball_stability` 记录的是“被巩固过多少次”的历史、不因删除一条内容而改变。

**结论**：强度守恒管的是 `ball_stored_size`、不是 `ball_stability`。这是“纠正只应改变强化归属于谁”在强度管理上的具体落地。

**关联**：审计先行、软删默认、对称操作、ball_stability。

---

### 对称操作

**起因**：用户对记忆的反馈需要对称的两种直接操作——否定和确认作用于同一组状态量、只是方向相反，不需要单独的“强化算法”。

**理念**：否定和确认都是对球和管道的直接状态操作，作用于同一组状态量（`ball_stored_size`、`ball_stability_stored`、`pipe_base_thickness`），只是方向相反——否定减少、确认增加；不需要为“确认”单独设计一套“强化算法”，因为它和结算强化在状态层面是同一件事、只是触发源不同（结算由水流触发、确认由用户显式触发）。

**解释**：**用户否定 = 放水缩球**——按贡献扣减 `ball_stored_size`、`ball_stability_stored` 不重置但可标记 `contested`、相关的管道不做强化（下一次结算时自然不被走通、随时间衰减），否定是“这次说得不对”、不删除记忆、球仍然存在、仍可被强线索唤醒。**用户确认 = 注水 + 球变大 + 管道变粗**——`ball_stored_size` 增加（按确认时的显著性、受 `ball_size_ceiling` 饱和约束）、`ball_stability_stored` 按注水次数增长、与当前语境相关的管道 `pipe_base_thickness` 增加（相当于一次额外结算强化），确认是“这个记得对，继续保留并加强”。

**方案**：**和“纠正”的关系**——否定是纠正的一种（用户显式否定），走“审计先行”写 `correction_log`、默认软删不物理删除、强度按贡献扣减、可逆；确认不是纠正、但也走审计——记录“用户在什么时间、对哪个球、确认了什么内容”，便于后续追溯和对照实验。**和“强度守恒”的关系**——否定的扣减遵循强度守恒（按贡献扣减、不为负、不重复计数）；确认的增加不破坏守恒（增加的是新增强化、不是迁移已有强化）。**和“状态”的关系**——否定把球标记为 `contested`（有争议）而非 `deleted`、等离线巩固再确认——用户单次否定可能是误触或情绪化、不直接删除；确认把 `contested` 的球恢复为 `active`、或给 `active` 的球增加强度。**和 `ball_stability` 的关系**——确认可以增加 `ball_stability_stored`（相当于一次注水），否定不重置 `ball_stability_stored`——它记录的是“被巩固过多少次”的历史，否定一次不改变历史事实、球仍然“曾经被反复强化过”、只是这次不对。边界情况：用户连续否定同一个球多次、`contested` 状态累积、离线巩固时优先处理；用户否定后立即确认、按最近一次操作为准、走审计记录两次操作；否定一个 `archived` 的球时唤醒它、标记 `contested`、不直接删除；确认一个已饱和的球时 `ball_stored_size` 不再增长但 `ball_stability_stored` 仍可增长、内容可追加。

**结论**：否定和确认是对称的直接操作，不是两套算法。这是“作用于同一组状态量、只是方向相反”在用户反馈上的具体落地。

**关联**：强度守恒、状态、隐式纠正、审计先行、ball_stability。

### 隐式纠正

**起因**：用户没有显式说“你记错了”，但用户的话与已注入的记忆语义矛盾——比如记忆说“用户喜欢简洁回答”、用户却说“详细说说”。单次矛盾可能误判：用户可能只是在开玩笑、可能表达有歧义、可能记忆本身没错只是当前语境变了（“这次想详细听听”不否定“平时喜欢简洁”）；直接删除会误伤正确记忆，而标记 `contested` 保留了“这条记忆可能有争议”的信号、等积累更多证据再决定。

**理念**：只标记 `contested`、不直接删除、不直接扣减强度，等离线巩固再确认——隐式纠正比显式纠正更保守。

**解释**：**检测方式**——注入块与用户后续输入做语义对比，如果用户输入与注入记忆的核心内容余弦低于矛盾阈值、或用户明确表达了相反偏好，触发标记；检测在 `turn_end` 异步执行、不阻塞主对话。**处置**——球的 `status` 从 `active` 改为 `contested`，`correction_log` 记录来源 `user_implicit`、原状态、新状态、触发矛盾的用户输入片段、时间；强度**不扣减**、`ball_stability_stored` **不重置**——`contested` 只是“有争议”、不是“已否定”。

**方案**：**离线巩固的确认流程**——离线巩固时扫描所有 `contested` 球，用更多上下文（该球的历史注入记录、用户后续反馈、其他相关球的语义一致性）判断——确认正确则恢复 `active`、写一条日志；确认错误则转 `archived` 或按显式纠正处理、扣减强度、写日志；证据不足则保持 `contested`、等下一轮巩固再判断。**和显式纠正的区别**——显式纠正是用户明确说“不对/忘掉”，直接走纠正流程、可软删、按贡献扣减强度；隐式纠正只是“检测到矛盾”、不删除、不扣减，只标记等确认——两者层级不同、隐式纠正更保守。**和对称操作的关系**——隐式纠正的“否定”不是用户显式否定、不触发“放水缩球”；它只是标记，等离线巩固时如果确认错误、才走显式纠正的扣减流程。**和“状态”的关系**——`contested` 状态的球仍可参与流动和注入，但注入时带“我之前的理解可能不准确”的标注、让模型知道这条记忆有争议、可以谨慎引用或向用户确认。边界情况：用户连续多次与同一条记忆矛盾时、`contested` 累积、离线巩固优先处理；矛盾检测误报时、离线巩固确认正确后恢复 `active`、日志记录“误报已澄清”；`contested` 球在注入时如果用户再次确认、可直接恢复 `active`、写日志。

**结论**：隐式纠正比显式纠正更保守，只标记不删除。这是“单次矛盾可能误判”在纠正层级上的具体落地。

**关联**：状态、对称操作、审计先行、离线巩固。

---

### 可逆性

**起因**：纠正不是“一次性销毁”，而是“可追溯、可回退的状态变更”——用户可能误触、可能改变主意、可能事后发现原记忆其实是对的；如果纠正不可逆，一次误判就永久丢失记忆，违背“疏而不堵、不删除”的理念。

**理念**：软删可逆、硬删不可逆，默认选可逆的那一侧。`correction_log` 记录原值、新值、原因、时间、操作者、可逆性标记，软删的球、内容、管道可以通过反向操作恢复到纠正前状态、强度按日志回补、`ball_stability_stored` 不重置（它记录的是历史、不因纠正改变）。

**解释**：**可逆的边界**——软删的球反向操作恢复为 `active`、强度按日志回补、`ball_stability_stored` 不重置；软删的内容恢复为 `active`、重新参与渲染；软删的管道跟随球的状态恢复；`contested` 标记可以清除、恢复 `active`；合并/分裂的反向操作按审计记录恢复原球和原管道（合并反向执行分裂、分裂反向执行合并）；`reassign` 的反向操作把内容/球重新归属回原球、强度按贡献回补。**不可逆的边界**——硬删（用户显式“永远忘掉” + 二次确认）是唯一不可逆操作，物理删除或加密归档后无法恢复，但审计日志保留、记录“曾经存在过、曾经被永久删除”。

**方案**：和“审计先行”配套——可逆性依赖原值快照，没有审计日志就没有恢复依据；和“软删默认”配套——软删保留数据、可逆，硬删不保留数据、不可逆，默认选可逆的那一侧；和“强度守恒”配套——反向操作时强度按日志回补、扣减和回补对称、总量守恒。边界情况：纠正后原球被归档、反向操作时先唤醒再恢复；纠正后原球被合并到其他球、反向操作时按审计记录拆分恢复；多次纠正同一球时，反向操作按日志逆序回退、每次回退一步；反向操作本身也写日志、也可逆（回退的回退）；硬删后反向操作被拒绝、返回“不可逆”错误。

**结论**：可逆性是“疏而不堵、不删除”在纠正层面的落地。这是“纠正不是一次性销毁”在可逆性上的具体落地。

**关联**：审计先行、软删默认、强度守恒、合并、分裂。

## 八、判别器

### 当前路径

**起因**：判别器需要一个可运行、可复现、可审计的第一版。判别器最核心的决策（是否起念、归属哪个球）本质是分类，嵌入 + 规则已经覆盖。

**理念**：当前“嵌入 + Rust 规则”的裁剪版方案，不引入生成模型——结论完全可复现、可审计，同一个输入永远得到同一个判定，相似度算出来是 0.72 就是 0.72、阈值是 0.6 就是 0.6，不存在生成模型的采样漂移；而生成模型在硬性 JSON schema 约束下存在“格式对但语义错”的已知风险（小模型实测可执行准确率可能从 91.5% 跌到 48.0%），不适合作为第一版。

**解释**：判别器当前采用“嵌入 + Rust 规则”的裁剪版方案，不引入生成模型。**嵌入层**用 `pizza-embed-zh-small-v1`（约 91 MB，ONNX，CPU 可跑，512 维）负责把文本变成向量、算余弦——它只提供语义距离、不做任何判断；**规则层**是 Rust 代码，负责阈值、灰区、兜底合并、归属判定等全部决策逻辑。判别器不是独立的分类模型，是一条“嵌入提供语义距离、规则层做决策”的流程。**流程**——候选片段嵌入 → 与最近 6 轮上下文算余弦得到 `significance` 近似 → 与候选球嵌入算余弦、取 Top-1、余弦 ≥ 0.7 判 `belongs_to`、该余弦即 `belong_confidence` → 规则层按阈值判断 `should_judge` → 兜底合并检查（与已有球余弦 > 0.95 则追加内容 + 强化、不建新球）→ 产出裁剪版 `Verdict`。

**方案**：裁剪版 `Verdict` **只填充四个必填字段**——`should_judge`、`significance`（当前用候选与最近 6 轮的余弦近似）、`belongs_to`（Top-1 且余弦 ≥ 0.7 判 Attach）、`belong_confidence`（即该余弦值）；情绪效价/强度、偏移方向、命中人格维度、`reason` 四个可选字段一律留空，由 `producer = EmbeddingRule` 标记来源、`capabilities()` 返回全部 false 显式声明“当前后端不产出这些字段”。**当前路径的局限是显式的**——显著性用余弦近似只是“相关度”不是真正的“值不值得记”（用户每天说“好的”余弦可能很高但完全不显著）；情绪、方向、人格维度、自然语言理由这些需要生成模型才能可靠产出的字段，当前不输出。**和“未来路径”的关系**——切换方式是把决策专用小模型作为 `JudgeBackend` 的新枚举变体接入，与当前嵌入 + 规则路径并列、通过对照实验决定是否替换，业务规则层代码不变——阈值、灰区、兜底合并只读必填字段，可选字段只影响渲染丰富度和指标记录、不影响“起不起念、归哪个球”。边界情况：嵌入后端不可用时降级为“仅归档、不起念”，不阻塞主对话；余弦恰好等于 0.7 时按“≥”判 Attach；候选球列表为空时直接判新球、不做兜底合并检查。

**结论**：当前路径的局限是显式的——显著性用余弦近似只是“相关度”不是“值不值得记”，情绪/方向/人格维度/理由不输出。这是“嵌入提供语义距离、规则层做决策”在当前路径上的具体落地。

**关联**：Verdict 必填字段、Verdict 可选字段、未来路径、业务规则层只读必填字段。

### Verdict 必填字段

**起因**：业务规则层需要一组任何后端都必须产出的字段。缺任何一个流程都无法进行，所以必须是必填、不能是 `Option`；如果某个后端无法产出某个必填字段（比如没有嵌入能力），它就不应该被注册为可用的 `JudgeBackend`、而不是返回一个默认值蒙混过关。

**理念**：四个字段的分工——`should_judge` 管“要不要记”，`significance` 管“记的分量有多重”，`belongs_to` 管“记到哪个球”，`belong_confidence` 管“这个归属判断有多可靠”。

**解释**：`Verdict` 有四个必填字段，任何 `JudgeBackend` 都必须产出、业务规则层只依赖它们：**`should_judge`**——布尔值，回答“这个候选片段是否起念”，是判别器的第一道闸门，`false` 则整个候选被丢弃、不建球不挂载；**`significance`**——`Relevance` 类型（`[0,1]` 的受约束标量），回答“这个起念有多显著”，当前用“候选片段嵌入与最近 6 轮上下文嵌入的余弦”近似、越高越显著、过 `strengthen_eligibility_threshold` 或固化阈值才进入后续流程；**`belongs_to`**——`Option<BallId>`，回答“这个念归属哪个已有球”，`None` 表示新球、`Some(id)` 表示挂到已有球，当前用“候选片段嵌入与候选球嵌入的 Top-1、余弦 ≥ 0.7 判 Attach”得到；**`belong_confidence`**——`Relevance` 类型，回答“归属判定有多确定”，当前就是那个 Top-1 余弦值、用于灰区判断（置信度 ≤ 0.7 时走 tentative 挂载、累计确认后才转正）和兜底合并判断。

**方案**：可选字段为 `None` 时消费方通过 `Option` 判断、不假设有值；必填字段没有 `Option` 包装、任何后端都必须给出合法值。边界情况：`significance` 必须在 `[0,1]` 内、超出范围按配置校验拒绝；`belong_confidence` 同理；`belongs_to = Some(id)` 但 `id` 不存在时按“归属目标已失效”处理、降级为新球；`should_judge = false` 时其余三个字段的值被忽略、不参与任何决策。

**结论**：四个必填字段是“业务规则层只读必填字段”的前提。这是“缺任何一个流程都无法进行”在字段设计上的具体落地。

**关联**：Verdict 可选字段、capabilities()、业务规则层只读必填字段。

### Verdict 可选字段

**起因**：情绪、方向、人格维度、理由需要生成模型才能可靠产出——嵌入 + 规则只能算语义距离、算不出情绪效价、描述不出偏移方向、列不出人格维度、写不出自然语言理由；当前裁剪版方案不引入生成模型，所以这些字段留空，不是“实现漏了”、是“当前路径的能力边界”。

**理念**：可选字段只影响渲染丰富度和指标记录、不影响判别决策——业务规则层只读四个必填字段、不读可选字段；这保证从“嵌入 + 规则”切到“决策模型”时，判别决策逻辑不变、只是输出更丰富。

**解释**：`Verdict` 有五个可选字段，用 `Option<T>` 包装，当前“嵌入 + 规则”路径一律填 `None`、未来由决策专用小模型填充：**`emotion_valence`**——`Option<f64>`，情绪效价 `[-1, 1]`，负值表示负面情绪、正值表示正面情绪；**`emotion_intensity`**——`Option<f64>`，情绪强度 `[0, 1]`、越高情绪越强烈；**`offset_direction`**——`Option<String>`，偏移方向、描述“注意力从什么滑向什么”，如“从‘结束话题’滑向‘他是不是在硬撑’”；**`hit_dimensions`**——`Option<Vec<String>>`，命中的角色人格敏感维度列表，如 `["在意对方是否硬撑", "对语气变化敏感"]`；**`reason`**——`Option<String>`，自然语言理由、解释“为什么判这个结果”，给人看、不是给系统消费。

**方案**：消费方通过 `Option` 判断、不假设有值——注入渲染时 `reason` 为 `Some` 则渲染为 `[记忆] 关于"X"，我记得：Y（因为 Z）`、为 `None` 则退化为 `[记忆] 关于"X"，我记得：Y`；`emotion_valence` 和 `emotion_intensity` 为 `Some` 时可用于情绪一致性指标、为 `None` 时跳过；`hit_dimensions` 为 `Some` 时可用于人格维度命中统计、为 `None` 时跳过；`offset_direction` 为 `Some` 时可用于审计和调试、为 `None` 时跳过。**关键约束**——可选字段只影响渲染丰富度和指标记录、不影响判别决策，业务规则层（阈值、灰区、兜底合并、新球创建）只读四个必填字段、不读可选字段。**和 `capabilities()` 的配合**——`capabilities()` 显式声明后端能产出哪些可选字段，`None` 有两种可能——“这个后端本来就不产出”和“这次没产出”，`capabilities()` 把前者显式化、消费方不用猜；当前 `EmbeddingRule` 后端的 `capabilities()` 全部返回 false，`DecisionModel` 后端返回 true。边界情况：`emotion_valence` 和 `emotion_intensity` 为 `Some` 时必须在合法范围内、超出范围按配置校验拒绝或截断；`hit_dimensions` 为 `Some` 但为空列表时按“无命中维度”处理、不等同于 `None`；`reason` 为 `Some` 但空字符串时按“无理由”处理、渲染时退化为无理由格式；可选字段部分有值、部分为 `None` 时，消费方按字段独立判断、不要求全部有值或全部无值。

**结论**：可选字段是“渲染丰富度”的素材，不是“判别决策”的依据。这是“可选字段只影响渲染和指标”在字段设计上的具体落地。

**关联**：Verdict 必填字段、capabilities()、业务规则层只读必填字段、渲染档位。

### Verdict producer

**起因**：每条判定需要回答“是谁做的”——出问题时能定位到具体后端，而不是“系统判的”这种模糊表述；同一批输入分别用 `EmbeddingRule` 和 `DecisionModel` 跑，结果按 `producer` 分组统计、能对比两个后端的召回质量、判定一致性、误判方向；指标按 `producer` 打标签，能分别监控每个后端的健康度、而不是混在一起。

**理念**：`producer` 是**身份标识**、`capabilities()` 是**能力声明**，两者配合让消费方知道“这条判定来自哪个后端、它有哪些字段可信”。在 `Verdict` 构造时由后端自己填入，不是外部赋值——后端最清楚自己是谁，让它自报身份比让调用方猜更可靠。

**解释**：`Verdict` 上带一个 `producer` 字段，标记这次判定来自哪个后端——取值是枚举：`EmbeddingRule`（当前“嵌入 + 规则”路径）、`DecisionModel`（未来决策专用小模型）、`Mock`（测试）。

**方案**：**和“枚举分派”的关系**——`BackendKind` 枚举分派时，每个变体的 `producer()` 方法返回对应的 `VerdictProducer` 值，`JudgeEngine` 不关心具体后端、只通过 `producer()` 拿标识；新增后端时枚举变体、`match` 分支、`producer()` 返回值三处一起加，编译器强制完整。它**不参与业务决策**——业务规则层不读 `producer` 做任何判断，它只用于审计、对照实验、指标标签；这保证“切换后端不改变业务逻辑”，后端差异被隔离在 `producer` 和 `capabilities()` 里。边界情况：`producer` 是必填字段、不能为空，任何后端都必须返回一个合法枚举值；未知后端类型时配置校验拒绝启动，而不是运行时返回一个 `Unknown` 值；对照实验时同一输入的两个 `Verdict` 按 `producer` 区分、不混在一起统计。

**结论**：`producer` 是身份标识、`capabilities()` 是能力声明，两者配合。这是“是谁做的判定”在字段设计上的具体落地。

**关联**：capabilities()、枚举分派、可观测性。

### capabilities()

**起因**：`Option` 为 `None` 有两种可能——“这个后端本来就不产出”和“这次没产出”，消费方如果只看 `Option` 无法区分、会误以为“后端能力有但这次没给”；`capabilities()` 把前者显式化、消费方不用猜。

**理念**：把“这个后端能不能产出某字段”从“运行时猜”变成“编译期声明”——`capabilities().emotion == false` 意味着“这个后端永远不产出情绪字段”，`emotion_valence == None` 且 `capabilities().emotion == true` 意味着“后端有能力但这次没给”。做成方法而不是字段——不同后端的能力是编译期确定的、不需要每次判定都存一份，做成方法让后端自报能力、不需要在每条 `Verdict` 里重复携带；`JudgeEngine` 可以在初始化时调用一次、缓存结果，不需要每次判定都调。

**解释**：`JudgeBackend` trait 上的一个方法，返回 `JudgeCapabilities` 结构，显式声明这个后端能产出哪些可选字段——四个布尔字段：`emotion`（能否产出情绪效价/强度）、`offset_direction`（能否产出偏移方向）、`hit_dimensions`（能否产出命中人格维度）、`reason`（能否产出自然语言理由）。当前取值——`EmbeddingRuleBackend` 的 `capabilities()` 四个字段全部返回 false（当前路径不产出任何可选字段）；`DecisionModelBackend` 四个字段全部返回 true（未来决策小模型产出全部可选字段）；`MockJudgeBackend` 可按测试需要配置，用于测试“部分能力”“全部能力”“无能力”三种场景。

**方案**：**和 `producer` 的分工**——`producer` 回答“谁做的判定”（身份标识），`capabilities()` 回答“这个后端能产出哪些字段”（能力声明）——两者配合让消费方知道“这条判定来自哪个后端、它有哪些字段可信”。**消费方如何使用**——注入渲染按 `capabilities().reason` 决定是否渲染“因为 Z”；可观测性按 `capabilities().emotion` 决定是否记录情绪相关指标；对照实验按 `capabilities()` 筛选“哪些字段可在两个后端之间对比”、不把“后端 A 有、后端 B 没有”的字段混在一起统计；业务规则层**不读** `capabilities()`、只读四个必填字段，这保证切换后端时判别决策逻辑不变。边界情况：`capabilities()` 声明为 true 但实际返回 `None` 时按“这次没产出”处理、不视为错误；声明为 false 但实际返回 `Some` 时按配置校验拒绝——后端能力声明与实际行为不一致是 bug、应该在测试中暴露而不是运行时静默接受；新增可选字段时 `JudgeCapabilities` 加字段、所有后端实现同步更新、编译器强制完整。

**结论**：消费方按 `capabilities()` 决定是否依赖某字段、不把“后端 A 有、后端 B 没有”的字段混在一起统计。这是“把运行时猜变成编译期声明”在能力声明上的具体落地。

**关联**：Verdict 可选字段、producer、业务规则层只读必填字段。

### 未来路径

**起因**：未来若要从“嵌入 + 规则”升级到生成模型，需要选型。通用生成模型在硬性 JSON schema 约束下存在“格式对了但语义错了”的风险——论文实测 Qwen2.5-1.5B 在 prompt-only JSON 下可执行准确率 91.5%、换成硬性工具调用 schema 后暴跌到 48.0%，错误是语义性的、不是结构性的。

**理念**：优先**决策专用小模型**，而不是通用生成模型——决策专用模型用一次前向传播直接输出候选概率、不需要自回归生成 JSON，从根本上绕开小模型在硬性 JSON schema 约束下“格式对了但语义错了”的风险；决策专用模型的输出空间是“候选标签的概率分布”、天然匹配“是否起念、归属哪个球”的选择题。

**解释**：候选模型——**`Jev-Style-0.8B-Decision-v3`**（专为“在一组给定选项中做单次判断”设计，0.8B 参数、GGUF Q4 约 0.53 GB、中英双语、短请求延迟约 0.15–0.2 秒，用它的方式是把候选标签作为参数传进去、它直接返回每个选项的概率）；**`Chinese Decision-0.8B`**（中科院计算所出品，同样是“单次前向、直接输出候选概率”的架构，0.8B 版本 Q8_0 约 812 MB，中文决策数据来自 1300 万条 CJ-Dataset、对中文语境判别更有针对性）；**`Xenomi-nano-0.8B`**（官方定位“面向路由、术语抽取、关键词与短文本判别”，不是通用对话模型）；**`SeqGPT-560M`**（阿里达摩院中文零样本理解模型，无需训练即可做分类和信息抽取，约 1.1 GB）。**通用模型作为对照基线**——Qwen3-0.6B/1.7B 有成熟的 ONNX 量化部署路径（0.6B Q4 约 1 GB、1.7B 约 1.5 GB），可作对照基线、但不默认更优——小模型在自由生成 JSON 下的语义漂移风险需要实测验证，不能因为“参数大一点”就假设更好。

**方案**：**接入方式**——实现一个新的 `DecisionModelBackend`、在 `BackendKind` 枚举里加一个变体、加一个 `match` 分支，`JudgeEngine`、`DayuCore`、注入渲染、可观测性全部不用改；`producer()` 返回 `DecisionModel`、`capabilities()` 返回全部 true（决策模型能产出全部可选字段）；切换只改配置 `judge.backend = "decision_model"`、不改代码。**验证方式**——同一批对话、同一批记忆，分别用 `EmbeddingRule` 和 `DecisionModel` 跑、按 `producer` 分组统计判定一致性、召回质量、误判方向，用数据决定是否替换——如果决策模型在必填字段上和嵌入 + 规则高度一致、且可选字段确实带来了渲染丰富度或召回质量提升，再切默认；如果一致性低或质量下降，保留嵌入 + 规则。**约束**——决策模型必须能产出四个必填字段（`should_judge`、`significance`、`belongs_to`、`belong_confidence`），否则不能注册为可用后端；可选字段按模型能力填充、`capabilities()` 如实声明；模型加载失败时降级为“仅归档、不起念”、不阻塞主对话。边界情况：决策模型的输出概率需要映射到 `Relevance` 的 `[0,1]` 范围、映射函数可配；`belongs_to` 的候选集来自嵌入检索的 Top-K、决策模型在候选集上做选择、不自由生成球 ID；模型推理延迟需控制在 200–800ms 的异步旁路预算内，超时丢弃候选、不重试。

**结论**：决策专用模型天然匹配“从候选球中选一个”的判别任务、避免自由生成 JSON 的语义漂移。这是“优先决策专用而非通用生成”在选型上的具体落地。

**关联**：枚举分派、producer、capabilities()、业务规则层只读必填字段。

### 枚举分派

**起因**：判别器后端需要一个可扩展、编译期完整、热路径无 vtable 的持有方式。判别器每轮要跑 1–3 次、每次 200–800ms，`dyn` 的虚函数调用和缓存不友好会抵消 Rust 的性能优势。

**理念**：后端集合是已知的、有限的（当前嵌入 + 规则、未来决策模型、测试 Mock），封闭比开放更安全；`match` 必须穷尽、不能有 `_ =>` 兜底——兜底会掩盖“忘了处理新变体”的错误。

**解释**：`JudgeEngine` 不直接持有 `Box<dyn JudgeBackend>`，而是持有一个 `BackendKind` 枚举——枚举的每个变体包裹一个具体后端（`EmbeddingRule(EmbeddingRuleBackend)`、`DecisionModel(DecisionModelBackend)`、`Mock(MockJudgeBackend)`），`BackendKind` 自身也实现 `JudgeBackend` trait，通过 `match` 把 `judge()`、`producer()`、`capabilities()` 转发到具体变体。

**方案**：**和 sealed trait 的关系**——`JudgeBackend` 是 sealed trait（下游不可实现、只能使用），后端集合封闭、正好适合枚举分派——如果 trait 是开放的、第三方可以注入任意实现，枚举分派就不成立、只能退回 `Box<dyn>`；当前设计选择封闭集合，是因为单用户、两个客户端的场景里后端是可枚举的、封闭比开放更安全。**和 `producer()`、`capabilities()` 的关系**——`BackendKind` 的 `match` 转发这三个方法，每个变体返回自己的 `producer` 和 `capabilities`，`JudgeEngine` 不关心具体后端、只通过 `match` 拿结果。**扩展方式**——未来接入决策专用小模型时，实现 `DecisionModelBackend`、加一个 `BackendKind::DecisionModel` 变体、加一个 `match` 分支，`JudgeEngine`、`DayuCore`、注入渲染、可观测性全部不用改——这是“新增后端只加一个变体”的具体落地。边界情况：枚举变体增加时所有 `match` 必须同步更新、编译器强制；`match` 必须是穷尽的、不能有 `_ =>` 兜底分支；枚举分派不适用于“后端数量动态增长、运行时才确定”的场景，如果未来真的需要开放扩展、再退回 `Box<dyn>` + sealed trait 的组合。

**结论**：热路径无 vtable 间接调用、编译器强制完整性、读者一眼看到全部合法路径。这是“封闭集合比开放更安全”在枚举分派上的具体落地。

**关联**：未来路径、producer、capabilities()。

---

### 业务规则层只读必填字段

**起因**：可选字段（情绪效价/强度、偏移方向、命中人格维度、`reason`）是“渲染丰富度”和“指标记录”的素材、不是“判别决策”的依据——它们依赖生成模型才能可靠产出，当前“嵌入 + 规则”路径一律留空，如果业务规则层依赖它们、当前路径就无法运行。

**理念**：这是一条“架构隔离线”——如果业务规则层读了某个可选字段，等于把“判别决策”和“生成模型能力”耦合在一起，切换后端时决策逻辑就会变，这违背“后端可替换、业务逻辑零改动”的设计目标；守住这条线，新增决策模型后端时只需实现 `JudgeBackend` trait，业务规则层一行不改。

**解释**：判别器的业务规则层——包括阈值判断（`significance` 是否过固化阈值）、灰区处理（`belong_confidence` 在 0.5–0.7 时走 tentative 挂载、累计确认后才转正）、兜底合并检查（与已有球余弦 > 0.95 则追加内容 + 强化、不建新球）、新球创建决策——**只读 `Verdict` 的四个必填字段**：`should_judge`、`significance`、`belongs_to`、`belong_confidence`，**不读任何可选字段**。**可选字段的去向**——只影响三件事：注入渲染（`reason` 为 `Some` 则渲染“因为 Z”、为 `None` 则退化为无理由格式）、可观测性（按 `capabilities()` 决定是否记录情绪/方向相关指标）、对照实验（按 `capabilities()` 筛选“哪些字段可在两个后端之间对比”）；它们不进入阈值判断、不进入灰区处理、不进入兜底合并、不进入新球创建。

**方案**：**和 `capabilities()` 的配合**——`capabilities()` 显式声明后端能产出哪些可选字段，业务规则层不读它、消费方（渲染、指标、对照实验）读它——两层职责分离：业务规则层管“起不起念、归哪个球”，消费方管“怎么渲染、怎么记录、怎么对比”。边界情况：可选字段为 `Some` 时业务规则层也**不读**——不是“有值就读、无值就跳过”，是“无论有没有值都不读”；如果某个可选字段未来被证明对判别决策有价值（比如“情绪强度”确实影响“值不值得记”），应该把它**提升为必填字段**、所有后端都必须产出，而不是让业务规则层“有条件地读”一个可选字段。

**结论**：业务规则层管“起不起念、归哪个球”，消费方管“怎么渲染、怎么记录、怎么对比”。这是“架构隔离线”在字段读取上的具体落地。

**关联**：Verdict 必填字段、Verdict 可选字段、capabilities()。

## 九、工程约束

### 前缀缓存

**起因**：DeepSeek 等模型的前缀缓存是**字节级最长公共前缀匹配**，任何对前缀区域的修改都会让其后所有缓存作废；一次会话的前缀（system prompt + 工具定义 + 早期历史）通常占输入 token 的绝大多数，如果每轮注入都改前缀，缓存命中率归零、长会话成本飙升。记忆系统的直觉是“想起什么就注入什么”，天然倾向于把记忆插到最相关的位置（比如 system prompt 里强化行为一致性），但这和前缀缓存直接冲突。

**理念**：把动态性全部赶到尾部、前缀只做只读冻结，是唯一能让“仿人脑记忆”和“前缀缓存”共存的方式——不是“完全兼容”，是“有条件兼容”，条件是接受“注入位置只能在尾部”这个约束。代价是注入位置的灵活性丧失——有些记忆系统会把关键记忆放在 system prompt 里以强化模型遵从，尾部注入的“遵从强度”可能弱于 system prompt；这是用“成本可控”换“注入位置受限”、是自觉的取舍。

**解释**：所有动态记忆**只追加在 messages 尾部**，不回写 system prompt、不回写工具 schema、不插入历史中段——这是 DeepSeek 等支持前缀缓存的模型上“注入不使已缓存前缀失效”的前提。**具体做法**——注入以 `role: "user"` 的 ephemeral 消息追加在历史末尾、带 `_ephemeral: true` 标记，**不写入持久 transcript**——下一轮重新召回时重新生成、而不是从历史里读旧的注入块；system prompt 和工具 schema 在会话启动时构建一次、之后逐字节冻结，工具按字典序确定性排序、不依赖插件加载顺序；时间戳、工作目录、git 状态等每轮可能变化的元信息不放前缀、移到尾部消息或配置里。

**方案**：和“流动只点亮、不写入”的关系——流动纯内存、结算才写入，写入的是存储不是上下文；注入是结算后的独立步骤、只追加尾部 ephemeral 消息、不修改任何已存在的字节。边界情况：同一轮多次注入时，多条 ephemeral 消息按顺序追加在尾部、不合并、不重排；注入块内容不影响前缀的字节稳定性、但会增加总输入长度、影响每次请求的输入 token 数和成本——前缀缓存管“不重复计费已缓存的前缀”，注入预算管“新增的尾部别太贵”、两者是不同层面的成本控制；如果宿主客户端在注入后重新序列化 messages、改变了前缀的字节表示（比如重排字段、改变空白），缓存仍会失效——这需要客户端配合，不是记忆系统单方面能保证的。

**结论**：不是“完全兼容”，是“有条件兼容”，条件是接受“注入位置只能在尾部”。这是“把动态性全部赶到尾部”在前缀缓存兼容上的具体落地。

**关联**：napi 进程内、注入预算两种模式、可观测性。

### napi 进程内

**起因**：在线路径需要低延迟、低复杂度。CLI 每次调用要 fork/exec、加载 Rust 运行时、打开 TriviumDB、加载子图，进程启动加数据库打开在冷启动时是几十毫秒级，而**结算必须同步立刻执行、它就是注入决策**，百毫秒级延迟会直接劣化主模型首 token 延迟；常驻守护虽然单写者天然串行化，但引入进程管理、IPC 协议、超时重试、生命周期等一整套复杂度，在单用户、两个客户端的场景下收益不明显。

**理念**：napi 进程内零 IPC、函数调用级延迟；在线走 napi、离线可 CLI，常驻守护不是第一版必需。TriviumDB 原生提供 napi-rs 绑定（`npm install triviumdb` 后直接 `require('triviumdb')`），**不需要自己写 Rust ↔ Node 的胶水层**，存储层的 Node 绑定由上游维护、稳定性由 TriviumDB 保证。

**解释**：在线路径的集成方式——Rust 内核编译为 `.node` 原生模块，由 dsh/pi 的 TypeScript 薄适配层**直接 `require` 调用**，不经过独立进程、不经过 HTTP/IPC——判别器的异步推理、流动的同步结算、注入组装全部在宿主进程内完成、零跨进程通信开销。**性能特征**——napi-rs 的边界开销在“每次调用处理较多工作”时很小，SheetKit 基准显示密集计算场景下 FFI 层额外开销约 3–4ms、比率 1.14–1.20×；但在“极小调用”上开销显著（一个只做加法的函数比纯 JS 慢 19×），plain JS array 的逐元素传递也可能成为瓶颈（18×）。**因此集成设计必须遵守“动词级 API、批量数据、typed array”三条**——`recall`、`judge_turn`、`archive_turn` 是动词级用例、每次调用处理一整轮对话，不是每帧调一次 getter；嵌入向量和 ID 列表用 `Buffer`/`Float64Array` 等 typed array 传递、不用 plain JS array；单次调用内部的工作量远大于边界开销、FFI 成本被摊薄到可忽略。

**方案**：**异步路径**——判别器是异步旁路，napi 的 `#[napi] pub async fn` 配合 `tokio_rt` feature 提供 Tokio 运行时，**自动把 Rust `async fn` 映射为 JavaScript `Promise<T>`**、不阻塞 JS 事件循环；但要注意 `async fn` 里的长时间同步计算仍会占用 Tokio worker 线程，阻塞型 CPU 工作应使用 `tokio::task::spawn_blocking` 或 `AsyncTask` 走 libuv 线程池、而不是在 `async fn` 里直接跑。**在线走 napi、离线巩固可 CLI 化**——离线巩固不要求实时、CLI 的几十毫秒启动开销可接受，且 CLI 作为独立进程隔离复杂度；常驻守护留作多客户端写冲突严重时的逃生舱、不是第一版必需。边界情况：napi 模块需要为每个平台编译 `.node` 产物（macOS x64/arm64、Linux x64/arm64、Windows x64）、用预编译分发机制处理、不是阻塞问题；宿主崩溃（dsh 闪退）会带崩 Rust 内核，但结算走 TriviumDB 事务、崩溃时未提交事务自动回滚、已提交的在 WAL 里、**不会丢数据**，只是正在进行的流动计算丢失、下一轮重来；`#[napi] async fn` 的取消不是自动的（丢弃 JS Promise 不会取消 Rust future），长时操作需要设计显式取消协议。

**结论**：在线走 napi、离线可 CLI，常驻守护不是第一版必需。这是“napi 进程内零 IPC”在集成方式上的具体落地。

**关联**：前缀缓存、模块化、独立测试。

### 模块化

**起因**：工程需要依赖方向单向、核心单份、适配薄壳。`dayu-flow` 的 dev-dependencies 里如果出现 `triviumdb`，就说明流动逻辑依赖了具体存储实现、无法独立测试。

**理念**：`dayu-domain` 零依赖、`dayu-flow`/`dayu-judge` 只依赖 trait、`dayu-core` 唯一组装点、`dayu-napi` 只做 DTO 翻译、`dayu-cli` 唯一允许 `anyhow`；依赖方向由编译期强制。

**解释**：Rust workspace 组织，`dayu-flow` 的 dev-dependencies 里不出现 `TriviumDB`、`dayu-judge` 的默认依赖里不出现 ONNX，依赖方向由编译期强制。**策略 trait 隔离算法变体**——`SupplementStrategy`、`StrengthenStrategy`、`LossModel`、`VerdictPostProcessor` 让“补充规则”“强化规则”“损失模型”“后处理规则”可替换、可对照实验，`ConstantLossModel` 精确复现旧规则用于验证“管道决定损耗”是否真的改变了行为。**feature flag 控制推理后端依赖**——`dayu-judge` 的 `onnx`、`candle`、`model2vec`、`test` feature 按需编译，CI 的快速测试路径只编译 `test` feature、不拉 ONNX Runtime。**独立测试由模块化保证**——每个 crate 的默认 `cargo test` 零真实依赖、秒级完成，`dayu-flow` 用 `TriviumStorage`（临时 `.tdb` 隔离）+ `MockEmbedding` + `MockClock`、`dayu-judge` 用 `MockJudgeBackend`、`dayu-napi` 只测 DTO 转换、`dayu-storage` 用 `tempfile` 隔离；mock 实现放在 `test` feature 下，夹具放在 dev-only 的 `dayu-testkit` crate。**渐进式交付也由模块化支撑**——M1 只有 `dayu-domain` + `dayu-storage` + `dayu-flow`（临时 `.tdb` 测试）+ `dayu-napi` 最小 `recall` API 就能跑通，M2 加嵌入、M3 加判别器，模块之间没有“必须同时完成”的耦合。

**方案**：新增存储后端或推理后端只改 `DayuCore::new` 的构造参数、业务逻辑零改动。

**结论**：新增存储后端或推理后端只改 `DayuCore::new` 构造参数、业务逻辑零改动。这是“依赖方向单向、核心单份、适配薄壳”在模块化上的具体落地。

**关联**：四个核心 trait、策略 trait、独立测试、napi 进程内。

### 四个核心 trait

**起因**：流动和结算需要只依赖 trait、不依赖具体实现。如果 `dayu-flow` 直接 import `TriviumDB` 类型，流动逻辑就无法用临时 `.tdb` 测试、也无法回退到 SQLite。

**理念**：隔离存储、判别、嵌入、时间四个基础设施，让 `dayu-flow` 和 `dayu-core` 的测试可以用四个 Mock 跑在纯内存里、零真实依赖、秒级完成。

**解释**：`dayu-domain` 定义的四个基础设施抽象——**`StorageBackend`**：读写球、管道、内容、冷存储，提供 `get_ball`、`load_subgraph`（加载起点球及 N 跳邻居子图）、`search_by_embedding`（向量检索起始球）、`begin_transaction`（返回 `StorageTx` 用于结算写入），唯一实现是 `TriviumStorage`（生产与测试共用，测试经 `TempDir` 隔离，不存在内存替身）；它不暴露 TriviumDB 的 TQL 或 Node/Edge 细节、只暴露领域语义的方法。**`JudgeBackend`**：判别器后端，提供 `judge(input) -> Verdict`、`producer() -> VerdictProducer`、`capabilities() -> JudgeCapabilities`，实现有 `EmbeddingRuleBackend`（当前路径）、`DecisionModelBackend`（未来预留）、`MockJudgeBackend`（测试）；它不暴露 ONNX Session 或 tokenizer 细节、只暴露“给定输入返回判定”的契约。**`EmbeddingBackend`**：把文本变成向量，提供 `embed_batch(texts) -> Vec<Vec<f32>>`、`dimension() -> usize`，实现有 `OrtEmbeddingBackend`（ONNX）、`MockEmbeddingBackend`（测试，固定向量或确定性向量）；`dimension()` 让 `DayuCore` 启动时校验嵌入维度与球存储的向量维度一致、不匹配则启动失败。**`Clock`**：提供 `now() -> DateTime<Utc>`，实现有 `SystemClock`（生产，调 `Utc::now()`）和 `MockClock`（测试，可快进 180 天验证归档触发、快进 90 天验证管道衰减）；所有时间计算——`ball_effective_size`、`pipe_effective_thickness`、`ball_stability` 衰减、`blocked_pass_count` 衰减、归档判定——都通过 `Clock`、不直接调 `Utc::now()`，保证测试时间完全可控。

**方案**：四个 trait 的分工——`StorageBackend` 管“数据从哪来、到哪去”，`JudgeBackend` 管“判别逻辑用哪个后端”，`EmbeddingBackend` 管“文本怎么变成向量”，`Clock` 管“现在是几点”；它们共同让 `dayu-flow` 和 `dayu-core` 的测试可以用 `TriviumStorage`（临时 `.tdb`）+ `MockJudgeBackend` + `MockEmbeddingBackend` + `MockClock` 跑在隔离环境里：零外部依赖（无网络、无模型、无 Node），全量约 9 秒。边界：trait 方法只暴露领域语义、不暴露具体实现的类型；`StorageBackend` 的 `begin_transaction` 返回 `Box<dyn StorageTx>`、结算在事务内完成所有写入、提交或回滚；`JudgeBackend` 是 sealed trait（下游不可实现、只能使用），后端集合封闭、适合枚举分派；`Clock` 是唯一的时间源，任何直接调 `Utc::now()` 的代码都是 bug。

**结论**：`dayu-flow` 和 `dayu-core` 的测试可以用四个 Mock 跑在纯内存里、零真实依赖、秒级完成。这是“隔离存储、判别、嵌入、时间”在 trait 设计上的具体落地。

**关联**：模块化、策略 trait、独立测试。

### 策略 trait

**起因**：同一流程内需要换算法变体、做对照实验。如果补充规则、强化规则、损失模型、后处理规则都硬编码在引擎里，做 A/B 实验就要改引擎代码、风险高。

**理念**：引擎主流程不变、只换策略实现——`FlowEngine` 和 `SettleEngine` 的流动、分配、判断、结算顺序不变，`SupplementStrategy` 只换“补充多少”、`StrengthenStrategy` 只换“强化多少”、`LossModel` 只换“损失多少”、`VerdictPostProcessor` 只换“后处理规则”；每个策略 trait 都有默认实现、默认实现是生产路径，替代实现主要用于对照实验和特定场景适配。

**解释**：`dayu-flow` 和 `dayu-judge` 内部定义的四个算法变体抽象——**`SupplementStrategy`**：计算球释放的补充量，默认实现是“资格 + 幅度”两段式（`ball_effective_size × (相关性 - supplement_threshold)/(1 - supplement_threshold)`，过资格阈值才补充），替代实现可以是线性补充（用于对照实验）、无补充（用于验证“补充是否必要”）；`FlowEngine` 持有 `Arc<dyn SupplementStrategy>`、默认用两段式。**`StrengthenStrategy`**：计算球和管道的强化增量，默认实现是“路径相关性 × 系数 + 球的边际递减、管道封顶”，替代实现可以是线性强化（无边际递减）、恒定强化（用于对照实验）；它让“强化规则”的 A/B 实验不需要改结算引擎代码。**`LossModel`**：计算每跳损失，默认实现是 `PipeWeightLossModel`（`loss = min(base_loss × (1 + loss_pipe_factor × (1 - pipe_effective_thickness)), loss_max)`，管道越细损失越大），替代实现是 `ConstantLossModel`（损失恒等于 `base_loss`，精确复现旧规则）；`ConstantLossModel` 的存在是为了验证“管道决定损耗”这个修正在当前参数下是否真的改变了行为——如果两种损失模型跑出来的召回质量没有差异，说明这个修正被其他机制掩盖了、需要检查，而不是假设它一定有效。**`VerdictPostProcessor`**：对原始 `Verdict` 做后处理（阈值、灰区、兜底合并），默认实现是“显著性过固化阈值才保留、归属置信度 0.5–0.7 走 tentative、与已有球余弦 > 0.95 兜底合并”，替代实现可以是“不同场景不同阈值”（编程场景宽松、量化场景严格），让后处理规则成为配置项而不是代码分支。

**方案**：**和“四个核心 trait”的分工**——核心 trait 隔离基础设施（存储、判别、嵌入、时间），策略 trait 隔离算法变体（补充、强化、损失、后处理）——前者是“数据从哪来、用哪个后端”，后者是“同一流程内换算法”。**和“可观测性”的配合**——每个策略实现带 `producer` 或 `strategy_kind` 标签、指标按策略打标签、对照实验按策略分组统计——`ConstantLossModel` 和 `PipeWeightLossModel` 的指标分开记，能对比“管道决定损耗”是否真的改变了召回质量。边界：策略 trait 不暴露具体实现的类型、只暴露“输入参数、返回标量”的契约；默认实现是生产路径，替代实现默认关闭、通过配置启用；策略 trait 不改变流动和结算的顺序、只改变某一步的计算方式。

**结论**：策略切换只改配置不改代码，默认实现是生产路径、替代实现默认关闭。这是“引擎主流程不变、只换策略实现”在策略 trait 上的具体落地。

**关联**：四个核心 trait、可观测性、模块化。

### 独立测试

**起因**：测试需要零真实依赖、秒级完成。如果每个 crate 的测试都要拉起真实数据库、加载模型文件、启动 Node 运行时，开发者的本地反馈循环会从秒级变成分钟级、CI 会被大文件拖慢。

**理念**：每个 crate 的默认 `cargo test` 都**零真实依赖、秒级完成**，不拉起其他 crate、不碰真实数据库、不加载模型文件、不启动 Node 运行时——这是由“模块化 + Mock 实现 + feature gate + 依赖方向”共同保证的工程事实、不是约定。

**解释**：具体分工——`dayu-flow` 用 `TriviumStorage`（临时 `.tdb`）+ `MockEmbeddingBackend` + `MockClock`，不 import TriviumDB 的类型——它的 `dev-dependencies` 里不出现 `triviumdb`、只出现 `dayu-storage` 的 `test-support` feature，编译期强制；`dayu-judge` 默认用 `MockJudgeBackend` 预设 `Verdict` 或预设错误，覆盖阈值、灰区、归属、兜底合并、解析失败丢弃等业务逻辑、不加载任何模型；`dayu-napi` 只测 DTO ↔ 领域类型的转换，不启动 Node、不加载 `.node`、不调 `#[napi]` 函数；`dayu-storage` 用 `tempfile::tempdir()` 创建临时 `.tdb`，每个测试一个独立目录、并行跑不冲突、永远不碰 `~/.dayu/store.tdb`；`dayu-domain` 测 newtype 构造验证、枚举 `Display`、错误 `From` 转换、零依赖；`dayu-config` 测 TOML 解析、非法配置拒绝、热更新生效、零依赖；`dayu-observability` 用 `MockMetricsRecorder` 断言指标被记录、诊断规则纯函数测试、不启动 Prometheus；`dayu-cli` 用临时 `.tdb` + `MockJudge` 跑端到端巩固流程、不连生产库。

**方案**：**Mock 实现放在 `test` feature 下**——`MockJudgeBackend`、`MockEmbeddingBackend`、`MockClock`、`MockMetricsRecorder` 只在测试或下游测试中编译、不进生产依赖树；夹具放在 dev-only 的 `dayu-testkit` crate（`publish = false`），提供 `sample_ball()`、`build_chain_graph()` 等辅助函数，多个 crate 的测试共用同一套夹具、但各自创建独立实例、零共享状态。**真实依赖的测试用 `#[ignore]` 标记**——ONNX 推理冒烟测试、真实模型加载测试、大规模存储测试标记为 `#[ignore]`，默认 `cargo test --workspace` 跳过、只在专用 CI job 或手动 `cargo test -- --ignored` 时跑；模型文件（pizza 的 91 MB、bge-m3 INT8 的 543 MB）不进入默认测试路径、CI 不会被大文件拖慢。**确定性与并行安全**——嵌入用 `MockEmbeddingBackend::deterministic` 按文本 hash 生成向量、同一文本永远同一向量；ID 用 `BallId::from_u64(1)` 构造固定值、不调 `Uuid::new_v4()`；时间用 `MockClock` 固定初始时间、不调 `Utc::now()`；配置用 `sample_config()` 返回固定值、不从文件加载；每个测试创建自己的临时 `.tdb`、`MockClock`、`MockJudgeBackend`，测试之间零共享、`cargo test` 默认多线程并行不冲突。**CI 分层**——快速单元测试 `cargo test --workspace` 预期 15 秒内跑完（真实 `.tdb` 落盘，不再是微秒级）、零网络零模型零 Node；存储集成测试 `cargo test -p dayu-storage` 用临时文件、无需网络；ONNX 冒烟测试 `cargo test -p dayu-judge -- --ignored` 需预下载模型、只在专用 job 跑；PR 的默认门禁只跑快速单元测试和属性测试，不下载模型、不碰 TriviumDB 文件、不启动 Node，任何开发者本地 `cargo test --workspace` 都能在 10 秒内得到反馈。**属性测试覆盖不变量**——用 `proptest` 随机生成输入，断言“球大小非负且不超 `ball_size_ceiling`”“管道 `pipe_base_thickness ∈ (0,1]`”“水量非负”“损失随 `pipe_effective_thickness` 非严格单调递减”“分配守恒”等物理不变量，比手写用例更能覆盖边界。边界：`dayu-flow` 的 `dev-dependencies` 里不出现 `triviumdb`、`dayu-judge` 的默认依赖里不出现 `ort`，依赖方向由编译期强制；任何超过 10 秒的默认测试要么被 `#[ignore]` 标记、要么说明它依赖了不该依赖的东西；`dayu-testkit` 是 dev-dependency、不进生产依赖树。

**结论**：任何开发者本地 `cargo test --workspace` 都能在 10 秒内得到反馈。这是“零真实依赖、秒级完成”在独立测试上的具体落地。

**关联**：模块化、四个核心 trait、策略 trait。

### 配置化

**起因**：系统几乎所有系数、阈值、预算、衰减参数都需要可调。如果硬编码在代码里，调参就要改代码、重新编译、重新部署，迭代速度慢、风险高。

**理念**：不改代码就能调参、热更新不重启、配置版本化可回滚；所有系数进 TOML，`arc-swap` 热更新、流动和结算在每次调用入口读当前快照；`config_version` + `param_change_log` 审计；安全边界——单次变更幅度 ≤ 20%、`cooldown` 24 小时、建议不超 `min/max`。

**解释**：流动层的 `base_loss`/`loss_pipe_factor`/`loss_max`/`flow_continuation_threshold`/`supplement_threshold`/`start_ball_threshold`/`start_top_n`/`strong_cue_threshold`/`strong_cue_multiplier`/`max_flow_depth`/`max_lit_ball_count`/`split_mode`，结算层的 `strengthen_eligibility_threshold`/`min_strengthen_value`/`discount_per_hop`/`min_discount`/`size_strengthen_factor`/`pipe_strengthen_factor`/`flow_context_blend_alpha`/`atomistic_settle`/`conflict_strategy`，注入层的 `injection_mode`/`token_budget`/`tokens_per_size`/`max_balls_per_inject`/`token_hard_cap`/`sort_exponent_a`/`sort_exponent_b`/`render_clear_threshold`/`render_impression_threshold`，球与管道的 `ball_size_ceiling`/`size_saturation_gamma`/`ball_stability_ceiling`/`ball_stability_decay`/`pipe_stability_base`/`pipe_stability_growth`/`blocked_discount`/`blocked_cap`/`blocked_decay`/`pipe_thickness_ceiling`，规模管理的 `max_ball_count`/`archive_inactive_days`/`archive_size_threshold`/`max_active_balls`/`cold_content_max_gb`，全部可在 TOML 里配。

**方案**：**热更新不重启**——配置以 `arc-swap`（或 `tokio::sync::watch`）加载为全局只读快照，流动和结算在**每次调用的入口处读当前快照**、不在函数内部多次读；变更通过管理 API 或文件监听触发 `arc-swap` 更新，不重启 napi 模块、不中断主对话；**结算的事务边界内使用同一个配置快照**，不会出现“流动用旧配置、结算用新配置”的撕裂。**配置版本化与审计**——每次变更生成一个 `config_version`、写入 `param_change_log` 表，记录 `{version, timestamp, parameter, old_value, new_value, trigger_signal, operator}`，与 `correction_log` 遵循同一套“审计先行、原值快照、可追溯、可回滚”的模式；指标按 `config_version` 打标签，调参前后的效果可以直接在 Prometheus 中按版本切片对比；某个版本的 `path_supplement_loss_ratio` 或 `injection_confidence_tier` 出现显著退化时、**按版本回滚**，而不是在海量日志里猜。**安全边界**——单次变更幅度 ≤ 当前值的 20%（可配）、超出需显式确认；同一参数在 `cooldown`（默认 24 小时）内不接受第二次自动建议；建议器不能建议超出 `min/max` 范围的值、越界拒绝；所有诊断规则带 `window` 和 `min_samples`、样本不足不触发；配置变更与 `param_change_log` 写入同一事务、失败回滚；配置变更**不触发前缀重建**、注入预算变更只影响尾部。**配置校验**——`ball_size_ceiling > 0`、`token_budget > 0`、`base_loss + base_loss × loss_pipe_factor < 1.0`、`base_loss × (1 + loss_pipe_factor) ≤ loss_max`（若要求严格单调）、`min_discount ∈ [0,1]`、`discount_per_hop ≥ 0`、`supplement_threshold ≥ flow_continuation_threshold`（建议）、`ball_stability_decay > 0`、`blocked_decay > 0`、`strong_cue_threshold ≥ start_ball_threshold`、`render_clear_threshold > render_impression_threshold`，非法组合在加载时拒绝、不进入运行时。**默认配置可跑**——不提供任何配置文件时用默认值能跑通全流程，默认值是保守起点、不是最优值，调参靠诊断规则和对照实验、不靠拍脑袋。边界：配置分文件加载（`flow.toml`、`settle.toml`、`judge.toml`、`storage.toml`、`scale.toml`）或单文件分区、结构清晰、便于版本管理；配置变更不改变 schema、不触发数据迁移；`arc-swap` 快照是只读的、流动和结算不修改快照。

**结论**：所有系数可配、默认配置可跑、热更新不重启、按版本回滚。这是“不改代码就能调参”在配置化上的具体落地。

**关联**：诊断规则、可观测性、策略 trait。

### 可观测性

**起因**：可观测性在这个项目里不是监控面板、是**证伪工具**——它让“动力学扩散是否优于查询检索”“阻力上限是否制造假阳性唤醒”“路径级强化是否导致联想僵化”这些概念赌注能被数据回答。没有这层可观测性，大禹就永远只是一个“概念上优雅”的提案，有了它至少这个提案有机会被数据支持或被数据推翻——而一个能被推翻的提案，比一个只能被欣赏的提案有价值得多。

**理念**：可观测性在**架构阶段**就要求“主路径可被旁路观测”——同一 `recall` 请求同时跑水流扩散和向量 Top-K、记录两套点亮集合和注入块、不影响主路径注入；这要求 `FlowEngine` 和“向量 Top-K 基线”共享同一份子图快照、分别计算、分别记录，如果当初把 `recall` 设计成“只能走水流一条路”，这个对照就做不了。**激活性价比不做在线指标、改为保留 `activation_log` 快照**（点亮集合、每条路径的 `semantic_similarity` 和路径折扣、注入块完整文本、注入 token 数、起始球和注水量分配），由用户后续用 AI 从 DB 检索判定；“不遗漏”同样不在线加规则、离线发现系统性遗漏后调配置。

**解释**：技术栈用 Rust 标准三件套——`tracing`（结构化日志/追踪，span 创建开销约 50ns）+ `metrics`（指标门面，记录延迟约 10μs）+ `metrics-exporter-prometheus`（独立端口暴露 `/metrics`，Prometheus 拉取）；开销相对于流动与结算的毫秒级预算可忽略、不需要为性能削减观测点；TriviumDB 的 `runtime.stats()`、`db.instance_stats()`、`search_with_context` 返回的 `ef_search`/`node_count`/`estimated_heap_bytes` 直接接入，存储层第一手数据不在应用层重新发明。**指标矩阵按水利模型分层**——流动层（`flow_trigger_rate` 有输入但无球超起始阈值的比例、`lit_balls_per_flow` 单次点亮球数分布、`flow_depth_reached` 实际深度分布、`path_supplement_loss_ratio` 补充/损失比的逐跳分布——这是调参核心信号，中位数长期 <1 说明补充规则太保守、长期 >2 说明可能陷入局部强化循环）；管道层（`pipe_pass_rate` 按年龄/粗细分桶的通过率、`pipe_blocked_rate` 被阻挡比例、`pipe_thickness_distribution` 粗细分布、`pipe_creation_by_source` 四条来源的计数——如果 90% 来自 `new_ball`、共激活和离线补边几乎不触发，说明图结构在“新建时一次性定型”、缺少后续演化）；结算层（`settle_increment_distribution` 球大小增量分布、`settle_firm_vs_min_count` 强化球与最低强化球比例、`settle_version_conflict_rate` 版本冲突频率、`size_saturation_rate` 触及 `ball_size_ceiling` 的球比例）；注入与判别层（`injection_token_used` 实际注入 token 分布、`injection_ball_count` 注入球数分布、`injection_confidence_tier` 清晰/印象档占比、`judge_confidence_distribution` 归属置信度分布、`judge_parse_failure_rate` JSON 解析失败率超过 5% 触发告警）；存储层（`active_ball_count`/`archived_ball_count` 规模、`resource_memory_bytes` 内存采样、`quiver_ef_search` 实际搜索宽度、`wal_size_bytes` WAL 增长）。

**方案**：**假设检验指标**（区别于系统健康指标）——对照实验的召回差异（扩散是否召回了 Top-K 漏掉的相关记忆）、唤醒质量审计（每次“强线索突破低阻力管道”的唤醒记录线索文本、被唤醒球、事后标注的真实相关性，断言“突破阻力”的唤醒中高相关占比不低于常规唤醒）、路径多样性（连续 N 次激活中被点亮路径的重复率、新路径发现率、老路径和新路径各自的注入命中率——如果重复率持续上升而命中率不升，说明系统在走老路）、方向不对称性（同一对球在“A→B 语境”和“B→A 语境”下被激活的频率差异，如果差异显著说明方向信息重要、无向是过度简化）。**动态调参闭环**——确定性诊断规则（不依赖 ML）把指标映射为结构化建议：`path_supplement_loss_ratio` 中位数长期 <0.5 → 建议降低 `base_loss` 或提高 `max_supplement_ratio`；`pipe_blocked_rate` 持续 >0.6 → 建议降低 `pipe_stability_growth` 或提高 `blocked_discount`；注入 token 长期贴预算上限或注入球数长期顶满 → 建议收紧 `strengthen_eligibility_threshold` 或重新校准判别器；每条规则带 `window` 和 `min_samples`、样本不足不触发、输出 `{rule_id, metric, current_value, suggested_direction, severity}` 写入 `diagnostics.jsonl`，第一版**只建议不自动执行**、由开发者或用户确认后变更配置；配置变更走 `arc-swap` 热更新、写 `param_change_log`、按 `config_version` 打标签、支持按版本回滚——和“纠正审计”同构，系统对“自身状态的修改”和“记忆的修改”都保持可审计。**关键原则**——指标记录是异步的、不进入结算事务的同步路径；对照实验的观测要求 `recall` 能被旁路调用、这反过来影响架构设计。边界：指标按 `producer`/`strategy_kind`/`config_version` 打标签、对照实验按标签分组；`/metrics` 端点独立端口、不阻塞主路径；诊断规则输出到 `diagnostics.jsonl`、不自动改配置；指标采样率可配、高基数指标做聚合避免 Prometheus 压力。

**结论**：可观测性在架构阶段就要求“主路径可被旁路观测”；在线只保留数据、离线做判定和调参；没有这层可观测性，大禹就永远只是一个“概念上优雅”的提案。这是“可观测性是证伪工具”在工程约束上的具体落地。

**关联**：诊断规则、配置化、activation_log、对照实验。

### 诊断规则

**起因**：指标异常时需要结构化的调参建议。如果只靠“看 Grafana 图、觉得差不多就改一改”，调参没有数据支撑、不可审计、不可回滚。

**理念**：确定性规则、不依赖 ML、只建议不自动执行——第一版不需要强化学习调参，确定性规则可解释、可审计、可回滚；规则本身可配置、可增删、可调整阈值，不需要改代码；如果未来数据显示某类规则的误报率过高，可以调整阈值或 `window`，而不是重新训练模型。

**解释**：诊断规则是确定性的、可配置的规则集合，把可观测性指标映射为结构化的调参建议——它回答“当前指标异常，可能是哪个参数偏了、往哪个方向调”。**规则结构**——每条规则包含 `rule_id`、监控的 `metric`（可带标签过滤，如 `injection_confidence_tier{label=clear}`）、比较操作（`<`/`>`/`ratio`）、阈值、`window`（观察窗口，如 `7d`/`3d`/`1d`）、`min_samples`（样本不足不触发）、`suggestion`（建议方向，如“考虑降低 `base_loss` 或提高 `max_supplement_ratio`”）、`severity`（严重程度）。**典型规则**——`path_supplement_loss_ratio` 中位数长期 < 0.5 → 建议降低 `base_loss` 或提高 `max_supplement_ratio`；`pipe_blocked_rate` 持续 > 0.6 → 建议降低 `pipe_stability_growth` 或提高 `blocked_discount`；注入 token 长期贴预算上限或注入球数长期顶满 → 建议收紧 `strengthen_eligibility_threshold` 或重新校准判别器；`settle_version_conflict_rate` 异常升高 → 建议检查多客户端并发或调整 `busy_timeout`；`size_saturation_rate` 过高 → 建议调高 `ball_size_ceiling` 或降低 `size_strengthen_factor`；`judge_parse_failure_rate > 5%` → 告警，建议检查判别器后端或 prompt。**输出格式**——每条触发的规则输出 `{rule_id, metric, current_value, threshold, suggested_direction, severity, window, timestamp}`，写入 `diagnostics.jsonl`，供开发者或用户查看、确认后手动变更配置；不自动改配置、不自动回滚、不自动调参。

**方案**：**安全边界**——建议器**不能建议超出 `min/max` 范围的值**、越界拒绝；单次变更幅度 ≤ 当前值的 20%（可配）、超出需显式确认；同一参数在 `cooldown`（默认 24 小时）内不接受第二次自动建议、防止反复建议、反复调参；所有规则带 `window` 和 `min_samples`、样本不足不触发、防止冷启动阶段误报。**和“动态调参闭环”的关系**——诊断规则是闭环的“诊断”环节：信号采集（指标）→ 诊断规则（结构化建议）→ 配置热更新（`arc-swap`）→ `param_change_log` 审计 → 按 `config_version` 回滚；规则只负责“诊断”、不负责“执行”，执行由开发者或用户确认后手动完成，第一版**不引入自动执行**。**和“纠正审计”的同构**——参数变更走 `param_change_log`，记录 `{change_id, parameter, old, new, reason, trigger_metric, trigger_value, config_version, reversible}`，和 `correction_log` 遵循同一套“审计先行、原值快照、可追溯、可回滚”的模式——系统对“自身状态的修改”和“记忆的修改”都保持可审计。边界：规则输出到 `diagnostics.jsonl`、不自动改配置；规则本身进 TOML 配置、可增删改；`severity` 分 `info`/`warning`/`critical`，`critical` 触发告警、`warning` 进建议列表、`info` 仅记录；多条规则同时触发时按 `severity` 排序、不合并。

**结论**：规则只负责“诊断”、不负责“执行”，执行由开发者或用户确认后手动完成。这是“确定性规则、只建议不自动执行”在诊断规则上的具体落地。

**关联**：可观测性、配置化、审计先行。

## 十、已废弃 / 已修正条目

| 条目 | 状态 | 修正说明 |
|---|---|---|
| **管道健康因子** | 已废弃 | 与水量同类二次计权、形成粗管正反馈；`pipe_effective_thickness` 已在流动阶段决定阻力与损耗，再乘进相关性是同一信号第二次计权；修正后路径折扣只含跳数折扣、不含任何 `pipe_effective_thickness` 相关因子、连默认关闭的开关都不留。 |
| **相关性含水量** | 已修正 | 水量是动力学量、不是语义相关性乘数；修正后相关性 = 语义相似度 × 路径折扣。 |
| **新鲜度乘三次** | 已修正 | 收敛到 `ball_effective_size` 只算一次；存储只存 `ball_stored_size`、读取时算一次 `ball_effective_size`、所有消费方共用。 |
| **每球各拿满总水量预算** | 已修正 | 改为总量守恒按余弦占比分配；`water_i = total_water_budget × cosine_i / Σcosine_j`。 |
| **回边参与分配** | 已修正 | 分配时排除已访问出边；只流向未访问出边、传播能力恢复。 |
| **管道有向权重** | 已废弃 | 改为无向共享；一根管子一个 `pipe_base_thickness`、一个 `blocked_pass_count`、一个 `last_flowed_at`、A↔B 共享。 |
| **管道阈值开关** | 已废弃 | 改为阻力有上限、强线索可突破；管道是阻力不是开关。 |
| **流动即写入** | 已修正 | 流动只点亮、结算才强化；流动纯内存、结算一次激活一次事务。 |
| **结算异步** | 已修正 | 结算同步立刻执行；结算 = 注入决策、同一同步步骤完成。 |
| **语义粗筛丢候选** | 已修正 | 对话消息全量判别；粗筛只保留结构性去重、且只作用于工具结果。 |

| **原型双层节点** | 已废弃 | 改为球—管—水单层模型；语义相近的球靠管道连接、不靠归并合并。 |
| **念想命名** | 已废弃 | 改名大禹水利记忆网络；模型核心是水文物理过程、名字体现“疏而不堵”。 |
| **blocked_pass_count 不随时间衰减** | 已修正 | 改为随时间按曲线速减；存储 `blocked_pass_count_stored` 和 `last_blocked_at`、读取时算有效值、结算时先衰减再叠加写回。 |
| **稳定性只增不减** | 已修正 | 改为饱和增长 + 长期不活动衰减；存储 `ball_stability_stored` 和 `last_watered_at`、读取时算 `ball_effective_stability`、结算时先衰减再叠加写回。 |
