## 关键决策确认

1. **在线只走 napi 进程内**，不走 CLI、不走守护进程；结算同步立刻执行，注入不异步。
2. **存储只用 TriviumDB**，不引入 SQLite、不引入独立向量库；接受其生态早期风险，用 trait 抽象保留回退可能。
3. **离线巩固可 CLI 化**，与在线路径隔离；写冲突频率低，可接受。
4. **判别器异步旁路**，不参与流动与结算；后端可替换，不绑定单一推理框架。
5. **所有系数配置化**，包括流动损失、强化阈值、路径折扣、注入预算、饱和参数、归档阈值、管道创建/衰减/阻塞参数。
6. **压缩插件只是可选适配器**，没有它系统完整运行；核心依赖树 CI 检查，禁止反向依赖。

## 一、流动与结算：用 typestate 把“阶段顺序”钉进类型

### 问题

流动和结算是两个严格顺序的阶段：流动只点亮、不写入；结算必须等流动结束后执行，且结算本身就是注入决策。如果用普通 struct + 运行时布尔标记（`is_settled: bool`），“先结算后流动”或“流动未结束就结算”只能在运行时报错，代码阅读者需要追踪 flag 才能理解顺序约束。

### 适用模式：Typestate

Typestate 用不同泛型参数表示不同状态，状态转换消耗旧类型、返回新类型，非法转换是**编译错误**。对于流动/结算，这能把“阶段顺序”从注释变成类型约束。

```rust
use std::marker::PhantomData;

pub struct Flowing;
pub struct Settling;

pub struct FlowEngine<Phase> {
    lit_balls: Vec<LitBall>,
    paths: Vec<FlowPath>,
    _phase: PhantomData<Phase>,
}

impl FlowEngine<Flowing> {
    pub fn start(start_balls: Vec<BallId>) -> Self { /* ... */ }

    /// 流动结束，消耗 Flowing，返回 Settling。
    /// 调用方不可能在 Flowing 上直接拿到注入结果。
    pub fn finish_flow(self) -> FlowEngine<Settling> {
        FlowEngine {
            lit_balls: self.lit_balls,
            paths: self.paths,
            _phase: PhantomData,
        }
    }
}

impl FlowEngine<Settling> {
    /// 结算 + 注入，消耗 Settling，返回注入块。
    /// 不存在“在 Flowing 上调用 settle”的路径。
    pub fn settle_and_inject(self, ctx: &Context) -> Vec<InjectionBlock> {
        // 结算写入 + 渲染注入，同一同步步骤
        todo!()
    }
}
```

**可读性收益**：函数签名本身说明了“流动 → finish_flow → 结算 → 注入”的合法顺序。新成员阅读 `settle_and_inject` 的 `self` 类型时，立刻知道它只能接在 `finish_flow()` 之后。这比在函数体里用 `assert!(self.flow_finished)` 可读得多，而且零运行时开销（`PhantomData` 是 ZST）。

**注意**：Typestate 不要粒度太细。“流动中”和“已结算”两个状态就够了，不必把“起始球加载”“第一跳”“补充计算”都拆成类型，否则正常控制流会变成一串单方法类型的迷宫。

## 二、判别器：用 sealed trait + 枚举配置约束后端，而不是裸 trait object

### 问题

判别器需要可替换后端（嵌入规则 / 决策模型 / 测试，未来可能还有别的）。如果直接暴露 `pub trait JudgeBackend { ... }` 给下游，下游可以任意实现，你就失去了对后端集合的控制；如果全部用泛型 `<B: JudgeBackend>`，热路径性能好但调用方代码会被泛型参数污染。

### 适用模式：Sealed Trait + 枚举分派

Sealed trait 让 trait “可被使用但不可被下游实现”，这样你可以随时给 trait 加方法而不会破坏下游。后端集合是**封闭的、已知的**，正好适合枚举分派——编译期 `match`，没有 vtable 间接调用，且对缓存友好。

```rust
mod backend_sealed {
    pub trait Sealed {}
}

/// 判别器后端。下游不能实现，只能使用。
pub trait JudgeBackend: backend_sealed::Sealed + Send + Sync {
    fn judge(&self, input: &JudgeInput) -> Result<Verdict, JudgeError>;
}

// 具体后端不暴露构造细节，只通过工厂返回枚举。
pub enum BackendKind {
    EmbeddingRule(EmbeddingRuleBackend),   // 嵌入余弦 + 阈值规则（默认）
    DecisionModel(DecisionModelBackend),   // 预留：决策专用模型
    Test(MockJudgeBackend),                // 测试
}

impl JudgeBackend for EmbeddingRuleBackend {
    fn judge(&self, input: &JudgeInput) -> Result<Verdict, JudgeError> { /* ... */ }
}
impl JudgeBackend for DecisionModelBackend { /* ... */ }
impl JudgeBackend for MockJudgeBackend { /* ... */ }
impl backend_sealed::Sealed for EmbeddingRuleBackend {}
impl backend_sealed::Sealed for DecisionModelBackend {}
impl backend_sealed::Sealed for MockJudgeBackend {}

/// 判别器的持有形态：枚举分派，不暴露 dyn。
pub struct Judge {
    backend: BackendKind,
}

impl Judge {
    pub fn judge(&self, input: &JudgeInput) -> Result<Verdict, JudgeError> {
        match &self.backend {
            BackendKind::EmbeddingRule(b) => b.judge(input),
            BackendKind::DecisionModel(b) => b.judge(input),
            BackendKind::Test(b) => b.judge(input),
        }
    }
}
```

**可读性收益**：读者一眼看到只有三种后端，`match` 的三个分支就是全部合法路径。不需要在文档里写“请不要实现这个 trait”，也不会出现运行时 “unknown backend” 的枚举解析错误。如果未来要加 `HttpBackend`，只需加一个枚举变体和 `match` 分支，类型系统会强制你处理完整——这是**封闭世界设计**的可读性优势。

**如果你确实需要开放扩展**（比如第三方想接自己的推理框架），再退回到 `Box<dyn JudgeBackend>`；但在你的单用户、两个客户端的场景里，封闭集合更可读、更安全。

## 三、球的 ID 与标量：用 newtype 消灭“单位混淆”和“非法值”

### 问题

系统里有多种 ID（球 ID、边 ID、内容 ID、回合 ID）和多种标量（水量、球大小、管道粗细、相关性）。如果全部用 `String` / `f64`，代码里出现 `fn connect(a: String, b: String)` 时，阅读者无法知道两个参数是不是同一种 ID；`fn adjust(w: f64, size: f64)` 时，也无法从类型判断“谁该在 [0,1]、谁该在 [0,size_max]”。

### 适用模式：Newtype + “Parse, don’t validate”

Newtype 为每种 ID 和受约束标量建立独立类型，构造时验证，持有即合法。

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct BallId(u64);           // 内部用整数或 UUID，不暴露构造

#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct PipeId(u64);

/// 管道粗细：构造时保证在 (0, 1]。
#[derive(Clone, Copy, Debug)]
pub struct PipeWeight(f64);

impl PipeWeight {
    pub fn new(raw: f64) -> Result<Self, ValueError> {
        if raw > 0.0 && raw <= 1.0 {
            Ok(Self(raw))
        } else {
            Err(ValueError::OutOfRange)
        }
    }
    pub fn get(self) -> f64 { self.0 }
}

/// 球大小：构造时保证非负；上限由 size_max 在写入时 clamp。
#[derive(Clone, Copy, Debug)]
pub struct BallSize(f64);

impl BallSize {
    pub fn new(raw: f64) -> Result<Self, ValueError> {
        if raw >= 0.0 { Ok(Self(raw)) } else { Err(ValueError::Negative) }
    }
}
```

**可读性收益**：`fn create_pipe(a: BallId, b: BallId, w: PipeWeight)` 的签名自解释。读者不需要翻文档确认 “a 和 b 是不是同一种 ID”“w 的范围是什么”。`PipeWeight::new` 是唯一入口，`get()` 返回的 `f64` 在持有 `PipeWeight` 期间永远合法——后续流动代码里不需要反复 `assert!(w > 0.0)`。

**边界建议**：只给**跨模块传递、容易混淆**的值做 newtype。局部计算中的中间变量不需要 newtype，否则会产生大量 `into_inner()` 噪音。球 ID、边 ID、`PipeWeight`、`BallSize`、`WaterAmount` 这几个是甜点区；循环下标、临时求和值不必包装。

## 四、流动的逐跳计算：用迭代器管道代替手工循环

### 问题

流动本质是一条流水线：当前水量 → 扣损失 → 比较阻力 → 通过则计算补充 → 更新下一跳水量。如果写成嵌套的 `for` + `if` + 可变累加器，代码会充满中间状态，读者需要在大脑中模拟变量变化。

### 适用模式：Iterator 管道 + `scan` / `map` / `filter`

Rust 的迭代器管道天然适合“带状态的逐元素转换”。`scan` 携带累加状态，`filter` 处理“阻力不足则停止该方向”的规则，每个阶段语义单一。

```rust
/// 沿一条出边方向逐跳推进，直到水量不足以通过或达到深度上限。
/// 管道粗细 w_eff 同时决定阻力和损耗——粗管好过且损耗小，细管难通过且损耗大。
fn flow_along_path(
    start_water: f64,
    pipes: impl Iterator<Item = PipeSnapshot>,
    loss_model: &dyn LossModel,
    cfg: &FlowConfig,
    max_depth: usize,
) -> Vec<LitStep> {
    pipes
        .take(max_depth)
        .scan(start_water, |water, pipe| {
            let w_eff = pipe.effective_weight();
            // 损失由管道粗细决定：先扣损、再判断阻力
            let loss = loss_model.loss(w_eff, cfg);
            *water *= 1.0 - loss.get();

            let resistance = 1.0 / (1.0 + w_eff);
            if *water <= resistance {
                // 水不通过，但损失已发生；返回 None 终止该方向
                return None;
            }

            // 通过后：管道变粗（由结算处理，这里只记录），水量变化留给补充阶段
            Some(LitStep { pipe_id: pipe.id, water: *water, passed: true })
        })
        .collect()
}
```

**可读性收益**：`take → scan → collect` 把"深度上限""逐跳损失""阻力比较""终止条件"拆成独立的管道阶段。读者不需要追踪一个 `water` 变量在循环里被修改了多少次；每个阶段的输入输出类型就是它的契约。`LossModel` trait 让损失计算本身可替换——`PipeWeightLossModel` 是默认实现，`ConstantLossModel` 精确复现旧规则用于对照实验。

**注意**：如果补充逻辑复杂（涉及球的可释放水量、相关性系数、补充上限），不要把全部逻辑塞进一个 `scan`。把"流动计算"和"补充计算"拆成两个函数/两段管道，保持每段管道的单一职责。补充阶段需要读取球状态，不适合纯 iterator，可以用 `filter_map` 配合一个只读上下文。补充加在扣损之后：`next_water = water_after_loss + supplement`。

### 多出边分配：先分配、再逐条判断

一个球有多条出边时，水量分配发生在进入 `flow_along_path` **之前**，是一层独立的 `map`——每条出边拿到自己的起始水量，然后各自独立跑逐跳管道。这样“分配”与“推进”职责分离，`flow_along_path` 仍然只处理单条路径。

```rust
/// 球的当前可分配水量按 `1 + w_eff` 加权分到各条出边。
/// 权重取 `1 + w` 而非 `w`：w=0 的管道分到最少但永不为零，
/// 否则分配规则会把细管永久封死，与“阻力不是开关”冲突。
fn split_water(water_available: f64, out_edges: &[PipeSnapshot], cfg: &FlowConfig) -> Vec<f64> {
    match cfg.split_mode {
        SplitMode::Equal => vec![water_available / out_edges.len() as f64; out_edges.len()],
        SplitMode::Weighted => {
            let weights: Vec<f64> = out_edges.iter().map(|p| 1.0 + p.effective_weight()).collect();
            let total: f64 = weights.iter().sum();
            weights.iter().map(|w| water_available * w / total).collect()
        }
    }
}
```

**关键语义**：每条管道用**自己分到的水量**独立判断能否通过；过不去的管道其水量按损失规则损失掉，**不回收**给其他出边（“想不起来就是白费力气”）。`SplitMode::Equal` 仅供对照实验——若加权与平均的召回质量无差异，说明该规则在当前场景不产生实质影响。

## 五、2024 edition 的“消除样板”特性：在正确的地方用，不在错误的地方用

### 5.1 `let-else`：替代“缩进-早返回”

流动和结算中有大量“取出某个值，否则提前返回/跳过”的场景。`let-else` 在 1.65 稳定，2024 edition 下是默认习惯。

```rust
fn settle_ball(ball: &mut Ball, verdict: &Verdict, cfg: &Config) -> Result<(), SettleError> {
    // 不是强化球也不是最低强化球 → 不结算
    let Some(path_corr) = compute_path_correlation(ball, verdict, cfg) else {
        return Ok(());
    };

    // 超过饱和上限 → 增量截断到 0，但仍然刷新 last_watered
    let effective_increment = path_corr * (1.0 - ball.size / cfg.size_max).max(0.0);
    ball.size = (ball.size + effective_increment).min(cfg.size_max);

    Ok(())
}
```

**可读性收益**：`let-else` 让“正常路径”保持在最低缩进层级，“失败分支”集中在 `else` 里。不要用它来处理“失败时返回默认值”的情况——那应该用 `unwrap_or` 或 `match`，`let-else` 的语义是**早返回 / 早跳过**。

### 5.2 原生 `async fn in trait`：判别器异步调用不再需要 `#[async_trait]`

原生 async fn in trait 自 1.75 稳定，覆盖了绝大多数曾经需要 `#[async_trait]` 宏的场景。判别器是**异步旁路**，后端 trait 可以直接写 `async fn`。

```rust
pub trait JudgeBackend: Send + Sync {
    async fn judge(&self, input: &JudgeInput) -> Result<Verdict, JudgeError>;
}
```

**边界**：原生 async trait 目前对 `dyn` 兼容仍需要 workaround（RPITIT 生成的 future 不是 `dyn`-safe）。但你的判别器后端用**枚举分派**（上一节），调用方持有的是具体枚举，不需要 `dyn JudgeBackend`，所以原生 async trait 可以直接用，代码干净。如果某天确实需要 `dyn`，再退回 `async_trait` 或 `Box<dyn Future>`，不要为了“预防未来”提前引入宏。

### 5.3 `RPITIT` / `impl Trait`：减少返回类型的泛型噪音

返回迭代器或 future 的辅助函数，用 `impl Trait` 而不是手写泛型参数。

```rust
/// 返回一个惰性迭代器，调用方不需要写泛型约束。
fn active_balls<'a>(
    store: &'a TriviumStore,
    ids: &'a [BallId],
) -> impl Iterator<Item = BallSnapshot> + 'a {
    ids.iter().filter_map(move |id| store.get_ball(*id).ok())
}
```

**可读性收益**：调用方看到的是 `impl Iterator<Item = BallSnapshot>`，而不是一长串 `FilterMap<Iter<'a, BallId>, ...>`。函数体内部的实现细节（是 `filter_map` 还是 `map` + `flatten`）被隐藏，签名只暴露契约。

## 六、napi 边界：把模式留在 Rust 内核，边界只做 DTO 翻译和错误映射

### 问题

napi 导出的函数如果直接暴露内部类型、或者用 `panic!` 处理可恢复错误，会把“Rust 内核的可读性”和“FFI 边界的安全性”混在一起。napi-rs 的边界应该是**薄且笨**的：接收 JS 友好输入 → 转成内核类型 → 调用内核 → 转回 JS 友好输出。

### 边界约定

**① 只在 `#[napi]` 函数里写 DTO 翻译，不写业务逻辑。**

```rust
#[napi(object)]
pub struct JsRecallInput {
    pub query_embedding: Vec<f32>,
    pub token_budget: u32,
}

#[napi(object)]
pub struct JsInjectionBlock {
    pub text: String,
    pub ball_ids: Vec<String>,
}

#[napi]
pub async fn recall(input: JsRecallInput) -> napi::Result<Vec<JsInjectionBlock>> {
    let core_input = RecallInput {
        query_embedding: input.query_embedding,
        token_budget: input.token_budget as usize,
    };
    let blocks = dayu_core::recall(core_input)
        .await
        .map_err(|e| napi::Error::from_reason(e.to_string()))?;
    Ok(blocks.into_iter().map(Into::into).collect())
}
```

**② 错误一律走 `Result<T>`，不用 `panic!` 处理可恢复错误。** napi-rs 会把 `Err` 转成 JS 异常或 Promise rejection。内核的 `thiserror` 错误在边界被转成 `napi::Error`，内核代码保持自己的错误类型和可读性，边界只做一次映射。

**③ 判别器是异步旁路，napi 侧用 `async fn` 返回 Promise，不阻塞 JS 事件循环。** 结算虽然是同步语义，但如果 TriviumDB 的写入可能阻塞，可以用 `async fn` 包一层，在 tokio 运行时里跑，避免阻塞 JS 线程。napi-rs 的 `#[napi] pub async fn` 会自动返回 Promise，这是默认的逃逸舱。

**④ 不要在 napi 边界暴露 `Flowing` / `Settling` 的 typestate 泛型。** 边界只暴露 `recall` 和 `archive_turn` 这类**动词级 API**，阶段顺序由内核的 typestate 保证，JS 侧不需要知道流动和结算是两个类型。

---

## 七、哪些模式**不要**用在水利记忆系统里

**不要在球/管道的热路径上用 `Box<dyn Trait>`。** 流动和结算每秒可能处理几十个球，`dyn` 的 vtable 间接调用和缓存不友好会抵消 Rust 的性能优势。判别器后端用枚举分派，热路径用具体类型或泛型单态化。

**不要给所有模块套 typestate。** 只有流动/结算的阶段顺序、新球创建的“验证前/验证后”这类**有限且重要的顺序约束**值得 typestate。球的大小更新、管道衰减这些连续数值计算不需要状态类型。

**不要用 trait 继承或“基类”思维组织球和管道。** 球和管道是组合关系，不是继承关系。球持有内容列表和嵌入；管道持有权重和阻塞计数。用 struct 组合 + 枚举变体表达差异，比 trait 层次更可读。

**不要在 napi 边界用 `#[napi]` 导出几十个小函数。** 边界的 API 应该是**用例级**的：`judge_turn`、`recall`、`archive_turn`、`settle_and_inject`。细粒度的 getter/setter 留在 Rust 内核里，不要暴露给 JS，否则边界会变成维护负担。

## 八、模块级模式速查

| 模块 | 推荐模式 | 可读性收益 | 避免 |
|---|---|---|---|
| 流动 → 结算 | Typestate（`Flowing` / `Settling`） | 阶段顺序变成编译期约束 | 运行时 bool 标记 |
| 判别器后端 | Sealed trait + enum dispatch | 后端集合封闭，`match` 完整 | 裸 `pub trait` + `Box<dyn>` |
| ID / 受约束标量 | Newtype + 构造时验证 | 签名自解释，消灭单位混淆 | `String` / 裸 `f64` 到处传 |
| 逐跳流动计算 | Iterator `scan` / `filter` / `take` | 每段管道单一职责 | 嵌套 `for` + 可变累加器 |
| 早返回 | `let-else` | 正常路径低缩进 | 用 `match` 包裹整个函数体 |
| 异步判别 | 原生 `async fn in trait` | 消除 `#[async_trait]` 宏噪音 | 无必要地引入宏 |
| 辅助返回类型 | `impl Iterator` / `impl Future` | 签名暴露契约而非实现类型 | 手写长泛型参数 |
| napi 边界 | DTO 翻译 + `Result<T>` + `async fn` | 边界薄、内核干净 | 边界写业务逻辑、`panic!` 处理可恢复错误 |

---

**一句话**：在“大禹水利记忆网络”的 Rust 工程里，设计模式的主线是**把约束推到类型系统**——用 typestate 钉住流动/结算的顺序，用 sealed trait + enum 钉住判别器后端的封闭集合，用 newtype 钉住 ID 和标量的合法性，用迭代器管道让流动的逐跳语义自解释，用 2024 edition 的 `let-else` / 原生 async trait / `impl Trait` 消除样板。napi 边界保持薄而笨，只做 DTO 翻译和错误映射。热路径不上 `dyn`，顺序约束之外不上 typestate，组合优于继承，边界的 API 是动词级用例而不是 getter/setter。


针对“大禹水利记忆网络”，数据类型、判别器与接口契约的设计，核心原则是**把约束推到类型系统，边界只做翻译**。基于 napi-rs 2025 的最佳实践——边界类型与内部领域类型分离、错误一律走 `Result<T>`、异步是默认逃逸舱——下面分三部分给出可落地的设计。

## 一、数据类型：分层定义，边界只做 DTO 翻译

数据类型分三层：**内部领域类型**（Rust 内核使用，携带约束）、**边界 DTO**（napi 导出，JS 友好）、**持久化映射**（TriviumDB Payload/Vector）。三层之间通过显式转换函数连接，**不直接混用**。

### 1.1 内部领域类型（dayu-core）

内部类型用 newtype 和枚举表达约束，“构造即合法”。

```rust
// —— 标识符：每种 ID 独立类型，消灭混用 ——
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct BallId(u64);

#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct PipeId(u64);

// —— 受约束标量：构造时验证，持有即合法 ——
#[derive(Clone, Copy, Debug)]
pub struct PipeWeight(f64); // (0, 1]

impl PipeWeight {
    pub fn new(raw: f64) -> Result<Self, ValueError> {
        if raw > 0.0 && raw <= 1.0 { Ok(Self(raw)) }
        else { Err(ValueError::PipeWeightOutOfRange(raw)) }
    }
    pub fn get(self) -> f64 { self.0 }
}

#[derive(Clone, Copy, Debug)]
pub struct WaterAmount(f64); // >= 0

impl WaterAmount {
    pub fn new(raw: f64) -> Result<Self, ValueError> {
        if raw >= 0.0 { Ok(Self(raw)) }
        else { Err(ValueError::NegativeWater(raw)) }
    }
}

#[derive(Clone, Copy, Debug)]
pub struct Relevance(f64); // [0, 1]

impl Relevance {
    pub fn new(raw: f64) -> Result<Self, ValueError> {
        if (0.0..=1.0).contains(&raw) { Ok(Self(raw)) }
        else { Err(ValueError::RelevanceOutOfRange(raw)) }
    }
}
```

**边界**：只给跨模块传递、容易混淆的值做 newtype。循环下标、局部求和值不包装，否则 `into_inner()` 噪音会淹没可读性。

### 1.2 状态与枚举：用类型表达合法状态集

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum BallStatus { Active, Contested, Archived, Deleted }

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum ContentEncoding { Raw, RmwUtf8 }

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum CorrectionType {
    DeleteEpisode, ReassignEpisode, UpdateArchetype,
    MergeArchetype, SplitArchetype, DeleteThought,
    UpdateThought, ForgetArchetype, RejectRecall,
}

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum ConflictStrategy { Recompute, Abort }
```

枚举是**封闭世界**——新增变体时编译器强制你更新所有 `match` 分支，这是可读性和安全性的来源。

### 1.3 边界 DTO（napi 导出）

DTO 是 **JS 形状**，字段用 camelCase，类型只用 JS 友好类型（`String`、`number`、`Buffer`、`Option<T>`）。DTO **不携带内部约束**，约束由内核类型负责。

```rust
#[napi(object)]
pub struct JsBallSnapshot {
    pub ball_id: String,
    pub size: f64,
    pub size_max: f64,
    pub status: String,          // "active" / "contested" / ...
    pub domain: Option<String>,
    pub content_preview: Vec<String>,
}

#[napi(object)]
pub struct JsRecallInput {
    pub query_embedding: Vec<f32>,
    pub token_budget: u32,
    pub mode: Option<String>,    // "token" / "ball_count"
}

#[napi(object)]
pub struct JsInjectionBlock {
    pub text: String,
    pub ball_ids: Vec<String>,
    pub confidence: String,      // "clear" / "impression"（"vague" 已废弃，不再注入）
}

#[napi(object)]
pub struct JsVerdict {
    pub should_judge: bool,
    pub significance: f64,
    pub offset_direction: String,
    pub emotion_valence: f64,
    pub emotion_intensity: f64,
    pub hit_dimensions: Vec<String>,
    pub belongs_to: Option<String>, // 已有原型 ID；None = 新球
    pub belong_confidence: f64,
    pub reason: String,
}
```

**可空字段策略**（关键，napi-rs 有已知陷阱）：默认 `Option<T>` 映射为 `field?: T`（`None` → `undefined`）；如果业务需要区分“未提供”和“显式 null”，使用 `#[napi(object, use_nullable = true)]` 让 `Option<T>` 映射为 `field: T | null`。**在项目早期定死策略**，不要混用，否则 TS 侧会收到意外的 `null` 导致 napi-rs 在转换 `Option<String>` 时崩溃。

### 1.4 持久化映射（TriviumDB）

TriviumDB 的 Node 承载 Vector + Payload（JSON），Edge 承载带属性的管道。内部类型 → TriviumDB 的映射是**单向落库**，DTO 不直接进 TriviumDB。

```rust
// 球 → TriviumDB Node
impl From<&Ball> for TriviumNode {
    fn from(ball: &Ball) -> Self {
        TriviumNode::new(ball.id.0, ball.embedding.clone())
            .payload(json!({
                "size": ball.size.get(),
                "size_max": ball.size_max,
                "status": ball.status.as_str(),
                "content_list": ball.content_list,
                "last_watered": ball.last_watered,
                "domain": ball.domain,
            }))
    }
}

// 管道 → TriviumDB Edge
impl From<&Pipe> for TriviumEdge {
    fn from(pipe: &Pipe) -> Self {
        TriviumEdge::new(
            pipe.a.0, pipe.b.0,
            json!({
                "w": pipe.weight.get(),
                "blocked_count": pipe.blocked_count,
                "last_flowed": pipe.last_flowed,
                "status": pipe.status.as_str(),
            }),
        )
    }
}
```

**注意**：`blocked_count` 封顶后不再增长，落库时直接写封顶值；`w` 落库的是**原始粗细**，流动时用的 `w_eff` 是惰性衰减计算出来的，**不落库**。

## 二、判别器：Sealed trait + 枚举分派 + 异步旁路

判别器是**异步旁路**——不参与流动与结算，只回答“是否产生新球、归属哪个已有球”。它的接口契约要同时满足：后端可替换、输出结构化、错误可映射、不阻塞主对话。

### 2.1 Trait 定义

```rust
mod judge_sealed {
    pub trait Sealed {}
}

/// 判别器后端。下游不可实现，只能使用。
pub trait JudgeBackend: judge_sealed::Sealed + Send + Sync {
    async fn judge(&self, input: &JudgeInput) -> Result<Verdict, JudgeError>;
}
```

Sealed trait 让后端集合**封闭**——只有 `EmbeddingRuleBackend`、`DecisionModelBackend`、`MockJudgeBackend` 等内部类型能实现，下游无法注入任意实现，你可以在不破坏下游的前提下给 trait 加方法。

### 2.2 输入输出类型

```rust
pub struct JudgeInput {
    pub candidate_text: String,
    pub candidate_embedding: Vec<f32>,
    pub role_state: RoleState,       // 人格敏感维度、当前情绪、未完成意图
    pub recent_window: Vec<Turn>,    // 最近 6 轮
    pub candidate_archetypes: Vec<ArchetypePreview>, // 嵌入检索 top-5
}

pub struct RoleState {
    pub sensitive_dimensions: Vec<SensitiveDimension>, // 描述 + 权重
    pub current_emotion: EmotionState,
    pub unfinished_intents: Vec<String>,
}

pub struct Verdict {
    pub should_judge: bool,
    pub significance: Relevance,
    pub offset_direction: String,
    pub emotion_valence: f64,
    pub emotion_intensity: f64,
    pub hit_dimensions: Vec<String>,
    pub belongs_to: Option<BallId>,  // None = 新球
    pub belong_confidence: Relevance,
    pub reason: String,
}
```

**字段分组**：`Verdict` 保留完整字段，但按契约强度分两组，供不同后端分档产出。

| 组 | 字段 | 产出要求 |
|---|---|---|
| **必填组** | `should_judge`、`significance`、`belongs_to`、`belong_confidence` | 任何后端都必须产出；缺失即视为后端不可用 |
| **可选组** | `offset_direction`、`emotion_valence`、`emotion_intensity`、`hit_dimensions`、`reason` | 按后端能力产出，可全部为空 |

“嵌入 + 规则”路径只产出必填组，可选组一律留空；未来的决策专用小模型（Jev-Style、Chinese Decision 等）补齐可选组。业务规则层只依赖必填组，因此两条路径共享同一套判定逻辑。

### 2.3 错误枚举

```rust
#[derive(Debug, thiserror::Error)]
pub enum JudgeError {
    #[error("model not loaded")]
    ModelNotLoaded,
    #[error("inference failed: {0}")]
    InferenceFailed(String),
    #[error("output parse failed: {0}")]
    OutputParseFailed(String),
    #[error("input too long: {tokens} tokens, limit {limit}")]
    InputTooLong { tokens: usize, limit: usize },
}
```

**契约**：`OutputParseFailed` **不重试**——判别器输出固定 JSON schema，解析失败直接丢弃该候选，避免噪声入库。`ModelNotLoaded` 和 `InferenceFailed` 可以降级为“仅归档、不起念”，但**不阻塞主对话**。

### 2.4 后端分派

```rust
pub enum BackendKind {
    EmbeddingRule(EmbeddingRuleBackend),   // 嵌入 + 规则（默认）
    DecisionModel(DecisionModelBackend),   // 预留：决策专用模型
    Test(MockJudgeBackend),                // 测试
}

pub struct Judge {
    backend: BackendKind,
}

impl Judge {
    pub async fn judge(&self, input: &JudgeInput) -> Result<Verdict, JudgeError> {
        match &self.backend {
            BackendKind::EmbeddingRule(b) => b.judge(input).await,
            BackendKind::DecisionModel(b) => b.judge(input).await,
            BackendKind::Test(b) => b.judge(input).await,
        }
    }
}
```

**枚举分派**代替 `Box<dyn JudgeBackend>`——热路径没有 vtable 间接调用，`match` 的完整性由编译器保证，新增后端时不会漏掉分支。

**后端变体与能力声明**：后端用枚举分派持有，当前两个变体——`embedding_rule`（嵌入 + 规则：一次嵌入，余弦 + 阈值裁决）与 `test`（测试用预设 `Verdict`），并**预留** `decision_model`（决策专用模型）。新增后端只需“一个实现 + 一个枚举变体 + 一个分派分支”，`JudgeEngine`、`DayuCore`、注入渲染、可观测性均不改动。

`JudgeBackend` 在 `judge()` 之外提供两个方法：`producer()` 返回后端标识（`embedding_rule` / `decision_model` / `test`），`capabilities()` 返回该后端能产出的可选字段集合。`capabilities()` 存在的理由是消除 `None` 的歧义——见 §2.6。

### 2.5 判别器与主流程的契约

| 契约项 | 约定 |
|---|---|
| **调用时机** | `turn_end` 之后，异步队列；不阻塞主对话 |
| **候选来源** | 对话消息**全量** + 工具结果经结构性过滤后的剩余片段；不做语义粗筛 |
| **输出消费** | `should_judge=true` 且 `significance ≥ 固化阈值` → 创建新球或归属已有球；否则丢弃 |
| **幂等性** | 同一 `episode_id` 不重复创建球；`belongs_to` 已有球时追加内容 + 强化，不新建 |
| **失败语义** | 解析失败丢弃候选；模型不可用降级为“仅归档”；**任何失败不阻塞主对话** |
| **超时** | 单次判别 200–800ms；超时丢弃候选，不重试 |
| **后端切换** | `judge.backend` 默认 `embedding_rule`；切换是**重配置**（替换后端实例），不是热调参 |

### 2.6 生产者标记、能力声明与消费方约定

**为什么需要 `capabilities()`**：可选字段为 `None` 有两种语义——“这个后端本来就不产出”（静态能力）与“这次没产出”（运行时结果）。若只用 `None` 表达，消费方无法区分“后端不支持情绪判定”和“本次未给出情绪判定”，会在渲染和指标上做出错误推断。`capabilities()` 把静态能力显式化，`None` 从此只表示“本次没产出”。

**生产者标记 `producer`**：每个 `Verdict` 携带 `producer`，标明本次判定来自 `embedding_rule`、`decision_model` 还是 `test`。用途有三：注入块溯源（该记忆是被哪条路径判进来的）、指标标签（按后端切片对比）、A/B 对照（同一查询下两后端的显著性分布）。

**消费方约定**：

| 消费方 | 读取范围 | 行为 |
|---|---|---|
| 业务规则层（阈值、灰区、兜底合并） | **只读必填组** | 不得因可选字段缺失而改变判定结果 |
| 注入渲染 | 必填组 + `reason` | 有 `reason` 渲染“因为 Z”，无则省略该句 |
| 可观测性 | 必填组 + `capabilities()` | 仅当后端声明支持时，才记录情绪/方向指标 |
| 审计与对照 | `producer` | 按后端标识分组统计 |

**切换语义**：配置项 `judge.backend` 默认 `embedding_rule`，可选 `decision_model`、`test`。切换属于**重配置**（替换后端实例），不属于**热调参**（改阈值、改预算）。两者都走 `arc-swap` 配置快照，但必须区分处理，否则会出现“配置已切换、后端实例仍是旧的”的撕裂。

**阈值必须随后端绑定**：`0.3 / 0.5 / 0.7` 是按模型打分分布标定的；嵌入规则路径输出的是余弦，分布不同、区分度更低。阈值按 `producer` 分组配置，切换后端时同步切换阈值组，否则“只改一行配置”会退化为整体判定漂移。

**归属判定的前置条件**：规则路径的 `belongs_to` 与 `belong_confidence` 来自“候选文本向量 × 候选球向量”的余弦。因此判别时候选球嵌入必须可达；当前 `JudgeInput.candidate_archetypes` 只携带“球 ID + 分数”，需扩展为可携带向量，或在判别时按 ID 回查嵌入。否则规则后端只能永远返回“新球”。

**不变式**：从“嵌入 + 规则”切到“决策模型”，判别决策逻辑不变，只是输出更丰富——必填组语义一致，可选组从空变为有值。

## 三、接口契约：napi 边界只暴露动词级用例

### 3.1 导出 API 集合

napi 边界**只导出用例级函数**，不导出 getter/setter，不泄漏内部泛型和生命周期。

```rust
#[napi]
pub async fn recall(input: JsRecallInput) -> napi::Result<Vec<JsInjectionBlock>>;

#[napi]
pub async fn judge_turn(input: JsJudgeTurnInput) -> napi::Result<Vec<JsVerdict>>;

#[napi]
pub async fn archive_turn(input: JsArchiveTurnInput) -> napi::Result<()>;

#[napi]
pub async fn correct_memory(correction: JsCorrectionInput) -> napi::Result<JsCorrectionResult>;

#[napi]
pub async fn get_stats() -> napi::Result<JsStats>;
```

**为什么全部 `async`**：TriviumDB 的写入和加载可能阻塞，napi-rs 的 `#[napi] pub async fn` 返回 Promise，在 tokio 运行时里执行，**不阻塞 JS 事件循环**。同步函数会阻塞事件循环，在 Agent 场景里是不可接受的。

### 3.2 错误映射契约

napi-rs 期望可失败函数返回 `napi::Result<T>`（即 `Result<T, napi::Error>`），`Err` 自动转成 JS 异常或 Promise rejection。**不能用 `panic!` 处理可恢复错误**——panic 跨 FFI 边界是未定义行为。

核心错误到 napi 错误的映射用**辅助函数**，不实现 `From` trait——`CoreError` 和 `napi::Error` 都是外部类型，违反 orphan rule：

```rust
fn to_napi_error(err: CoreError) -> napi::Error {
    let code = match &err {
        CoreError::Trivium(e) => format!("TRIVIUM_{}", e.kind()),
        CoreError::Judge(e) => format!("JUDGE_{}", e.kind()),
        CoreError::Value(e) => format!("VALUE_{}", e.kind()),
        CoreError::Settle(e) => format!("SETTLE_{}", e.kind()),
    };
    napi::Error::new(
        napi::Status::GenericFailure,
        format!("[{code}] {err}"),
    )
}
```

**为什么不用 `Status` 直接区分业务错误**：`Status` 是 Node-API 的状态枚举，粒度太粗（`GenericFailure` 覆盖大多数变体）。在 `message` 里嵌入 `[code]` 前缀，TS 侧可以通过 `error.message.startsWith("[TRIVIUM_")` 做分类，同时 `error.code` 仍然是 `GenericFailure`，不破坏 napi-rs 的默认行为。

### 3.3 各 API 的行为契约

**`recall` — 同步语义的异步封装**

| 契约项 | 约定 |
|---|---|
| 输入 | 查询嵌入、token 预算、注入模式 |
| 输出 | 完整球的注入块列表；**不切割球内容** |
| 时序 | 流动 → 结算 → 注入，**同一调用内完成**；结算就是注入决策 |
| 无匹配 | 返回空数组，**不是错误** |
| 失败 | 结算写入失败 → 注入照常返回，下一轮重试强化；流动失败 → 返回空数组 |

**`judge_turn` — 异步旁路**

| 契约项 | 约定 |
|---|---|
| 输入 | 本轮候选片段、角色状态、最近窗口 |
| 输出 | 每个候选一个 `JsVerdict`；不产生新球时 `shouldJudge=false` |
| 幂等 | 同一 `episodeId` 不重复创建；`belongsTo` 存在时追加而非新建 |
| 失败 | 解析失败丢弃该候选；模型不可用返回空数组，**不抛异常** |

**`archive_turn` — 归档原始想**

| 契约项 | 约定 |
|---|---|
| 输入 | 本轮对话块、归属球 ID 列表 |
| 行为 | 写入内容列表（`rmw-utf8` 编码）；超出上限的内容转冷存储 |
| 幂等 | 按 `turnId + 序号` 去重 |
| 失败 | 记录 `pending_retry`，不阻塞 |

**`correct_memory` — 纠正**

| 契约项 | 约定 |
|---|---|
| 输入 | 目标类型/ID、纠正类型、新值、原因 |
| 行为 | 审计先行 → 改状态 → 强度扣减/迁移 → 下一轮注入体现更正 |
| 可逆性 | 默认软删；硬删需 `hardDelete=true` 显式确认 |
| 失败 | 同事务回滚，`correction_log` 不丢 |

### 3.4 版本化与向后兼容

napi 边界的 DTO **只加字段不删字段**。新字段一律 `Option<T>`，默认 `None`，TS 侧可选。如果必须改变语义，新增一个 API（如 `recall_v2`），旧 API 保留一个版本周期。TriviumDB 的 Payload 用 `schema_version` 字段标记，迁移脚本向前兼容。

### 3.5 并发契约

| 场景 | 契约 |
|---|---|
| dsh 与 pi 同时 `recall` | TriviumDB 进程级文件锁：多读单写；写冲突时 `busy_timeout` 等待，冲突重算增量 |
| 结算与流动并发 | 流动读快照（版本号 `V_start`）；结算写事务校验版本，冲突则重读涉及球/边重算增量 |
| `judge_turn` 并发 | 判别器是只读推理 + 异步写入；同一 `episodeId` 的幂等性由写入层保证 |
| 强度更新 | TriviumDB 的 `$inc` 原子增量，不读-改-写 |

## 四、一张表看清三层类型的转换关系

| 层 | 代表类型 | 约束由谁保证 | 转换方向 |
|---|---|---|---|
| **内部领域** | `BallId`、`PipeWeight`、`Relevance`、`Verdict` | newtype 构造验证 + 枚举封闭 | 不直接暴露给 JS |
| **边界 DTO** | `JsBallSnapshot`、`JsVerdict`、`JsRecallInput` | 无约束，JS 形状 | napi 导出；`From`/`Into` 与内部类型互转 |
| **持久化** | TriviumDB `Node` / `Edge` / `Payload` | TriviumDB 事务 + WAL | 内部类型单向落库；`w_eff` 不落库 |

**一句话**：内部类型携带约束，DTO 只做翻译，TriviumDB 只存状态；判别器用 sealed trait + 枚举分派 + 异步旁路，输出结构化 `Verdict`，失败不阻塞主对话；napi 边界只暴露动词级用例，错误通过辅助函数映射为带 `[code]` 前缀的 `napi::Error`，并发靠 TriviumDB 文件锁 + 版本号乐观重算。


将可观测性与动态调参补入技术方案，核心目标不是“加一个 Prometheus 端点”，而是让“水利模型”的每一次流动、结算、调参决策都留下**可量化、可追溯的数据痕迹**，使参数调整从“凭感觉”变为“由指标信号驱动”。

## 🌊 可观测性技术栈：Rust 标准栈 + TriviumDB 原生统计

Rust 侧的可观测性在 2026 年已经成熟到与 Java/Go 生态对齐的程度。你的技术栈不需要引入重型 APM，用 **`tracing`（结构化日志/追踪）+ `metrics`（指标门面）+ `metrics-exporter-prometheus`（导出器）** 即可覆盖三支柱。

**开销数据**：2026 年的生产实践基准显示，Rust 的 span 创建开销约 **~50ns**，指标记录延迟约 **~10μs**，内存效率也处于领先水平。这些开销相对于流动与结算的毫秒级预算可以忽略，**不需要为了性能而削减观测点**。

**TriviumDB 的原生统计直接接入**：0.9.0 版本提供了 `runtime.stats()`、`db.resource_stats()` 和 `db.instance_stats()`，覆盖共享账本、内存采样、活动操作数、周期维护状态等。`search_with_context` 的返回中已经包含 `ef_search`、`node_count`、`estimated_heap_bytes` 等字段。**这些是存储层的第一手数据，不需要在应用层重新发明。**


## 📊 水利模型核心指标矩阵：按“球—管—水”分层定义

指标必须直接映射到水利模型的物理量，否则调参时无法定位问题。按层组织：

### 💧 流动层（“水”的行为）
| 指标 | 类型 | 用途 |
|---|---|---|
| `flow_trigger_rate` | Gauge | 有输入但无球超过起始阈值的比例，过高说明 `start_ball_threshold` 太严或图覆盖不足 |
| `lit_balls_per_flow` | Histogram | 单次激活点亮球数分布，配合 `max_lit_ball_count` 安全阀判断是否频繁触顶 |
| `flow_depth_reached` | Histogram | 实际到达深度分布，判断 `max_flow_depth` 是否过紧 |
| `path_supplement_loss_ratio{dominant=loss}` | Histogram | 损失主导的路径占比——损失太大（细管道太多或 loss_pipe_factor 太高） |
| `path_supplement_loss_ratio{dominant=supplement}` | Histogram | 补充不足的路径占比——补充太小（球太小或相关性太低） |
| `flow_loss_by_pipe_weight` | Histogram | 按 w_eff 分桶的每跳损失率，判断损失是否由细管道主导 |
| `flow_supplement_by_pipe_weight` | Histogram | 按 w_eff 分桶的补充量，判断补充是否集中在粗管道 |

### 🚰 管道层（“管”的状态）
| 指标 | 类型 | 用途 |
|---|---|---|
| `pipe_pass_rate` | Gauge（按管道年龄/粗细分桶） | 水流通过率，持续低于某个阈值说明管道衰减过快或 `resistance` 计算偏严 |
| `pipe_blocked_rate` | Gauge | 被阻挡比例，过高说明 `w` 衰减太快或 `blocked_discount` 不够 |
| `pipe_w_distribution` | Histogram | 管道粗细分布，判断是否大量管道已沉底到“几乎断流” |
| `pipe_creation_by_source` | Counter（标签：new_ball / co_activation / offline / manual） | 判断图生长是否过度依赖某一条来源 |

### 🏀 结算层（“球”的强化）
| 指标 | 类型 | 用途 |
|---|---|---|
| `settle_increment_distribution` | Histogram | 球大小增量分布，判断 `size_strengthen_factor` 是否合适 |
| `settle_firm_vs_min_count` | Counter（标签：firm / min） | 强化球与最低强化球的比例，最低强化占比过高说明 `strengthen_eligibility_threshold` 可能偏低 |
| `settle_version_conflict_rate` | Counter | 结算版本冲突频率，判断并发调参/多客户端场景下重算是否频繁 |
| `size_saturation_rate` | Gauge | 触及 `size_max` 的球比例，过高说明饱和上限太低 |

### 🎯 注入与判别层
| 指标 | 类型 | 用途 |
|---|---|---|
| `injection_token_used` | Histogram | 实际注入 token 分布，对照 `token_budget` 判断预算是否合理 |
| `injection_ball_count` | Histogram | 注入球数分布，模式 B 下判断 `max_balls_per_inject` 是否过紧 |
| `injection_confidence_tier` | Counter（标签：clear / impression） | 注入置信度分布 |
| `judge_confidence_distribution` | Histogram | 判别器归属置信度分布，用于动态调整灰区阈值 |
| `judge_parse_failure_rate` | Gauge | JSON 解析失败率，超过 5% 触发告警 |

### 🗄️ 存储层（直接来自 TriviumDB）
| 指标 | 来源 | 用途 |
|---|---|---|
| `active_ball_count` / `archived_ball_count` | 应用层计数 + TriviumDB `node_count` | 判断规模是否接近 `max_balls` 归档触发线 |
| `resource_memory_bytes` | `db.instance_stats()` | 内存采样，判断是否接近配额 |
| `quiver_ef_search` | `search_with_context` 返回 | 向量检索的实际搜索宽度，判断 ANN 是否在健康区间 |
| `wal_size_bytes` | TriviumDB / 文件系统 | 极端长会话下监控 WAL 膨胀 |


## 🔄 动态调参闭环：从“指标信号”到“参数变更”

可观测性的真正价值在于**驱动调参**，而不是画在 Grafana 上看。借鉴 Smriti AI 的可观测 harness 设计——检索参数、图深度、压缩阈值等存为 YAML，**每一次自动或手动变更记录到 JSONL manifest**，使调参本身可审计、可回滚。你的动态调参闭环可以按四层设计：

### 📈 信号采集（在线，异步，不阻塞主路径）
指标通过 `metrics` 门面记录，由 `metrics-exporter-prometheus` 在独立端口暴露，Prometheus 拉取或由守护进程周期性聚合。**指标记录是异步的，不进入结算事务的同步路径。** Qwen Memory Agent 的实践值得参考：**分离“检索质量”“存储状态”“Agent 是否实际使用记忆”三个维度**，而不是只看命中率。你的 `path_supplement_loss_ratio` 和 `injection_confidence_tier` 正是在做这种分离——前者衡量流动质量，后者衡量注入置信度。

### 🩺 诊断规则（确定性，可配置，不依赖 ML）
第一版**不要上强化学习调参**。用确定性规则把指标映射为“诊断信号”：

```toml
[diagnostics]
# 连续 N 个窗口满足条件才触发，避免抖动
loss_dominant_high = { metric = "path_supplement_loss_ratio{dominant=loss}", op = ">", ratio = 0.6, window = "3d", suggestion = "检查管道衰减是否过快，或降低 loss_pipe_factor" }
supplement_weak_high = { metric = "path_supplement_loss_ratio{dominant=supplement}", op = ">", ratio = 0.5, window = "3d", suggestion = "考虑提高 max_supplement_ratio 或降低 strengthen_eligibility_threshold" }
loss_saturation = { metric = "flow_loss_by_pipe_weight", op = "p95 > loss_max × 0.95", window = "1d", suggestion = "大量管道处于损失上限，检查 loss_max 是否过低或管道整体过细" }
pipe_block_high = { metric = "pipe_blocked_rate", op = ">", value = 0.6, window = "3d", suggestion = "考虑降低 pipe_stability_growth 或提高 blocked_discount" }
injection_budget_pressure_high = { metric = "injection_token_used", op = ">", ratio = 0.95, window = "1d", suggestion = "考虑收紧 strengthen_eligibility_threshold 或重新校准判别器" }
```

每条诊断规则输出一个**结构化信号**（`{rule_id, metric, current_value, suggested_direction, severity}`），写入 `diagnostics.jsonl`。**调参建议不自动执行**——第一版只“建议”，由开发者或用户确认后变更配置。

### 🧪 A/B 与回滚（安全调参的前提）
动态调参最危险的是“调了之后系统变差但不知道是哪次调参导致的”。解决方案是**每次参数变更生成一个 `config_version`**，写入 `config_history` 表，记录 `{version, timestamp, parameter, old_value, new_value, trigger_signal, operator}`。流动和结算的指标按 `config_version` 打标签。当某个版本的 `path_supplement_loss_ratio` 或 `injection_confidence_tier` 出现显著退化时，可以**按版本回滚**，而不是在海量日志里猜。

Smriti 的 `evolution` 配置块还定义了参数的**安全范围**（如 `top_k_min/max`、`decay_lambda_min/max`）。你的动态调参必须同样受边界约束——**建议器不能建议超出 `min/max` 范围的值**，配置加载时做校验，越界拒绝。

### 📝 变更审计（与纠正审计同构）
你已经有了 `correction_log` 的审计模式。**参数变更复用同一套审计范式**：`param_change_log` 记录 `{change_id, parameter, old, new, reason, trigger_metric, trigger_value, config_version, reversible}`。这样“记忆纠正”和“参数纠正”共享同一个审计语义——系统对“自身状态的修改”和“记忆的修改”都保持可追溯。


## ⚙️ 配置热更新：不重启、不破坏前缀缓存

参数变更必须**不重启 napi 模块**、**不中断主对话**。实现方式：

- 配置以 **TOML + `arc-swap`**（或 `tokio::sync::watch`）加载为全局只读快照；
- 流动和结算在每次调用的**入口处读取当前快照**，不在函数内部多次读；
- 变更通过管理 API（或文件监听）触发 `arc-swap` 更新；
- **结算的事务边界内使用同一个配置快照**，不会出现“流动用旧配置、结算用新配置”的撕裂。

Rust 的 `metrics` 生态明确支持**热更新兼容性**和**动态指标注册**。`config_version` 作为标签附加到关键指标上，使调参前后的效果可以直接在 Prometheus 中按版本切片对比。


## 🛡️ 动态调参的安全边界（必须显式定义）

| 风险 | 约束 |
|---|---|
| 调参导致流动行为突变 | 单次变更幅度 ≤ 当前值的 20%（可配），超出需显式确认 |
| 调参建议循环触发 | 同一参数在 `cooldown`（默认 24h）内不接受第二次自动建议 |
| 调参破坏前缀缓存 | 配置变更**不触发前缀重建**；注入预算变更只影响尾部 |
| 诊断规则本身误报 | 所有诊断规则带 `window` 和 `min_samples`，样本不足不触发 |
| 非原子调参 | 参数变更与 `param_change_log` 写入**同一事务**；失败回滚 |


## 💎 一句话

**可观测性用 Rust 标准栈（`tracing` + `metrics` + `metrics-exporter-prometheus`，开销 ~50ns/span、~10μs/metric）+ TriviumDB 原生 `runtime.stats()`/`instance_stats()`/`search_with_context` 统计；指标矩阵按"流动—管道—结算—注入—判别—存储"分层，核心信号是 `path_supplement_loss_ratio{dominant=loss}`（损失主导）和 `path_supplement_loss_ratio{dominant=supplement}`（补充不足）——两者拆开才能区分"损失太大"和"补充太小"两种退化模式；动态调参走"确定性诊断规则 → 结构化建议 → 配置热更新（`arc-swap` 快照）→ `param_change_log` 审计 → 按 `config_version` 回滚"的闭环，第一版不自动执行、不超出安全边界、不引入强化学习。** 这样参数调整有数据支撑、有审计追溯、有回滚能力，而不是在 Prometheus 图上"看起来差不多就改一改"。


# 大禹水利记忆网络 · 模块化代码设计

**目标**：每个模块边界清晰、依赖单向、可独立替换与测试、可渐进式实现。核心原则是**业务逻辑不依赖具体基础设施**——流动和结算只依赖 trait，不依赖 TriviumDB、不依赖 ort、不依赖 napi。


## 🏗️ Workspace 结构：按“依赖方向”分层

```
dayu-workspace/
├── crates/
│   ├── dayu-domain/          # 纯领域类型，零外部依赖
│   ├── dayu-flow/            # 流动与结算引擎，只依赖 domain + traits
│   ├── dayu-judge/           # 判别器抽象与后端，依赖 domain + traits
│   ├── dayu-storage/         # 存储抽象与 TriviumDB 实现
│   ├── dayu-embedding/       # 嵌入抽象与 ONNX/model2vec 实现
│   ├── dayu-config/          # 配置加载、热更新、版本化
│   ├── dayu-observability/   # 指标、日志、诊断规则
│   ├── dayu-core/            # 门面 crate，组装所有模块
│   ├── dayu-napi/            # napi 绑定，只做 DTO 翻译
│   └── dayu-cli/             # 离线巩固 CLI
└── Cargo.toml                # workspace 根
```

**依赖方向严格单向**：

```
dayu-domain  ← 所有模块都依赖它，它不依赖任何模块
dayu-flow    → domain + 抽象 trait（不依赖 storage/judge 实现）
dayu-judge   → domain + 抽象 trait
dayu-storage → domain + TriviumDB
dayu-embedding → domain + ort/model2vec
dayu-core    → 所有模块，负责组装
dayu-napi    → dayu-core，只做 DTO 翻译
dayu-cli     → dayu-core + anyhow（唯一允许用 anyhow 的地方）
```

**为什么这样分**：`dayu-flow` 不 import `dayu-storage`，意味着流动引擎可以在没有真实数据库的情况下用内存 mock 测试；`dayu-judge` 不 import `dayu-napi`，意味着判别器逻辑与 FFI 边界完全隔离。**任何模块的测试都不需要拉起完整系统。**


## 🧩 核心 trait 抽象：四个必须隔离的边界

### 1. 存储抽象（`dayu-storage::StorageBackend`）

流动和结算需要读写球、管道、内容，但它们不应该知道背后是 TriviumDB 还是 SQLite 还是内存。

```rust
// dayu-domain 定义 trait，dayu-storage 提供实现
#[async_trait]
pub trait StorageBackend: Send + Sync {
    // —— 读 ——
    async fn get_ball(&self, id: BallId) -> Result<Option<Ball>, StorageError>;
    async fn get_balls(&self, ids: &[BallId]) -> Result<Vec<Ball>, StorageError>;
    async fn load_subgraph(&self, starts: &[BallId], depth: usize) 
        -> Result<SubGraph, StorageError>;
    async fn search_by_embedding(&self, query: &[f32], top_k: usize) 
        -> Result<Vec<(BallId, f32)>, StorageError>;

    // —— 写 ——
    async fn begin_transaction(&self) -> Result<Box<dyn StorageTx>, StorageError>;
}

#[async_trait]
pub trait StorageTx: Send + Sync {
    async fn upsert_ball(&mut self, ball: &Ball) -> Result<(), StorageError>;
    async fn increment_ball_size(&mut self, id: BallId, delta: f64) 
        -> Result<(), StorageError>;
    async fn upsert_pipe(&mut self, pipe: &Pipe) -> Result<(), StorageError>;
    async fn commit(self: Box<Self>) -> Result<(), StorageError>;
    async fn rollback(self: Box<Self>) -> Result<(), StorageError>;
}
```

**实现集合**：
- `TriviumStorage`（生产，`dayu-storage` 默认实现）
- `SqliteStorage`（回退逃生舱，未来可选）

**扩展点**：新增存储后端只需实现 `StorageBackend` + `StorageTx`，`dayu-flow` 一行不改。

### 4. 时间抽象（`dayu-domain::Clock`）

衰减、归档、`last_watered` 都依赖时间。直接调 `chrono::Utc::now()` 会让测试无法控制时间。

}

    fn now(&self) -> DateTime<Utc> { Utc::now() }

pub struct MockClock(Arc<Mutex<DateTime<Utc>>>);

## 🧱 模块内部的扩展点设计

### 流动引擎：策略可替换

```rust
// dayu-flow 内部
pub trait SupplementStrategy: Send + Sync {
    fn compute_supplement(
        &self,
        ball: &Ball,
        current_water: f64,
        relevance: f64,
        config: &FlowConfig,
    ) -> f64;
}

pub struct DefaultSupplementStrategy; // size_effective × 归一化 relatedness（cos(query,B)），带上限
pub struct LinearSupplementStrategy;  // 线性补充，用于对照实验
```

流动引擎持有 `Box<dyn SupplementStrategy>`，**默认实现是 `DefaultSupplementStrategy`，但可以按配置切换**。这让“补充规则”的 A/B 实验不需要改引擎代码。

#### 有效值只有一个来源

`size_effective` 与 `w_eff` 必须在**进入流动之前**由快照层算好，下游只读不重算：

```rust
/// 子图加载时一次算好，之后所有消费方只读这两个字段。
pub struct BallSnapshot {
    pub id: BallId,
    pub vector: Vec<f32>,
    pub size: f64,            // 存储原值（截至 last_watered 的强度）
    pub size_effective: f64,  // = size × exp(-(now - last_watered) / S)，唯一衰减点
    pub last_watered: DateTime<Utc>,
    pub stability_s: f64,
}

pub struct PipeSnapshot {
    pub id: PipeId,
    pub weight: f64,
    pub w_eff: f64,           // = weight × exp(-(now - last_flowed) / S_pipe)，唯一衰减点
}
```

**为什么放进快照**：如果让每个消费方自己乘 `exp(-Δt/S)`，就会重演“同一个衰减乘三次”的历史问题——起始选择、补充、排序各乘一次，陈旧球被平方沉底。放进快照后，消费侧只读 `size_effective`，不必也不应知道 `S` 与 `last_watered`。

**写入路径是另一条线**：快照是只读视图，结算强化走 `Storage::apply_settlement`，在事务里先物化衰减再加增量（§4.6 步骤①～④）——**不能把快照里的 `size_effective` 直接写回去**，否则后续消费方会把同一个衰减再乘一次。当前 `crates/dayu-flow/src/engine.rs:195` 仍是 `let w_eff = pipe.weight; // TODO`，球侧尚未实现 `size_effective`。

## 💎 一句话

**Workspace 按依赖方向分层，`dayu-domain` 零依赖、`dayu-flow`/`dayu-judge` 只依赖 trait 不依赖实现、`dayu-core` 是唯一组装点；四个核心 trait（`StorageBackend`、`JudgeBackend`、`EmbeddingBackend`、`Clock`）隔离基础设施，策略 trait（`SupplementStrategy`、`StrengthenStrategy`、`VerdictPostProcessor`）隔离算法变体；feature flag 控制推理后端依赖，模块可独立测试、独立交付、渐进式实现。新增存储后端或推理后端只改 `DayuCore::new` 的构造参数，业务逻辑零改动。**


核心要求是：**任何一个 crate 的测试，都不需要拉起其他 crate、不需要真实数据库、不需要模型文件、不需要 Node 运行时。** 实现方式是“依赖注入 + 内存实现 + 测试夹具 + feature gate + 分层命令”，让 `cargo test -p dayu-flow` 在纯内存里秒级跑完。

## 🚀 分层运行命令：按需选择测试范围

```bash
# 只跑某个 crate 的单元测试，不碰其他 crate
cargo test -p dayu-flow
cargo test -p dayu-judge
cargo test -p dayu-domain

# 跑所有 crate 的默认测试（跳过 #[ignore] 和 ONNX 集成测试）
cargo test --workspace

# 跑集成测试（需要模型文件）
cargo test -p dayu-judge -- --ignored

# 只跑某个测试函数
cargo test -p dayu-flow flow_stops_when_water_below_resistance

# 并行 + 显示输出
cargo test --workspace -- --nocapture --test-threads=8
```

**默认 `cargo test --workspace` 的预期**：**全部在 10 秒内跑完**，零网络、零模型文件、零 Node 运行时。任何超过 10 秒的测试要么被 `#[ignore]` 标记，要么说明它依赖了不该依赖的东西。

## 🔁 确定性与隔离：测试可重复、可并行

### 确定性

- **嵌入**：`MockEmbeddingBackend::deterministic` 按文本 hash 生成向量，**同一文本永远同一向量**；
- **随机 ID**：测试里用 `BallId::from_u64(1)` 构造固定 ID，**不调 `Uuid::new_v4()`**；
- **时间**：`MockClock` 固定初始时间，**不调 `Utc::now()`**；
- **配置**：`sample_config()` 返回固定配置，**不从文件加载**；
- **无全局状态**：每个测试创建自己的临时 `.tdb`、`MockClock`、`MockJudgeBackend`，**测试之间零共享**。

### 并行安全

- `cargo test` 默认多线程并行；
- 每个测试持有独立的 `TempDir`，数据库文件互不干扰，**不跨测试共享**；
- `tempfile::tempdir()` 每个测试独立目录，**并行跑不冲突**；
- `MockClock` 每个测试独立实例，**时间快进互不影响**。

### 属性测试覆盖不变量

```rust
use proptest::prelude::*;

proptest! {
    #[test]
    fn size_never_exceeds_max(
        initial in 0.0..10.0f64,
        increment in 0.0..5.0f64,
        size_max in 1.0..10.0f64,
    ) {
        let result = apply_saturation(initial, increment, size_max, 1.0);
        prop_assert!(result >= 0.0);
        prop_assert!(result <= size_max);
    }
}
```

**属性测试**覆盖“球大小非负且不超上限”“管道 `w ∈ (0,1]`”“水量非负”这类数值不变量，比手写用例更能覆盖边界。

## 🧭 CI 分层：快速路径 vs 集成路径

| CI Job | 命令 | 耗时 | 依赖 |
|---|---|---|---|
| **快速单元测试** | `cargo test --workspace` | <10s | 零外部依赖 |
| **属性测试** | `cargo test --workspace --features proptest` | <30s | 零外部依赖 |
| **存储集成测试** | `cargo test -p dayu-storage` | <60s | 临时文件，无需网络 |
| **ONNX 冒烟测试** | `cargo test -p dayu-judge -- --ignored` | 取决于模型加载 | 需预下载模型文件 |
| **napi 构建验证** | `cargo build -p dayu-napi` | <60s | 无 Node 运行时依赖 |

**PR 的默认门禁只跑“快速单元测试”和“属性测试”**——不下载模型、不碰 TriviumDB 文件、不启动 Node。**任何开发者本地 `cargo test --workspace` 都能在 10 秒内得到反馈**，不需要先配置模型或数据库。

## 💎 一句话

**每个 crate 的默认 `cargo test` 都零外部依赖（不联网、不加载模型、不启动 Node）：`dayu-flow` 用 `TriviumStorage`（临时 `.tdb`）+ `MockEmbedding` + `MockClock`，`dayu-judge` 用 `MockJudgeBackend`，`dayu-napi` 只测 DTO 转换，`dayu-storage` 用 `tempfile` 隔离；mock 实现放在 `test` feature 下，夹具放在 dev-only 的 `dayu-testkit` crate；`dayu-flow` 的 dev-dependencies 里不出现 `triviumdb`，依赖方向由编译期强制；真实模型和真实数据库的测试用 `#[ignore]` 标记，只在专用 CI job 跑。** 这样“不启动项目”不是一个约定，而是**编译期约束 + 依赖方向 + feature gate** 共同保证的工程事实。
