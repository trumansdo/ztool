# 12 · 公开基准评测对接（LoCoMo / LongMemEval）

> 目的：在公开记忆检索基准上拿到第一组可复现、可对比的数字，回答
> 「水流扩散的检索质量，比 BM25 / dense 基线好还是差」。
>
> 评测框架：`memory-core-eval`（`mceval`），只测**检索质量**（Recall@k），
> 不涉及端到端答案生成。

---

## 1. 架构

```
mceval (Python)                 dayu-serve (Rust)              TriviumDB
  │                                │                              │
  ├─ reset(ns) ──POST /reset──────►│ 删掉 ns 对应的库文件          │
  ├─ store(turn)×N（本地缓冲）     │                              │
  ├─ 缓冲满 / search 前            │                              │
  │   ──POST /store_batch────────►│ 一批一个事务：建球 + 连管道 ─►│
  ├─ search(query, top_k) ───────►│ embed → recall → 回填来源 ───►│
  ◄── memories[{session_id,        │                              │
        turn_idx, score}]          │                              │
```

一个 namespace = 一个独立 TriviumDB 文件。评测框架给**每道题**分配独立
namespace，因此 `reset` 退化为删文件，题与题之间不可能互相污染。

## 2. dayu-serve HTTP 契约

`crates/dayu-serve`。启动：

```bash
cargo build -p dayu-serve --release
./target/release/dayu-serve \
    --config <merged.toml> --store-dir <dir> --listen 127.0.0.1:18080
```

就绪后向 stdout 打印 `LISTENING <port>` 并 flush（端口 0 时由内核分配）。

| 端点 | 请求 | 响应 |
|:--|:--|:--|
| `GET /health` | — | `ok` |
| `POST /reset` | `{namespace}` | `{ok:true}` |
| `POST /store` | `{namespace, turn:{content, role, session_id, turn_idx, session_idx, timestamp}}` | `{memory_id}` |
| `POST /store_batch` | `{namespace, turns:[turn...]}` | `{memory_ids:[...]}` |
| `POST /search` | `{namespace, query, top_k, as_of_date?}` | `{memories:[{memory_id, content, session_id, turn_idx, session_idx, score}]}` |

### 三条关键约定

1. **`/search` 必须回填 `session_id` / `turn_idx`**，否则 Recall@k 恒为 0。
   实现方式：写入时把 `{session_id, turn_idx, session_idx}` 编码成 JSON 存进
   `Content.source: TurnId`，随球落库（重启后仍可读回），检索时解回。
2. **`/search` 返回顺序就是 recall 的注入顺序**，服务端不重排。
3. **`as_of_date` 当前忽略**（不报错）。dayu-core 尚无时间过滤。

### 为什么要有 `/store_batch`

评测每题要灌几百到几千回合。逐个 `/store` 时每球一个事务，实测 ~37ms/球
（fsync 主导），一题几百球就要几十秒；`/store_batch` 整批一个事务后降到
毫秒级。语义与逐条 `store` + `link_balls` 等价（`DayuCore::create_turn_balls_batch`）。

### 管道从哪来

`/store` 与 `/store_batch` 都会把**同一 session 内相邻回合**连成一条管道
（粗细由 `--link-weight` 指定，默认 0.5，`off` 关闭）。

没有管道时 recall 退化为纯余弦 Top-N，测不出流动的作用；有了管道才能观测
扩散。`--link-weight off` 就是「纯 dense 对照」。

## 3. Python 适配器

`memory-core-eval/mceval/adapters/dayu.py`，已注册为 `--adapter dayu`。

- 地址：`--base-url` 或 `DAYU_SERVE_URL`，默认 `http://127.0.0.1:18080`
- 构造时先 `GET /health`，服务没起来立刻报错（否则每题静默 0 分，跑完才发现白跑）
- `store` 走 per-namespace 缓冲（`DAYU_BATCH_SIZE`，默认 512），在 `search` / `reset`
  前一次性 `/store_batch`，保证读后写

## 5. 运行

统一入口：`test/memory-eval/run-eval.cjs`。一次运行 = `test/memory-eval/<时间戳>-<adapter>-<dataset>[-<tag>]/`
一个自描述目录（配置快照 / 服务日志 / 库 / 结果 / meta）。

```bash
cd D:/code_space/rust/ztool/dayu-mem-sys

# dayu（需要先 cargo build -p dayu-serve --release）
node test/memory-eval/run-eval.cjs --dataset locomo --sample 100 --stratified --seed 0

# 基线对照
node test/memory-eval/run-eval.cjs --adapter bm25 --dataset locomo --sample 100 --stratified

# 管道 on/off 对照
node test/memory-eval/run-eval.cjs --dataset locomo --sample 100 --stratified --link-weight off --tag nolink

# LongMemEval
node test/memory-eval/run-eval.cjs --dataset longmemeval --split oracle --sample 50 --seed 0
```

运行器做三件事：合并 `test/config/base.toml ← <config>.toml ← 参数覆盖` 写成单文件、
拉起 `dayu-serve`（日志写进运行目录）、调 `python -m mceval.cli run` 并把结果写进同一目录。

`--sample` 必须配 `--seed` 或 `--stratified`：数据集按问题类型聚集，
裸 `data[:N]` 有偏。

### 为什么评测产物不放在 test/out/

`test/out/` 是 `cargo test` 的一次性产物，`rm -rf test/out` 是日常操作；
评测一次跑几十分钟、结果要留着横向对比。两者生命周期不同，混在一起就会
误删评测结果，或者评测的几百 MB 库拖慢日常测试。所以单独开 `test/memory-eval/`。

### 手工跑（不经运行器）

```bash
# 1) 合并配置
test/out/eval/lms.merged.toml  ← node 一行：config.load('lms', {start_top_n:10, max_balls_per_inject:10})

# 2) 起服务
dayu-serve --config <merged.toml> --store-dir <dir> --listen 127.0.0.1:18080

# 3) 跑评测
cd D:/code_space/other/memory-core-eval
DAYU_SERVE_URL=http://127.0.0.1:18080 python -m mceval.cli run \
    --adapter dayu --dataset locomo --sample 100 --stratified --seed 0 --workers 4
```

## 6. 首轮结果（LoCoMo，n=100 stratified，seed=0）

嵌入：Qwen3-Embedding-0.6B（1024 维，本地 LM Studio）

| 配置 | R@1 | R@5 | R@10 |
|:--|--:|--:|--:|
| BM25（复现论文锚点） | **54.0** | **74.0** | **84.0** |
| dayu 纯余弦 top-10（`--link-weight off`） | 42.0 | 64.0 | 78.0 |
| dayu + 管道 0.5（start_top_n=10） | 42.0 | 64.0 | 78.0 |
| dayu + 管道 0.5（start_top_n=20） | 43.0 | 64.0 | 73.0 |
| dayu + 管道 0.5（start_top_n=5） | 43.0 | 72.0 | 72.0 |

BM25 三次复现论文锚点完全一致（54/74/84），说明评测链路可信。

### 两条结论

1. **管道当前不产生任何效果。** `--link-weight off` 与 `0.5` 两次运行结果
   逐位相同（42/64/78）。说明水在 600 球规模下没能越过管道点亮任何新球，
   系统等价于「余弦 Top-N」。
2. **当前检索弱于 BM25**，差距集中在 R@1（42 vs 54）。余弦 Top-1 不如词面匹配，
   有两个独立原因：一是扩散没发生（第 1 条），二是 0.6B 嵌入模型在 LoCoMo
   这类对话上的区分度不足。

### 下一步（按优先级）

| 优先级 | 事项 | 依据 |
|:--|:--|:--|
| P0 | 校准注水量使扩散在 600 球规模下真实发生 | 管道 on/off 无差异 = 核心机制未生效 |
| P1 | 换更强嵌入模型（Qwen3-Embedding-4B）复测 | R@1 差距主要来自编码器 |
| P2 | 跑 LongMemEval-S（n=100）对比 | 另一基准，验证结论不是 LoCoMo 特有 |

## 7. 工程注意

- **评测产物位置**：全部落在 `test/memory-eval/<时间戳>-<adapter>-<dataset>[-<tag>]/`，
  与 `test/out/`（`cargo test` 一次性产物）隔离。`.gitignore` 只放行
  `README.md` 与 `run-eval.cjs`。
- **Windows 文件锁**：`reset` 要删库文件，必须先从注册表移除 `Arc<NamespaceState>`
  并 drop（释放 `Database`），再删；删除带 20 次递增退避重试。
- **`taskkill` 语法**：cygwin 下 `taskkill //F //IM` 会失败，用 `/F /IM`。
  旧的 `dayu-serve` 进程没被杀掉时，新进程绑定失败，评测会静默连到旧进程
  （表现为「改了配置但结果一模一样」）。`run-eval.cjs` 用端口 0 避开这个问题。
- **嵌入缓存**：按文本内容全局缓存（跨 namespace），上限 20 万条。
  同一对话的第 2 题起嵌入全部命中，单题耗时从 ~30s 降到 ~0.5s。
- **`/search` 返回条数可能少于 top_k**：受引擎 `max_balls_per_inject` 与
  「实际点亮的球数」双重限制。运行器把 `start_top_n` / `max_balls_per_inject`
  都设成 `--top-k`（默认 10），但若扩散没发生，点亮数仍可能只有起始球数。
