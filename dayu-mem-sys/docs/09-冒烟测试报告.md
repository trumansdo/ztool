## 1. 测试目的

验证「水沿管道传播、联想链有长度」这条核心设计理念是否成立，并确定 `total_water_budget` 的合理取值。

**背景**：此前冒烟用同一向量建球，所有球都是起始球，水从未走过管道，`reinforced_pipe_count` 恒为 0。本次改用**真实嵌入模型 + 随机中文文本**，让水必须靠管道扩散。

## 5. 结论

### 5.1 机制验证：通过

| 设计理念 | 验证结果 | 证据 |
|:--|:--:|:--|
| 水沿管道传播 | ✅ | `budget ≥ 2.5` 时点亮数 > 起始球数 |
| 管道粗细决定损耗 | ✅ | 损耗率 0.216 / 0.248 / 0.280 / 0.344 严格随 w 递减 |
| 阻力不是开关 | ✅ | `budget = 1.0, sig = 3.0` 时细管 0.1 被突破（0.1 → 0.1262） |
| 强线索可突破 | ✅ | 同一 budget 下 sig 1.0 → 3.0，点亮数 1 → 3.75 |
| 通过后管道变粗 | ✅ | 管 1 从 0.9 → 0.9947 |
| 细管增幅大于粗管 | ✅ | 细管 +76%，粗管 +10.5% |
| 只有被想起才变牢固 | ✅ | 球 2 的 S 从 7 → 10.09，未点亮的球停在 7.0 |
| 注入三级渲染 | ✅ | clear / deep_impression / impression / faint_impression 全部出现 |
| 注入受 token 预算约束 | ✅ | 6 球全注入时 101 token，未超 2048 |

### 5.2 参数问题：`total_water_budget = 1.0` 过小

**当前默认值 1.0 使扩散完全失效**：

```
budget = 1.0, sig = 1.0
  → 点亮 1 个球（就是起始球自己）
  → 2 条出边全部被挡
  → 所有管道粗细不变
  → 联想机制形同虚设
```

**原因**：阻力 `1/(1+w) ∈ [0.5, 1]`，而水从 1.0 出发，分叉一次（2 条出边各分 ~50%）再扣损（~20%）后只剩 ~0.4，低于阻力下限 0.5。

### 5.3 参数问题：`budget ≥ 6.5` 会淹没整图

```
budget = 6.5, sig = 1.0
  → 6 个球全部点亮
  → 0 条管道被挡
  → 所有查询返回同样的 6 个球
```

**「什么都想起来等于什么都想不起来」**——查询「今天午饭吃了什么」和「管道粗细代表什么」返回完全相同的注入块，检索失去区分度。

### 5.4 推荐取值：`2.5`

| 候选 | 平均点亮 | 平均被挡 | 区分度 | 评价 |
|--:|--:|--:|:--|:--|
| 1.0 | 1.00 | 2.00 | 无（只有起始球） | ❌ 扩散失效 |
| **2.5** | **3.25** | **1.00** | **有**（2~4 球，随查询变化） | ✅ **推荐** |
| 6.5 | 6.00 | 0.00 | 无（全部 6 球） | ❌ 淹没整图 |
| 15 / 38 | 6.00 | 0.00 | 无 | ❌ 与 6.5 完全相同，纯浪费 |

`2.5` 的实测表现：

- 4 条查询分别点亮 3 / 4 / 2 / 4 个球——**有区分度**
- 仍有 1 条管道被挡——**阻力机制在工作**
- 配合 `significance = 3.0` 时能点亮全部 6 球——**强线索仍能突破**

## 6. 测试中发现并修复的缺陷

### 6.1 `lit_count` 从未递增（严重）

**现象**：所有球的 `litCount` 恒为 0，即使被反复强化。

**原因**：`TriviumTx::increment_ball_size` 只更新 `ball_stored_size` 和 `last_watered`，**没有递增 `lit_count`**。

**影响**：

- `ball_stability` 的增长公式依赖 `lit_count`（文档 §4.6 的间隔效应），实际实现用的是 delta 驱动，所以 S 仍能增长——但 `lit_count` 作为「被想起多少次」的语义完全失效
- 归档判定、观测指标都读不到真实值

**修复**：`crates/dayu-storage/src/trivium.rs` 的 `increment_ball_size` 增加 `updated.lit_count = updated.lit_count.saturating_add(1)`。

### 6.2 缺少管道观测接口

**现象**：无法从 napi 侧看到管道粗细变化，只能靠日志推断。

**修复**：新增 `StorageBackend::list_pipes()` + `DayuCore::list_pipes()` + napi `listPipes()`，返回 `{id, a, b, thickness, stability, blockedCount}`。

### 6.3 缺少单轮统计返回

**现象**：`recall` 只返回注入块，看不到「点亮几个、被挡几条、强化几个」，必须去解析日志或指标文件。

**修复**：`RecallResultDto` 增加 `stats: RecallStatsDto`，含 `startCount / litCount / strengthenedCount / impressionCount / blockCount / tokenCount / blockedPipeCount / elapsedMs`。

### 6.4 同进程重复 `init` 会退化成 mock

**现象**：参数扫描时第二组开始 `query_dim` 从 512 变成 384，起始球数为 0。

**原因**：ONNX Runtime 每进程只允许一个环境，第二次 `OrtEmbeddingBackend::load` 失败后回退到 `MockEmbeddingBackend`（384 维）。

**处理**：扫描脚本改为**每组独立子进程**。同时新增 napi `shutdown()`，允许显式释放实例。

## 13. 最终结论（更新）

### 13.1 系统行为总结

| 规模 | 瓶颈 | 主题相关性 | 推荐 start_top_n |
|:--|:--|:--|:--|
| 6 球 | budget=1.0 扩散失效 | ✅ 良好 | N/A |
| 100 球 | start_top_n=10 | ⚠️ 可接受 | 20 |
| 1000 球 | start_top_n=10 | ⚠️ 可接受 | 30 |
| 5000 球 | start_top_n=30 | ❌ 跨主题污染 | 50+ |

### 13.2 模型局限

pizza-embed-zh-small-v1（384 维）在 5000 球规模下跨主题区分度不足。建议：
- 短期：调大 `start_ball_relative_threshold`（0.7 → 0.85）过滤弱相关球
- 长期：换用更高维度模型（如 768 维或 1024 维中文嵌入模型）

### 13.3 推荐配置（5000+ 球）

| 参数 | 推荐值 | 理由 |
|:--|:--|:--|
| `start_top_n` | 50 | 当前瓶颈，越大召回越广 |
| `start_ball_threshold` | 0.15 | 适配 pizza-embed-zh-small-v1 |
| `start_ball_relative_threshold` | 0.85 | 过滤弱相关，减少跨主题污染 |
| `total_water_budget` | 2.5 | 大图下无副作用 |
| `significance` | 1.0 | 大图下影响微弱 |
