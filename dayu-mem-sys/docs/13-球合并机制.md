# 球合并机制

> 状态：**设计已定，代码未实现**
> 本文定义「同一记忆被记成多个球」时如何合并。规则一旦落地，代码必须与本文逐条对应。

---

## 0. 为什么需要它

实测（5000 球，`total_water_budget = 10`，Qwen3-Embedding-0.6B，query「两个部门报表数字对不上怎么办」）：

**注入 29 条，只有 8 个唯一基础句。**

| 唯一句 | 副本数 | cos |
|:--|--:|--:|
| 指标定义不统一导致两个部门报表对不上，后来建了指标字典 | 4 | 0.815 |
| 数据质量问题八成来自上游系统变更没通知 | 4 | 0.528 |
| 把绝对值换成占比之后，趋势才看得清楚 | 4 | 0.466 |
| 把转化率拆成曝光点击下单三段，才知道卡在哪 | 4 | 0.453 |
| 把用户分成新老两组分别算留存，整体数字才有意义 | 4 | 0.440 |
| 相关性不等于因果，我们做了对照组才敢下结论 | 1 | 0.427 |
| 做了归因分析才知道，转化主要来自老用户复购 | 4 | 0.397 |
| 留存率按周看比按天看更稳定，噪音小 | 4 | 0.389 |

同一句话的 4 个球，文本只差前缀：

```
再确认一下：指标定义不统一导致两个部门报表对不上，后来建了指标字典
值得记：    指标定义不统一导致两个部门报表对不上，后来建了指标字典
周会上提过：指标定义不统一导致两个部门报表对不上，后来建了指标字典
整理笔记：  指标定义不统一导致两个部门报表对不上，后来建了指标字典
```

代价有三层：

1. **token 浪费** —— 注入预算被同一内容占满，其他记忆挤不进来
2. **图膨胀** —— 球数虚高、边数虚高，扩散被重复节点消耗
3. **巩固语义错位** —— "同一件事记了 4 次"本该是 1 个球更壮，不是 4 个球各一样弱

## 2. 两条路径

| | 写入端兜底 | 离线合并 |
|:--|:--|:--|
| 触发 | 每次写入新记忆前 | 定时任务（建议每日一次）+ 手动 CLI |
| 阈值 | `0.90` | `0.88` |
| 比较范围 | ANN 检索 top-k 邻居 | 全库聚类 |
| 目的 | 立刻止血，不让副本进入图 | 清理历史遗留，收窄图规模 |
| 失败影响 | 单条写入退化为普通建球 | 整轮跳过，下轮重试 |

**两条路径共用同一套合并规则（§3）**，只是候选集和阈值不同。

## 3. 六条合并规则

### R1 — 保留哪个 id：`size` 最大的那个

| 候选 | 取舍 |
|:--|:--|
| **`size_effective` 最大** | ✅ 承载最多巩固历史 |
| 最老 | ❌ 老不等于强，长期未访问的球可能已衰减 |
| 最近访问 | ❌ 会让 id 频繁变动，日志难以追踪 |

`size_effective` 相同时按 `ball_id` 升序（确定性，保证可复现）。

被合并的球记为 **从属球**，主球记为**保留球**。

### R2 — `size` 怎么合：剩余空间连乘

现有强化公式（`crates/dayu-flow/src/settle.rs:364-366`）：

```
s' = s + delta × (1 - s / C)^gamma        C = ball_size_ceiling，gamma = size_saturation_gamma
```

`gamma = 1` 时剩余空间是乘性衰减：

```
(1 - s'/C) = (1 - s/C) × (1 - delta/C)
```

因此 n 个副本合并的解析解：

```
s_merged = C × (1 - Π (1 - s_i / C))
```

**性质**（都可断言）：

| 性质 | 证明 |
|:--|:--|
| 有界 | `Π ≥ 0` → `s_merged ≤ C` |
| 单调 | `Π ≤ (1 - max_i s_i/C)` → `s_merged ≥ max_i s_i` |
| 可交换 | 乘积与顺序无关 |
| 不等同相加 | `s=5, s=5, C=10` → `7.5`，不是 `10`（clamp）也不是 `5`（max） |

`gamma ≠ 1` 时无闭式解，上式作为**保守近似**（`gamma < 1` 时实际增长更快，连乘低估），文档与代码都注明这一点。

**为什么不是相加**：`size` 是饱和量，相加后 clamp 会让 4 个 `size=5` 的球变成 `size=10`（顶格），等于宣称"这件事被强化到极限"，而实际只是"说了 4 次"。连乘给出 7.5，语义正确。

**为什么不是取 max**：取 max 等于丢弃其余 3 次的巩固，与"合并 = 承认这 4 次都是真的"矛盾。

### R3 — 管道 `w` 怎么合：取最大值

`docs/07-测试方案原则.md:10` 已定：

> **管道粗细**：`w ∈ (0, 1]`，永不归零；合并时取最大值不叠加，不会因合并突然变粗。

实现要点：
- 两球合并后，其出边并集去重（`(from, to)` 唯一）
- 同一条边两侧都存在的，`w = max(w_a, w_b)`
- 自环（主球 ↔ 从属球之间原有的边）直接删除
- 已存在的边不重复累加 `w`

### R4 — 内容怎么合：主球保留 + 副本追加

| 项 | 决定 |
|:--|:--|
| `content`（主内容） | 保留主球的，不改 |
| `content_list`（变体） | 追加从属球的 `content`，**完全相同的去重** |
| 超出 `content_list_max` | 按 FIFO 丢弃最旧的变体，记一条 `tracing::warn` 带丢弃条数 |
| 变体来源标记 | 保留 `source_turn_id`，便于回溯"这句话是哪一轮说的" |

理由：主内容代表"最典型的那次表述"，变体代表"同一件事的不同说法"。全丢掉会损失"用户怎么描述这件事"的信息，全保留会撑爆 `content_list`。

### R5 — 哪些球不参与合并

| 组合 | 是否合并 |
|:--|:--|
| Active ↔ Active | ✅ |
| Archived ↔ Archived | ✅（离线任务可选开启，默认关闭） |
| Active ↔ Archived | ❌ |
| **Contested ↔ 任何** | ❌ |
| **Deleted ↔ 任何** | ❌（已合并过，见 R6） |

理由：

- **归档球**被唤醒后会按唤醒时的上下文重新解释，语义可能漂移；把一个活跃球合并进归档球等于让它消失。
- **Contested（有争议）球**被 `correct_memory` 标记过，说明用户或模型指出这条记忆有问题。把它当作「已有记忆」去强化，等于用一条待复查的内容吞掉新信息。

第二条顺带解决了一个隐患：`correct_memory` 一旦被调用，球就进入 Contested，**从此不再参与合并**，它的 id 永久有效（见 R6）。

默认只处理 Active。配置 `merge_archived = false`。

### R6 — 旧 id 怎么处理：软删除 + 单指针，不做 alias 表

**不做 alias 表。** 理由不是「省事」，是这条链路本身不需要它：

1. **从属球软删除后，`search_by_embedding` 自动排除它**（`crates/dayu-storage/src/trivium.rs:270` 过滤 `status == "Deleted"`），所以调用方拿到的 `ballIds` 永远来自存活球。
2. **`BallStatus::Deleted` 本来就是软删除**（`crates/dayu-domain/src/types/enums.rs:17`），球行还在。所以旧 id **天然有效**，不需要另建映射表——`get_ball(旧id)` 能查到，只是状态是 `Deleted`。
3. **`correct_memory(id)` 的跨周期风险被 R5 关掉**：它把球标成 Contested，而 Contested 球不参与合并，id 永久有效。
4. **不会有链**：合并后被合并的球变成 `Deleted`，而 `Deleted` 不参与合并（R5），所以不存在 A→B→C。

代价对比：

| | 做 alias 表 | 软删除 + 单指针 |
|:--|:--|:--|
| 新增存储表 + schema 迁移 | ✅ 需要 | ❌ 不需要 |
| 每个按 id 查球的入口加重定向 | ✅ 需要 | ❌ 不需要 |
| 链式跟随 + 防环 | ✅ 需要 | ❌ 不需要（最多一跳） |
| 额外查询 | ✅ 每次查球都要 | ❌ 随球一起返回 |
| 「这条记忆去哪了」可查 | ✅ | ✅ |

**做法**：从属球 `set_ball_status(Deleted)`，并在 payload 上写一个指针：

```
merged_into: <保留球 id>
merged_at:   <时间戳>
```

它不是 alias 表——没有独立存储、没有读取重定向、没有链式解析。它只是墓碑上的一个指针，`get_ball` 时随球一起返回，给人看。

合并时同时打一条结构化日志：

```rust
tracing::info!(
    from = from_id.0, to = keep_id.0, similarity = sim,
    "ball merged"
);
```

**内容没有丢**：R4 已把副本内容追加进主球的 `content_list`（带 `source_turn_id`）。丢的只是 id 这个内部标识。

**已知代价**：软删除的球仍占存储与索引体积（检索时被过滤，但数据在）。物理清理不在本期范围，见 §9。

## 4. 阈值

实测余弦分布（`test/lab/dedupe-threshold.cjs`，Qwen3-Embedding-4B）：

| 类别 | cos | 该不该合并 |
|:--|--:|:--|
| 完全副本（加口语前缀） | 0.9691 | ✅ |
| 同事实不同细节 | 0.9315 | ❌ |
| 同义改写（换词） | 0.9161 | ✅ |
| 同句换一个词（语义反转） | 0.8282 | ❌ **绝不能** |

因此：

| 参数 | 值 | 约束 |
|:--|--:|:--|
| `merge.write_threshold` | **0.90** | 必须 > 0.8282（语义反转），< 0.9315（同事实不同细节） |
| `merge.offline_threshold` | **0.88** | 同上，比写入端更松以覆盖换词改写 |

写入端取 0.90 而不是 0.95：0.95 只挡得住"完全副本"，挡不住"换词改写"（0.9161），而换词改写同样会浪费注入位。0.90 落在 0.8282 与 0.9315 之间，两侧各留 0.07 / 0.03 余量。

**换嵌入模型必须重标**：阈值随模型变化，`docs/11-嵌入模型对照.md` 的流程要走一遍。

## 5. 配置

新增 `[merge]` 段（`crates/dayu-domain/src/types/config.rs`）：

```toml
[merge]
# 写入端兜底：建球前查邻居，余弦 ≥ 此值则合并进已有球
write_enabled = true
write_threshold = 0.90
# 写入端只看最近邻，取多少个候选
write_top_k = 3

# 离线合并：定时任务扫描全库
offline_enabled = true
offline_threshold = 0.88
# 一次扫描最多处理多少个球（防止大库长时间占锁）
offline_max_balls = 2000
# 一轮最多执行多少次合并（防止一次改动过大）
offline_max_merges = 500
# 是否处理归档球
merge_archived = false

# 试运行：只统计不落库，用于调阈值
dry_run = false
```

校验（`crates/dayu-config/src/lib.rs`）：
- 两个阈值都必须 `∈ (0, 1]`
- `write_threshold ≥ offline_threshold`（写入端应更严格）
- `offline_max_merges > 0`

## 6. 算法与复杂度

### 写入端兜底

```
embedding = embed(新内容)
neighbors = storage.search_by_embedding(embedding, write_top_k)
best = neighbors 中余弦最大且 ≥ write_threshold 的 Active 球
if best 存在:
    强化 best（追加 content_list、按 R2 提升 size、刷新 last_access）
    新内容不建球
else:
    按现有流程建球
```

复杂度：`O(k log n)`，k = `write_top_k`。

### 离线合并

全库两两比较是 `O(n²)`——10 万球是 100 亿次，不可行。用 ANN 邻居 + 并查集：

```
1. 取一批球（offline_max_balls）
2. 对每个球 b：neighbors = search_by_embedding(b.embedding, k)
   对每个邻居 n：若 cos(b, n) ≥ offline_threshold → union(b, n)
3. 并查集得到连通分量（size ≥ 2 的才是待合并簇）
4. 每个簇：按 R1 选保留球，按 R2/R3/R4 合并，按 R6 软删除从属球并写 `merged_into`
5. 单簇一个事务；任何一簇失败不影响其他簇
6. 达到 offline_max_merges 停止，下一轮继续
```

复杂度：`O(n × k × log n)`。5000 球、k=8 约 4 万次检索。

**为什么用并查集而不是贪心**：贪心（按余弦降序，与已选球冲突则跳过）结果依赖处理顺序；并查集得到的是"余弦图上的连通分量"，与顺序无关，可复现。

**为什么单簇一个事务**：合并会同时改球的 size、内容、边，并删除从属球。跨簇原子性没有意义（两簇无关），单簇原子性保证「不会出现半个合并」。

## 7. 必须断言的不变量

| # | 不变量 | 为什么 |
|--:|:--|:--|
| 1 | 合并后 `size ≤ ball_size_ceiling` | R2 的连乘天然满足，但要防浮点溢出 |
| 2 | 合并后 `size ≥ max(合并前各球 size)` | 合并不能削弱记忆 |
| 3 | 合并后 `w = max(w_a, w_b)`，且 `w ∈ (0, 1]` | R3 + `docs/07:10` |
| 4 | 合并后球数减少 `n-1`，边数不增加 | 图只能变干净 |
| 5 | 无自环、无孤立边；无任何边指向 `Deleted` 球 | 边完整性 |
| 6 | 幂等：同一批球再跑一次不产生新合并 | 副本已删除，簇内只剩 1 个球 |
| 7 | 顺序无关：打乱输入顺序，合并结果相同 | 保留球由 `size` 决定，与顺序无关 |
| 8 | Contested 球不被合并（合并前后都在） | R5 的守卫 |
| 9 | 语义反转不合并：`cos = 0.8282` 的两球在阈值 0.88 下分开 | 阈值下限的守卫 |
| 10 | 合并后注入不再出现重复内容（同一 query） | 端到端目标 |
