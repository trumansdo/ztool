### 🧠 判别器 ONNX 依赖（独立 crate 或 feature gate）

```toml
[dependencies]
# ONNX Runtime 绑定
# 必须使用 rc.15：rc.15 修复了 30+ 处未定义行为和内存泄漏/内存安全问题，
# rc.13 已跳过 ONNX Runtime 1.28，rc.15 强烈建议升级
ort = { version = "2.0.0-rc.15", features = ["load-dynamic"] }
# 或不用 load-dynamic，让 ort 静态链接运行时（体积更大，部署更简单）

# HuggingFace Tokenizer
# 默认 feature 含 onig → 拉 onig_sys（C 语言 oniguruma），在 Windows + rust-lld +
# 新版 UCRT 下会因 __imp_realloc / __imp_strcat_s 符号不匹配而链接失败。
# 换成纯 Rust 的 fancy-regex（tokenizers 要求 onig 或 fancy-regex 二选一），
# 保留 esaxx_fast（Unigram 分词加速，C++ 但不碰 UCRT 符号）。
tokenizers = { version = "0.21", default-features = false, features = ["fancy-regex", "esaxx_fast"] }

# 张量处理（ort 的 TensorRef 通常需要 ndarray 视图）
ndarray = "0.16"
```

**关于 `tokenizers` 的 onig 与 Windows 链接**：`tokenizers 0.21` 默认开启 `onig` feature，它把 oniguruma 的 C 源码编进来。在本机（Windows 11 + `rust-lld` + 新版 UCRT）链接阶段会失败：

```
rust-lld: error: undefined symbol: __declspec(dllimport) realloc
rust-lld: error: undefined symbol: __declspec(dllimport) strcat_s
note: 'realloc' is available in ucrt.lib but cannot be used because it is not an import library
```

原因是 onig 的目标文件按「动态 CRT」编译（引用 `__imp_realloc`），而最终链接拉的是 `libucrt.lib`（静态 CRT，本地定义了 `realloc`）——两边 CRT 模型不一致。这不是本项目代码问题，换 `fancy-regex` 即可绕开整条 C 编译链，且对普通 `tokenizer.json` 行为等价。`esaxx_fast` 保留（它只影响 Unigram 分词速度，不引入 UCRT 符号）。

**关于 `ort` 版本的明确结论**：`2.0.0` **尚未稳定**，rc.15 是当前推荐版本。rc.15 修复了 rc.13 中的 30+ 处未定义行为，并修复了多个内存泄漏/内存安全问题，**不要使用 rc.12 或更早版本**。rc.13 将 ONNX Runtime 跳到了 1.28，带来了新的算子支持和性能改进。

**CPU 执行提供者**：`ExecutionProvider::CPU` 始终可用，**放在执行提供者列表的最后作为兜底**；如果你只跑 CPU，不需要启用 CUDA/CoreML 等 feature，保持依赖树干净。

## 🔧 ONNX 推理管线（Rust 实现骨架）

核心管线是 **Session + Tokenizer → 前向推理 → mean-pooling（按 attention mask 加权）→ 余弦相似度**。以下是基于搜索到的实际代码模式整理的骨架。

### 1. 加载 Session 与 Tokenizer

```rust
use ort::session::{Session, builder::GraphOptimizationLevel};
use ort::execution_providers::CPUExecutionProvider;
use tokenizers::Tokenizer;

pub struct EmbeddingEngine {
    session: Session,
    tokenizer: Tokenizer,
    need_token_type_ids: bool,
}

impl EmbeddingEngine {
    pub fn load(model_path: &str, tokenizer_path: &str) -> Result<Self, Box<dyn std::error::Error>> {
        let tokenizer = Tokenizer::from_file(tokenizer_path)
            .map_err(|e| format!("tokenizer load failed: {e}"))?;

        let session = Session::builder()?
            .with_optimization_level(GraphOptimizationLevel::Level3)?
            .with_execution_providers([CPUExecutionProvider::default().build()])?
            .commit_from_file(model_path)?;

        // 检查模型是否需要 token_type_ids（BGE 系列通常不需要，但有些模型需要）
        let need_token_type_ids = session
            .inputs()
            .iter()
            .any(|i| i.name() == "token_type_ids");

        Ok(Self { session, tokenizer, need_token_type_ids })
    }
}
```

**`Session::builder()` 的关键配置**：
- `GraphOptimizationLevel::Level3`：最高图优化级别，对嵌入模型通常有收益；
- `CPUExecutionProvider`：CPU 始终可用，**放在执行提供者列表最后**；如果只跑 CPU，不需要启用 CUDA/CoreML feature；
- `commit_from_file`：从本地文件加载，**避免 `fetch-models` 的隐式下载**（`fetch-models` 官方明确说“almost never use in production”）。

### 2. 批量编码与推理

```rust
use ort::inputs;
use ort::value::TensorRef;
use ndarray::Array2;

pub fn embed_batch(&self, texts: &[&str]) -> Result<Vec<Vec<f32>>, Box<dyn std::error::Error>> {
    // 1. Tokenize + padding + truncation
    let encodings = self.tokenizer
        .encode_batch(texts.to_vec(), true)
        .map_err(|e| format!("tokenize failed: {e}"))?;

    let batch_size = encodings.len();
    let max_len = encodings.iter().map(|e| e.get_ids().len()).max().unwrap_or(0);

    // 2. 构建 input_ids / attention_mask 张量
    let mut input_ids = Array2::<i64>::zeros((batch_size, max_len));
    let mut attention_mask = Array2::<i64>::zeros((batch_size, max_len));

    for (i, enc) in encodings.iter().enumerate() {
        let ids = enc.get_ids();
        let mask = enc.get_attention_mask();
        for j in 0..ids.len() {
            input_ids[[i, j]] = ids[j] as i64;
            attention_mask[[i, j]] = mask[j] as i64;
        }
    }

    // 3. 构建 ort inputs
    let mut feeds = vec![
        ("input_ids", TensorRef::from_array_view(&input_ids.view())?.into()),
        ("attention_mask", TensorRef::from_array_view(&attention_mask.view())?.into()),
    ];
    if self.need_token_type_ids {
        let token_type_ids = Array2::<i64>::zeros((batch_size, max_len));
        feeds.push(("token_type_ids", TensorRef::from_array_view(&token_type_ids.view())?.into()));
    }

    // 4. 推理
    let outputs = self.session.run(feeds)?;
    let hidden = outputs["last_hidden_state"].try_extract_tensor::<f32>()?;
    // hidden shape: [batch, seq_len, hidden_dim]

    // 5. Mean-pooling（按 attention_mask 加权）
    let mut embeddings = Vec::with_capacity(batch_size);
    for i in 0..batch_size {
        let mut sum = vec![0.0f32; hidden.shape()[2]];
        let mut count = 0.0f32;
        for j in 0..max_len {
            if attention_mask[[i, j]] == 0 { continue; }
            for k in 0..hidden.shape()[2] {
                sum[k] += hidden[[i, j, k]];
            }
            count += 1.0;
        }
        for v in &mut sum { *v /= count.max(1.0); }
        // L2 归一化（余弦相似度前置条件）
        let norm = sum.iter().map(|x| x * x).sum::<f32>().sqrt();
        for v in &mut sum { *v /= norm.max(1e-8); }
        embeddings.push(sum);
    }

    Ok(embeddings)
}
```

**关键细节**：
- **Pooling 策略**：BGE 系列用 **mean-pooling（按 attention mask 加权）**，不是 CLS。如果模型输出已经是 pooled 向量（某些导出配置），则跳过 pooling 直接用输出。
- **L2 归一化**：嵌入向量归一化后，余弦相似度退化为点积，后续计算更简单。**归一化必须在 pooling 之后做**。
- **`Session::run` 的 `&mut self` 约束**：`ort` 的 `Session::run` 在 Rust API 上要求 `&mut self`，但 ONNX Runtime C API 的 `Run()` 是线程安全的。如果需要在多线程间共享 session，可以用 `Mutex<Session>`，或者用内部 unsafe 的方式证明无数据竞争（仅当你完全理解风险时）。

### 3. 余弦相似度（判别器的核心计算）

```rust
pub fn cosine_similarity(a: &[f32], b: &[f32]) -> f32 {
    // 两个向量都已 L2 归一化，余弦 = 点积
    a.iter().zip(b.iter()).map(|(x, y)| x * y).sum()
}
```

判别器对每个候选片段和每个候选球的内容嵌入做余弦相似度，输出 `Relevance`（映射到 `[0, 1]`）。


## ⚠️ 需要留意的实际问题

### ort rc.15 的 API 变动

rc.15 相对 rc.12 有多处 API 变动，**按 rc.15 的文档写代码，不要照搬旧教程**：
- `run_async` 现在只接受 owned inputs；
- `ExecutionProviderLibrary::unregister` 已移除；
- `ValueRefMut` 不再实现 `DerefMut` 到 `Value`；
- `InMemorySession` 不再实现 `DerefMut` 到 `Session`；
- `Kernel` 现在要求 `Send`，`ThreadManager` 要求 `Send + Sync`。

这些变动主要影响异步推理和自定义算子场景；你的嵌入推理管线（同步 `run`）受影响较小。

### 模型文件的部署形态

- **快速验证**：`pizza-embed-zh-small-v1` 约 91 MB，`ort` 静态链接运行时（不用 `load-dynamic`）即可，插件分发时把 `.onnx` 和 `tokenizer.json` 作为数据文件打包；
- **性价比层**：`piccolo-large-zh` 约 0.65 GB，建议**用 `load-dynamic` + 系统安装的 ONNX Runtime**，避免把运行时和模型都塞进插件包；
- **`load-dynamic` 的代价**：运行时需要 `ORT_DYLIB_PATH` 指向 ONNX Runtime 共享库；如果用户环境没有，启动会失败。**在插件初始化时做健康检查，失败则降级为“仅归档、不起念”**。

### 批量大小与延迟

ONNX Runtime 在 CPU 上对嵌入模型做了高度优化，**小模型在 CPU 上的推理延迟与 GPU 相当**，不需要 GPU 依赖。单条中文短文本的嵌入延迟通常在 **10–30ms** 量级；判别器是异步旁路，200–800ms 的预算完全够用。**不要为了批量推理而攒批**——单用户对话的候选片段数量少，攒批的等待时间会超过推理本身。

```bash
# 1. 下载原始模型（HuggingFace 或 Modelers）
git lfs clone https://huggingface.co/sensenova/piccolo-large-zh
# 或国内镜像：
# git lfs clone https://hf-mirror.com/sensenova/piccolo-large-zh

# 2. 用 optimum-cli 导出 ONNX
pip install optimum[onnxruntime]
optimum-cli export onnx \
  --model ./piccolo-large-zh \
  --task feature-extraction \
  ./piccolo-large-zh-onnx/

# 3. 导出后得到 model.onnx 和 tokenizer.json（BERT 分词器）
```

导出后的 tokenizer 是标准的 BERT 分词器，`tokenizer.json` 会一并生成；如果 `optimum-cli` 没有自动复制 `vocab.txt`，从原始仓库手动拷贝一份即可。


### 💎 汇总：一条命令批量下载（pizza + bge-m3）

```bash
#!/bin/bash
set -e
mkdir -p models/{fast/onnx,balanced}

# pizza-embed-zh-small-v1（快速验证，推荐首选）
p="https://huggingface.co/infinilabs/pizza-embed-zh-small-v1/resolve/main"
curl -L -o models/fast/onnx/model.onnx      "$p/onnx/model.onnx"
curl -L -o models/fast/onnx/model.onnx.data "$p/onnx/model.onnx.data"
curl -L -o models/fast/tokenizer.json       "$p/tokenizer.json"
curl -L -o models/fast/tokenizer_config.json "$p/tokenizer_config.json"

# bge-m3 INT8（性价比，社区版）
b="https://huggingface.co/gpahal/bge-m3-onnx-int8/resolve/main"
curl -L -o models/balanced/model_quantized.onnx "$b/model_quantized.onnx"
curl -L -o models/balanced/sentencepiece.bpe.model "$b/sentencepiece.bpe.model"
curl -L -o models/balanced/tokenizer.json "$b/tokenizer.json"

echo "done."
```

**目录结构**：
```
models/
├── fast/                      # pizza-embed-zh-small-v1（~91 MB）
│   ├── onnx/model.onnx
│   ├── onnx/model.onnx.data
│   ├── tokenizer.json
│   └── tokenizer_config.json
└── balanced/                  # bge-m3 INT8（~543 MB）
    ├── model_quantized.onnx
    ├── sentencepiece.bpe.model
    └── tokenizer.json
```

**快速验证直接用 `models/fast/` 下的四个文件**，它们和 `ort` + `tokenizers` 的加载路径完全匹配，不需要任何转换。piccolo-large-zh 的 ONNX 导出作为后续升级路径，不在第一版阻塞。

## 附：不采用进程内 GGUF 加载（2026-11-10 结论）

尝试过 `llama-cpp-2` 0.1.161 直接加载 GGUF，结论是**必须从源码编译**，因此放弃：

| 尝试 | 结果 |
|:--|:--|
| 预编译 `llama.dll` + `dynamic-link` | ❌ 段错误（exit 139） |
| 自编译 `llama.dll` + `dynamic-link` | ✅ 但 `dynamic-link` 只是把 llama.cpp 编成 DLL，仍要 CMake + LLVM |

段错误的原因不是缺符号，而是 ABI 不兼容：发布包 b12244 的 `llama.dll` 导出 299 个符号，
crate 内置源码编出的只有 278 个，且 **278 个全在 299 里**（一个不缺）。
但发布包多出了 `llama_batch_ext_add_embd_row` 等接口，说明 `llama_batch` / `context_params`
的结构定义变了 —— Rust 侧按旧布局构造结构体传给新 DLL，字段错位，直接崩。

**结论**：`llama-cpp-2` 没有跳过编译的入口（`build.rs` 的 32 个环境变量全部检查过），
`system-ggml` 反而需要读取 CMake 生成的 `CMakeCache.txt`。

**替代方案**：需要本地 GGUF 模型时，用预编译的 `llama-server.exe` 起一个 OpenAI 兼容服务，
走已有的 `http` 后端，零编译、零代码改动。
