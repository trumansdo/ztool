# 大禹水利记忆网络 · 全部讨论条目分类清单

## 一、初始水量（注水入口）

| 条目 | 内容 |
|---|---|
| **总水量 W₀** | 每次激活的硬预算，固定值，不随命中球数变化 |
| **起始球选择** | 当前输入嵌入与所有 active 球算余弦，过滤 `< start_threshold`（默认 0.3），取 Top-N（默认 3） |
| **无球超阈值** | 本轮不注水，无记忆注入，正常状态非故障 |
| **注水分配** | `W_i = W₀ × cos_i / Σcos_j`，总量守恒（已修正代码中每球各拿满 W₀ 的 bug） |
| **单起始球退化** | 只有一个起始球时占比 100%，退化为拿满 W₀ |
| **强线索放大** | 某起始球余弦 > `strong_cue_threshold`（默认 0.85）时，W₀ 先放大 `strong_cue_multiplier`（默认 3.0）再分配 |
| **多输入源汇合** | 多输入源汇合要解决的问题是：一轮对话里用户消息、工具结果、模型自己的话可能各自产生查询嵌入，如果每个源都独立按 W₀ 分配起始球水量，总注水量会随源数量线性膨胀，让“多塞一个输入源”变成无成本的扩散放大器，破坏注水守恒的预算前提。理由是多个线索共同指向同一批球本身就是强信号，值得比单源略强的扩散力，但不该线性叠加。解决方式是各源独立选起始球后，先按扩散区域重叠度（|A∩B| / |A∪B| ≥ `multi_source_overlap_threshold`，默认 0.3）做连通分组——重叠的源并成一组共享一次流动、不重叠的各自独立流动，组内合并去重、同一球取最大余弦，总水量按 `W₀ × min(1 + source_bonus × (n_sources−1), source_cap)` 次线性放大并封顶（单源退化为严格守恒），子预算按各源最高余弦占比分配，同一球被多源命中时再受 `multi_source_merge_cap` 约束单球注水量；`source_bonus=0` 可关闭放大用于对照实验。 |
| **除零防御** | `Σcos` 理论上 >0（起始球已过滤阈值），实现仍需兜底 |


## 二、水球（Ball）

| 条目 | 内容 |
|---|---|
| **size_stored** | 水球在存储中的固有大小，代表这个球历史上累积了多少强化。它只在水球被结算强化时增加、被纠正时扣减，存储层不做任何时间衰减——今天存进去多大，明天读出来还是多大。DB 里与它一起存的还有 last_watered（上次注水时间）和 S（稳定性，随注水次数增长），三者共同构成球的完整状态；S 必须独立存，不能从 size_stored 推导，因为它承载的是“这个球抗衰减的能力有多强”这一独立信息——两个 size_stored 相同的球，注水 20 次和注水 2 次的 S 不同，衰减速度不同，这就是间隔效应。写入时机只有结算事务（size_stored += 含边际递减的有效增量、last_watered = now、S 按注水次数增长）和纠正操作（按贡献扣减），饱和时 clamp 到 [0, size_max]。它不直接进入任何消费计算——不直接决定补充量、不直接进入注入排序、不直接进入相关性，这些都用 size_effective。 |
| **size_effective** | 水球在当前时刻真正可用的有效大小，回答的是“这个球现在还有多活”。读取时现算 size_stored × exp(-Δt/S)，Δt = now - last_watered，S 是稳定性。永不落库——因为它是时间的函数，存了明天就过时，还得定时刷新；而存 size_stored + last_watered + S 三个稳定量，任何时刻都能算出正确值，且 size_stored 可增量更新。所有消费方统一使用它：补充规则用它算可释放水量、归档触发用“size_effective 低 + 久未注水”判断。它**不参与任何“谁更重要”的决策**——起始球选择只用余弦、注入排序只用 semantic_similarity、注水分配按余弦占比；size 是“相关性 → 强化 → size_stored 增长”的历史累积结果，是相关性的滞后代理，决策时再乘它等于同一信号算两遍。它只保留两个物理角色：补充释放的活性（含时间衰减）、渲染长度的估算（用 size_stored、不衰减）。这修正了此前“球自身衰减一次、补充规则乘一次新鲜度、排序再乘一次”的重复计权问题——衰减只在读取时算这一次，不再额外乘。结算时也不写回它，写回的是 size_stored。管道遵循完全同构的模式：存 w、last_flowed、S_pipe，读取时算 w_eff = w × exp(-Δt/S_pipe)，但 S_pipe 独立演化，管的是“这条联想通不通”，与球的“记忆牢不牢”是两套独立的衰减。 |
| **新鲜度只算一次** | 这条要解决的问题是：衰减因子 `R(t) = exp(-Δt/S)` 曾在前面的设计里被乘了三次——球自身衰减一次（`size *= exp(-Δt/S)` 直接改存储值）、补充规则乘一次新鲜度（`可释放水量 = 球大小 × R(t)`）、注入排序再乘一次（`排序 = 相关性 × 球大小 × 新鲜度`），同一个衰减被重复计算，陈旧球被平方甚至立方地过度沉底。理由是：`R(t)` 本身不能删——它的稳定性 `S` 随注水次数增长，编码了“这个球被巩固过多少次”的间隔效应，两个 `size_stored` 相同的球，注水 20 次和注水 2 次的衰减速度不同，这个差异只能由 `S` 承载；但它在多个环节重复出现，说明“衰减到底在哪里算”没有收敛。解决方式是把衰减收敛到**读取时算一次**：存储层只存 `size_stored`（固有大小，不衰减）、`last_watered`、`S`，读取时统一计算 `size_effective = size_stored × exp(-Δt/S)`，所有消费方——起始球选择、补充规则、注入排序、归档触发——统一使用 `size_effective`，不再额外乘任何新鲜度；结算时只写回 `size_stored`、刷新 `last_watered`、增长 `S`，**永不写回 `size_effective`**。关键在于“对齐”：同一次激活内，衰减基准点固定在流动开始读快照的那一刻，流动和结算共用同一个 `size_effective`，结算不重新调 `now()` 再算一遍——否则流动跑几十毫秒后结算时 `Δt` 又变了，同一个球在流动里和结算时算出的有效大小不一致，“只算一次”就破了；跨激活时每次激活各自算一次，不跨激活累积乘法；版本冲突时旧计算作废、基于最新状态重算一次，这不算重复计权，因为旧的那次结果已经因冲突失效。管道的 `w_eff = w × exp(-Δt/S_pipe)` 遵循同构但完全独立的模式，`S_pipe` 随流动次数增长，管的是“这条联想通不通”，与球的“记忆牢不牢”是两套衰减，不混用。这条原则的判据很简单：任何消费方如果需要“陈旧就弱一点”，都应该直接读 `size_effective`，而不是在它之上再乘一个 `R(t)`——后者就是重复计权。 |
| **稳定性 S** | S 决定球抗遗忘的能力，R(t) = exp(-Δt / S_effective)，它与 size_stored 正交——size_stored 回答“被强化了多少”，S 回答“衰减得有多慢”，两个 size_stored 相同的球，注水 20 次和 2 次的 S 不同、衰减速度不同，这就是间隔效应，必须由 S 独立承载，不可从 size_stored 推导。S 采用饱和增长 + 长期不活动衰减的双重规则：每次结算强化时 S 按注水次数或强化增量增长，增长有上限 S_max（如 730 天）、增长速率随 S 增大而递减；同时 S 随时间间隔按曲线速减，存储 S_stored 和 last_watered，读取时算 S_effective = S_stored × exp(-Δt / S_decay)，S_decay 建议 180–365 天（比 blocked_count 的衰减慢得多，因为“记忆本身淡化”比“差点通过的痕迹淡化”慢）；结算时先算 S_decayed = S_stored × exp(-Δt / S_decay)，再叠加增长增量、封顶 S_max，写回 S_stored 并刷新 last_watered——写回的是“已衰减到当前时刻的值 + 增长量”，不是原始累积值，这样长期不活动的球 S_effective 自然下降、R(t) 衰减加速，符合“长期不用、稳定性本身也会流失”的直觉，不会出现“年轻时反复强化、之后多年不用、S 永远保值、永不淡忘”的问题。纠正不重置 S_stored，但 S_stored 会随时间自然衰减；S 不参与流动和结算的任何直接计算，唯一用途是进入 R(t) 间接影响 size_effective。管道的 S_pipe 遵循完全同构的模式（饱和增长 + 长期不流动衰减，读取时算 S_pipe_effective，结算时先衰减再叠加），管“联想通不通”，与球的“记忆牢不牢”是两套独立状态 |
| **size_max** | size_max 是球固有大小 size_stored 的硬天花板，全局统一、默认 10.0、可配，不按球分类型——长期/短期的差异靠稳定性 S 表达，不靠不同的 size_max。它只出现在结算的边际递减公式里：有效增量 = 强化值 × (1 - size_stored/size_max)^γ（γ 默认 1.0），球越接近上限增量越小，饱和后 size_stored 不再增长，但 last_watered 仍刷新、管道照常变粗、内容仍可追加，长时间不注水衰减到上限以下后可以重新增长。注入排序曾用 size_effective / size_max 作归一化分母，已废弃——排序不再乘球大小。引入它的理由是：没有上限，一个被反复强化的球会无限变大，最终压过一切，注入排序里“大小”这个因子会失控；有了上限，“强化边际递减”和“一件事想太多次就不会再加深”的直觉才能落地。写入时 size_stored = min(size_stored + 有效增量, size_max) 且 clamp 到 [0, size_max]，防止浮点误差越界；size_max 配置校验拒绝 0 和负数，避免归一化除零。它和 S_max 是两套独立的上限——size_max 管“球能变多大”，S_max 管“衰减能变多慢”，两者不混用。 |
| **边际递减** | 球被结算强化时，写入 size_stored 的不是原始强化值，而是乘上一个随 size_stored 接近 size_max 而递减的系数：有效增量 = 强化值 × (1 - size_stored/size_max)^γ，γ 默认 1.0、可配，γ=0 退化为纯线性硬饱和，γ 越大边际递减越强。球越接近上限，同样强度的路径强化带来的增量越小；严格达到 size_max 后有效增量为 0，size_stored 不再增长，但 last_watered 仍刷新、管道照常变粗、内容仍可追加。引入它的理由是：没有边际递减，一个被反复强化的球会线性膨胀到上限然后突然停住，“从 9.9 到 10.0”和“从 1.0 到 1.1”的强化效果一样，不符合“越强越难更强”的直觉；有了它，饱和不是一个突兀的开关，而是一个平滑的、可配置的逼近过程，同时避免少数大球长期贴在上限、彼此失去区分度。它只作用于结算写入侧，size_effective 是读取时现算的派生值，不参与边际递减计算；它和 S 的饱和增长是两套独立的机制——边际递减管“球能变多大”，S 饱和增长管“衰减能变多慢”，两者公式同构（都是趋近上限、增量递减）但作用对象不同，不混用。 |
| **饱和后行为** | 球达到 `size_max` 后，**只有 `size_stored` 这一个量停止增长**（有效增量为 0），其余状态照常演化：`last_watered` 仍刷新为本次结算时间——因为“我刚想起过它”这个事实必须记录，否则衰减计时会错，球会被误判为“很久没注水”而被归档；稳定性 `S` 仍按饱和增长规则继续演化——强化次数仍在累积，只是 `S` 自身也有 `S_max` 上限；路径上的管道照常变粗——球饱和不等于它和邻居的关联饱和，“一起被想起”这个信号仍要写进管道；内容列表仍可追加（去重后）——球的大小到顶了，但它仍可以承载新的经验，只是这些新内容不再让它变大。饱和**不是永久状态**：长时间不注水，`size_effective` 随衰减降到 `size_max` 以下，下次被强化时有效增量恢复为正，球可以重新增长——记忆会淡化，淡化后可以再次被强化，这与“疏而不堵、不删除”的理念一致。关键是饱和只封住“大小”这一个维度，不封住“最近注水时间”“稳定性”“管道强度”“内容容量”这些维度，球不会因为饱和而变成僵死的状态。 |
| **新球初始大小** | 新球创建时的 size_stored 由 size_init_min + 显著性 × size_init_factor 决定，size_init_min 默认 0.1、size_init_factor 默认 0.5，两者均可配——显著性 0.8 的球初始约 0.5，显著性 0.5 的球初始约 0.35。引入这个公式的理由有两条：一是新球不能太小，如果初始 size_stored 接近零，它释放的可释放水量 size_effective × 相关性系数 不足以突破任何中等阻力管道，就会变成永远扩散不出去的“死球”，size_init_min 是保证新球至少能释放一次足以通过中等管道的补充的保底值，全局统一、不随球变；二是新球初始大小要与触发它的显著性相关，一个在高度显著片段上起念的球，初始就应该比弱显著片段上的球更大，这样它在下一轮流动里有更高的 size_effective、更容易被起始球选中和补充，符合“强烈的念刚产生时就更有分量”的直觉。size_init_min 和 size_init_factor 只作用于新球创建那一刻，之后球的增长完全由结算强化和边际递减决定；新球创建走独立事务，与流动/结算解耦，判别器异步产出新球时不影响本轮注入，只影响下一轮流动。兜底合并命中已有球时不创建新球，而是给已有球 size_stored += 显著性 × size_init_factor 的强化，不叠加 size_init_min——因为已有球不需要“保底可扩散”，它已经在线上了。 |
| **新球接图** | 新球创建时，用其嵌入与所有 active 球算余弦，过滤低于 `new_pipe_threshold`（默认 0.5）的球，取 Top-K（默认 2）建弱管道，初始 `w = 余弦 × new_pipe_initial_factor`（默认 0.5），创建来源标记为 `new_ball`。引入这个机制的理由是：新球没有管道就是孤岛，下次流动永远到不了它；但也不能乱连——阈值 0.5 是“语义上有明确关联”的保守分界，太低会让新球连上一堆弱相关球、图变成乱麻，太高会让大多数新球成为孤岛；Top-2 而非 Top-5 是因为新球刚创建、语义身份还不稳定（只有一条内容），连太多球会让它过早绑定到多个方向，后续强化时水流分散；初始 `w` 取“余弦 × 0.5”是刻意做细——新球刚建立，关联强度还没被验证，细管道让常规水流不容易通过，但强线索可以突破，后续共激活或结算强化会让它自然变粗。没有球超过阈值时，新球就是孤岛，这是**正常状态不是故障**——新概念、新话题刚出现时，图上确实没有相关节点，强行接一条弱管道反而破坏结构；孤岛球的后续路径是强线索直接命中（成为起始球、注水后释放补充）、离线巩固补边（余弦 > `offline_pipe_threshold` 时建管道）、或永远孤岛（仍然可以被强线索直接命中而激活，只是不参与多跳扩散）。新球创建、建内容、建初始管道在同一事务内完成，要么完整存在要么不存在，不会出现“球建了但管道没建”的半完成状态；`graph_version` 随之递增，正在流动的其他进程会在结算时检测到版本变化并重算。 |
| **兜底合并** | 判别器判定“产生新球”后，系统层在真正建球之前先做一次兜底检查：用候选片段的嵌入与已有 active 球算余弦，若与某个球的余弦超过 merge_cosine_threshold（默认 0.95），不创建新球，而是把触发片段追加到该已有球的内容列表，并给已有球一次强化 size_stored += 显著性 × size_init_factor（不叠加 size_init_min——已有球不需要“保底可扩散”，它已经在线上了）。引入这个机制的理由是：判别器的职责是“是否起念”，不是“是否是新球”——它可能在 prompt 里看到 top-5 候选球后仍误判“新球”，系统层需要兜底拦截“几乎完全相同”的情况，否则同一个记忆会被反复创建成多个球，产生碎片化；但阈值必须很高（0.95），只拦截“几乎完全相同”，不拦截“语义相近但确实不同”的球——语义相近但不同的球应该作为两个球存在、靠管道连接，而不是合并。兜底合并和新球创建走同一个事务：要么建新球 + 建内容 + 建初始管道，要么追加内容 + 强化已有球，不会出现半完成状态；graph_version 递增。它和离线巩固里的“原型合并”是两层不同的机制：兜底合并是写入时拦截“几乎完全相同”的重复创建，离线合并是巩固时合并“语义相近且管道很粗”的已有球，前者防碎片化于未然，后者收敛历史遗留的冗余。 |
| **内容列表** | 每个球挂载一个内容列表，存放可渲染为文本的记忆本体——触发片段原文、后续被强化时追加的语境片段、离线巩固生成的摘要或抽象，默认上限 5 条、可配。新球创建时挂触发片段原文作为第一条内容；球被强化时，本次流动中经过该球且产生补充的语境片段在去重后追加；离线巩固时，同一球下多条内容聚类生成摘要或抽象，作为新内容追加。超出上限时按“被注入次数”淘汰最不常用的那条，淘汰不是删除，而是转入冷存储表、带球 ID 索引，强线索需要回源时才读取——这符合“疏而不堵、不删除”的理念，内容列表只是热层，冷层永远保留。内容本身可被纠正：用户否定某条内容时标记 archived，不再参与渲染，但不删除；内容列表的长度和总字节数也是“这个球承载多少信息”的度量，未来若要做“内容丰富度调制衰减”，用的是这个维度而不是 size_stored。每条内容带编码标记（rmw-utf8 或 raw），中文短文本压缩存储、不膨胀则回退原文；单条内容长度有上限（默认 4000 字符），超出截断为“前 N 字符 + 摘要”，原文转冷存储。内容列表和 size_stored 是正交的：size_stored 是“这个球被强化了多少”，内容列表是“这个球里装了什么”；一个球可以很大但内容列表很短（反复强化同一条内容），也可以很小但内容列表很长（刚创建、多条不同语境被追加），两者互不替代。 |
| **嵌入** | 每个球持有一条语义向量，用于计算相似度——起始球选择、流动相关性、结算路径相关性、新球接图、离线补边、归档召回，全部依赖它。关键设计是：一个球可以挂多条内容，但只有一个嵌入，这个嵌入是内容列表的“语义重心”，不是某一条内容的复制——球被强化时，若本次语境片段被追加为内容，嵌入做一次 EMA 更新 新嵌入 = 旧嵌入×(1−β) + 本次内容嵌入×β，β 默认 0.1，让球的语义身份缓慢漂移，不会因为追加一条内容就突变；内容被纠正标记 archived 后，嵌入不立即重算，由后续 EMA 自然稀释。引入 EMA 而非“对内容列表重新嵌入取平均”的理由是：EMA 是增量的，不需要每次重算全部内容；且它让球的语义身份稳定。嵌入存储用 TriviumDB 原生 Vector 字段，f32 存储、内部可 f16 量化，存储体积随维度线性变化——维度不是固定常量，由具体嵌入后端决定：pizza-embed-zh-small-v1 是 512 维，piccolo-large-zh 是 1024 维，bge-small-zh-v1.5 是 512 维，bge-m3 是 1024 维。QuIVer ANN 在向量数超过阈值时自动激活，无需额外向量库。嵌入不承担检索职责——它只提供向量，余弦计算、阈值判断、归属判定都由规则层完成；不直接出现在注入文本里——注入渲染的是内容列表里的文本。维度一致性是启动时的硬校验：DayuCore 初始化时校验 EmbeddingBackend::dimension() 与球存储的向量维度一致，不匹配则启动失败而不是运行时静默错乱；换嵌入模型（如从 pizza 的 512 维切到 piccolo 的 1024 维）时，需要一次显式的迁移——要么全库重算嵌入，要么新建球表、旧球按需回填，不能在同一张表里混存不同维度的向量。 |
| **可释放水量** | 可释放水量是球在水流到达时能贡献给水流的补充量，不是 size_effective × 相关性系数 的线性乘积，而是“资格 + 幅度”两段式：先看相关性是否过补充资格阈值 supplement_threshold（默认建议 0.4–0.5，高于 flow_threshold），低于它时补充量为零——球不贡献任何水，防止一个勉强过流动阈值的弱相关大球靠历史强度放大水流；高于它时补充按归一化相关性增长，补充量 = size_effective × (相关性 - supplement_threshold) / (1 - supplement_threshold)，相关性刚好过阈值时补充接近零、接近 1 时才拿满 size_effective，size_effective（当前有效大小，已含时间衰减）是“潜力”、归一化相关性是“兑现比例”。关键语义是：球释放补充后自身不变——可释放水量是计算值，不是从球里扣水，球的大小变化只在结算时发生（被路径强化则变大、久不注水则惰性衰减），流动过程中球只是贡献了一个由当前状态决定的水量。补充量还受 max_supplement_ratio（默认 2.0）截断：补充量 = min(可释放水量, 当前水量 × max_supplement_ratio)，防止大球让水流指数爆炸。可释放水量 > 当前损失 时水流可能被放大、继续扩散，可释放水量 < 当前损失 时水流衰减、联想链更早终止——这就是“补充 > 损失当且仅当球大、新鲜、强相关”的工程对应，但“强相关”现在有了明确的资格阈值，不是线性乘一个小的相关性系数；supplement_threshold 不能设太高，否则中等相关球都不补充、水流衰减太快、多跳联想被扼杀，supplement_threshold = flow_threshold 时退化为旧行为，可作为对照基线。 |
| **状态** | 球有四种状态：active、contested、archived、deleted，状态决定它是否参与流动、是否可被注入、是否可被纠正。active 是正常运行状态，参与起始球选择、流动、结算、注入排序；contested 是“有争议”状态，由隐式纠正（用户话与注入记忆矛盾）或离线矛盾检测触发，仍可参与流动，但注入时带“我之前的理解可能不准确”的标注，不直接删除是因为单次矛盾可能误判，等离线巩固再确认——确认正确则回 active，确认错误则转 archived；archived 是“休眠”状态，不参与常规流动和起始球选择，但存储保留、嵌入保留、内容保留，且**仍参与检索**——被余弦 ≥ `start_ball_threshold` 的线索命中即直接翻回 active（无临时态、无 TTL），归档触发条件是“距上次注水超 `archive_inactive_days` + `size_effective` 低于 `archive_size_threshold`”两条同时满足（另有活跃球数超 `max_active_balls` 时按有效大小强制归档的兜底）；deleted 是唯一不可逆状态，只能由用户显式“永远忘掉”并二次确认触发，执行硬删或加密归档，纠正审计保留但球本身不再可召回。状态转换的路径是：新建 → active；active → contested（隐式纠正/矛盾检测）；contested → active（确认正确）或 archived（确认错误/显式纠正）；active → archived（规模管理触发）；archived → active（被检索命中即翻回）；archived → deleted（显式永久删除+二次确认）。这套状态设计的核心理由是“疏而不堵”：除了 deleted，没有任何状态是“删除”——contested 只是标注不确定、archived 只是休眠可唤醒，球始终在存储里，只是“能不能被这次水流想起”不同；状态转换全部走纠正审计，correction_log 记录原状态、新状态、触发来源、时间、可逆性，保证每一次状态变化都可追溯、可回退（deleted 除外）。状态和 size_stored、S、内容列表是正交的：状态管“这个球现在参不参与”，size_stored 管“它被强化了多少”，S 管“它衰减多慢”，内容列表管“它装了什么”——一个球可以 active 但很小、可以 archived 但内容很多，状态不替代其他维度，只回答“此刻它是否可被召回”。 |
| **归档触发** | 归档由离线扫描执行（`DayuCore::archive_sweep`），定时任务与 `dayu archive` CLI 共用这一个入口。判定是**时间与大小两条同时满足**：距 `last_watered` 超过 `archive_inactive_days`（默认 90 天），且 `size_effective` 低于 `archive_size_threshold`（默认 0.2）。这里不要求“球数超过 max_balls × 0.8”——“又小又旧”本身就是精确的归档信号，把它和“规模超限”绑在一起会让归档在球数没超时永不发生，小旧球一直占着起始球扫描成本。规模超限单独处理：活跃球数超过 `max_active_balls`（默认 1 万）时，按 `size_effective` 升序（同分按 id，保证可复现）强制归档最弱的球，直到回落到上限——这条是兜底，不是常规路径。两条规则叠加的效果是：平时只归档“又小又旧”的，规模真的超了才动还没衰减透的球。归档只改 `status` 字段，`size_stored`、`S`、`last_watered`、`embedding`、内容列表全部保留；归档球不删除、不进独立表，仍留在同一张球表里、与主图共用同一份索引——“归档区也建索引”不是另建一套，而是归档不摘索引。每次扫描记指标（归档球数、扫描前活跃球数、扫描后活跃球数），用于判断 `max_active_balls` 是否设得太小。 |
| **归档唤醒** | 归档球必须能被检索到，这是“疏而不堵”的底线。`search_by_embedding` 只过滤 `deleted`、不过滤 `archived`，归档球与活跃球在同一索引里按余弦排序，共用同一个 `start_ball_threshold`（默认 0.3），不设独立的 `archive_recall_threshold`。理由是：给归档球设更高的唤醒门槛（旧设计的 0.9）等于让它几乎不可召回，而“是否值得唤醒”应该由相似度本身回答，不该再叠一个状态相关的阈值。唤醒**不做临时加载**：归档球一旦被选为起始球，直接持久化翻回 `active`，没有临时态、没有 TTL、没有“流动后未强化则回归 archived”。理由是临时态需要在每次流动后做一次判定和写回，多一个状态机分支、多一次写事务；而“被问到”本身就是足够强的唤醒信号——它已经进入起始球，说明线索够了。唤醒发生在结算之前（`DayuCore::recall` 取 `depth == 0` 的球调 `wake_archived`），本次流动它已按普通球参与，下一次检索它就是活跃球。代价是归档球会因一次偶然的高相似输入永久回到主图，但这与“不删除、只降可提取性”一致：既然被想起，就该留在主图。 |
| **点亮次数** | 球被水流点亮时累加的轻量计数，与 size_stored、S、last_watered 完全解耦——点亮不刷新衰减计时、不触发 size_stored 增长、不改变 S，它只记录“这个球被水流到达过多少次”，不记录“它被强化了多少次”。引入它的唯一用途是舌尖效应：一个被多次点亮但从未被强化（相关性没过 supplement_threshold 或没过 strengthen_threshold_X）的球，说明它“反复差点被想起”，下次流动时给予轻微的阻力折扣（blocked_count 的折扣是“被阻挡”的补偿，点亮次数的折扣是“反复被到达但未兑现”的补偿），让它更容易被再次点亮、更容易在下次强线索下真正通过。如果点亮就刷新 last_watered，那经常被路过但从未被真正激活的球会“永葆青春”，衰减机制失效——这正是之前“路过与注入必须区分”那条修正的核心，点亮次数是那条修正在存储层的落地：点亮是“到达”，不是“注入”，两者必须分开记账。写入时机在流动阶段点亮球时 +1，与结算解耦，不需要事务；封顶（如 100）防止无限增长，封顶后不再增加但不清零；它不参与任何消费计算——不进入起始球选择、不进入补充规则、不进入注入排序、不进入相关性，唯一消费方是“下次流动时判断是否给予轻微阻力折扣”，且这个折扣默认关闭、作为对照实验的可选增强，开启时也远小于 blocked_count 的折扣幅度。它和 blocked_count 是两套独立的轻量计数：blocked_count 记“水到了但过不去”，点亮次数记“水到了且点亮了”，前者用于“差点通过”的补偿，后者用于“反复被到达”的补偿，两者都不刷新衰减计时，都不改变球的大小。 |

## 三、水管（Pipe）

| 条目 | 详细说明 |
|---|---|
| **无向权重** | 一根管子只有一个 `w`、一个 `blocked_count`、一个 `last_flowed`，A↔B 共享，不分上下游；水从 A 流向 B 和从 B 流向 A 遇到同一个阻力、同一个损耗、同一个阻塞记忆。有向权重 `w_ab`/`w_ba` 是过度设计，增加存储和逻辑复杂度却没有对应的人脑直觉；“A 让 B 想起”和“B 让 A 想起”在大多数情况下强度相当，方向性若需表达，应由内容或额外边类型承载，不塞进 `w`。 |
| **唯一性约束** | 存储层用 `(min(a_id, b_id), max(a_id, b_id))` 作为唯一键，保证 A-B 和 B-A 不会重复建边。因为管道无向，两端 ID 顺序没有语义，必须规范化后才能做唯一性判断；否则同一个关联可能被建两条记录，流动时随机走其中一条，导致阻力、损耗、阻塞记忆不一致。 |
| **w 范围** | 管道的粗细，`w ∈ (0, 1]`，永不归零。下界开区间保证管道不会完全消失，上界 1.0 是粗细归一化天花板；`w` 可衰减到极接近 0，但不会等于 0，因为“归零”语义上等于删除管道，违背“不删除、只降可提取性”的理念。阻力有上限（`w→0` 时 `resistance→1`），即使最细的管道，强线索水量足够大时仍能突破。 |
| **阻挡记忆折扣** | 每次水流因阻力不足无法通过某条管道，`blocked_count` 增加一次（封顶 `blocked_cap`，默认 5）；下次水流到达同一条管道时，有效阻力 `resistance × (1 - blocked_discount × min(blocked_count_effective, blocked_cap))`，`blocked_discount` 默认 0.1，最多降低 50% 阻力。这是舌尖效应的工程对应——“差点想起”的记忆下次更容易被想起，但折扣最多 50%、不会降到零，保证它只是“更容易通过”而非“必然通过”。`blocked_count` **随时间间隔按曲线速减**：存储 `blocked_count_stored` 和 `last_blocked`，读取时算 `blocked_count_effective = blocked_count_stored × exp(-Δt / blocked_decay)`，`blocked_decay` 建议 30–90 天；结算时先算 `blocked_count_decayed = blocked_count_stored × exp(-Δt / blocked_decay)`，再叠加本次新增阻挡次数、封顶 `blocked_cap`，写回 `blocked_count_stored` 并刷新 `last_blocked`——写回的是“已衰减到当前时刻的值 + 新增量”，不是原始累积值，这样长期不活动的管道折扣自然失效、重新活动后从低基线重新增长，不会出现“年轻时攒了一辈子、永久保值”。成功通过后 `blocked_count_stored` 不清零、不再增长，但会随时间自然衰减。它和点亮次数是两套独立计数：`blocked_count` 记“水到了但过不去”、点亮次数记“水到了且点亮了”，两者都遵循“存储原始值、读取时算衰减、结算时先衰减再叠加”的闭环模式。 |
| **阻力** | `resistance = 1/(1+w_eff) × 阻挡记忆折扣`。`w_eff` 越大阻力越小，水越容易通过；`w_eff` 越小阻力越大，水更容易在这一跳停住。但阻力有上限，`w_eff→0` 时 `resistance→1`，不是无穷大——任何管道在足够大水量下都能被突破，这是“阻力不是开关”的物理依据。阻挡记忆折扣让被阻挡过的管道下次有效阻力略降，是舌尖效应的载体。 |
| **w_eff** | w_eff 是管道在当前时刻真正可用的有效粗细，是读取时现算的派生值，公式 w_eff = w × exp(-Δt / S_pipe_effective)，Δt = now - last_flowed，S_pipe_effective 是管道稳定性的有效值（已含自身衰减），w 是存储里的基础粗细、不随时间变。它回答的是“这条联想现在还有多通”，和球的 size_effective 完全同构但独立演化——球管“记忆牢不牢”，管道管“联想通不通”。w_eff 在流动中承担两个角色：先算阻力 resistance = 1/(1+w_eff) × 阻挡记忆折扣 判断能不能过，过了之后用同一个 w_eff 算这一跳损失 loss = min(base_loss × (1 + loss_pipe_factor × (1-w_eff)), loss_max)——阻力和损耗是同一属性的两个正相关侧面，共用同一个 w_eff，不是两个独立参数。w_eff 永不落库：流动时用 w_eff 算阻力和损耗，不写回存储；只有结算强化时才写回 w（基础粗细），衰减是读取时现算的。S_pipe_effective 本身也遵循“饱和增长 + 长期不流动衰减”的双重规则（读取时算 S_pipe_effective = S_pipe_stored × exp(-Δt / S_pipe_decay)，结算时先衰减再叠加增长量），所以 w_eff 实际是“基础粗细 × 管道稳定性的有效衰减”，长期不流动的管道 S_pipe_effective 下降、w_eff 加速变细，符合“长期不通的联想应该越来越难走”的直觉。w_eff 不进入相关性计算、不进入注入排序、不进入球的任何计算——它只活在流动阶段的阻力和损耗里，不污染其他维度。 |
| **粗细双重角色** | 管道粗细同时决定阻力和损耗——粗管好过且损耗小，细管难通过且损耗大。这是已修正的设计，原设计里管道只决定阻力、损耗是全局常数；修正后 `w_eff` 在流动中承担两个角色：先算阻力判断能不能过，过了之后用同一个 `w_eff` 算这一跳损失多少。阻力和损耗是同一属性的两个正相关侧面，共用同一个 `w_eff`，不是两个独立参数。 |
| **损失函数** | 损失函数定义水流经一条管道时，这一跳要扣掉多少水：loss = min(base_loss × (1 + loss_pipe_factor × (1 - w_eff)), loss_max)，其中 base_loss 是粗管基准损失（默认 0.2），loss_pipe_factor 是细管额外损耗系数（默认 0.8），loss_max 是损失率上限（默认 0.8，必须 <1.0）。w_eff=1（最粗）时损失等于 base_loss，只有基准损失；w_eff→0（最细）时损失趋近 base_loss × (1+loss_pipe_factor)，被 loss_max 截断，防止细管把水全部吃掉、导致永远流不动。引入这个函数的理由是：原设计里损失是全局常数 L，与管道无关，但管道粗细的语义是“关联强度”——粗管不仅好过，过了之后也应该损耗小；细管不仅难通过，通过了也应该剩不下多少。把损失从“全局常数”改成“w_eff 的确定性函数”，让管道粗细在流动中承担完整的物理角色：阻力决定能不能过，损耗决定过了之后剩多少，两者共用同一个 w_eff、正相关但机制不同。关键约束有三条：损失是确定性的，不是随机噪声，同一 w_eff 永远算出同一损失；损失单调递减于 w_eff，管道越细损失越大，这是属性测试要覆盖的不变量；损失永不超过 loss_max，细管的额外损耗被上限截断，保证再细的管道也不会让水完全消失。损失发生在通过判断之前——水到达管道先扣损，再判断剩余水量能否通过阻力，不管最终是否通过，这一跳的损失都已经发生；过不去的管道损失不回收，符合“想不起来就是白费力气”的直觉。base_loss、loss_pipe_factor、loss_max 全部进配置，可调参；base_loss + base_loss × loss_pipe_factor < 1.0 是配置校验的硬约束，否则 loss_max 形同虚设。LossModel 做成可替换 trait，PipeWeightLossModel 是默认实现，ConstantLossModel 精确复现旧规则（损失恒等于 base_loss），用于对照实验——如果两种损失模型跑出来的召回质量没有差异，说明“管道决定损耗”这个修正在当前参数下不产生实质影响，需要检查是不是被其他机制掩盖了。 |
| **损失单调性** | 损失单调性是损失函数必须满足的一条物理不变量：管道越细，损失越大，即 loss(w_eff) 随 w_eff 增大而单调递减。形式上，对任意 w_eff_1 < w_eff_2，都有 loss(w_eff_1) ≥ loss(w_eff_2)。它保证“细管难通过且损耗大、粗管好过且损耗小”这个物理直觉在任何参数配置下都成立——不是靠某个具体参数值恰好满足，而是损失函数的结构本身就该保证。另一条配套不变量是损失有界：loss ∈ [base_loss, loss_max]，w_eff=1 时取下界 base_loss，w_eff→0 时趋近上界 base_loss × (1+loss_pipe_factor) 但被 loss_max 截断；损失永不低于 base_loss（粗管也有基准损失）、永不超过 loss_max（细管不会把水全部吃掉）。这两条不变量用属性测试覆盖，而不是手写用例——用 proptest 随机生成 w_eff 对和参数组合，断言单调性和有界性永远成立；手写用例只能覆盖有限几个点，属性测试能覆盖整个输入空间。单调性还隐含一条边界约束：base_loss + base_loss × loss_pipe_factor < 1.0，否则 w_eff→0 时算出的损失会超过 1.0，被 loss_max 截断后单调性在截断点附近被破坏（出现平台），配置校验时拒绝这种组合。测试用例要覆盖三个关键点：w_eff=1 时损失恰好等于 base_loss、w_eff→0 时损失被 loss_max 截断、中间任意两点严格满足单调递减。如果单调性被破坏，说明损失函数实现有误（比如把 1-w_eff 写成了 w_eff、或 loss_pipe_factor 符号错了），这是物理法则层面的错误，比业务逻辑错误更严重——它会让“细管损耗大”的整个设计意图失效。 |
| **创建来源（四条）** | 管道有四条创建来源，每条对应不同的“关联产生场景”，用 source 字段标记，便于审计和指标归因。① 新球接图：新球创建时，用其嵌入与已有 active 球算余弦，过滤低于 new_pipe_threshold（默认 0.5）的球，取 Top-K（默认 2）建弱管道，初始 w = 余弦 × new_pipe_initial_factor（默认 0.5），来源标记 new_ball；这是新球进入图的主要路径，没有它新球就是孤岛。② 共激活建边：同一次激活中，两个球都产生补充且都进入注入 Top-K，在它们之间建弱管道，初始 w = co_activation_initial（默认 0.1），来源标记 co_activation；语义是“它们一起被想起过”，初始权重极低、需要多次共激活才能变粗，默认关闭（enable_co_activation_pipe = false），因为会增加图密度，MVP 阶段先不开，Phase 3 再评估。③ 离线相似补边：离线巩固时，孤岛球或图稀疏区域，余弦 > offline_pipe_threshold（默认 0.7）且当前无管道 → 建管道 w = 余弦 × 0.3；已有管道但 w_eff 低于 offline_pipe_min（默认 0.05）且余弦 > 0.8 → 适度加粗，防止本该连接的球因长期不流动而断开；来源标记 offline_similarity。④ 手动建边：纠正或用户显式操作时直接建管道或调粗，来源标记 manual，走纠正审计，记录原值、新值、原因、操作者。引入四条而非一条的理由是：不同场景产生的关联，可信度和初始强度不同——新球接图是“语义相似但未验证”的弱关联，初始做细；共激活是“被水流一起走通过”的关联，但单次共现不足以建立强关联，初始更细；离线补边是“事后发现的相似”，比新球接图更保守；手动建边是“用户确认的关联”，可信度最高，可以直接指定较强权重。四条来源的初始 w 刻意都做细，因为新建立的关联强度还没被验证，需要后续流动和结算自然变粗——这和“结算变粗”是配套的：创建时细、走通后粗、久不走则惰性衰减，形成完整的生命周期。四条来源都遵守无向权重和唯一性约束，不会重复建边；来源标记进入指标 pipe_creation_by_source，用于判断图生长是否过度依赖某一条来源——如果 90% 的管道都来自 new_ball、co_activation 和 offline_similarity 几乎不触发，说明图结构在“新建时一次性定型”、缺少后续演化，需要检查共激活和离线补边是否被正确启用。 |
| **结算变粗** | 结算时，水流走通的路径上的每一条管道按路径相关性强化：w += 路径相关性 × pipe_strengthen_factor（默认 0.05），饱和 w_max（默认 1.0），写入时 clamp 到 [0, w_max] 防浮点越界。这是“一起被想起的东西一起变强”的持久化——不只是被点亮的球变大，路径上的管道也变粗，把“这条联想路径被走通过”这个事实写进结构，下次同类线索来临时这条路径更通、更容易被再次走通。强化值随路径相关性缩放，强相关路径的管道加粗更多，弱相关路径加粗少甚至接近零。关键约束有三条：只强化路径上的管道，不是所有被点亮球之间的管道，也不是全图管道；有饱和上限 w_max，防止单条管道无限变粗、形成正反馈；同一结算中管道出现在多条路径上时，取最大路径相关性强化一次，不累加——这和球的多路径取最大值是同一个原则，防止一条管道被多条弱路径“刷”成过强，导致流动时越来越倾向于走这条管道、联想僵化。它和“创建来源”的初始 w 是配套的：创建时初始 w 刻意做细（新建立的关联强度还没被验证），走通后结算变粗（关联被验证了），久不走则惰性衰减变细（关联淡化了），形成“创建细 → 走通粗 → 不走细”的完整生命周期。它和“管道衰减”是两套独立的写入路径：结算变粗写的是基础 w（存储值），惰性衰减算的是 w_eff（读取时的派生值），两者不在同一时刻发生——变粗只在结算事务里写回，衰减只在读取时现算，不落库。强化走原子增量 UPDATE pipe SET w = w + ?，不用读-改-写，并发安全；写入与球大小更新在同一结算事务内，要么全成功要么全回滚。测试要覆盖：路径上的管道被强化、非路径上的不被强化、强化值随路径相关性缩放、多路径取最大值不累加、w 不超过 w_max、结算事务回滚时管道不变。 |
| **多路径取最大** | 同一结算中，一个球或一条管道出现在多条路径上时，取最大路径相关性强化一次，不累加。球和管道都遵守这条规则。引入它的理由是：防止一个球或一条管道被多条弱路径“刷”成过强——如果累加，一条被三条 0.3 相关性路径经过的管道会得到 0.3+0.3+0.3=0.9 的强化，比一条被单条 0.8 相关性路径经过的管道还强，这违背“强相关路径应该主导强化”的直觉，也会让被多条弱路径反复经过的管道突然变得极粗，流动时形成正反馈，越来越倾向于走这条管道，导致联想僵化。取最大值后，同一结算中每条路径的贡献独立、不叠加，最强的路径决定强化幅度，弱路径不因为“数量多”而补偿。这条规则和“路径级强化”是配套的：路径级强化让“一起被想起的东西一起变强”，多路径取最大值防止“被反复想起但每次都不够强”的东西被过度强化。它和“管道合并取最大值”是同一类原则——两条管道合并时 w = max(w_ac, w_bc) 而不是相加，多路径强化时也取最大值而不是累加，两者都遵循“强度取最强、不叠加”的守恒逻辑。测试要覆盖：一个球出现在两条路径上（相关性 0.8 和 0.3），断言强化值只按 0.8 算、不按 1.1 算；一条管道出现在三条路径上，断言取最大不累加；同一球和同一管道同时出现在多路径上，两者各自独立取最大、互不影响。 |
| **阻塞记忆** | 每次水流因阻力不足无法通过某条管道，blocked_count_stored += 1（封顶 blocked_cap，默认 5），并刷新 last_blocked；下次水流到达同一条管道时，有效阻力 resistance × (1 - blocked_discount × min(blocked_count_effective, blocked_cap))，blocked_discount 默认 0.1，最多降低 50% 阻力。这是舌尖效应的工程对应——“差点想起”的记忆下次更容易被想起，但折扣最多 50%、不会降到零，保证它只是“更容易通过”而非“必然通过”，不违背“阻力不是开关”的理念。blocked_count 随时间间隔按曲线速减：读取时算 blocked_count_effective = blocked_count_stored × exp(-Δt / blocked_decay)，Δt = now - last_blocked，blocked_decay 建议 30–90 天；结算时先算 blocked_count_decayed = blocked_count_stored × exp(-Δt / blocked_decay)，再叠加本次新增阻挡次数、封顶 blocked_cap，写回 blocked_count_stored 并刷新 last_blocked——写回的是“已衰减到当前时刻的值 + 新增量”，不是原始累积值。引入衰减的理由：不衰减会让“年轻时差点通过”的痕迹永久保值，一个管道十年前被阻挡 5 次和昨天被阻挡 5 次不应享受同样折扣；衰减后长期未被试探的管道折扣自然失效，重新活动后从低基线重新增长。成功通过后 blocked_count_stored 不清零、不再增长——已通的管道不需要继续降阻，但“曾被阻挡过”是历史事实，清零会丢失信息，它只是停止增长并随时间自然衰减。它和点亮次数是两套独立计数：blocked_count 记“水到了但过不去”、点亮次数记“水到了且点亮了”，前者补偿“差点通过”、后者补偿“反复被到达”，两者都遵循“存储原始值、读取时算衰减、结算时先衰减再叠加、不刷新对方衰减计时”的闭环模式。blocked_decay、blocked_discount、blocked_cap 全部进配置可调；测试覆盖“长期不活动后折扣失效”“重新活动后从低基线增长”“折扣不超过 50%”“成功通过后停止增长但不清零”。 |
| **成功通过后** | `管道被水流成功通过后，blocked_count_stored 不清零、不再增长——已通的管道不需要继续降阻，但“曾经被阻挡过”是历史事实，清零会丢失信息，它只是停止增长；同时 blocked_count_stored 仍会随时间自然衰减，读取时算 blocked_count_effective = blocked_count_stored × exp(-Δt / blocked_decay)，长期不再被试探的管道折扣自然失效，重新被阻挡时从低基线重新增长。last_blocked 不在“成功通过”时刷新——它记的是“上次被阻挡”的时间，不是“上次流动”的时间，成功通过不改变这个时间戳，衰减计时继续从上次阻挡时刻算起。这条规则和“阻塞记忆”的衰减机制配套：被阻挡时增长、成功通过后停止增长、长期不活动自然衰减，形成“差点想起 → 更容易通过 → 通过了就不再累积 → 久了痕迹淡化”的完整生命周期。它和管道粗细的 w 是两套独立状态：w 在成功通过后会因结算强化而变粗（路径级强化），blocked_count 在成功通过后不会增长——前者记“这条联想被走通了”，后者记“这条联想差点走不通”，两者语义不同、更新时机不同、互不替代。 |
| **blocked_count 随时间衰减** | blocked_count 不是永久累积计数，而是随时间间隔按曲线速减的历史痕迹。存储 blocked_count_stored 和 last_blocked；读取时算 blocked_count_effective = blocked_count_stored × exp(-Δt / blocked_decay)，Δt = now - last_blocked，blocked_decay 建议 30–90 天，只用于计算阻力折扣；结算时先算 blocked_count_decayed = blocked_count_stored × exp(-Δt / blocked_decay)，再叠加本次激活中该管道被阻挡的次数、封顶 blocked_cap（默认 5），写回 blocked_count_stored 并刷新 last_blocked——写回的是“已衰减到当前时刻的值 + 新增量”，不是原始累积值。引入衰减的理由是：不衰减会让“年轻时差点通过”的痕迹永久保值，一个管道十年前被阻挡 5 次和昨天被阻挡 5 次不应享受同样折扣；衰减后长期未被试探的管道折扣自然失效，重新活动时从低基线重新增长，符合“历史痕迹随时间淡化”的直觉。它和 w 的惰性衰减遵循同一套“存储原始值、读取时算有效值、不落库”的模式，但写回策略不同——w 只在结算变粗时写回、不衰减写回，blocked_count 在每次结算时先衰减再叠加写回，因为前者是“质量”、后者是“痕迹”。 |
| **合并** | 合并有两个触发时机。① 离线巩固时的相似合并：离线巩固阶段，扫描球对，当两个球的内容嵌入余弦超过 merge_cosine_threshold（默认 0.95）且它们之间的管道 w_eff 超过 merge_edge_threshold（默认 0.9）时，触发合并——两个条件同时满足才合并，语义几乎相同但管道很细的球不合并（它们只是相似，还没被水流反复验证为同一个），管道很粗但语义不同的球也不合并（它们是被频繁一起想起的不同记忆，不是同一个）。合并时大球吸收小球，size_stored 取合并后重新计算（不简单相加，按内容贡献加权），S_stored 取最大值，内容列表合并去重。② 用户手动合并：用户显式说“这两个是同一件事”或通过纠正操作指定合并，走纠正审计，不受阈值约束——用户的显式判断优先于离线相似度。合并的具体管道处理规则：另一端就是吸收方 → 删除自环；另一端是 C 且吸收方与 C 已有管道 → 取 w = max(...)、blocked_count_stored = max(...)、S_pipe_stored = max(...)、时间戳取最大值，删除被吸收方的管道；另一端是 C 且吸收方与 C 无管道 → 重定向保留原值。核心约束是不叠加权重（取最大值不相加，否则合并让管道突然变粗）、时间戳取最大值（反映最活跃那条管道的历史，取最小值会让衰减计时错乱）。合并是分裂的逆操作，走纠正审计，反向执行分裂时按审计记录恢复原管道。离线相似合并在离线巩固时执行、不在线触发，用户手动合并可随时触发但走同步事务。 |
| **分裂** | 分裂是合并的逆操作，有两个触发时机。① 离线巩固时的内聚度分裂：离线巩固阶段，扫描球的内容列表，计算该球下所有内容嵌入的两两平均余弦（内聚度），当内聚度低于 split_cohesion_threshold（默认建议 0.6）且内容条数 ≥ split_min_contents（默认 5）时，说明这个球里混了多个语义方向的内容，触发分裂——内容条数太少不分裂（样本不足，可能是噪声），内聚度还高不分裂（语义还集中，没到该拆的时候）。分裂时用嵌入聚类把内容分成若干组（组数由聚类结果决定，不预设），每组创建一个新球，原球保留其中一组、其余组成为新球。② 用户手动分裂：用户显式说“这两件事不是一回事”或通过纠正操作指定分裂，走纠正审计，不受阈值约束。分裂的具体处理规则：强度按比例拆分——原球的 size_stored 按各组内容的贡献比例（如内容条数或显著性总和）拆到新球，不复制、不重复计数，拆完总和守恒；S_stored 按各组独立演化，新球从基础值开始、不继承原球的高 S（因为“被反复强化过”是原球整体的历史，不是某个内容组的历史）；内容列表按分组迁移，每条内容只属于一个球；管道按内容组的归属重定向——与组内球相连的管道复制 w/blocked_count_stored/S_pipe_stored 到新球，跨组的管道按“该管道另一端属于哪个组”重定向到对应新球，原球与自身新球之间不建管道（它们是分裂出来的，不是独立关联的）。分裂走纠正审计，correction_log 记录原球的内容列表、聚类分组结果、每组的新球 ID、size_stored 拆分比例、每条管道的重定向去向，保证可追溯、可回退——反向执行合并时按审计记录恢复原球和原管道。分裂只发生在球分裂时，管道本身不独立分裂——不存在“一条管道主动分裂为两条”的操作，管道的增删总是跟着球走。测试要覆盖：内聚度低于阈值且内容足够多才触发、size_stored 拆分总和守恒、新球 S_stored 从基础值开始不继承、管道按组重定向、审计记录完整、分裂后合并能恢复原状。 |
| **归档** | 管道的归档跟随球归档，不独立触发。当球被归档（距上次注水超 `archive_inactive_days` + `size_effective` 低于 `archive_size_threshold`，或活跃球数超 `max_active_balls` 被强制归档）时，与它相连的所有管道一起转入归档表、状态置为 archived，不删除——w、blocked_count_stored、S_pipe_stored、时间戳全部保留，只是不参与常规流动。归档球被检索命中翻回 active 时，管道随之恢复 active。核心约束是管道不因 w_eff 低而独立归档——w_eff 低只说明“这条联想现在很细”，不代表“这条联想没价值”，两端球都还活跃时，强线索仍可能用到它；如果把低 w_eff 的管道独立归档，等于变相删除细管道，违背“阻力不是开关、永不封死”的理念。管道独立归档只在一种情况下发生：两端球都已被归档，管道无处附着，随最后一个归档球一起归档——这不是“管道主动归档”，是“球归档的连带结果”。归档不改变管道的任何状态值，只改变 status 字段；归档管道的 blocked_count 和 S_pipe 仍随时间衰减，但读取时不参与主图流动，只在被唤醒后算 w_eff 和折扣。归档表的管道同样做嵌入分桶索引，归档球被唤醒时按球 ID 直接查关联管道，不做全量扫描。测试要覆盖：球归档时管道跟随归档、球唤醒时管道临时恢复、未强化时一起回归、低 w_eff 管道不独立归档、两端球都归档时管道连带归档、归档不改变 w/blocked_count_stored/S_pipe_stored。 **不归档管道的理由**：管道是球之间的关系，球醒了路就该能用；单独归档管道只会制造“球活着但路断了”的怪状态。`archive_sweep` 只改球状态，管道保持 active。 |
| **管道健康因子** | 	已废弃。它曾是“管道粗细也决定损耗”修正时提出的可选增强：在结算的路径折扣里，除了按跳数打折，再乘一个“路径上 w_eff 均值”的健康因子，公式形如 路径相关性 × 长度折扣 × (pipe_health_floor + (1 - pipe_health_floor) × avg_w_eff)，默认 pipe_health_floor = 0.5，意图是让“管道都很粗的长路径”少打折、“管道很细的短路径”多打折，让路径折扣“更物理”。废弃理由是：w_eff 已经在流动阶段决定了阻力和损耗，再乘进相关性是同一个信号第二次计权——这和“水量乘进相关性”“size_stored 塞进衰减函数”是同一类错误，一个量在它不该出现的地方被当成了另一个量的乘数；更严重的是它会形成“粗管→更受偏爱→强化更多→变得更粗”的正反馈，细管和孤岛记忆永远等不到水流，违背“疏而不堵”的理念。修正后路径折扣只含跳数折扣 max(min_discount, 1 - discount_per_hop × 跳数)，不含任何 w_eff 相关因子；管道的粗细信息只活在流动阶段的阻力和损耗里，不进入结算的相关性计算、不进入注入排序。当时曾建议“MVP 阶段先只保留跳数折扣，等对照实验数据显示管道粗细对路径质量有独立解释力再开启”，但后续在“相关性与水量解耦”的修正中，它被识别为与水量乘进相关性同构的二次计权错误，正式废弃，不再作为可选项保留，连默认关闭的开关都不留。 |

## 四、流动动力学

| 条目 | 详细说明 |
|---|---|
| **流动只点亮、不写入** | 流动阶段是纯内存计算，不产生任何持久化写入。水从起始球出发、沿管道传播、逐跳扣损失、判断阻力、释放补充、点亮球——全程在内存子图上完成，点亮集合和路径集合是临时状态，不落库、不开启写事务、不持有数据库写锁。写入只发生在结算阶段，且是一次激活一次事务，不是每跳一次。引入这条规则的理由有三层：① 消除竞态——如果流动过程中每跳写入，同一轮多条路径同时到达同一个球、或 dsh 和 pi 两个客户端同时流动时，会出现“读-改-写”竞态，需要复杂的锁；流动纯内存、结算统一写入，竞态被压缩到结算那一次事务里。② 职责分离——流动回答“哪些球被点亮、沿什么路径”，结算回答“强化多少、注入哪些”，两者混在一起会让流动逻辑被写入逻辑污染，也让“流动可以纯粹用内存子图跑”这个性能优势丧失。③ 结算即注入决策——结算必须同步立刻执行、基于刚强化后的球状态决定注入排序，如果流动过程中已经写入了部分强化值，结算时的“强化前状态”就不存在了，注入排序会基于被污染的状态。具体机制：流动开始时开短读事务加载起点子图、记录全局版本号 V_start、立刻结束读事务，流动在内存子图上纯计算；结算时开写事务、校验版本号（无冲突直接写、有冲突重读涉及球/管道重算增量）、写入球大小增量、管道粗细增量、last_watered/last_flowed 刷新、blocked_count 和 S 先衰减再叠加，提交后落库。流动阶段被阻挡的管道，blocked_count 的本次新增只记在内存里，结算时才写回——如果本次结算因版本冲突失败或进程崩溃，这次阻挡记录丢失，下一轮重新开始，丢失一次阻挡记录可接受（只影响下次阻力折扣，不影响记忆内容）。测试要覆盖：流动过程中快照球大小和管道粗细、断言流动结束后结算前它们没有任何变化；结算后断言变化发生；结算事务回滚时断言球和管道回到流动前状态。 |
| **每跳损失先扣** | 水到达一条管道时，先按 loss(w_eff) 扣掉这一跳的损失，再判断能否通过阻力，顺序不能反。扣损后的剩余水量才拿去和阻力比较：通过则用扣损后的水量加补充继续流向下一跳，不通过则这部分水损失掉、不回收给其他管道。引入“先扣后判”而非“先判后扣”的理由是：损失是试探本身的成本，不是“通过才付的代价”——水被分散到一条管道上，不管最终能不能通过，这一跳的试探已经发生了，“想不起来就是白费力气”的直觉要求试探有成本；如果先判断能否通过、通过才扣损，那失败的试探零成本，系统会倾向于广撒网、失去“选择方向”的意义，也不符合物理直觉（水流过一段管子，不管最后有没有流出去，摩擦损耗都已经发生了）。损失函数是 loss = min(base_loss × (1 + loss_pipe_factor × (1-w_eff)), loss_max)，是 w_eff 的确定性函数——粗管损失小、细管损失大，损失永不超过 loss_max，保证再细的管道也不会把水全部吃掉。它和“通过条件”是配套的两步：先扣损（不管通过与否，损失都发生）→ 再判断（扣损后的水量 > 阻力才能通过）。它和“分配权重”“损失不回收”一起构成完整的流动成本模型：分配时按 1+w 加权把水分到各条未访问出边，每条管道先扣自己的损失，再判断能否通过，过不去的损失不回流——三步合起来保证“每条管道的试探成本独立、失败不拖累其他方向、成功与否都不退还已付出的成本”。测试要覆盖：水量不足以通过时仍扣了损失、扣损后水量严格小于扣损前、通过判断用的是扣损后的水量而不是原始水量、不通过时损失不回收给其他管道。 |
| **通过条件** | 水能否通过一条管道，唯一判据是扣损后的剩余水量 > 阻力：water_after_loss > resistance，其中 water_after_loss = current_water × (1 - loss(w_eff))，resistance = 1/(1+w_eff) × 阻挡记忆折扣。满足则通过——目标球被点亮，扣损后的水量加上目标球释放的补充继续流向下一跳；不满足则不通过——这部分水按损失规则损失掉、不回收，该方向尝试结束，改试该球的其他未访问出边。这条判据有两个关键属性：① 它是纯物理量比较，不是语义判断、不是阈值开关——语义相关性只在“是否补充”和“是否强化”里起作用，不直接决定“能不能过”；一个球语义上完全无关，只要水压足够大、管道足够粗，水照样能通过它继续流向远处，这正是“水流不按语义预判方向、让水自己找路”的体现。② 阻力有上限，所以通过永远可能——w_eff→0 时 resistance→1，不是无穷大，这意味着任何管道在水量足够大时都能被突破；强线索放大起始水量、放大可释放水量、降低被阻挡管道的有效阻力，三条规则叠加，让“沉睡记忆被强线索唤醒”在通过条件上成为可能，而不是靠给细管开特例。它和“每跳损失先扣”是严格的两步顺序：先扣损、再用扣损后的水量判断，不能反——如果先判断再扣损，失败的试探零成本，违背“试探本身有成本”的直觉。它和“分配权重”“损失不回收”一起构成完整的流动成本模型：分配按 1+w 把水分到各条未访问出边，每条管道先扣自己的损失，再用扣损后的水量独立判断能否通过，过不去的损失不回流——三步合起来保证每条管道的成败互不影响。边界情况：w_eff 极小时阻力接近上限 1，常规水量过不去，但强线索放大后水量可超过 1 而通过；blocked_count_effective 高时阻力被折扣到最低 50%，让“差点通过”的管道更容易通过，但不会到零阻力、不会变成必然通过。测试要覆盖：水量刚好等于阻力时不通过（严格大于才通过）、扣损后水量不足时不通过且损失不回收、强线索放大水量后原本过不去的细管能通过、阻挡记忆折扣降低阻力后原本过不去的管道能通过、语义无关但水压足够的球能通过并继续流向远处。 |
| **回边排除** | 水从球出发流向它的出边时，只流向目标未被访问过的出边，目标已访问的出边不参与水量分配。这是已修正的设计，原设计里回边（来路，目标已访问）和去路（目标未访问）同等参与 1+w 加权分配，导致每经过一个中间球水量腰斩——ball1 的出边有来路（ball0，已访问）和去路（ball2，未访问），两条各拿 50%，回边那 50% 按“第二次到达只损失”白费，5 球链只能点亮深度 0，改造前能到深度 3。修正后，ball1 的出边只有 ball2 参与分配，水 100% 流向去路，传播能力恢复。规则表述从“水球流向所有连接它的水管”精确化为“水球流向所有未访问的连接水管”——这不是理念变更，是精确化：回边不是“待探索的方向”，是“已经走过的路”，排除它不违背“不按语义预判方向”的本意。用拓扑事实（已访问标记）排除确定性浪费，和用语义判断（相关性）预判方向，是两回事——前者不扼杀探索，后者会。它和“第二次到达只损失”是两条独立规则：回边排除在分配前就生效（目标已访问的出边不分配水），“第二次到达只损失”只在分配后的多路径汇聚场景生效（两条不同路径同时指向一个未访问球，先到者变已访问，后到者全损）。边界情况：球的所有出边都已访问时，没有未访问出边，水全部损失、该球成为死路、无特例回流——实现时不能加“如果没有未访问出边就回流”的特例，那会重新引入回边浪费。测试要覆盖：回边不参与分配、去路拿到 100% 水量、5 球链能正常传播、所有出边已访问时水全部损失无回流、多路径汇聚仍走“第二次到达只损失”。 |
| **分配权重** | 	水从球流向多条未访问出边时，按 1+w 加权分配，每条出边分到的水量 = 球可分配水量 × (1+w_i) / Σ(1+w_j)，其中 j 遍历所有未访问出边。不是平均分——平均分让粗管和细管拿到一样的水，违背“粗管是强关联”的语义，w=0.9 和 w=0.1 两条管道各拿 50%，等于告诉系统“这两条关联一样强”。也不是直接按 w 分——直接按 w 分会让 w→0 的管道分到趋近于零的水，等于用分配规则把路封死，和“阻力不是开关、强线索可突破”的理念直接冲突。1+w 的权重下限是 1，保证细管分到的水最少但非零，粗管分到最多；w=1 的管道权重 2、w=0.1 的管道权重 1.1，粗管拿约 64.5%、细管拿约 35.5%，比例合理但不极端。引入这个权重的理由是：让管道粗细在流量分配上也有语义，而不只是在阻力判断和损耗计算上有语义——三条路径（分配、阻力、损耗）都用同一个 w_eff 的不同侧面，粗管“分得多、好通过、损耗小”，细管“分得少、难通过、损耗大”，三者一致。它和“细管保底非零”是同一件事的两面：1+w 加权既保证了粗管多分（语义正确），又保证了细管非零（不封死）。它和“先分配后判断”配套：分配是一次性完成的，每条管道拿到自己的那份水后独立判断能否通过，过不去的损失不回收。分配权重做成可配置：split_mode = "weighted"（默认，1+w）或 "equal"（对照实验用，平均分）；equal 不是为了生产使用，是为了验证“按粗细加权分配”是否真的带来召回质量差异——如果两种模式跑出来没有差异，说明分配规则在当前场景下不产生实质影响；如果有差异，方向是否符合预期也需要数据判断。测试要覆盖：三条出边 w 为 0.9/0.5/0.1 时按 1.9:1.5:1.1 分配而非 0.9:0.5:0.1 或 1:1:1、所有出边分到的水量之和等于可分配总量、w 极接近 0 的出边分到严格大于零的水量。 |
| **细管保底非零** | 	1+w 加权分配保证每条未访问出边至少分到严格大于零的水量，即使 w 极接近 0。w→0 时权重趋近 1，不是 0——细管分到的是“最少但非零”的那一份，而不是零。这是“阻力不是开关、强线索可突破”在分配规则上的落地：如果分配时细管分到零水，它就永远过不去，等于用分配规则把路封死，违背“不删除、只降可提取性”的理念；有了非零保底，细管在常规水量下确实过不去（分到的水太少、低于阻力），但当总水量因强线索放大时，细管的绝对水量也随之放大，可能超过阻力上限而被突破——不是靠给细管开特例，是靠权重下限保住基础水量，让“强线索突破细管”在分配层面成为可能。它和“通过条件”是配套的：分配保证非零，通过条件保证“水量 > 阻力才通过”，两者叠加的效果是“细管平时过不去、强线索下可能过去”。它和“直接按 w 分”是两条对立的设计：直接按 w 分会让 w→0 的管道分到趋近于零的水，等于用分配规则封死；1+w 加权则保留了非零下限。测试要覆盖：w 极接近 0 的出边分到的水量严格大于零（哪怕极小）、总水量放大后这条细管能通过阻力、w=0 的极端情况（虽然 w 范围是 (0,1]，不会真正为 0，但测试要验证趋近 0 时行为正确）、所有出边分到的水量之和等于可分配总量（保底非零不破坏分配守恒）。 |
| **先分配后判断** | 水到达一个球后，先把球的可分配水量按 1+w 加权一次性分到所有未访问出边，然后每条管道用自己分到的那份水量独立判断能否通过——顺序不能反，也不能改成“逐条尝试、失败了把水还给其他管道”。可分配水量 = 流入该球的水量 + 该球释放的补充；分配是一次性完成的，各条出边拿到的水量之和等于可分配总量（分配守恒）；分配完成后，每条管道先扣自己的损失、再用扣损后的水量和阻力比较，通过则继续流向下一跳，不通过则这部分水损失掉、不回收给其他管道。引入“先分配后判断”而非“逐条尝试”的理由是：逐条尝试会让判断顺序影响结果——先试的管道如果失败、把水还回来，后面的管道就能拿到更多水，这意味着“哪条管道先被尝试”成了一个有语义影响的决策，而管道之间本应平等，没有“谁先谁后”的语义；先分配后判断让每条管道的成败互不影响，结果与尝试顺序无关，可复现、可审计。它和“分配权重”“损失不回收”一起构成完整的流动成本模型：分配按 1+w 把水分到各条未访问出边（粗管多分、细管少分但非零），每条管道先扣自己的损失，再用扣损后的水量独立判断能否通过，过不去的损失不回流——三步合起来保证“每条管道的试探成本独立、失败不拖累其他方向、成功与否都不退还已付出的成本”。它和“回边排除”配套：分配前先排除已访问出边，只对未访问出边分配，避免把水分到注定白费的回边上。边界情况：球只有一条未访问出边时，分配退化为 100% 给这条边；球没有未访问出边时，不分配、水全部损失、球成为死路；多条出边时，按 1+w 加权比例分配，不是平均分。测试要覆盖：分配后各出边水量之和等于可分配总量、每条管道用自己分到的水量判断而非球的总水量、一条管道失败不影响其他管道的判断结果、调整尝试顺序不改变最终点亮集合、没有未访问出边时水全部损失无回流。 |
| **损失不回收** | 一条管道判断不通过后，它分到的那份水按损失规则扣掉后直接消失，不回流给其他管道、不重新分配、不退还。水被分散到多条出边后，每条管道的成败独立——某条走不通，那部分水就白流了，其他管道该拿多少还是多少，不会因为这条失败而多拿。引入这条规则的理由是：如果回收，等于“试探无成本”——失败的方向把水还给成功的方向，系统就会倾向于广撒网、每个方向都试一遍，因为试错没有代价；这会让“选择方向”失去意义，也让水流变成“穷举所有路径”而非“有成本地探索”。不回收则让每次分配成为一次有代价的承诺：水一旦分出去，不管走不走得通，都已经消耗在试探里，“想不起来就是白费力气”的直觉正是这条规则的工程对应。它和“每跳损失先扣”配套——损失先扣、不管通过与否都发生；和“先分配后判断”配套——分配是一次性的，判断独立，失败不退还；和“回边排除”配套——回边在分配前就被排除，不产生“分了水又退回”的情况。边界情况：球的所有出边都失败时，可分配水量全部损失，球成为死路，水耗尽、不回流到上游；上游球不会因为下游失败而重新获得水量，上游那一步的分配已经完成、不可逆。它和“结算”是两件事：流动阶段的损失是水量的消失（不落库、只影响本次激活能传多远），结算阶段的强化是球和管道状态的写入（落库、影响后续激活）——损失不回收说的是水量，不是强化值。测试要覆盖：一条出边失败后其他出边分到的水量不变、所有出边失败时水量全部损失无回流、上游球不因下游失败而重新获得水量、损失不回收不改变分配守恒（分配时总量守恒，判断后总量减少是因为损失，不是因为回流）。 |
| **同一次激活每球只注一次** | 水第一次到达一个球时，正常注水、释放补充、继续流向它的下游；第二次到达同一个球时，不注水、不释放补充、只扣损失。这条规则的作用是防止 A→B→C→A 的循环无限注水，也保证“点亮集合”天然是去重的球 ID 集合——max_lit_balls 约束的就是这个集合的大小，不是“点亮动作发生的次数”。它不是“禁止循环”，而是“循环的那一段不产生收益、只有损失”：水可以沿着环路流回去，但回流到已访问球时既不加注、也不补充，还要付这一跳的损失，水流自然会在几次循环后衰减到零，不需要显式检测环、不需要给循环设特例。它和“回边排除”是两条独立但配套的规则：回边排除在分配前生效（目标已访问的出边不参与水量分配，水 100% 流向未访问去路），“第二次到达只损失”在分配后的多路径汇聚场景生效（两条不同路径同时指向一个未访问球，先到者把它变已访问，后到者到达时水已经分好、无法回收，只能全损）。两条规则分工明确：回边排除防的是“同一球沿来路原样退回”，第二次到达只损失防的是“多路径汇聚时后到者的浪费”。边界情况：一个球第一次被到达时注水释放补充，之后无论通过哪条路径再次到达，都不再注水、不再释放，只扣损失——所以一个球在一次激活中最多贡献一次补充，不会因为被多条路径到达而贡献多次。测试要覆盖：同一球第二次到达时不注水不释放只损失、A→B→C→A 的循环不会无限注水而是自然衰减、多路径汇聚时先到者注水后到者只损失、点亮集合是去重的球 ID 集合而非重复计数、max_lit_balls 按不同球数计数而非按到达次数计数。 |
| **第二次到达只损失** | 水第二次到达同一个球时，不注水、不释放补充、只扣这一跳的损失。这条规则现在只用于多路径汇聚场景——两条不同路径在分配后同时指向一个未访问球，第一条到达后该球变已访问，第二条到达时水已经分好、无法回收，只能全损。它和“回边排除”是两条独立规则、分工明确：回边排除在分配前生效（目标已访问的出边不参与水量分配，水 100% 流向未访问去路），防的是“同一球沿来路原样退回”；第二次到达只损失在分配后生效，防的是“多路径汇聚时后到者的浪费”。引入它的理由是：多路径汇聚是拓扑事实——两条路径在分配时都指向同一个未访问球，分配已经完成、水已经分好，等到第一条到达后该球变已访问，第二条的水无法回收（回收就违背“损失不回收”），只能全损；如果不做这条规则，第二条到达时会重复注水、重复释放补充，一个球在一次激活中贡献多次补充，破坏“每球只注一次”的守恒。它和“同一次激活每球只注一次”是同一件事的两面：后者是规则表述（每球只注一次），前者是到达时的处置方式（第二次到达只损失）。边界情况：一个球第一次被到达时注水释放补充，之后无论通过哪条路径再次到达，都不再注水、不再释放、只扣损失——所以一个球在一次激活中最多贡献一次补充，不会因为被多条路径到达而贡献多次；如果第二次到达时该球已经通过某条路径继续向下游流动，第二次到达的水不影响已发生的下游流动，只是自己损失掉。测试要覆盖：多路径汇聚时先到者注水后到者只损失、同一球第二次到达时不注水不释放、第二次到达的损失不回收、一个球在一次激活中最多贡献一次补充、与回边排除的边界不混淆（回边在分配前排除，不走这条规则）。 |
| **所有出边已访问** | 水到达一个球后，如果它的所有出边目标都已经是已访问状态，则没有未访问出边可分配——水全部损失，该球成为死路，本方向流动终止，无任何特例回流。这是“回边排除”的边界情况：回边排除在分配前过滤掉目标已访问的出边，正常情况下至少还有去路可分配；但当球处于图的末端、或所有下游都已被本次激活走过时，过滤后剩余出边为零，分配无从进行，水只能全部损失。引入这条规则的理由是：如果加“所有出边已访问就回流”的特例，等于重新引入回边浪费——水退回上游、上游再重新分配，本质上还是把水送回了已经走过的路，和“回边排除”的初衷冲突；而且回流会让“损失不回收”失效，试探变成无成本，系统倾向于穷举而非有成本地探索。它符合直觉：所有方向都走过了，水在这里耗尽，这个球对本次激活的贡献到此为止——它可能已经在第一次被到达时贡献过补充，现在作为路径终点自然终止。它和“同一次激活每球只注一次”配套：一个球第一次到达时注水释放补充，之后无论从哪条路径再次到达都不再注水；当它作为当前球、所有出边又都已访问时，水在这里损失，不会因为“没有去路”而获得任何补偿。边界情况：起始球本身如果所有出边都已访问（极端情况，比如图上只有两个球且互相连接），水在起始球处全损，本轮激活点亮集合只含起始球自身，结算时按最低强化值或正常资格判断；球只有一条出边且该出边目标已访问时，等同于所有出边已访问，水全损。测试要覆盖：所有出边已访问时水全部损失、无回流到上游、该球成为死路、上游球不因下游死路而重新获得水量、起始球所有出边已访问时点亮集合只含自身、与“回边排除”的边界一致（过滤后为零出边即触发本条）。 |
| **补充规则** | 水到达一个球并完成扣损后，若该球满足补充资格，会释放补充水量汇入水流，用于继续流向下一跳。补充采用“资格 + 幅度”两段式，不是 size_effective × 相关性系数 的线性乘积。资格：先看相关性是否过补充资格阈值 supplement_threshold（默认建议 0.4–0.5，高于 flow_threshold），低于它时补充量为零——球不贡献任何水，防止一个勉强过流动阈值的弱相关大球靠历史强度放大水流；过了资格阈值，水流仍可继续探索（靠剩余水量），但球不补充。幅度：高于资格阈值时补充按归一化相关性增长，补充量 = size_effective × (相关性 - supplement_threshold) / (1 - supplement_threshold)，相关性刚好过阈值时补充接近零、接近 1 时才拿满 size_effective，size_effective（当前有效大小，已含时间衰减）是“潜力”、归一化相关性是“兑现比例”。上限：补充量受 max_supplement_ratio（默认 2.0）截断，补充量 = min(可释放水量, 当前水量 × max_supplement_ratio)，防止一个大球让水流指数爆炸。关键语义：球释放补充后自身不变——可释放水量是计算值，不是从球里扣水，球的大小变化只在结算时发生（被路径强化则变大、久不注水则惰性衰减），流动过程中球只是贡献了一个由当前状态决定的水量。补充加在扣损之后：下一跳水量 = 扣损后水量 + 补充量，细管道上的补充需要更大力才能让水流维持甚至增长，粗管道上的补充更容易让水越流越猛。补充量 > 当前损失时水流可能被放大、继续扩散，补充量 < 当前损失时水流衰减、联想链更早终止——这就是“补充 > 损失当且仅当球大、新鲜、强相关”的工程对应，但“强相关”现在有了明确的资格阈值，不是线性乘一个小的相关性系数。supplement_threshold = flow_threshold 时退化为“过流动阈值就补充”的旧行为，可作为对照基线；supplement_threshold 不能设太高，否则中等相关球都不补充、水流衰减太快、多跳联想被扼杀。测试要覆盖：相关性低于 supplement_threshold 时补充为零、刚好过阈值时补充接近零、接近 1 时拿满 size_effective、补充受 max_supplement_ratio 截断、球释放补充后 size_stored 不变、补充加在扣损后而非扣损前。 |
| **补充 > 损失条件** | 水在一个球处能否被放大、继续扩散，取决于补充量是否大于这一跳的损失量：补充量 > 当前水量 × loss(w_eff) 时，下一跳水量 = 扣损后水量 + 补充量 大于流入水量，水流被放大、联想链继续延伸；补充量 < 损失 时，下一跳水量小于流入水量，水流衰减、联想链更早终止；补充量 ≈ 损失 时水流勉强维持，传几跳后自然停下。条件从早期的“球大、新鲜、强相关”三个因子平权的乘法关系，改成“资格 + 幅度”两段式——资格是相关性是否过 supplement_threshold（默认 0.4–0.5），低于它时补充为零、无论球多大都不可能补充 > 损失；幅度是过了资格后 补充量 = size_effective × (相关性 - supplement_threshold)/(1 - supplement_threshold)，此时“球大、新鲜”才通过 size_effective 在幅度里起作用。这个改动的理由是：早期公式 size_effective × 相关性系数 会让一个勉强过 flow_threshold（0.3）的弱相关大球靠历史强度释放大量补充、主导流动方向，和“大球赢家通吃”是同一个结构问题；两段式后，弱相关的大球无法靠历史强度放大水流，相关性没过资格阈值时补充为零，过了之后球大、新鲜才在幅度里起作用。三个条件的分工是：强相关（过 supplement_threshold）决定“有没有资格补充”，球大、新鲜（size_effective 高）决定“有资格时补充多少”；三者不再平权相乘，而是“相关性管资格、大小和新鲜度管幅度”。边界情况：相关性刚好等于 supplement_threshold 时补充为零（归一化分子为零）；相关性接近 1 时补充接近 size_effective，但仍受 max_supplement_ratio（默认 2.0）截断，防止水流指数爆炸；supplement_threshold = flow_threshold 时退化为“过流动阈值就补充”的旧行为，可作为对照基线。测试要覆盖：弱相关大球的补充为零而非“小量补充”、强相关大球补充 > 损失、强相关小球补充 < 损失、同等相关性下 size_effective 高的球补充更多、补充受 max_supplement_ratio 截断、supplement_threshold = flow_threshold 时退化行为正确。 |
| **安全阀 max_flow_depth** | 默认 5，单条路径的最大跳数，是流动的两个硬安全阀之一（另一个是 max_lit_balls）。深度从起始球算起，起始球深度 0，每经过一条管道 +1，达到上限时该方向停止向下游流动，已点亮的球照常进入结算、不丢弃。深度按 BFS 首次到达算，不是最长路径——同一次激活每球只注一次，首次到达后就标记为已访问，后续再到达不注水，所以深度天然是“最短路径深度”；depth_count_mode 保留 longest_path 作为逃生舱，但默认且推荐 bfs_first，因为 longest_path 需要额外记录每条路径的深度，复杂度高且没有明显收益。引入它的理由是：自然衰减理论上会让水停下，但强相关链可能越流越猛（补充 > 损失），一条 A→B→C→D→… 的强相关链如果每跳都满足补充条件，水可以流几十跳不衰减，延迟不可控、点亮球数爆炸；深度阀是防“单链极深”的兜底，和 max_lit_balls 防“分支太多”分工不同——深度阀防延迟，球数阀防内存和结算成本，两个阀都设是因为只设一个挡不住另一种爆炸。它和 max_lit_balls 是“或”的关系：任一触发，触发阀的那个方向停止流动，其他方向继续，直到所有方向都停或都触阀。强线索唤醒通常 1–2 跳就够（起始球直接命中沉睡大球），5 跳是保守兜底、不是常规限制；频繁触发说明默认值太小或图太密，该调配置而不是机制有问题。安全阀触发时记一次 safety_valve_triggered 指标、标签区分深度/球数，用于调参。边界情况：起始球深度 0 不触阀；深度恰好等于 max_flow_depth 时该方向停止，但不影响该球本身被点亮和结算；多个方向同时触阀时各自停止、互不影响。测试要覆盖：深度到顶该方向停止但已点亮球照常结算、不同方向独立触阀、BFS 首次到达深度而非最长路径、触阀时记指标、max_flow_depth=0 时只有起始球被点亮、调大上限后传播深度相应增加。 |
| **安全阀 max_lit_balls** | 默认 50，单次激活最多点亮的不同球数（不是点亮次数）——因为同一次激活每球只注一次，点亮集合天然是去重的球 ID 集合，这个上限约束的就是集合大小，同一个球被多条路径到达只算一个、不重复计数。达到上限时不再点亮新球，但水流仍可以在已点亮的球之间尝试管道——尝试会消耗损失、但不会产生新点亮，已点亮的球照常进入结算、该强化的照常强化，安全阀只阻止“继续扩散”、不撤销“已经发生的点亮”。引入它的理由是：一个球可能有几十条出边，5 跳就可能触及几千个球，自然衰减挡不住分支爆炸——点亮球数爆炸会让延迟不可控、点亮集合过大、结算成本飙升、水量被摊薄到每个球都不够结算；它是防“分支太多”的兜底，和 max_flow_depth（防“单链极深”）分工不同，两个阀都设是因为只设一个挡不住另一种爆炸，实际场景中球数阀通常先触发、深度阀是防单链极深的兜底。它和 max_flow_depth 是“或”的关系：任一触发，触发阀的那个方向停止流动，其他方向继续，直到所有方向都停或都触阀。计数时机是球第一次被点亮时 +1，后续路径再到达同一球不增加计数；去重键是球 ID，不是路径 ID；结算范围以点亮集合为准，集合大小不超过 max_lit_balls。安全阀触发时记一次 safety_valve_triggered 指标、标签区分球数/深度，用于调参——频繁触发说明默认值太小或图太密，该调配置而不是机制有问题。边界情况：恰好第 50 个球被点亮时触发，该球本身正常点亮、正常结算，只是之后不再点亮新球；已点亮球之间的管道尝试不增加球数、不触阀；多个方向同时触阀时各自停止、互不影响。测试要覆盖：点亮球数达到上限后不再点亮新球、已点亮球照常结算、同一球被多路径到达只计一次、已点亮球之间仍可尝试管道但不产生新点亮、与 max_flow_depth 独立触发、触阀时记指标、调大上限后点亮球数相应增加。 |
| **安全阀触发后** | 	触发安全阀的那个方向停止流动，其他方向继续，直到所有方向都停或都触阀——不是“整个流动立刻停止”，而是“触发阀的那条路径/那个分支停止，其余分支不受影响”。已点亮的球照常进入结算、不丢弃，该强化的照常强化——安全阀只阻止“继续扩散”，不撤销“已经发生的点亮”，这和“流动只点亮、结算才强化”的职责分离一致：流动阶段只决定“哪些球被点亮”，安全阀限制的是这个集合的大小，不改变已经进入集合的球。两个阀的触发效果略有不同：max_flow_depth 触发时该方向不再向下游流动，但水流仍可在当前球尝试其他未访问出边（如果还有）；max_lit_balls 触发时不再点亮新球，但水流仍可以在已点亮的球之间尝试管道——尝试会消耗损失、但不会产生新点亮，已点亮球之间的管道尝试仍可能产生结算强化（因为管道被走通了）。触发时记一次 safety_valve_triggered 指标，标签区分“深度”和“球数”，用于调参——频繁触发说明默认值太小或图太密，该调配置而不是机制有问题；偶发触发说明安全阀在正常工作，兜住了极端情况。安全阀触发不影响结算的正确性：点亮集合是触发前已经确定的，结算按点亮集合和路径集合正常进行，强化值、注入排序、渲染都不因触发而改变。边界情况：两个阀同时触发时，两个方向各自停止、互不影响；触发后仍有未访问出边但水量已不足以通过时，水自然损失、无需额外处理；触发后已点亮球之间的管道尝试如果全部失败，水耗尽、流动自然结束。测试要覆盖：触阀方向停止但其他方向继续、已点亮球照常结算、触阀后不再点亮新球但已点亮球之间仍可尝试管道、两个阀独立触发互不影响、触阀时记指标、触发不改变结算结果。 |
| **深度计算** | 	深度从起始球算起，起始球深度为 0，每经过一条管道 +1；深度按 BFS 首次到达计算，不是最长路径——因为同一次激活中每个球只被注水一次，首次到达后就标记为已访问，后续再到达不注水、不释放、只损失，所以每个球的深度天然是“从起始球到它的最短路径深度”，不需要额外维护每条路径的深度、也不需要比较哪条路径更长。引入 BFS 首次到达而非最长路径的理由是：最长路径需要记录每条路径的深度、在球被多路径到达时比较并更新，复杂度高且没有明显收益——深度的唯一用途是触达 max_flow_depth 安全阀，而“最短路径深度”已经能回答“这个球离起始球最近有多远”，最长路径深度在“每球只注一次”的规则下没有语义（第二次到达不注水，长路径的那次到达不产生任何效果）。depth_count_mode 保留 longest_path 作为逃生舱，但默认且推荐 bfs_first，切换只改配置不改代码。它与“回边排除”和“第二次到达只损失”配套：回边在分配前被排除，不产生“沿来路退回”的深度计算；第二次到达只损失，多路径汇聚时后到者不注水、不更新深度——首次到达者决定该球的深度。边界情况：起始球深度 0，不触任何深度阀；深度恰好等于 max_flow_depth 的球被正常点亮、正常结算，只是它的下游不再被流动；多个起始球时，每个球从各自的起始球算深度，同一球被不同起始球到达时取首次到达的深度（先到者决定）。测试要覆盖：起始球深度为 0、每经过一条管道深度 +1、同一球被多路径到达时取首次到达深度而非最长路径、深度到顶时该方向停止但球本身正常结算、depth_count_mode 切换为 longest_path 时行为按配置变化。 |
| **全失败** | 水到达一个球、该球有未访问出边，但按 1+w 分配后，每条未访问出边先扣损失、再用扣损后水量和阻力比较，全部不通过——此时该球的可分配水量全部损失，没有下游被点亮，该球成为本次激活的动力学死路。它和“所有出边已访问”是两种不同的死路：后者是拓扑死路（没有未访问出边可分配，分配阶段就为零），前者是动力学死路（有未访问出边、水也分了，但每条都因水量不足过不去），两者都让水在该球处耗尽、不回流，但触发原因不同。全失败发生后，该球被“润湿”——不是“什么都没发生”，而是留下两层痕迹：每条失败的管道 blocked_count_stored += 1、刷新 last_blocked，下次同类线索到达时有效阻力打折，这是“差点通过”的补偿；该球本身记一次点亮（它已经被点亮过，只是没能继续传播），用于舌尖效应的轻量计数。润湿的语义是“这次没想起来，但留下了痕迹，下次更容易”——它和“流动只点亮、不写入”不冲突：blocked_count 和点亮次数的本次新增只记在内存里，结算时才按“先衰减再叠加”写回，流动阶段仍然纯内存、不落库。全失败的水量损失不回收给上游——上游那一步的分配已经完成、不可逆，失败的那份水按“损失不回收”消失，上游球不会因为下游全失败而重新获得水量。边界情况：球只有一条未访问出边且该出边失败时，等同于全失败；球有未访问出边但分配后每条分到的水量都为零（极端情况，1+w 保底非零使这几乎不可能）时，也按全失败处理；全失败后该球不尝试回边（回边已在分配前排除），直接结束该方向。测试要覆盖：全失败时水量全部损失无回流、每条失败管道 blocked_count 增加、球被记一次点亮、结算时按“先衰减再叠加”写回、与“所有出边已访问”的触发条件区分、全失败后上游球不重新获得水量。 |

## 五、结算决策

| 条目 | 详细说明 |
|---|---|
| **结算同步立刻执行** | 	流动结束后立刻结算，结算与注入在同一同步步骤内完成、不可异步——结算的结果直接决定本轮注入哪些球，写入和注入是同一个步骤的前后两半，中间没有异步间隙。引入这条规则的理由有三层：① 结算即注入决策——结算不是“事后写库”，是“决定这轮想起什么”，注入排序基于刚强化后的球状态（刚被强化的球权重更高），如果异步结算、注入用流动过程中已确定的球，排序会基于旧状态、结果过时。② 避免状态窗口——异步结算会引入“注入基于旧状态、结算基于新状态”的窗口，同一个球在注入时和写入时的 size_stored 不一致，虽然差异微小但“只算一次”就破了。③ 延迟可控——结算延迟直接叠加到注入延迟上，必须控制在毫秒级，这也是为什么相关性判定只能用嵌入、不能用 LLM——LLM 延迟是百毫秒到秒级，同步结算里放不下。具体机制：流动纯内存计算、只点亮不写入；流动结束后立刻进入结算，计算流动加权语境（α ≤ 0.3）、对每个点亮球算相关性（语义相似度 × 路径折扣，不含水量）、多路径取最大值、划分强化球/最低强化球、计算路径相关性和强化增量、开写事务校验版本号（无冲突直接写、有冲突重读涉及球/管道重算增量）、写入球大小增量、管道粗细增量、last_watered/last_flowed 刷新、blocked_count 和 S 先衰减再叠加、提交事务、按刚强化后的状态做注入排序、渲染注入块、返回给宿主拼装尾部消息。失败降级：结算写入失败或版本冲突重算失败时，注入照常进行（用流动阶段已确定的点亮集合和路径），只是本轮强化没写入、下一轮重试——记忆系统可以降级，但不能让主对话卡住。它和“流动只点亮、不写入”是严格配套的两步：流动只回答“哪些球被点亮、沿什么路径”，结算回答“强化多少、注入哪些”，两者职责分离但同步衔接，中间不能插入异步。测试要覆盖：流动结束后立刻结算、结算结果决定注入内容、注入排序基于刚强化后的状态而非流动前状态、结算失败时注入照常进行但强化未写入、结算延迟在毫秒级、版本冲突时重算增量而非放弃。 |
| **流动加权语境** | 结算时用于计算相关性的语境嵌入，是“原始查询嵌入 × (1-α) + 流动路径上各球嵌入的加权平均 × α”，α 是流动加权系数，α ≤ 0.3（默认 0.2），原始查询嵌入占主导、流动路径只做轻微染色。原始查询嵌入是触发本次激活的那条输入（用户消息/工具结果/模型的话）经过嵌入模型得到的向量，也是起始球选择时用来和所有球算余弦的那个向量——系统里只有这一个“原始”概念，“原始语境”和“原始查询”是同一个东西，统一叫“原始查询嵌入”。流动阶段不用流动加权语境：水到达一个球时，用原始查询嵌入和球嵌入算相关性、判断是否补充，逐跳不做语境更新；结算时才做一次性的路径加权，把整条路径的信息汇总后重新算语境，用于结算的相关性计算（语义相似度 × 路径折扣中的“语义相似度”就是用这个加权语境算出的余弦）。加权平均的权重是各球在路径上获得的水量占比——路径越长、水量越分散，染色越弱，符合“想得越远，越不确定自己在想什么”的直觉。引入它的理由是：水流经过中间球后语境会“被带偏”，用轻微染色的语境算相关性比用纯原始查询更贴近“顺着联想往下想”的真实过程；但 α 不能高，否则语境会被中间球带跑偏到无关方向，一个语义上只和原始问题相关的球会被错误判为不相关，所以 α ≤ 0.3 是硬约束、原始查询占至少 70%。它只影响结算阶段的相关性计算，不影响起始球选择、不影响流动阶段的逐跳相关性判定、不影响注入排序之外的其他计算；它和“相关性定义”配套——相关性 = 语义相似度 × 路径折扣，水量本身仍不进入相关性，流动加权语境是“语境被染色”，不是“水量乘进相关性”，两者是不同的事。边界情况：流动路径为空（只有起始球被点亮、没有传播）时加权平均项为零、退化为原始查询嵌入；α=0 时完全退化为原始查询嵌入，可作为对照基线；α 超过 0.3 时配置校验拒绝。测试要覆盖：α=0 时语境等于原始查询嵌入、α=0.2 时语境被轻微染色、α 超过上限时配置校验拒绝、路径为空时退化为原始查询嵌入、染色后的语境算出的相关性介于“纯原始查询”和“纯路径语境”之间、水量占比高的球对染色贡献更大、流动阶段的逐跳相关性不受流动加权语境影响。 |
| **相关性定义** | 相关性 = 语义相似度 × 路径折扣，不含水量，不含 w_eff。语义相似度是“当前语境嵌入与该球嵌入的余弦”——结算时用流动加权语境（原始查询嵌入 × (1-α) + 路径上各球嵌入的加权平均 × α，α ≤ 0.3、默认 0.2），流动逐跳时用原始查询嵌入；路径折扣是 max(min_discount, 1 - discount_per_hop × 跳数)，默认每跳 0.1、最低 0.5、触底不再降。这是已修正的设计，原定义把水量乘进了相关性（water × sim × 路径折扣），混淆了两个正交维度——语义相关性应由嵌入相似度和路径位置决定，水量反映的是路径通畅度，不是语义相关性；一个球语义上很相关但水勉强够到，它的相关性不应因“路难走”被打折，一个球语义一般但水很充足，也不应因“路好走”被抬高。w_eff 同样不进入相关性——它已在流动阶段决定了阻力和损耗，再乘进相关性是同一个信号第二次计权，会形成“粗管→更受偏爱→更粗”的正反馈，管道健康因子因此被废弃。相关性和“资格与幅度分离”配套：资格看 semantic_sim（判断是否值得强化，与路径折扣无关），幅度和排序用 sim × 折扣（判断强化多少、排序多靠前）——资格不该被路径长度惩罚，深度 5、sim=0.95 的球语义上完全匹配，应该被强化，幅度是 0.95 × 0.5 = 0.475，被强化但幅度较小，而不是被否定。相关性不进入流动阶段的通过判断（通过条件只看水量 > 阻力），只进入结算的强化幅度；注入排序只用 semantic_similarity（不含路径折扣、不含 size、不含水量）——size 是相关性的历史累积结果，不是独立信号。边界情况：路径折扣触底后不再随深度下降；多路径取最大值时，同一球取最大路径相关性强化一次、不累加；semantic_sim ≥ 0.7 为强化球，0.3–0.7 为印象球（拿最低强化值但注入），< 0.3 为最低强化球（拿最低强化值且不注入）；流动路径为空时流动加权语境退化为原始查询嵌入。测试要覆盖：相关性不含水量和 w_eff、语义相似度用流动加权语境而非原始查询、路径折扣按跳数正确计算且触底、资格用 semantic_sim 而幅度用 sim × 折扣、深度 5 且 sim=0.95 的球仍被强化（死区修复）、多路径取最大值不累加。 |
| **路径折扣** | 路径折扣是相关性的第二个因子，公式 max(min_discount, 1 - discount_per_hop × 跳数)，默认每跳 0.1、最低 0.5——跳数 0（起始球本身）折扣 1.0，跳数 3 折扣 0.7，跳数 5 折扣 0.5，触底后不再随深度下降（深度 10 也是 0.5）。跳数按 BFS 首次到达深度算，不是最长路径——同一次激活每球只注一次，首次到达后标记为已访问，后续再到达不注水，所以深度天然是“最短路径深度”。引入它的理由是：结算时按路径长度打折强化值，防止“一条长路径上的所有球都被大幅强化”导致远处球被误强化——路径越长，终点球即使语义相关，也因为“绕了远路”而获得较少强化，这是“想得越远越不确定”在强化幅度上的体现；它用跳数作为“这次激活有多强”的粗糙代理，确定、可复现、不依赖水量，但不如直接用水量精确——强线索可能在 5 跳后水量仍充足，弱线索可能在 2 跳后就衰减殆尽，跳数和水量的关系不是线性的，这是它作为代理的已知不精确之处。管道健康因子已废弃，不再作为路径折扣的因子——w_eff 已在流动阶段决定阻力和损耗，再乘进相关性是二次计权，会形成“粗管→更受偏爱→更粗”的正反馈，细管和孤岛永远等不到水流；这和“水量乘进相关性”“size_stored 塞进衰减函数”是同一类错误，一个量在它不该出现的地方被当成了另一个量的乘数。路径折扣和“资格与幅度分离”配套：资格看 semantic_sim（判断是否值得强化，与路径折扣无关），幅度和排序用 sim × 折扣（判断强化多少、排序多靠前）——资格不该被路径长度惩罚，深度 5、sim=0.95 的球语义上完全匹配，应该被强化，幅度是 0.95 × 0.5 = 0.475，被强化但幅度较小，而不是被否定。旧公式下路径折扣作用在 sim × 折扣 上时存在死区：strengthen_threshold_X=0.6、深度 3 折扣 0.7 需要 sim=1.0 才能过线、深度 4 折扣 0.6 需要 sim=1.17、深度 5 折扣 0.5 需要 sim=1.4——不可能，max_flow_depth 默认就是 5，第 4、5 跳的球永远无法成为强化球；旧公式乘 water 时被掩盖（强线索 water=3 能把 0.5 抬到 1.5），移除 water 后暴露，方案 A 修复。多路径取最大值时，同一球取最大路径相关性强化一次、不累加；discount_per_hop 和 min_discount 全部进配置可调，min_discount 触底后不再降是显式确认的行为，实现时不能把 max 写成 min 或漏掉触底逻辑。测试要覆盖：跳数 0 折扣 1.0、每跳递减 0.1、触底后不再降、管道健康因子不参与路径折扣、资格用 semantic_sim 而幅度用 sim × 折扣、深度 5 且 sim=0.95 的球仍被强化、多路径取最大值不累加、配置校验拒绝 min_discount > 1.0 或 discount_per_hop < 0。 |
| **折扣触底** | 路径折扣降到 min_discount（默认 0.5）后，不再随深度继续下降——深度 5 折扣 0.5，深度 10 还是 0.5，深度 100 也是 0.5。公式 max(min_discount, 1 - discount_per_hop × 跳数) 里的 max 就是触底逻辑：当 1 - discount_per_hop × 跳数 低于 min_discount 时，取 min_discount，不再继续降。引入触底的理由是：没有下限，无限长路径的折扣会趋近于零，强化幅度也趋近于零，等于“路径越长越不可能被强化”，这会让多跳联想在强化层面被系统性扼杀；有了下限，远处球至少能拿到 min_discount 比例的强化，虽然少但不会归零，“想得越远越不确定”有下限，不是“想得越远越等于没想”。触底不是死区问题的原因，死区是“资格判断作用在含折扣的值上”导致的——strengthen_threshold_X 如果判断 sim × 折扣，深度 4 需要 sim=1.0、深度 5 需要 sim=1.2 才能过线，这是资格被折扣惩罚；触底只是让折扣停在一个非零下限，不改变“资格该不该看折扣”这个问题。方案 A 修复死区的方式是资格看 semantic_sim（不含折扣），触底仍然保留在幅度计算里——资格不被折扣惩罚，幅度仍随深度递减到下限，两者分工明确。触底后深度 5 和深度 10 的球拿同样的幅度，这是可接受的——它们都是“很远的球”，再区分 5 跳和 10 跳的差异没有语义价值，反而增加不必要的复杂度。实现时有一个容易犯的错误：把 max 写成 min，或者漏掉触底逻辑直接让折扣线性递减到零甚至负数；测试要显式覆盖“深度 5 折扣 0.5、深度 10 折扣仍是 0.5、深度 100 折扣仍是 0.5”，以及“min_discount 配置为 0.3 时触底值相应变化”。min_discount 进配置可调，但配置校验要拒绝 min_discount > 1.0（触底值不能比不折扣还高）和 min_discount < 0（不能为负）；discount_per_hop 也要拒绝负数。触底和“多路径取最大值”独立——触底决定单条路径的折扣下限，多路径取最大值决定同一球在多条路径上取哪条的值，两者不冲突。测试要覆盖：深度 5 和深度 10 折扣相同、min_discount 配置变化时触底值相应变化、max 没写成 min、折扣不为负、配置校验拒绝非法 min_discount 和 discount_per_hop、触底不影响资格判断（资格仍看 semantic_sim）。 |
| **资格与幅度分离（方案 A）** | 资格看 semantic_sim（纯语义相似度，不含路径折扣、不含水量、不含 w_eff），幅度和排序用 sim × 折扣。这是解决死区问题的方案：旧设计里 strengthen_threshold_X 作用在 sim × 折扣 上，深度 3 折扣 0.7 需要 sim=1.0 才能过线、深度 4 折扣 0.6 需要 sim=1.17、深度 5 折扣 0.5 需要 sim=1.4——不可能，max_flow_depth 默认就是 5，第 4、5 跳的球即使内容完全匹配也永远无法成为强化球，只能拿 min_strengthen_value；旧公式乘 water 时被掩盖（强线索 water=3 能把 0.5 抬到 1.5），移除 water 后暴露。方案 A 的核心理由是“每种信号只负责一件事”：资格回答“这个球语义上够不够相关、值不值得强化”，不该被路径长度惩罚——深度 5、sim=0.95 的球语义上完全匹配，它“值得强化”这个判断不应该因为它离起始球远而被否定；幅度回答“强化多少、排序多靠前”，路径长度应该在这里起作用——远处球被强化得少，但不会被否定。具体规则：semantic_sim > strengthen_threshold_X（默认 0.7）→ 资格通过，按 路径相关性 = semantic_sim × 路径折扣 计算幅度；未通过 → 拿统一最低强化值（默认 0.05），不参与幅度计算。注入排序用 sim × 折扣（幅度口径），不是 semantic_sim（资格口径）——排序要考虑“多相关”和“离起始球多远”，远处高相关球排序靠后是合理的，但这不影响它被强化。连带影响：strengthen_threshold_X 的语义从“路径相关性阈值”改为“语义相似度阈值”，所有文档表述和测试注释同步改；死区消失，深度 5、sim=0.95 的球幅度是 0.95 × 0.5 = 0.475，被强化但幅度较小，而不是拿最低值；现有手算测试中深度 0 的数值不变（折扣 1.0），涉及阈值的测试要改判断对象。边界情况：semantic_sim 恰好等于 strengthen_threshold_X 时按“严格大于”判断，等于不算通过；semantic_sim 过阈值但路径相关性极低（深度触底、sim 刚过线）时，幅度很小但仍按幅度强化，不退回最低值——最低值只给资格未通过的球。测试要覆盖：深度 5 且 sim=0.95 的球资格通过、幅度 0.475、不再是死区；深度 5 且 sim=0.5 的球资格未通过、拿最低强化值；strengthen_threshold_X 判断的是 semantic_sim 而非 sim × 折扣；注入排序用 sim × 折扣；资格通过但幅度极低的球不退回最低值。 |
| **strengthen_threshold_X 语义** | strengthen_threshold_X（默认 0.7）是语义相似度阈值，判断的是 semantic_sim——纯语义相似度，不含路径折扣、不含水量、不含 w_eff。它回答的是“这个球语义上够不够相关、值不值得强化”，不是“路径相关性多高才值得强化”。这是已修正的语义，原语义是“路径相关性阈值”，判断的是 sim × 折扣，导致死区问题——深度 3 折扣 0.7 需要 sim=1.0 才能过线、深度 4 折扣 0.6 需要 sim=1.17、深度 5 折扣 0.5 需要 sim=1.4，max_flow_depth 默认就是 5，第 4、5 跳的球永远无法成为强化球，即使内容完全匹配也只能拿最低强化值；旧公式乘 water 时被掩盖（强线索 water=3 能把 0.5 抬到 1.5），移除 water 后暴露。语义修正的理由是“每种信号只负责一件事”：资格回答“值不值得强化”，不该被路径长度惩罚——深度 5、semantic_sim=0.95 的球语义上完全匹配，它值得强化这个判断不应该因为它离起始球远而被否定；幅度和排序才用 sim × 折扣，路径长度在那里起作用。它和“资格与幅度分离（方案 A）”是同一件事的两面：后者是机制表述（资格看 semantic_sim、幅度用 sim × 折扣），前者是参数语义表述（这个阈值判断的是 semantic_sim）。判断规则是严格大于——semantic_sim > strengthen_threshold_X 才算资格通过，等于不算；通过则按 路径相关性 = semantic_sim × 路径折扣 计算幅度，未通过则拿统一最低强化值（默认 0.05），不参与幅度计算。它和 supplement_threshold（补充资格阈值，默认 0.4–0.5）是两个不同的阈值：前者管“是否值得强化”，作用在结算阶段；后者管“是否释放补充”，作用在流动阶段；两者独立配置、不要求相等，但都遵循“资格严格、幅度宽容”的分工。连带影响：所有涉及 strengthen_threshold_X 的文档表述和测试注释要同步改为“语义相似度阈值”，测试判断对象从 sim × 折扣 改为 semantic_sim；现有手算测试中深度 0 的数值不变（折扣 1.0），涉及阈值的测试要改判断对象。边界情况：semantic_sim 恰好等于阈值时按严格大于判断、不算通过；semantic_sim 过阈值但路径相关性极低（深度触底、sim 刚过线）时仍按幅度强化，不退回最低值——最低值只给资格未通过的球；阈值配置校验拒绝 > 1.0 或 < 0。测试要覆盖：深度 5 且 semantic_sim=0.95 的球资格通过、不再死区；深度 5 且 semantic_sim=0.5 的球资格未通过、拿最低强化值；判断对象是 semantic_sim 而非 sim × 折扣；等于阈值不算通过；过阈值但幅度极低的球不退回最低值；与 supplement_threshold 独立配置、互不影响。 |
| **死区问题** | 	死区问题是旧公式下“路径折扣”与“强化资格阈值”叠加产生的系统性缺陷：strengthen_threshold_X（默认 0.7）作用在 sim × 折扣 上时，深度 4 折扣 0.6 需要 semantic_sim=1.0 才能过线，深度 5 折扣 0.5 需要 semantic_sim=1.2——而余弦相似度上限是 1.0，后者在数学上不可能。max_flow_depth 默认就是 5，这意味着第 4 跳的球只有语义完全匹配（sim=1.0）才能成为强化球，第 5 跳的球永远无法成为强化球，即使内容完全匹配也只能拿 min_strengthen_value（默认 0.05）。旧公式乘 water 时被掩盖——强线索 water=3 能把 0.5 的路径相关性抬到 1.5，越过 0.6 的阈值，看起来“远处球也能被强化”；移除 water 后，路径相关性回到 sim × 折扣 的纯语义量纲，死区立刻暴露。死区的本质是资格判断被路径长度惩罚：一个球“值不值得强化”应该由它的语义相关性决定，不应该因为它离起始球远而被否定；旧设计把资格和幅度混在同一个量 sim × 折扣 上，路径折扣本来只该影响“强化多少”，却越权影响了“是否强化”。修复方案是资格与幅度分离（方案 A）：strengthen_threshold_X 改为判断 semantic_sim（不含折扣），资格不再被路径长度惩罚；幅度和排序仍用 sim × 折扣，远处球被强化得少但不会被否定。修复后深度 5、sim=0.95 的球资格通过，幅度是 0.95 × 0.5 = 0.475，被强化但幅度较小，而不是拿最低值。连带影响：strengthen_threshold_X 的语义从“路径相关性阈值”改为“语义相似度阈值”，所有文档表述和测试注释同步改；现有手算测试中深度 0 的数值不变（折扣 1.0），涉及阈值的测试要改判断对象。边界情况：semantic_sim 恰好等于阈值时按严格大于判断、不算通过；资格通过但幅度极低的球仍按幅度强化，不退回最低值——最低值只给资格未通过的球。测试要覆盖：深度 5 且 sim=0.95 的球资格通过、幅度 0.475、不再是死区；深度 5 且 sim=0.5 的球资格未通过、拿最低强化值；深度 4 且 sim=0.9 的球在旧公式下拿最低值、新公式下资格通过；strengthen_threshold_X 判断对象是 semantic_sim 而非 sim × 折扣；修复后深度 5 的球不再被系统性排除在强化之外。 |
| **多路径取最大值** | 	同一结算中，一个球或一条管道出现在多条路径上时，取最大路径相关性强化一次，不累加。球和管道都遵守这条规则。引入它的理由是：防止一个球或一条管道被多条弱路径“刷”成过强——如果累加，一条被三条 0.3 相关性路径经过的管道会得到 0.3+0.3+0.3=0.9 的强化，比一条被单条 0.8 相关性路径经过的管道还强，这违背“强相关路径应该主导强化”的直觉，也会让被多条弱路径反复经过的管道突然变得极粗，流动时形成正反馈、越来越倾向于走这条管道，导致联想僵化。取最大值后，同一结算中每条路径的贡献独立、不叠加，最强的路径决定强化幅度，弱路径不因为“数量多”而补偿。它和“路径级强化”是配套的：路径级强化让“一起被想起的东西一起变强”，多路径取最大值防止“被反复想起但每次都不够强”的东西被过度强化。它和“管道合并取最大值”是同一类原则——两条管道合并时 w = max(w_ac, w_bc) 而不是相加，多路径强化时也取最大值而不是累加，两者都遵循“强度取最强、不叠加”的守恒逻辑。它和“资格与幅度分离”独立——资格仍看 semantic_sim，幅度仍用 semantic_sim × 路径折扣，多路径取最大值只作用于“同一球/管道被多条路径命中时选哪条路径的幅度”，不改变单条路径内的计算。边界情况：同一球出现在两条路径上、相关性分别是 0.8 和 0.3，只按 0.8 算强化值、不按 1.1 算；同一管道出现在三条路径上，取最大不累加；同一球和同一管道同时出现在多路径上，两者各自独立取最大、互不影响；两条路径相关性相同时取哪条都一样，只强化一次。测试要覆盖：一个球出现在两条路径上断言强化值只按最大值算、一条管道出现在三条路径上断言取最大不累加、球和管道各自独立取最大、多路径取最大值不改变单条路径内的 sim × 折扣 计算、与“管道合并取最大值”行为一致。 |
| **强化球 / 印象球 / 最低强化球** | 结算时，每个被点亮的球按语义相似度分三档：**强化球**（semantic_sim ≥ 0.7）按 路径相关性 = semantic_sim × 路径折扣 计算幅度，乘 size_strengthen_factor 后经边际递减写入 size_stored，并参与注入；**印象球**（0.3 ≤ semantic_sim < 0.7）不参与幅度计算、直接拿统一最低强化值（base_reinforcement × min_strengthen_value，默认 0.1 × 0.05 = 0.005），但**参与注入**（渲染为印象档）；**最低强化球**（semantic_sim < 0.3）同样拿最低强化值，但**不注入**。引入最低强化值的理由是：资格未通过不代表“完全不该强化”，如果完全不强化，就失去了“多次弱相关点亮累积起来也能变强”的可能——最低强化值远小于正常强化值，保留一条极慢的累积路径，又不会让无关球被过度强化。印象球与最低强化球的区别只在“是否值得被说起”，不在“是否值得被记住”——0.3 以上说明内容与当前输入确实相关、值得让模型看见（哪怕只是“有模糊印象”）；0.3 以下连说起都是噪声。关键边界：强化球但幅度极低的仍按幅度强化，不退回最低值；semantic_sim 恰好等于 0.7 时归入强化球（≥）、恰好等于 0.3 时归入印象球（≥）；印象球与最低强化球多路径命中时也只给一次最低值，不累加、不取最大（不按路径相关性算幅度，多路径规则对它无意义）；最低强化值进配置可调，但必须远小于正常强化值，否则“最低”失去区分意义。它和“资格与幅度分离”配套：强化球是“按幅度强化”，印象球与最低强化球是“按固定最低值强化”；它和“多路径取最大值”的关系是：只有强化球走多路径取最大值。测试要覆盖：≥0.7 按路径相关性强化、0.3–0.7 拿最低值但被注入、<0.3 拿最低值且不注入、强化球幅度极低不退回最低值、边界值归属、印象球多路径不累加、最低强化值远小于正常强化值、仍受 size_max 饱和约束。 |
| **注入排序** | 结算后、注入前，对强化球按 semantic_similarity 降序排序，取 Top-K 装预算。排序量是 semantic_similarity（资格口径），不是 semantic_similarity × 路径折扣——注入要回答的是“这条记忆和用户当前说的话有多像”，路径走了多远不影响这条记忆的回答价值；折扣已在强化幅度里起作用，不该在排序里第二次惩罚远处球。不乘 size_effective——size_effective 是“相关性 → 强化 → size_stored 增长”这条链的历史累积结果、是相关性的滞后代理，不是独立信号；决策时已能算当前相关性，再乘历史累积值等于把同一个信号算两遍，和“新鲜度被乘三次”“水量乘进相关性”是同一类错误。类比图书馆推荐位：读者要找什么取决于此刻的检索词，不取决于这本书在馆藏里有多厚。水量同样不出现在排序公式里。sort_exponent_a 默认 1.0、作为可调指数保留；sort_exponent_b 默认 0，仅保留为对照实验入口、不作为推荐配置——如果数据显示“巩固度确实该参与排序”，再调默认值，但那时要有数据支撑。同等语义相关性不区分水量强弱——两个球相关性相同，一个被强水量点亮、一个被弱水量勉强点亮，排序不区分；如果未来数据显示“同等相关性下强激活的球确实更该被注入”，应作为显式的第三因子（激活强度）加入排序，可配置、默认关闭、有对照实验支撑。排序结果配合“注入预算两种模式”和“不切割完整球”使用——排序决定候选顺序，预算决定装几个完整球。测试要覆盖：排序只用 semantic_similarity、不含水量、不含 size、同等相关性下不区分水量强弱、sort_exponent_b 变化时行为相应变化。 |
| **同等语义相关性不区分水量强弱** | 两个球语义相关性相同（semantic_sim × 路径折扣 相同），一个被强水量点亮、一个被弱水量勉强点亮，注入排序不区分——它们排序分相同，按预算装谁都可以。引入这条规则的理由是：语义相关性相同意味着对当前问题的回答价值相同，水量差异反映的是路径通畅度（水从粗管顺畅流来还是从细管勉强挤过来），不是回答价值；把水量作为隐式区分因子，等于让“路好走”冒充“更相关”，混淆了两个正交维度。它和“相关性定义”配套：相关性 = 语义相似度 × 路径折扣，不含水量；水量是动力学量，通过“谁被点亮、谁的相关性高、谁被强化得多”间接影响结果，但不出现在排序公式里。它和“注入排序”配套：排序公式只用 semantic_similarity、不含水量、不含 size，同等相关性下排序分相同。如果未来要区分，应该作为一个显式的、有名字的第三因子（如“激活强度” activation_strength = 到达该球时的水量 / 起始水量）加入排序，公式形如 semantic_similarity × 激活强度^c，c 默认 0（关闭）、可配置、有对照实验支撑——而不是藏在相关性定义里的隐式乘数，也不是在排序后偷偷按水量二次排序。这样做的好处是：区分是显式的、可审计的、可关闭的；如果数据显示“同等相关性下强激活的球确实更该被注入”，打开 c 即可，不需要改相关性定义；如果数据显示不必要，c=0 保持当前行为。边界情况：同等相关性、不同水量、同预算下两个球只能装一个时，按排序分相同、取任意一个，结果可复现（按球 ID 排序兜底）；如果开了激活强度因子，强激活的球优先，但这是显式配置的结果，不是默认行为。测试要覆盖：同等相关性下两个球排序分相同、水量差异不影响排序分、c=0 时激活强度不参与排序、c>0 时激活强度显式参与排序、按球 ID 兜底保证可复现、不因水量差异偷偷二次排序。 |
| **注入预算两种模式** | 注入预算有两种可配置模式，统一遵守“不切割完整球”的底线。模式 A：token 映射——按注入排序逐个加入完整球，对每个球估算 token（est_i = ball_stored_size_i × tokens_per_size，默认 20；用不衰减的 size_stored——估算的是渲染长度，内容不会因为放久了变短），累加估算值直到 est_sum + est_{i+1} > token_budget（默认 500）时停止，得到候选球数 K；渲染前 K 个完整球，用真实 tokenizer 对渲染结果计数——若 real_sum > token_budget 则从 K 开始逐个减球直到不超，若 real_sum < token_budget 则尝试加入第 K+1 个球直到下一个会超；估算系数 tokens_per_size 是保守值、宁可估高不估低，最终截断由真实 tokenizer 兜底。模式 B：球数映射——配置固定球数上限 max_balls_per_inject（默认 5），直接取排序前 K_max 个完整球，渲染后用真实 tokenizer 校验，若超过 token_hard_cap（默认 800）则减球直到不超，token 只作硬上限兜底、不参与主排序。统一停止规则：从排序后的候选球开始逐个加入完整球，加入下一个完整球后会超预算（模式 A）或超球数（模式 B）时停止，返回已加入的完整球——不切割、不截断、不部分渲染，一个球内容 800 token、预算只剩 500 token 时整个球不注入，而不是注入前 500 token，这保住“模型看到的每条记忆都是完整的”。为什么用 token 作为预算单位：模型上下文窗口、API 成本、推理延迟全部按 token 计，水量是内部调度单位、token 是外部约束单位，语义相关性决定优先级、token 决定截断点，两者解耦；用球数作预算单位是因为某些场景希望“每次注入固定条数、行为稳定”，两种模式对应不同偏好。模式 A 适合成本敏感、上下文窗口紧张的场景，模式 B 适合行为一致性优先、球内容长度相对均匀的场景；injection.mode 配置切换，默认 token。allow_partial_ball 保留为配置项，但默认且推荐永远为 false，只在极端场景（单个球内容远超预算且必须注入）才考虑，属于逃生舱不是常规路径。测试要覆盖：模式 A 按 token 预算整球增减、模式 B 按球数取前 K 个、真实 tokenizer 校验后整球减、不切割完整球、tokens_per_size 保守估算、token_hard_cap 兜底生效、模式切换时行为相应变化。 |
| **不切割完整球** | 注入时，一个球的内容要么完整注入、要么完全不注入，永不注入半个球——一个球内容 800 token、预算只剩 500 token 时，这个球整个不注入，而不是注入前 500 token、丢掉后 300 token。引入这条规则的理由是记忆完整性：模型看到的每条记忆都必须是完整的，半个球意味着模型看到的是“半句话的记忆”，它可能误解语义、可能基于残缺内容做出错误判断，而且这种误解无法被审计——模型不知道这条记忆被截断了，它以为自己看到的就是全部。它和“注入预算两种模式”配套：模式 A 的“估算粗筛 + 真实 tokenizer 整球增减”、模式 B 的“取前 K 个完整球 + token 硬上限兜底”，统一停止规则都是“下一个完整球会超预算时停止、返回已累加的完整球”，不切割是两种模式共同的底线。它和“冷热分层”配套：内容列表超出上限时淘汰最不常用的内容转冷存储，是“球内的内容条目级淘汰”，不是“单条内容被截断”——单条内容长度上限（默认 4000 字符）超出时截断为“前 N 字符 + 摘要”、原文转冷存储，这是写入时的处理，不是注入时的切割；注入时球的内容列表已经是“可渲染的完整内容”，不再切割。allow_partial_ball 保留为配置项，但默认且推荐永远为 false——只在极端场景（单个球内容远超预算且必须注入）才考虑，属于逃生舱不是常规路径；即使打开，也要在注入块里显式标注“这条记忆被截断”，让模型知道它看到的不完整。边界情况：预算只够装 0 个完整球时，返回空注入块，不注入任何记忆——这是正常状态，不是故障；排序第一的球就超预算时，整个跳过它、尝试下一个能装下的球，而不是截断它；所有球都超预算时，返回空注入块。测试要覆盖：长球超预算时整个不注入、短球完整注入、预算只够装 0 个球时返回空、排序第一超预算时跳过它装后面的球、allow_partial_ball=false 时永不切割、allow_partial_ball=true 时切割并显式标注截断、渲染后的 token 数不超过预算。 |
| **渲染档位（清晰档 + 印象档三档措辞）** | 注入块按 semantic_similarity 分档渲染，让模型知道这条记忆有多可靠：清晰档（≥ 0.7）→ [记忆] 关于"X"，我记得：Y，表示内容明确、可放心引用；印象档·深（0.6–0.7）→ 我对"X"有比较深的印象……；印象档·中（0.5–0.6）→ 我对"X"有印象……；印象档·浅（0.3–0.5）→ 我对"X"有模糊的印象……。低于 0.3 的球不注入——“我好像有关于X的印象”这类无内容空壳已废弃，它对回答没有价值、只增加噪声。四档对应不同的置信度，不是“装饰性文案”，是给模型的可靠性信号——模型看到“我记得”和看到“我印象中”，对这条记忆的信任程度应该不同，前者可以当作事实引用，后者应该作为参考、必要时向用户确认。引入它的理由是：如果所有注入都用同一种确定性语气，模型无法区分“高置信召回”和“低置信召回”，会把模糊记忆当事实用，产生“过度自信”的幻觉；渲染分档把“系统对这条记忆有多确定”显式传递给模型，让模型自己决定怎么用。它和“元记忆”是同一件事的工程落地：系统知道自己“记得清”还是“只记得大概”，并通过渲染文本表达出来。渲染发生在尾部注入组装阶段，不触碰前缀缓存；每一级的文本模板可配置，但语义分工不变。边界情况：清晰档的球内容必须完整（受“不切割完整球”约束）；印象档可以是完整内容但相关性中等，也可以是高相关但内容列表里只有摘要；内容列表为空且冷层无内容的球跳过注入；同一轮注入可以同时出现四档，按各自相关性分别渲染。它和“注入排序”独立：排序决定“装哪几个球”，渲染决定“每个球用什么语气写出来”，排序靠前的球不一定都是清晰档、排序靠后的球也不一定都是印象档，两者按各自维度独立判断。测试要覆盖：≥0.7 渲染清晰档、0.6–0.7 深印象、0.5–0.6 印象、0.3–0.5 模糊印象、<0.3 不注入、清晰档内容完整不切割、模板可配置、渲染不改变前缀缓存。 |
| **版本冲突重算** | 结算写入前校验全局版本号：流动开始时读快照记录 V_start，结算开写事务时读当前版本 V_now；V_now == V_start 说明流动之后图没被其他进程改过，直接按流动结果写入增量；V_now != V_start 说明流动期间有其他进程（dsh/pi 同时结算、或离线巩固并发写入）改过图，旧的计算结果作废，重读本次结算涉及的球和管道、用最新状态重算路径相关性和强化增量再写入。引入它的理由是：结算的强化增量基于流动时读到的球大小、管道粗细、S、blocked_count 等状态算出，如果这些状态在流动期间被改过，直接用旧增量写入会基于过时数据——比如球已经被另一个进程强化过，再按旧 size_stored 算边际递减会算错；冲突重算保证增量总是基于最新状态计算，不丢更新、不写错数据。重算不是重复计权——旧的那次计算结果因版本冲突已经作废、从未写入，重算是基于新状态的一次全新计算，和“新鲜度被乘三次”“水量乘进相关性”是不同性质的问题，后者是在同一份数据上重复乘同一个因子，前者是旧结果失效后重新算一次。成本可控：重算范围限于本次结算涉及的球和管道，最多 max_lit_balls（默认 50）个球 + 对应管道，重读和重算在毫秒级；单用户场景下冲突概率极低（两个客户端同时结算的概率很小），重算不是常态、是兜底。冲突策略可配：conflict_strategy = "recompute"（默认，重算增量后写入）或 "abort"（放弃本次强化，注入照常进行，下一轮重试）——abort 是逃生舱，如果重算逻辑出问题可以切到“冲突即放弃”，保证不写错数据，代价是丢失本次强化。注入不依赖结算成败：重算失败或选择 abort 时，注入仍照常进行（用流动阶段已确定的点亮集合和路径），只是本轮强化没写入、下一轮重试——记忆系统可以降级，但不能让主对话卡住。它和“快照隔离”配套：流动开短读事务加载子图、记录 V_start、立刻结束读事务，流动在内存子图上纯计算；结算写事务校验版本号，版本一致直接写、不一致重算——两者合起来保证“流动读到一致性子图、结算写入不基于过时数据”。它和“非原子结算”的关系：原子模式下冲突重算后在同一事务内写入，要么全成功要么全回滚；非原子模式下重算后逐条写入，失败项进 pending_retry，下一轮或启动时重试。边界情况：多个进程同时结算时，后到的进程检测到版本冲突、重算、写入，两次结算的强化都保留、不丢更新；冲突重算时如果涉及的球已被归档，按归档球处理、不强行加载；版本号递增在结算事务提交时完成，与写入同一事务，不会出现“版本号加了但写入没成功”的情况。测试要覆盖：版本一致时直接写入不重算、版本冲突时重读重算增量、重算基于最新状态而非旧快照、冲突重算不丢更新、conflict_strategy="abort" 时放弃强化但注入照常、重算范围限于涉及球/管道、版本号递增与写入同事务、多个进程同时结算时两次强化都保留。 |

## 六、存储与持久化

| 条目 | 详细说明 |

| **存储内核** | 选用TriviumDB——一个用纯 Rust 编写的嵌入式三模数据库引擎，将向量检索（Vector）、属性图谱（Graph）和文档型元数据（Document） 原生融合在同一个存储内核里。它的定位是“AI 应用领域的 SQLite”：服务单机环境下的 Agent 复杂上下文和多模态记忆编织，而非分布式高并发后端。选它作为存储内核的核心理由，是它原生承接了系统最吃重的三件事——向量检索（QuIVer ANN，高维 768/1024/1536 维上同召回吞吐约为 HNSW 类的 1.4–5.0×）、图遍历（TQL MATCH，类 Cypher 模式匹配，支持多跳遍历和可变长路径）、文档查询（TQL FIND，类 MongoDB 过滤语法，10 万节点内单查询亚毫秒），避免 SQLite + 向量库 + 图库的多库拼接。存储形态上，Rom 模式保持单个 *.tdb 文件的便携性，拷贝即完整备份；默认 Mmap 模式将向量和已发布 Payload 分离到 sidecar 文件，按需映射。持久化与并发方面，TriviumDB 提供WAL 日志 + 原子替换 + 事务干跑验证（Dry-Run）+ Mmap COW 隔离四层保障，.flush_ok v3 绑定主文件和 sidecar，发布前旧代备份与撤销日志支持中断恢复；共享只读打开支持多进程 Reader 并发查询已完成代际，Writer 保持排他锁与 WAL 安全边界。0.9.0 是正式版（2026-10-30 发布），汇总了 beta.1–beta.4 的嵌入式资源管理、事务与恢复、类型化存储、统一查询及跨语言契约；Rust crate、Python、Node 均有正式版分发，Server 和 WebUI 仍处于 nightly 预览、不建议生产依赖。需要接受的代价：TriviumDB 生态早期，版本节奏快（从 0.4.x 到 0.9.0 约五个月），长期维护风险、API 稳定性、社区支持规模都无法与 SQLite 相比；因此 dayu-core 通过 StorageBackend trait 抽象保留回退可能——如果 TriviumDB 在生产验证中出现不可接受的问题，存储层可替换回 SQLite + sqlite-vec，业务逻辑不改，只改存储适配层。选型时的关键约束：QuIVer ANN 的优势随维度增大而扩大，128 维仅 0.21×、384 维 0.82×、768 维 1.4–2.9×、1024 维 3.4×、1536 维 3.6–5.0×——系统的嵌入维度（pizza 512 维、piccolo/bge-m3 1024 维）落在 QuIVer 的优势区间，这是选它而非 HNSW 类方案的重要理由；低维场景下 TriviumDB 并不占优，如果未来嵌入模型降到 384 维以下，需要重新评估。 |
| **持久化** | 	持久化由 TriviumDB 的 WAL（预写日志）+ 原子事务 + Dry-Run 预检 + COW 隔离 四层机制共同保证。事务提交时先写 WAL，COMMIT 返回即表示已持久化——进程被 kill -9、panic 或客户端闪退，已提交事务不丢，下次打开数据库时自动重放 WAL 恢复到崩溃前最后一个已提交事务，未提交事务自动回滚；断电场景下 synchronous=NORMAL 可能丢最后几秒未 checkpoint 的事务，但数据库不会损坏，synchronous=FULL 可配成不丢任何已提交事务。每个写入单元是一个原子事务——结算写入（球大小增量、管道粗细增量、last_watered/last_flowed 刷新、S/S_pipe/blocked_count 先衰减再叠加）、新球创建（建球+建内容+建初始管道）、归档、纠正（审计日志+状态变更+强度扣减/迁移）各自在一个事务内完成，要么全成功要么全回滚，不存在“球变大了但管道没变粗”“审计写了但状态没改”的半完成状态。启动恢复流程：打开数据库自动重放 WAL、回滚未提交事务；检查 pending_retry 表重试非原子结算模式下失败的写入；检查未完成结算标记（有则丢弃本次结算，下一轮重新计算）；执行 schema 版本迁移；可选 integrity_check 快速校验关键页。备份：启动时距上次快照超过 backup_interval_hours（默认 24 小时）则用 VACUUM INTO 生成一致性快照到 backup/ 目录，保留最近 N 份（默认 7），旧的自动删除；快照是热备份、不阻塞读写，用户也可以直接拷贝 store.tdb 文件做完整备份。多进程并发：WAL 支持多读单写，dsh 和 pi 可同时打开同一 .tdb，结算用 BEGIN IMMEDIATE 获取写锁、流动用 BEGIN DEFERRED 读快照，busy_timeout 控制等锁上限，写冲突串行化、不丢更新。原文压缩：rmw-utf8 压缩后的内容以 BLOB 存储、带编码标记，读取时按标记决定是否解压；压缩后不更小则回退 raw，不膨胀。边界情况：TriviumDB 的 Dry-Run 预检在事务提交前完成所有验证，验证失败不写 WAL；COW 隔离保证未提交的修改不影响正在读的快照；版本号递增与写入在同一事务内，不会出现“版本号加了但写入没成功”。测试要覆盖：kill -9 后已提交事务不丢、未提交事务回滚、WAL 重放正确、pending_retry 重试、未完成结算标记被丢弃、schema 迁移向前兼容、快照备份可恢复、多进程同时读写不丢更新、原文压缩 round-trip 一致、压缩后不膨胀回退 raw。 |
| **并发** | 	并发控制分进程级和线程级两层。进程级由 TriviumDB 的文件锁保证——Writer 排他、Reader 共享，dsh 和 pi 可同时打开同一 store.tdb，WAL 支持多读单写，多个流动可并行读快照，结算写入串行化；busy_timeout（默认 5000ms）控制等锁上限，写冲突时等待而非立即报错，单用户场景下冲突概率极低、等待通常在毫秒级。线程级由内核内部的 RwLock/Mutex 保护共享状态，napi 的异步调用在 Tokio 运行时上执行、不阻塞 JS 事件循环。流动与结算的并发边界：流动开始时开短读事务加载起点子图、记录全局版本号 V_start、立刻结束读事务，流动在内存子图上纯计算、不持有数据库锁；结算时开 BEGIN IMMEDIATE 写事务、校验版本号——V_now == V_start 直接写入增量，V_now != V_start 则重读涉及球/管道、用最新状态重算增量再写（版本冲突重算），重算范围限于本次结算涉及的球和管道、最多 max_lit_balls 个、毫秒级。强度更新用原子增量 UPDATE ball SET size_stored = size_stored + ?、UPDATE pipe SET w = w + ?，不用读-改-写，即使两个进程同时结算同一球也不会丢更新；版本号递增与写入在同一事务内，不会出现“版本号加了但写入没成功”。非原子结算模式（atomistic_settle = false）下逐条写入、失败项进 pending_retry 表，下一轮结算或启动时重试，最终一致；原子模式（默认）下所有写入在一个事务内，要么全成功要么全回滚，不需要 pending_retry。未完成结算标记只在非原子模式下使用——结算前写入、成功后清除，启动时发现标记还在则丢弃本次结算、下一轮重算，避免“半结算”状态污染图。冲突策略可配：conflict_strategy = "recompute"（默认，重算后写入）或 "abort"（放弃本次强化、注入照常、下一轮重试）。注入不依赖结算成败——结算失败或选择 abort 时注入仍照常进行，记忆系统可以降级但不能让主对话卡住。边界情况：两个进程同时结算同一球时，后到者检测到版本冲突、重算、写入，两次强化都保留；流动读快照不阻塞写、写不阻塞读；busy_timeout 超时后返回错误而非无限等待，由上层决定重试或降级。测试要覆盖：多进程同时读写不丢更新、版本冲突时重算而非覆盖、原子增量更新正确、busy_timeout 超时行为、非原子模式 pending_retry 重试、未完成结算标记被丢弃、abort 策略下注入照常、流动读快照不被写阻塞。 |
| **快照隔离** | 	流动开始时打开一个短读事务，从 TriviumDB 加载起点球及其 N 跳邻居子图到内存，同时记录全局版本号 V_start，然后立刻结束读事务——读事务只持续到子图加载完成，不持有到流动结束，避免长读事务阻止 WAL checkpoint、让 -wal 文件膨胀。子图加载完成后，流动全程在内存里纯计算，不再读数据库，因此流动看到的是一份一致性子图快照——不会出现“球 A 的旧大小 + 管道 A-B 的新粗细”这种撕裂状态，也不会因为另一个进程在流动期间结算而读到半新半旧的数据。TriviumDB 的快照隔离由 WAL + Mmap COW（写时复制） 支撑：读事务看到的是事务开始那一刻的已发布代际，写事务在 COW 隔离的副本上修改、提交后才原子替换发布，读不阻塞写、写不阻塞读。结算时打开 BEGIN IMMEDIATE 写事务，读当前版本号 V_now 与 V_start 比较：V_now == V_start 说明流动之后图没被改过，直接按流动结果写入增量；V_now != V_start 说明流动期间有其他进程（dsh/pi 同时结算、或离线巩固并发写入）改过图，旧的计算结果作废，重读本次结算涉及的球和管道、用最新状态重算路径相关性和强化增量再写入——重算不是重复计权，旧的那次结果因版本冲突从未写入，重算是基于新状态的一次全新计算。重算范围限于本次结算涉及的球和管道，最多 max_lit_balls（默认 50）个球 + 对应管道，毫秒级；单用户场景下冲突概率极低，重算不是常态、是兜底。快照隔离与“流动只点亮、不写入”配套：流动不持有写锁、不产生任何写入，只在内存子图上算；与“结算同步立刻执行”配套：结算必须在同一同步步骤内完成版本校验和写入，不能异步——异步会让版本窗口变大、冲突概率上升。与“并发”的关系：快照隔离解决的是“读一致性”，版本冲突重算解决的是“写不基于过时数据”，两者合起来保证流动读到一致性子图、结算写入不丢更新。边界情况：读事务加载子图期间如果有写事务提交，读事务看到的是写事务提交前的代际，不会读到未提交的修改；版本号递增在结算事务提交时完成、与写入同一事务，不会出现“版本号加了但写入没成功”；冲突重算时如果涉及的球已被归档，按归档球处理、不强行加载回主图。测试要覆盖：流动期间另一进程结算不导致流动读到撕裂状态、版本一致时直接写入不重算、版本冲突时重算基于最新状态、重算范围限于涉及球/管道、版本号与写入同事务、读事务不阻塞写、写事务不阻塞读、长流动不导致 WAL 膨胀。 |
| **崩溃恢复** | 进程被 kill -9、panic、客户端闪退或系统断电后，恢复流程分四步。① WAL 重放：TriviumDB 打开数据库时自动重放 WAL，把崩溃前最后一个已提交事务恢复到主库，未提交事务自动回滚——已提交的结算写入（球大小增量、管道粗细增量、时间戳刷新、S/S_pipe/blocked_count 先衰减再叠加）、新球创建（球+内容+初始管道）、纠正（审计日志+状态变更+强度扣减/迁移）、归档全部不丢；断电场景下 synchronous=NORMAL 可能丢最后几秒未 checkpoint 的事务，但数据库不会损坏，synchronous=FULL 可配成不丢任何已提交事务。② pending_retry 重试：仅非原子结算模式下使用——结算逐条写入、失败项进 pending_retry 表，崩溃后重启时检查该表、重试失败项，保证最终一致；原子模式下这张表永远为空。③ 未完成结算标记：非原子结算前写入 settle_in_progress 标记、成功后清除，崩溃后启动时发现标记还在，说明上次结算中途崩溃——丢弃本次结算（注入已经发生过了，强化值丢失可接受），清除标记，下一轮正常结算，避免“半结算”状态污染图。④ schema 版本迁移 + integrity_check：启动时检查 schema 版本，低于当前则执行迁移脚本、向前兼容；可选 integrity_check 快速校验关键页，失败则从最近的 backup/ 快照恢复，快照也损坏时用 TriviumDB 的 .recover 工具抢救可读数据。TriviumDB 自身的恢复机制包括 .flush_ok v3 绑定主文件和 sidecar、旧代备份与撤销日志、Dry-Run 预检——发布前完成所有验证、验证失败不写 WAL，COW 隔离保证未提交修改不影响正在读的快照。备份策略：启动时距上次快照超过 backup_interval_hours（默认 24 小时）则用 VACUUM INTO 生成一致性快照到 backup/、保留最近 N 份（默认 7），快照是热备份、不阻塞读写。边界情况：崩溃发生在结算事务提交前，事务回滚、球和管道回到结算前状态，下一轮重新计算；崩溃发生在提交后，WAL 已持久化、重放恢复；崩溃发生在 pending_retry 写入过程中，该条重试记录可能丢失，但只影响一次强化、不影响记忆内容；崩溃发生在归档或纠正事务中，事务回滚、状态不变。测试要覆盖：kill -9 后已提交事务不丢、未提交事务回滚、WAL 重放正确、pending_retry 重试、未完成结算标记被丢弃、schema 迁移向前兼容、integrity_check 失败时从快照恢复、快照可恢复、原文压缩 round-trip 一致、崩溃发生在结算不同阶段时数据一致性正确。 |
| **原文压缩** | 	球的内容原文写入存储前用 rmw-utf8 压缩——这是专门针对中文 UTF-8 短文本优化的压缩算法，对 12–120 字节的中文文本压缩率 21%–39%，远优于 zstd/gzip 在同等短文本上的表现（zstd 对 12 字节中文文本反而膨胀到 175%、gzip 膨胀到 275%，通用算法是为大文件和网络流设计的，在几十到几百字节的短文本上“帮倒忙”）。写入时：先按 rmw-utf8 压缩，压缩后长度严格小于原始长度才存压缩版、编码标记 rmw-utf8，否则回退存原始字节、编码标记 raw——永远不存“膨胀”的结果，这是短文本场景的必要兜底；单条内容长度上限（默认 4000 字符）超出时截断为“前 N 字符 + 摘要”、原文转冷存储。读取时：按编码标记决定是否解压，rmw-utf8 的解压发生在注入渲染或冷存储回源时，不触碰前缀缓存。只压缩文本内容，不压缩嵌入向量——嵌入是浮点 BLOB，rmw-utf8 是为文本设计的，对向量无效；向量用 f16 量化省空间，是另一个独立话题。存储格式：内容以 BLOB 存储、带 编码 字段（rmw-utf8 或 raw），行内标记让读取路径知道该不该解压，不需要全库重写就能逐行切换编解码器。为什么不用 zstd/brotli/gzip：这些算法为长文本和大文件设计，在念想系统的“几十到几百字节中文短片段”场景下压缩收益极低甚至为负；rmw-utf8 专门为中文短文本优化，是当前技术栈（Rust）下最匹配的选择，可直接作为 crate 依赖、无跨语言开销。边界情况：内容极短（字节数小于 MIN_COMPRESS_BYTES，默认 8）时直接存 raw，减少无意义压缩调用；非中文内容（纯英文、代码、JSON）压缩率可能不高，但“严格小于才压缩”的兜底保证不会膨胀；压缩后长度恰好等于原始长度时回退 raw（“严格小于”才压缩）；编解码 round-trip 必须 100% 一致。测试要覆盖：中文短文本压缩率在 21%–39% 区间、压缩后不膨胀回退 raw、极短内容直接存 raw、非中文内容不膨胀、round-trip 一致、编码标记正确、解压发生在读取时而非写入时、嵌入向量不经过此压缩层。 |
| **冷热分层** | 内容按访问频率和读取时机分三层，三层都是保留、不删除，只是存储位置和读取成本不同。热层是注入时渲染的代表性内容——球内容列表里被选中渲染进注入块的那条（或几条）内容，读取时直接解压、拼进尾部消息，是访问最频繁的一层。温层是球内容列表里的完整原文——每条内容以 rmw-utf8 压缩后存于球的 Payload 中，带编码标记，注入渲染时按需解压，是“这个球里装了什么”的完整记录，默认上限 5 条、可配。冷层是被淘汰出内容列表的旧内容和归档球的内容，单独存 cold_content 表、带球 ID 索引，注入回源时才读取——内容列表超出上限时按“被注入次数”淘汰最不常用的那条，淘汰不是删除，是转入冷层；归档球的内容也整体转入冷层，归档球被唤醒时按球 ID 直接查关联内容，不做全量扫描。引入三层分层的理由是：内容列表如果无限增长，球的 Payload 会膨胀、读取和序列化成本上升；但直接删除旧内容又违背“不删除、只降可提取性”的理念——分层是“降级”而非“删除”，热层最常用、温层完整保留、冷层按需回源，三层合起来既控制热数据的体积，又保留全部内容。它和“原文压缩”配套：三层都经过 rmw-utf8 压缩，不膨胀则回退 raw；它和“内容列表”配套：列表上限触发淘汰、淘汰转入冷层；它和“归档”配套：球归档时内容一起转冷层，唤醒时按需回源。冷层有软上限（cold_content_max_gb，默认 10 GB），超出时把更早的冷内容转入离线备份文件——单独的文件、不参与在线查询、但保留可恢复性，这不是删除，是“移到另一个存储介质”。边界情况：内容被纠正标记 archived 时不转入冷层，而是留在温层但不再参与渲染（保留审计追溯）；内容列表为空但冷层有内容时，按球 ID 回源后正常渲染；冷层回源失败时该球跳过注入、不阻塞其余球。测试要覆盖：内容列表超上限时最不常用的转入冷层而非删除、归档球内容转冷层、强线索唤醒时按球 ID 回源冷层、冷层软上限超出时转离线备份、三层内容都经过 rmw-utf8 压缩、纠正标记 archived 的内容留在温层不转冷层、冷层回源失败时该球跳过注入。 |
| **嵌入存储** | 每个球在 TriviumDB 的 Node 里持有一条语义向量，存在原生 Vector 字段中，与 Payload（内容列表、size_stored、S、状态等元数据）同属一个 Node——不是分离的向量表、不需要额外的向量库。存储用 f32、内部可 f16 量化，f16 每维 2 字节、384 维约 768 字节、1 万球约 7.5 MB；维度不是固定常量，由具体嵌入后端决定——pizza-embed-zh-small-v1 是 512 维、piccolo-large-zh 是 1024 维、bge-m3 是 1024 维，存储体积随维度线性变化。QuIVer ANN 在向量数超过阈值时自动激活（约 209–834 视版本），无需额外配置、无需建索引语句；球数少时退化为全量扫描，球数多时自动走索引——起始球选择、新球接图、离线补边、归档召回全部受益。维度一致性是启动时的硬校验：DayuCore 初始化时校验 EmbeddingBackend::dimension() 与球存储的向量维度一致，不匹配则启动失败而不是运行时静默错乱——这是防止“换模型后新旧球维度混存、余弦计算出错”的最后一道防线。换嵌入模型需要显式迁移：从 pizza 的 512 维切到 piccolo 的 1024 维时，要么全库重算嵌入（离线批量执行）、要么新建球表、旧球按需回填，不能在同一张表里混存不同维度的向量——混存会让余弦计算无法进行、QuIVer 索引失效。嵌入的更新走 EMA：球被强化时若本次语境片段被追加为内容，嵌入做一次 新嵌入 = 旧嵌入×(1−β) + 本次内容嵌入×β（β 默认 0.1），让球的语义身份缓慢漂移、不会因为追加一条内容就突变；内容被纠正标记 archived 后嵌入不立即重算，由后续 EMA 自然稀释。嵌入不承担检索职责——它只提供向量，余弦计算、阈值判断、归属判定都由规则层完成；不直接出现在注入文本里——注入渲染的是内容列表里的文本，嵌入只参与“选哪个球、强化多少”的计算。嵌入向量不经过 rmw-utf8 压缩——它是浮点 BLOB，文本压缩算法对它无效；省空间靠 f16 量化，是独立于原文压缩的另一条路径。边界情况：球创建时嵌入来自触发片段原文；球的内容列表被淘汰、纠正、归档时嵌入不立即重算；归档球的嵌入保留在归档表、强线索唤醒时直接使用、不重新嵌入。测试要覆盖：维度一致性启动校验失败时拒绝启动、换模型时显式迁移不混存、QuIVer 自动激活、f16 量化精度损失可接受、EMA 更新缓慢漂移、嵌入不参与注入渲染、嵌入不经过文本压缩、归档球嵌入保留。 |

## 七、纠正机制

| 条目 | 详细说明 |
|---|---|
| **审计先行** | 任何纠正操作先写 correction_log，再改状态——顺序不能反。日志记录目标类型与 ID、纠正类型（删除内容/球、重新归属、更新描述、合并、分裂、删除管道、忘记球、拒绝召回）、原值快照、新值、来源（用户显式/用户隐式/离线巩固/判别器回滚/拒绝召回）、原因、时间戳、操作者、可逆性；日志与状态变更在同一事务内，要么全成功要么全回滚，不会出现“状态改了但日志没写”或“日志写了但状态没改”的半完成状态。引入这条规则的理由有三层：① 纠正意图必须留痕——即使纠正中途失败、事务回滚，纠正的“意图”也已经通过日志尝试记录，失败后重试时能追溯到“曾经想改什么”；② 可逆性依赖原值快照——软删的球要通过反向操作恢复，必须知道删除前的完整状态，原值快照是恢复的唯一依据；③ 强度守恒可审计——删除或重新归属时强度按贡献扣减或迁移，日志记录扣减前后的值，能验证“不为负、不重复计数”是否被遵守。它和“软删默认”配套：审计日志记录原值，软删保留可恢复性，两者合起来保证“误触纠正不会永久丢失记忆”；和“可逆性”配套：日志记录原值、新值、原因、时间，反向操作按日志恢复；和“隐式纠正”配套：隐式纠正标记 contested 时也写日志，来源标记 user_implicit，离线巩固确认正确/错误时再写一条日志，形成完整的纠正链。日志本身不删除——即使球被硬删、deleted 状态不可逆，correction_log 仍保留，作为“这个球曾经存在过、曾经被纠正过”的审计记录；硬删时日志额外记录“不可逆删除”标记、二次确认的操作者、时间。它和“参数变更审计”同构：param_change_log 记录配置变更的原值、新值、触发信号、操作者，和 correction_log 遵循同一套“审计先行、原值快照、可追溯、可回滚”的模式——系统对“自身状态的修改”和“记忆的修改”都保持可审计。边界情况：纠正目标已不存在时，日志仍写入、状态变更跳过、标记“目标不存在”；纠正类型非法时，日志写入、事务回滚、返回错误；批量纠正时每条独立写日志、同一事务提交。测试要覆盖：日志先于状态变更写入、日志与状态同事务、事务回滚时日志也不留（或按配置保留意图记录）、原值快照完整可恢复、强度扣减前后值被记录、硬删时日志保留且标记不可逆、隐式纠正写日志、批量纠正每条独立日志。 |
| **软删默认** | 	纠正操作默认执行软删——球、内容或管道不被物理删除，而是状态置为 archived 或 deleted（软删标记），原值保留、原因记录、支持反向操作恢复；硬删需要用户显式确认、二次确认，才执行物理删除或加密归档。引入这个默认值的理由是：误触纠正的代价不对称——软删误触可以恢复，硬删误触永久丢失记忆，违背“疏而不堵、不删除”的理念；默认选代价低的那一侧，把“永久删除”变成需要刻意确认的例外，而不是随手可得的默认。它和“审计先行”配套：correction_log 记录原值快照，软删的球通过反向操作按日志恢复，两者合起来保证“纠正可逆”；和“状态”配套：软删的球状态变为 archived（休眠，强线索可唤醒）或 deleted 软删标记（不参与流动但保留数据），物理删除只发生在硬删；和“强度守恒”配套：软删时强度按贡献扣减但不归零，恢复时按日志回补。硬删的约束：用户必须显式说“永远忘掉”并二次确认，执行物理删除或加密归档，correction_log 保留但标记“不可逆删除”、记录操作者和时间；硬删不可回退，是系统里唯一不可逆的操作。边界情况：软删的球仍在存储中、嵌入保留、内容保留，只是状态变了、不参与常规流动；软删的球可以通过反向操作恢复为 active，恢复时按日志回补强度；软删的内容标记 archived，留在温层但不参与渲染，保留审计追溯；软删的管道跟随球的状态，球恢复时管道一起恢复。与隐式纠正的区别：隐式纠正只标记 contested、不软删，等离线巩固确认；软删是用户显式纠正或离线巩固确认错误后的操作，两者层级不同。测试要覆盖：默认纠正走软删不物理删除、软删后球仍在存储中、软删可通过反向操作恢复、恢复时强度按日志回补、硬删需二次确认、硬删后日志保留且标记不可逆、软删的内容不参与渲染但保留审计、软删的管道跟随球状态。 |
| **强度守恒** | 	纠正操作涉及删除或重新归属内容/球时，强度按贡献扣减或迁移，不为负、不重复计数、总量守恒。删除一条内容时，从球的 size_stored 中扣减该内容贡献的强度——扣减量不超过该内容的贡献，扣减后 max(0, ...)，不会因扣减过头变成负数；重新归属时，从旧球扣减、向新球累加，两边总量守恒，不会出现“旧球没扣、新球加了”导致强度凭空多出一份。引入这条规则的理由是：强度是“这个球被强化了多少”的账本，纠正只应改变“这份强化归属于谁”，不应凭空创造或销毁强化——如果删除时不扣减，球的强度会虚高、后续注入排序和补充规则被污染；如果扣减过头，球可能变成负数、破坏 size_effective 和衰减计算；如果重新归属时只加不减，同一份强化会被两个球各算一次，总量膨胀。它和“审计先行”配套：correction_log 记录扣减前后的值、扣减量、贡献比例，能验证守恒是否被遵守；和“软删默认”配套：软删时强度按贡献扣减但不归零，恢复时按日志回补，扣减和回补对称；和“多路径取最大值”是不同层面的守恒——后者防止同一结算内多条路径重复强化，前者防止纠正时强度重复计数或凭空消失。贡献比例的确定：删除一条内容时，该内容的贡献按“这条内容在球的内容列表中的占比”或“这条内容被注入次数占该球总注入次数的比例”估算，具体口径可配；重新归属时，按新球和旧球各自应得的比例拆分，不简单对半分。边界情况：扣减后 size_stored 变为 0 时球不删除、只是极小，仍可被强线索唤醒；扣减量超过当前 size_stored 时按当前值扣到 0、不产生负数；重新归属的目标球已有强度时累加、不覆盖；批量删除多条内容时逐条扣减、总量不超过球当前强度。它和“S”的关系：纠正不重置 S_stored，但 S_stored 会随时间自然衰减——强度守恒管的是 size_stored，不是 S；S 记录的是“被巩固过多少次”的历史，不因删除一条内容而改变。测试要覆盖：删除内容后 size_stored 按贡献扣减、扣减后不为负、扣减量不超过贡献、重新归属时两边总量守恒、恢复时按日志回补、批量删除总量不超当前强度、S_stored 不因纠正重置、软删与恢复的扣减/回补对称。 |
| **对称操作** | 用户对记忆的反馈是对称的两种直接操作，不需要单独的“强化算法”。用户否定 = 放水缩球——按贡献扣减 size_stored、S_stored 不重置但可标记 contested、相关的管道不做强化（下一次结算时自然不被走通、随时间衰减），否定是“这次说得不对”，不删除记忆，球仍然存在、仍可被强线索唤醒。用户确认 = 注水 + 球变大 + 管道变粗——size_stored 增加（按确认时的显著性、受 size_max 饱和约束）、S_stored 按注水次数增长、与当前语境相关的管道 w 增加（相当于一次额外结算强化），确认是“这个记得对，继续保留并加强”。两者对称的理由是：否定和确认都是对球和管道的直接状态操作，作用于同一组状态量（size_stored、S_stored、w），只是方向相反——否定减少、确认增加；不需要为“确认”单独设计一套“强化算法”，因为它和结算强化在状态层面是同一件事，只是触发源不同（结算由水流触发、确认由用户显式触发）。和“纠正”的关系：否定是纠正的一种（用户显式否定），走“审计先行”写 correction_log、默认软删不物理删除、强度按贡献扣减、可逆；确认不是纠正，但也走审计——记录“用户在什么时间、对哪个球、确认了什么内容”，便于后续追溯和对照实验。和“强度守恒”的关系：否定的扣减遵循强度守恒（按贡献扣减、不为负、不重复计数）；确认的增加不破坏守恒（增加的是新增强化，不是迁移已有强化）。和“状态”的关系：否定把球标记为 contested（有争议）而非 deleted，等离线巩固再确认——用户单次否定可能是误触或情绪化，不直接删除；确认把 contested 的球恢复为 active，或给 active 的球增加强度。和“S”的关系：确认可以增加 S_stored（相当于一次注水），否定不重置 S_stored——S 记录的是“被巩固过多少次”的历史，否定一次不改变历史事实，球仍然“曾经被反复强化过”，只是这次不对。边界情况：用户连续否定同一个球多次，contested 状态累积，离线巩固时优先处理；用户否定后立即确认，按最近一次操作为准、走审计记录两次操作；否定一个 archived 的球时唤醒它、标记 contested、不直接删除；确认一个已饱和的球时 size_stored 不再增长但 S_stored 仍可增长、内容可追加。测试要覆盖：否定按贡献扣减强度、否定不重置 S_stored、否定标记 contested 不删除、确认增加 size_stored 和 S_stored、确认强化相关管道、两者都写审计日志、否定后确认走最近操作、否定归档球时唤醒并标记、确认饱和球时 size_stored 不再增长但 S_stored 仍增长。 |
| **隐式纠正** | 用户没有显式说“你记错了”，但用户的话与已注入的记忆语义矛盾——比如记忆说“用户喜欢简洁回答”、用户却说“详细说说”，系统检测到这种矛盾后只标记 contested，不直接删除、不直接扣减强度，等离线巩固时再确认。引入“只标记不删除”的理由是：单次矛盾可能误判——用户可能只是在开玩笑、可能表达有歧义、可能记忆本身没错只是当前语境变了（“这次想详细听听”不否定“平时喜欢简洁”）；直接删除会误伤正确记忆，而标记 contested 保留了“这条记忆可能有争议”的信号，等积累更多证据再决定。检测方式：注入块与用户后续输入做语义对比，如果用户输入与注入记忆的核心内容余弦低于矛盾阈值、或用户明确表达了相反偏好，触发标记；检测在 turn_end 异步执行，不阻塞主对话。处置：球的 status 从 active 改为 contested，correction_log 记录来源 user_implicit、原状态、新状态、触发矛盾的用户输入片段、时间；强度不扣减、S_stored 不重置——contested 只是“有争议”，不是“已否定”。离线巩固的确认流程：离线巩固时扫描所有 contested 球，用更多上下文（该球的历史注入记录、用户后续反馈、其他相关球的语义一致性）判断——确认正确则恢复 active、写一条日志；确认错误则转 archived 或按显式纠正处理、扣减强度、写日志；证据不足则保持 contested、等下一轮巩固再判断。和显式纠正的区别：显式纠正是用户明确说“不对/忘掉”，直接走纠正流程、可软删、按贡献扣减强度；隐式纠正只是“检测到矛盾”，不删除、不扣减，只标记等确认——两者层级不同，隐式纠正更保守。和对称操作的关系：隐式纠正的“否定”不是用户显式否定，不触发“放水缩球”；它只是标记，等离线巩固时如果确认错误，才走显式纠正的扣减流程。和“状态”的关系：contested 状态的球仍可参与流动和注入，但注入时带“我之前的理解可能不准确”的标注，让模型知道这条记忆有争议、可以谨慎引用或向用户确认。边界情况：用户连续多次与同一条记忆矛盾时，contested 累积、离线巩固优先处理；矛盾检测误报时，离线巩固确认正确后恢复 active、日志记录“误报已澄清”；contested 球在注入时如果用户再次确认，可直接恢复 active、写日志。测试要覆盖：矛盾检测触发标记 contested、标记不扣减强度、contested 球仍可参与流动但注入带标注、离线巩固确认正确恢复 active、确认错误转 archived 并扣减、证据不足保持 contested、连续矛盾优先处理、误报可澄清、注入时用户再次确认可恢复。 |
| **可逆性** |	纠正操作默认是可逆的——correction_log 记录原值、新值、原因、时间、操作者、可逆性标记，软删的球、内容、管道可以通过反向操作恢复到纠正前状态，强度按日志回补、状态回退到原值；硬删是唯一不可逆的操作，需用户显式确认、二次确认，执行物理删除或加密归档，correction_log 保留但标记“不可逆删除”、记录操作者和时间。引入可逆性的理由是：纠正不是“一次性销毁”，而是“可追溯、可回退的状态变更”——用户可能误触、可能改变主意、可能事后发现原记忆其实是对的；如果纠正不可逆，一次误判就永久丢失记忆，违背“疏而不堵、不删除”的理念。可逆的边界：软删的球反向操作恢复为 active、强度按日志回补、S_stored 不重置（它记录的是历史，不因纠正改变）；软删的内容恢复为 active、重新参与渲染；软删的管道跟随球的状态恢复；contested 标记可以清除、恢复 active；合并/分裂的反向操作按审计记录恢复原球和原管道（合并反向执行分裂、分裂反向执行合并）；reassign 的反向操作把内容/球重新归属回原球、强度按贡献回补。不可逆的边界：硬删（用户显式“永远忘掉”+二次确认）是唯一不可逆操作，物理删除或加密归档后无法恢复，但审计日志保留，记录“曾经存在过、曾经被永久删除”。和“审计先行”配套：可逆性依赖原值快照，没有审计日志就没有恢复依据；和“软删默认”配套：软删保留数据、可逆，硬删不保留数据、不可逆，默认选可逆的那一侧；和“强度守恒”配套：反向操作时强度按日志回补，扣减和回补对称、总量守恒。边界情况：纠正后原球被归档、反向操作时先唤醒再恢复；纠正后原球被合并到其他球、反向操作时按审计记录拆分恢复；多次纠正同一球时，反向操作按日志逆序回退、每次回退一步；反向操作本身也写日志、也可逆（回退的回退）；硬删后反向操作被拒绝、返回“不可逆”错误。测试要覆盖：软删可恢复、强度按日志回补、S_stored 不重置、内容恢复参与渲染、管道跟随恢复、contested 可清除、合并/分裂反向操作恢复原状、reassign 反向回补、硬删不可逆且拒绝反向、多次纠正逆序回退、反向操作本身可逆、硬删后日志保留。 |

## 八、判别器

| 条目 | 详细说明 |
|---|---|
| **当前路径** | 判别器当前采用“嵌入 + Rust 规则”的裁剪版方案，不引入生成模型。嵌入层用 pizza-embed-zh-small-v1（约 91 MB，ONNX，CPU 可跑，512 维）负责把文本变成向量、算余弦——它只提供语义距离，不做任何判断；规则层是 Rust 代码，负责阈值、灰区、兜底合并、归属判定等全部决策逻辑。判别器不是独立的分类模型，是一条“嵌入提供语义距离、规则层做决策”的流程。流程：候选片段嵌入 → 与最近 6 轮上下文算余弦得到 significance 近似 → 与候选球嵌入算余弦、取 Top-1、余弦 ≥ 0.7 判 belongs_to、该余弦即 belong_confidence → 规则层按阈值判断 should_judge → 兜底合并检查（与已有球余弦 > 0.95 则追加内容+强化、不建新球）→ 产出裁剪版 Verdict。裁剪版 Verdict 只填充四个必填字段——should_judge、significance（当前用候选与最近 6 轮的余弦近似）、belongs_to（Top-1 且余弦 ≥ 0.7 判 Attach）、belong_confidence（即该余弦值）；情绪效价/强度、偏移方向、命中人格维度、reason 四个可选字段一律留空，由 producer = EmbeddingRule 标记来源、capabilities() 返回全部 false 显式声明“当前后端不产出这些字段”。引入这个方案的理由：判别器最核心的决策（是否起念、归属哪个球）本质是分类，嵌入 + 规则已经覆盖，且结论完全可复现、可审计——同一个输入永远得到同一个判定，相似度算出来是 0.72 就是 0.72、阈值是 0.6 就是 0.6，不存在生成模型的采样漂移；而生成模型在硬性 JSON schema 约束下存在“格式对但语义错”的已知风险（小模型实测可执行准确率可能从 91.5% 跌到 48.0%），不适合作为第一版。当前路径的局限是显式的：显著性用余弦近似只是“相关度”不是真正的“值不值得记”（用户每天说“好的”余弦可能很高但完全不显著）；情绪、方向、人格维度、自然语言理由这些需要生成模型才能可靠产出的字段，当前不输出。和“未来路径”的关系：切换方式是把决策专用小模型作为 JudgeBackend 的新枚举变体接入，与当前嵌入+规则路径并列，通过对照实验决定是否替换，业务规则层代码不变——阈值、灰区、兜底合并只读必填字段，可选字段只影响渲染丰富度和指标记录，不影响“起不起念、归哪个球”。边界情况：嵌入后端不可用时降级为“仅归档、不起念”，不阻塞主对话；余弦恰好等于 0.7 时按“≥”判 Attach；候选球列表为空时直接判新球、不做兜底合并检查。测试要覆盖：裁剪版 Verdict 只填四个必填字段、可选字段为 None、producer=EmbeddingRule、capabilities() 全部 false、同一输入判定可复现、余弦 ≥ 0.7 判 Attach、兜底合并命中不建新球、嵌入不可用时降级、业务规则层只读必填字段。 |
| **Verdict 必填字段** | Verdict 有四个必填字段，任何 JudgeBackend 都必须产出、业务规则层只依赖它们：should_judge——布尔值，回答“这个候选片段是否起念”，是判别器的第一道闸门，false 则整个候选被丢弃、不建球不挂载；significance——Relevance 类型（[0,1] 的受约束标量），回答“这个起念有多显著”，当前用“候选片段嵌入与最近 6 轮上下文嵌入的余弦”近似，越高越显著，过 strengthen_threshold_X 或固化阈值才进入后续流程；belongs_to——Option<BallId>，回答“这个念归属哪个已有球”，None 表示新球、Some(id) 表示挂到已有球，当前用“候选片段嵌入与候选球嵌入的 Top-1、余弦 ≥ 0.7 判 Attach”得到；belong_confidence——Relevance 类型，回答“归属判定有多确定”，当前就是那个 Top-1 余弦值，用于灰区判断（置信度 ≤ 0.7 时走 tentative 挂载、累计确认后才转正）和兜底合并判断。四个字段的分工是：should_judge 管“要不要记”，significance 管“记的分量有多重”，belongs_to 管“记到哪个球”，belong_confidence 管“这个归属判断有多可靠”。为什么必须是必填：业务规则层（阈值判断、灰区处理、兜底合并、新球创建）完全依赖这四个字段做决策，缺任何一个流程都无法进行；Verdict 的可选字段（情绪、方向、人格维度、reason）只影响渲染丰富度和指标记录，不影响判别决策，所以可以是 None，但这四个不行。和“可选字段”的边界：可选字段为 None 时消费方通过 Option 判断、不假设有值；必填字段没有 Option 包装、任何后端都必须给出合法值——如果某个后端无法产出某个必填字段（比如没有嵌入能力），它就不应该被注册为可用的 JudgeBackend，而不是返回一个默认值蒙混过关。边界情况：significance 必须在 [0,1] 内，超出范围按配置校验拒绝；belong_confidence 同理；belongs_to = Some(id) 但 id 不存在时按“归属目标已失效”处理、降级为新球；should_judge = false 时其余三个字段的值被忽略、不参与任何决策。测试要覆盖：四个字段任何后端都必须产出、缺任何一个时业务规则层报错而非静默使用默认值、significance 和 belong_confidence 范围校验、belongs_to 指向不存在球时降级为新球、should_judge=false 时其余字段被忽略、可选字段为 None 不影响决策、必填字段与可选字段的边界清晰。 |
| **Verdict 可选字段** | Verdict 有五个可选字段，用 Option<T> 包装，当前“嵌入+规则”路径一律填 None，未来由决策专用小模型填充：emotion_valence——Option<f64>，情绪效价 [-1, 1]，负值表示负面情绪、正值表示正面情绪；emotion_intensity——Option<f64>，情绪强度 [0, 1]，越高情绪越强烈；offset_direction——Option<String>，偏移方向，描述“注意力从什么滑向什么”，如“从‘结束话题’滑向‘他是不是在硬撑’”；hit_dimensions——Option<Vec<String>>，命中的角色人格敏感维度列表，如 ["在意对方是否硬撑", "对语气变化敏感"]；reason——Option<String>，自然语言理由，解释“为什么判这个结果”，给人看、不是给系统消费。为什么是可选：这五个字段都需要生成模型才能可靠产出——嵌入+规则只能算语义距离，算不出情绪效价、描述不出偏移方向、列不出人格维度、写不出自然语言理由；当前裁剪版方案不引入生成模型，所以这些字段留空，不是“实现漏了”，是“当前路径的能力边界”。消费方如何处理 None：通过 Option 判断、不假设一定有值——注入渲染时 reason 为 Some 则渲染为 [记忆] 关于“X”，我记得：Y（因为 Z）、为 None 则退化为 [记忆] 关于“X”，我记得：Y；emotion_valence 和 emotion_intensity 为 Some 时可用于情绪一致性指标、为 None 时跳过；hit_dimensions 为 Some 时可用于人格维度命中统计、为 None 时跳过；offset_direction 为 Some 时可用于审计和调试、为 None 时跳过。关键约束：可选字段只影响渲染丰富度和指标记录，不影响判别决策——业务规则层（阈值、灰区、兜底合并、新球创建）只读四个必填字段，不读可选字段；这保证从“嵌入+规则”切到“决策模型”时，判别决策逻辑不变，只是输出更丰富。和 capabilities() 的配合：capabilities() 显式声明后端能产出哪些可选字段，None 有两种可能——“这个后端本来就不产出”和“这次没产出”，capabilities() 把前者显式化，消费方不用猜；当前 EmbeddingRule 后端的 capabilities() 全部返回 false，DecisionModel 后端返回 true。边界情况：emotion_valence 和 emotion_intensity 为 Some 时必须在合法范围内，超出范围按配置校验拒绝或截断；hit_dimensions 为 Some 但为空列表时按“无命中维度”处理、不等同于 None；reason 为 Some 但空字符串时按“无理由”处理、渲染时退化为无理由格式；可选字段部分有值、部分为 None 时，消费方按字段独立判断、不要求全部有值或全部无值。测试要覆盖：当前路径五个可选字段全为 None、消费方通过 Option 判断不假设有值、reason 有值时渲染带理由、reason 为 None 时退化为无理由、capabilities() 声明与字段实际产出一致、可选字段为 None 不影响判别决策、范围校验、空列表与 None 的区分、部分有值部分 None 时独立判断。 |
| **Verdict producer** | Verdict 上带一个 producer 字段，标记这次判定来自哪个后端——取值是枚举：EmbeddingRule（当前“嵌入 + 规则”路径）、DecisionModel（未来决策专用小模型）、Mock（测试）。引入它的理由有三层：① 审计可追溯——每条判定都能回答“是谁做的”，出问题时能定位到具体后端，而不是“系统判的”这种模糊表述；② 对照实验可区分——同一批输入分别用 EmbeddingRule 和 DecisionModel 跑，结果按 producer 分组统计，能对比两个后端的召回质量、判定一致性、误判方向；③ 指标可按后端打标签——judge_parse_failure_rate、judge_confidence_distribution 等指标带 producer 标签，能分别监控每个后端的健康度，而不是混在一起。和 capabilities() 的分工：producer 回答“谁做的判定”，capabilities() 回答“这个后端能产出哪些可选字段”——前者是身份标识、后者是能力声明，两者配合让消费方知道“这条判定来自哪个后端、它有哪些字段可信”。和“枚举分派”的关系：BackendKind 枚举分派时，每个变体的 producer() 方法返回对应的 VerdictProducer 值，JudgeEngine 不关心具体后端、只通过 producer() 拿标识；新增后端时枚举变体、match 分支、producer() 返回值三处一起加，编译器强制完整。写入时机：在 Verdict 构造时由后端自己填入，不是外部赋值——后端最清楚自己是谁，让它自报身份比让调用方猜更可靠；MockJudgeBackend 返回 Mock、EmbeddingRuleBackend 返回 EmbeddingRule、DecisionModelBackend 返回 DecisionModel。它不参与业务决策——业务规则层不读 producer 做任何判断，它只用于审计、对照实验、指标标签；这保证“切换后端不改变业务逻辑”，后端差异被隔离在 producer 和 capabilities() 里。边界情况：producer 是必填字段、不能为空，任何后端都必须返回一个合法枚举值；未知后端类型时配置校验拒绝启动，而不是运行时返回一个 Unknown 值；对照实验时同一输入的两个 Verdict 按 producer 区分、不混在一起统计。测试要覆盖：每个后端返回正确的 producer、producer 必填不为空、业务规则层不读 producer、指标按 producer 打标签、对照实验按 producer 分组、新增后端时 producer() 与枚举变体同步、未知后端配置校验拒绝。 |
| **capabilities()** | 	JudgeBackend trait 上的一个方法，返回 JudgeCapabilities 结构，显式声明这个后端能产出哪些可选字段——四个布尔字段：emotion（能否产出情绪效价/强度）、offset_direction（能否产出偏移方向）、hit_dimensions（能否产出命中人格维度）、reason（能否产出自然语言理由）。引入它的理由是解决 Option 为 None 的语义歧义：可选字段为 None 有两种可能——“这个后端本来就不产出”和“这次没产出”，消费方如果只看 Option 无法区分，会误以为“后端能力有但这次没给”；capabilities() 把前者显式化，消费方不用猜——capabilities().emotion == false 意味着“这个后端永远不产出情绪字段”，emotion_valence == None 且 capabilities().emotion == true 意味着“后端有能力但这次没给”。当前取值：EmbeddingRuleBackend 的 capabilities() 四个字段全部返回 false（当前路径不产出任何可选字段）；DecisionModelBackend 四个字段全部返回 true（未来决策小模型产出全部可选字段）；MockJudgeBackend 可按测试需要配置，用于测试“部分能力”“全部能力”“无能力”三种场景。和 producer 的分工：producer 回答“谁做的判定”（身份标识），capabilities() 回答“这个后端能产出哪些字段”（能力声明）——两者配合让消费方知道“这条判定来自哪个后端、它有哪些字段可信”。消费方如何使用：注入渲染按 capabilities().reason 决定是否渲染“因为 Z”；可观测性按 capabilities().emotion 决定是否记录情绪相关指标；对照实验按 capabilities() 筛选“哪些字段可在两个后端之间对比”，不把“后端 A 有、后端 B 没有”的字段混在一起统计；业务规则层不读 capabilities()，只读四个必填字段，这保证切换后端时判别决策逻辑不变。为什么是方法而不是字段：不同后端的能力是编译期确定的、不需要每次判定都存一份，做成方法让后端自报能力、不需要在每条 Verdict 里重复携带；JudgeEngine 可以在初始化时调用一次、缓存结果，不需要每次判定都调。边界情况：capabilities() 声明为 true 但实际返回 None 时，按“这次没产出”处理、不视为错误；声明为 false 但实际返回 Some 时，按配置校验拒绝——后端能力声明与实际行为不一致是 bug，应该在测试中暴露而不是运行时静默接受；新增可选字段时，JudgeCapabilities 加字段、所有后端实现同步更新，编译器强制完整。测试要覆盖：EmbeddingRule 全部 false、DecisionModel 全部 true、Mock 可配置、消费方按 capabilities() 决定是否依赖某字段、声明为 false 但返回 Some 时配置校验拒绝、声明为 true 但返回 None 时按“这次没产出”处理、业务规则层不读 capabilities()、新增字段时所有后端同步更新。 |
| **未来路径** | 判别器未来若要从“嵌入+规则”升级到生成模型，优先选择决策专用小模型，而不是通用生成模型。候选模型：Jev-Style-0.8B-Decision-v3（专为“在一组给定选项中做单次判断”设计，0.8B 参数、GGUF Q4 约 0.53 GB、中英双语、短请求延迟约 0.15–0.2 秒，用它的方式是把候选标签作为参数传进去、它直接返回每个选项的概率）；Chinese Decision-0.8B（中科院计算所出品，同样是“单次前向、直接输出候选概率”的架构，0.8B 版本 Q8_0 约 812 MB，中文决策数据来自 1300 万条 CJ-Dataset，对中文语境判别更有针对性）；Xenomi-nano-0.8B（官方定位“面向路由、术语抽取、关键词与短文本判别”，不是通用对话模型）；SeqGPT-560M（阿里达摩院中文零样本理解模型，无需训练即可做分类和信息抽取，约 1.1 GB）。为什么优先决策专用而非通用生成：决策专用模型用一次前向传播直接输出候选概率，不需要自回归生成 JSON，从根本上绕开小模型在硬性 JSON schema 约束下“格式对了但语义错了”的风险——论文实测 Qwen2.5-1.5B 在 prompt-only JSON 下可执行准确率 91.5%，换成硬性工具调用 schema 后暴跌到 48.0%，错误是语义性的、不是结构性的；决策专用模型的输出空间是“候选标签的概率分布”，天然匹配“是否起念、归属哪个球”的选择题。通用模型作为对照基线：Qwen3-0.6B/1.7B 有成熟的 ONNX 量化部署路径（0.6B Q4 约 1 GB、1.7B 约 1.5 GB），可作对照基线，但不默认更优——小模型在自由生成 JSON 下的语义漂移风险需要实测验证，不能因为“参数大一点”就假设更好。接入方式：实现一个新的 DecisionModelBackend、在 BackendKind 枚举里加一个变体、加一个 match 分支，JudgeEngine、DayuCore、注入渲染、可观测性全部不用改；producer() 返回 DecisionModel、capabilities() 返回全部 true（决策模型能产出全部可选字段）；切换只改配置 judge.backend = "decision_model"，不改代码。验证方式：同一批对话、同一批记忆，分别用 EmbeddingRule 和 DecisionModel 跑，按 producer 分组统计判定一致性、召回质量、误判方向，用数据决定是否替换——如果决策模型在必填字段上和嵌入+规则高度一致、且可选字段确实带来了渲染丰富度或召回质量提升，再切默认；如果一致性低或质量下降，保留嵌入+规则。约束：决策模型必须能产出四个必填字段（should_judge、significance、belongs_to、belong_confidence），否则不能注册为可用后端；可选字段按模型能力填充，capabilities() 如实声明；模型加载失败时降级为“仅归档、不起念”，不阻塞主对话。边界情况：决策模型的输出概率需要映射到 Relevance 的 [0,1] 范围，映射函数可配；belongs_to 的候选集来自嵌入检索的 Top-K，决策模型在候选集上做选择、不自由生成球 ID；模型推理延迟需控制在 200–800ms 的异步旁路预算内，超时丢弃候选、不重试。测试要覆盖：新后端枚举变体接入不改业务规则层、producer=DecisionModel、capabilities() 全部 true、四个必填字段必产、可选字段按能力填充、对照实验按 producer 分组、切换只改配置、模型加载失败降级、输出概率映射到 [0,1]、超时丢弃不重试。 |
| **枚举分派** | JudgeEngine 不直接持有 Box<dyn JudgeBackend>，而是持有一个 BackendKind 枚举——枚举的每个变体包裹一个具体后端（EmbeddingRule(EmbeddingRuleBackend)、DecisionModel(DecisionModelBackend)、Mock(MockJudgeBackend)），BackendKind 自身也实现 JudgeBackend trait，通过 match 把 judge()、producer()、capabilities() 转发到具体变体。引入枚举分派而非 Box<dyn> 的理由有三层：① 热路径无 vtable 间接调用——判别器每轮要跑 1–3 次、每次 200–800ms，dyn 的虚函数调用和缓存不友好会抵消 Rust 的性能优势，枚举分派是编译期确定的直接调用；② 编译器强制完整性——新增后端时加一个枚举变体，所有 match 分支编译失败、强制你处理，不会出现“忘了更新某个 match 导致运行时 panic”；③ 封闭集合更可读——后端集合是已知的、有限的（当前嵌入+规则、未来决策模型、测试 Mock），读者一眼能看到全部合法路径，不需要在文档里写“请不要实现这个 trait”。和 sealed trait 的关系：JudgeBackend 是 sealed trait（下游不可实现、只能使用），后端集合封闭，正好适合枚举分派——如果 trait 是开放的、第三方可以注入任意实现，枚举分派就不成立，只能退回 Box<dyn>；当前设计选择封闭集合，是因为单用户、两个客户端的场景里后端是可枚举的，封闭比开放更安全。和 producer()、capabilities() 的关系：BackendKind 的 match 转发这三个方法，每个变体返回自己的 producer 和 capabilities，JudgeEngine 不关心具体后端、只通过 match 拿结果。扩展方式：未来接入决策专用小模型时，实现 DecisionModelBackend、加一个 BackendKind::DecisionModel 变体、加一个 match 分支，JudgeEngine、DayuCore、注入渲染、可观测性全部不用改——这是“新增后端只加一个变体”的具体落地。边界情况：枚举变体增加时所有 match 必须同步更新，编译器强制；match 必须是穷尽的，不能有 _ => 兜底分支（兜底会掩盖“忘了处理新变体”的错误）；枚举分派不适用于“后端数量动态增长、运行时才确定”的场景，如果未来真的需要开放扩展，再退回 Box<dyn> + sealed trait 的组合。测试要覆盖：每个枚举变体都能正确分派到对应后端、match 穷尽无兜底、新增变体时编译器报错提示未处理、producer() 和 capabilities() 按变体返回正确值、JudgeEngine 不直接依赖具体后端类型、切换后端只改枚举构造不改引擎代码。 |
| **业务规则层只读必填字段** | 判别器的业务规则层——包括阈值判断（significance 是否过固化阈值）、灰区处理（belong_confidence 在 0.5–0.7 时走 tentative 挂载、累计确认后才转正）、兜底合并检查（与已有球余弦 > 0.95 则追加内容+强化、不建新球）、新球创建决策——只读 Verdict 的四个必填字段：should_judge、significance、belongs_to、belong_confidence，不读任何可选字段。引入这条规则的理由是：可选字段（情绪效价/强度、偏移方向、命中人格维度、reason）是“渲染丰富度”和“指标记录”的素材，不是“判别决策”的依据——它们依赖生成模型才能可靠产出，当前“嵌入+规则”路径一律留空，如果业务规则层依赖它们，当前路径就无法运行；把它们隔离在决策之外，保证从“嵌入+规则”切到“决策模型”时，判别决策逻辑不变，只是输出更丰富。可选字段的去向：只影响三件事——注入渲染（reason 为 Some 则渲染“因为 Z”、为 None 则退化为无理由格式）、可观测性（按 capabilities() 决定是否记录情绪/方向相关指标）、对照实验（按 capabilities() 筛选“哪些字段可在两个后端之间对比”）；它们不进入阈值判断、不进入灰区处理、不进入兜底合并、不进入新球创建。和“capabilities()”的配合：capabilities() 显式声明后端能产出哪些可选字段，业务规则层不读它、消费方（渲染、指标、对照实验）读它——两层职责分离：业务规则层管“起不起念、归哪个球”，消费方管“怎么渲染、怎么记录、怎么对比”。为什么这条规则重要：它是一条“架构隔离线”——如果业务规则层读了某个可选字段，等于把“判别决策”和“生成模型能力”耦合在一起，切换后端时决策逻辑就会变，这违背“后端可替换、业务逻辑零改动”的设计目标；守住这条线，新增决策模型后端时只需实现 JudgeBackend trait，业务规则层一行不改。边界情况：可选字段为 Some 时业务规则层也不读——不是“有值就读、无值就跳过”，是“无论有没有值都不读”；如果某个可选字段未来被证明对判别决策有价值（比如“情绪强度”确实影响“值不值得记”），应该把它提升为必填字段、所有后端都必须产出，而不是让业务规则层“有条件地读”一个可选字段。测试要覆盖：业务规则层不读可选字段、可选字段有值/无值时判别决策结果相同、可选字段只影响渲染和指标、capabilities() 与业务规则层解耦、新增后端时业务规则层零改动、可选字段未来提升为必填时所有后端同步更新。 |

## 九、工程约束

| 条目 | 详细说明 |
|---|---|
| **前缀缓存** | 所有动态记忆只追加在 messages 尾部，不回写 system prompt、不回写工具 schema、不插入历史中段——这是 DeepSeek 等支持前缀缓存的模型上“注入不使已缓存前缀失效”的前提。前缀缓存是字节级最长公共前缀匹配，任何对前缀区域的修改都会让其后所有缓存作废；一次会话的前缀（system prompt + 工具定义 + 早期历史）通常占输入 token 的绝大多数，如果每轮注入都改前缀，缓存命中率归零、长会话成本飙升。具体做法：注入以 role: "user" 的 ephemeral 消息追加在历史末尾，带 _ephemeral: true 标记，不写入持久 transcript——下一轮重新召回时重新生成，而不是从历史里读旧的注入块；system prompt 和工具 schema 在会话启动时构建一次、之后逐字节冻结，工具按字典序确定性排序，不依赖插件加载顺序；时间戳、工作目录、git 状态等每轮可能变化的元信息不放前缀，移到尾部消息或配置里。为什么必须这样做：记忆系统的直觉是“想起什么就注入什么”，天然倾向于把记忆插到最相关的位置（比如 system prompt 里强化行为一致性），但这和前缀缓存直接冲突；把动态性全部赶到尾部、前缀只做只读冻结，是唯一能让“仿人脑记忆”和“前缀缓存”共存的方式——不是“完全兼容”，是“有条件兼容”，条件是接受“注入位置只能在尾部”这个约束。代价：注入位置的灵活性丧失——有些记忆系统会把关键记忆放在 system prompt 里以强化模型遵从，尾部注入的“遵从强度”可能弱于 system prompt；这是用“成本可控”换“注入位置受限”，是自觉的取舍。和“流动只点亮、不写入”的关系：流动纯内存、结算才写入，写入的是存储不是上下文；注入是结算后的独立步骤，只追加尾部 ephemeral 消息、不修改任何已存在的字节。边界情况：同一轮多次注入时，多条 ephemeral 消息按顺序追加在尾部，不合并、不重排；注入块内容不影响前缀的字节稳定性，但会增加总输入长度、影响每次请求的输入 token 数和成本——前缀缓存管“不重复计费已缓存的前缀”，注入预算管“新增的尾部别太贵”，两者是不同层面的成本控制；如果宿主客户端在注入后重新序列化 messages、改变了前缀的字节表示（比如重排字段、改变空白），缓存仍会失效——这需要客户端配合，不是记忆系统单方面能保证的。测试要覆盖：注入前后对比 system prompt 和工具 schema 的字节完全不变、注入只追加在 messages 尾部、ephemeral 消息不写入持久 transcript、下一轮重新召回而非读旧注入块、工具按字典序确定性排序、动态元信息不在前缀区、注入后总输入长度增加但前缀缓存命中不降、客户端重新序列化不改变前缀字节。 |
| **napi 进程内** | 在线路径的集成方式：Rust 内核编译为 .node 原生模块，由 dsh/pi 的 TypeScript 薄适配层直接 require 调用，不经过独立进程、不经过 HTTP/IPC——判别器的异步推理、流动的同步结算、注入组装全部在宿主进程内完成，零跨进程通信开销。引入进程内而非“常驻守护”或“CLI 短进程”的理由是延迟和复杂度：CLI 每次调用要 fork/exec、加载 Rust 运行时、打开 TriviumDB、加载子图，进程启动加数据库打开在冷启动时是几十毫秒级，而结算必须同步立刻执行、它就是注入决策，百毫秒级延迟会直接劣化主模型首 token 延迟；常驻守护虽然单写者天然串行化，但引入进程管理、IPC 协议、超时重试、生命周期（dsh 关掉守护还活着吗）等一整套复杂度，在单用户、两个客户端的场景下收益不明显——TriviumDB 的进程级文件锁已经能处理 dsh 和 pi 同时打开同一 store.tdb 的情况。关键优势：TriviumDB 原生提供 napi-rs 绑定（npm install triviumdb 后直接 require('triviumdb')），不需要自己写 Rust ↔ Node 的胶水层，存储层的 Node 绑定由上游维护，稳定性由 TriviumDB 保证。性能特征（有实测数据）：napi-rs 的边界开销在“每次调用处理较多工作”时很小——SheetKit 基准显示密集计算场景下 FFI 层额外开销约 3–4ms、比率 1.14–1.20×；但在“极小调用”上开销显著（一个只做加法的函数比纯 JS 慢 19×），plain JS array 的逐元素传递也可能成为瓶颈（18×）。因此集成设计必须遵守“动词级 API、批量数据、typed array”三条：recall、judge_turn、archive_turn 是动词级用例，每次调用处理一整轮对话，不是每帧调一次 getter；嵌入向量和 ID 列表用 Buffer/Float64Array 等 typed array 传递，不用 plain JS array；单次调用内部的工作量远大于边界开销，FFI 成本被摊薄到可忽略。异步路径：判别器是异步旁路，napi 的 #[napi] pub async fn 配合 tokio_rt feature 提供 Tokio 运行时，自动把 Rust async fn 映射为 JavaScript Promise<T>，不阻塞 JS 事件循环；但要注意 async fn 里的长时间同步计算仍会占用 Tokio worker 线程，阻塞型 CPU 工作应使用 tokio::task::spawn_blocking 或 AsyncTask 走 libuv 线程池，而不是在 async fn 里直接跑。在线走 napi、离线巩固可 CLI 化：离线巩固不要求实时，CLI 的几十毫秒启动开销可接受，且 CLI 作为独立进程隔离复杂度；常驻守护留作多客户端写冲突严重时的逃生舱，不是第一版必需。边界情况：napi 模块需要为每个平台编译 .node 产物（macOS x64/arm64、Linux x64/arm64、Windows x64），用预编译分发机制处理，不是阻塞问题；宿主崩溃（dsh 闪退）会带崩 Rust 内核，但结算走 TriviumDB 事务，崩溃时未提交事务自动回滚、已提交的在 WAL 里，不会丢数据，只是正在进行的流动计算丢失、下一轮重来；#[napi] async fn 的取消不是自动的（丢弃 JS Promise 不会取消 Rust future），长时操作需要设计显式取消协议。测试要覆盖：进程内调用延迟在毫秒级、typed array 传递无额外拷贝、异步 API 返回 Promise 不阻塞事件循环、tokio_rt 运行时正确启动、阻塞 CPU 工作走 spawn_blocking 而非占用 Tokio worker、TriviumDB 的 napi-rs 绑定直接可用、崩溃后已提交数据不丢、动词级 API 而非细粒度 getter/setter。 |
| **模块化** | 工程按“依赖方向单向、核心单份、适配薄壳”组织为 Rust workspace：dayu-domain 零依赖，只定义 newtype、枚举、四个核心 trait（StorageBackend、JudgeBackend、EmbeddingBackend、Clock）和错误类型，不 import 任何 workspace 内其他 crate；dayu-flow 和 dayu-judge 只依赖 dayu-domain 的 trait、不依赖任何具体实现——dayu-flow 的 dev-dependencies 里不出现 TriviumDB、dayu-judge 的默认依赖里不出现 ONNX，依赖方向由编译期强制；dayu-storage、dayu-embedding、dayu-judge 各自提供具体实现（TriviumDB、ONNX、嵌入+规则/Mock/预留决策模型），通过 BackendKind 枚举分派或 trait object 被组装；dayu-core 是唯一知道所有实现的地方，DayuCore::new 接收 Arc<dyn Trait> 组装，新增存储后端或推理后端只改构造参数、业务逻辑零改动；dayu-napi 只做 DTO 翻译和错误映射、不含业务逻辑；dayu-cli 是唯一允许用 anyhow 的地方，离线巩固独立进程。策略 trait 隔离算法变体——SupplementStrategy、StrengthenStrategy、LossModel、VerdictPostProcessor 让“补充规则”“强化规则”“损失模型”“后处理规则”可替换、可对照实验，ConstantLossModel 精确复现旧规则用于验证“管道决定损耗”是否真的改变了行为。feature flag 控制推理后端依赖——dayu-judge 的 onnx、candle、model2vec、test feature 按需编译，CI 的快速测试路径只编译 test feature、不拉 ONNX Runtime。独立测试由模块化保证——每个 crate 的默认 cargo test 零真实依赖、秒级完成，dayu-flow 用 TriviumStorage（临时 `.tdb` 隔离）+ MockEmbedding + MockClock、dayu-judge 用 MockJudgeBackend、dayu-napi 只测 DTO 转换、dayu-storage 用 tempfile 隔离；mock 实现放在 test feature 下，夹具放在 dev-only 的 dayu-testkit crate。渐进式交付也由模块化支撑——M1 只有 dayu-domain + dayu-storage + dayu-flow（临时 `.tdb` 测试）+ dayu-napi 最小 recall API 就能跑通，M2 加嵌入、M3 加判别器，模块之间没有“必须同时完成”的耦合。测试要覆盖：dayu-domain 零 workspace 依赖、dayu-flow 的 dev-dependencies 不出现 TriviumDB、新增后端只改 DayuCore::new 构造参数、feature flag 按需编译、每个 crate 默认测试零真实依赖、策略 trait 可替换、dayu-napi 只做 DTO 翻译。 |
| **四个核心 trait** | dayu-domain 定义的四个基础设施抽象，隔离存储、判别、嵌入、时间，让流动和结算只依赖 trait、不依赖具体实现。StorageBackend——读写球、管道、内容、冷存储，提供 get_ball、load_subgraph（加载起点球及 N 跳邻居子图）、search_by_embedding（向量检索起始球）、begin_transaction（返回 StorageTx 用于结算写入），唯一实现是 TriviumStorage（生产与测试共用，测试经 `TempDir` 隔离，不存在内存替身）；它不暴露 TriviumDB 的 TQL 或 Node/Edge 细节，只暴露领域语义的方法。JudgeBackend——判别器后端，提供 judge(input) -> Verdict、producer() -> VerdictProducer、capabilities() -> JudgeCapabilities，实现有 EmbeddingRuleBackend（当前路径）、DecisionModelBackend（未来预留）、MockJudgeBackend（测试）；它不暴露 ONNX Session 或 tokenizer 细节，只暴露“给定输入返回判定”的契约。EmbeddingBackend——把文本变成向量，提供 embed_batch(texts) -> Vec<Vec<f32>>、dimension() -> usize，实现有 OrtEmbeddingBackend（ONNX）、MockEmbeddingBackend（测试，固定向量或确定性向量）；dimension() 让 DayuCore 启动时校验嵌入维度与球存储的向量维度一致，不匹配则启动失败。Clock——提供 now() -> DateTime<Utc>，实现有 SystemClock（生产，调 Utc::now()）和 MockClock（测试，可快进 180 天验证归档触发、快进 90 天验证管道衰减）；所有时间计算——size_effective、w_eff、S 衰减、blocked_count 衰减、归档判定——都通过 Clock，不直接调 Utc::now()，保证测试时间完全可控。四个 trait 的分工是：StorageBackend 管“数据从哪来、到哪去”，JudgeBackend 管“判别逻辑用哪个后端”，EmbeddingBackend 管“文本怎么变成向量”，Clock 管“现在是几点”；它们共同让 dayu-flow 和 dayu-core 的测试可以用 TriviumStorage（临时 `.tdb`）+ MockJudgeBackend + MockEmbeddingBackend + MockClock 跑在隔离环境里：零外部依赖（无网络、无模型、无 Node），全量约 9 秒。新增存储后端或推理后端只改 DayuCore::new 的构造参数，业务逻辑零改动；换嵌入模型只换 EmbeddingBackend 实现、校验维度、显式迁移，dayu-flow 一行不改。边界：trait 方法只暴露领域语义、不暴露具体实现的类型；StorageBackend 的 begin_transaction 返回 Box<dyn StorageTx>，结算在事务内完成所有写入、提交或回滚；JudgeBackend 是 sealed trait（下游不可实现、只能使用），后端集合封闭、适合枚举分派；Clock 是唯一的时间源，任何直接调 Utc::now() 的代码都是 bug。测试要覆盖：四个 trait 各有生产实现和 Mock 实现、dayu-flow 只依赖 trait 不依赖实现、DayuCore 启动时校验嵌入维度、MockClock 可快进时间、新增后端只改构造参数、sealed trait 下游不可实现、Clock 是唯一时间源。 |
| **策略 trait** | 	dayu-flow 和 dayu-judge 内部定义的四个算法变体抽象，隔离“补充规则”“强化规则”“损失模型”“后处理规则”，让它们可替换、可对照实验，而不改引擎主流程。SupplementStrategy——计算球释放的补充量，默认实现是“资格 + 幅度”两段式（size_effective × (相关性 - supplement_threshold)/(1 - supplement_threshold)，过资格阈值才补充），替代实现可以是线性补充（用于对照实验）、无补充（用于验证“补充是否必要”）；FlowEngine 持有 Arc<dyn SupplementStrategy>，默认用两段式。StrengthenStrategy——计算球和管道的强化增量，默认实现是“路径相关性 × 系数 + 球的边际递减、管道封顶”，替代实现可以是线性强化（无边际递减）、恒定强化（用于对照实验）；它让“强化规则”的 A/B 实验不需要改结算引擎代码。LossModel——计算每跳损失，默认实现是 PipeWeightLossModel（loss = min(base_loss × (1 + loss_pipe_factor × (1-w_eff)), loss_max)，管道越细损失越大），替代实现是 ConstantLossModel（损失恒等于 base_loss，精确复现旧规则）；ConstantLossModel 的存在是为了验证“管道决定损耗”这个修正在当前参数下是否真的改变了行为——如果两种损失模型跑出来的召回质量没有差异，说明这个修正被其他机制掩盖了、需要检查，而不是假设它一定有效。VerdictPostProcessor——对原始 Verdict 做后处理（阈值、灰区、兜底合并），默认实现是“显著性过固化阈值才保留、归属置信度 0.5–0.7 走 tentative、与已有球余弦 > 0.95 兜底合并”，替代实现可以是“不同场景不同阈值”（编程场景宽松、量化场景严格），让后处理规则成为配置项而不是代码分支。四个策略 trait 的共同设计原则是：引擎主流程不变，只换策略实现——FlowEngine 和 SettleEngine 的流动、分配、判断、结算顺序不变，SupplementStrategy 只换“补充多少”、StrengthenStrategy 只换“强化多少”、LossModel 只换“损失多少”、VerdictPostProcessor 只换“后处理规则”；每个策略 trait 都有默认实现，默认实现是生产路径，替代实现主要用于对照实验和特定场景适配。和“四个核心 trait”的分工：核心 trait 隔离基础设施（存储、判别、嵌入、时间），策略 trait 隔离算法变体（补充、强化、损失、后处理）——前者是“数据从哪来、用哪个后端”，后者是“同一流程内换算法”。和“可观测性”的配合：每个策略实现带 producer 或 strategy_kind 标签，指标按策略打标签，对照实验按策略分组统计——ConstantLossModel 和 PipeWeightLossModel 的指标分开记，能对比“管道决定损耗”是否真的改变了召回质量。边界：策略 trait 不暴露具体实现的类型，只暴露“输入参数、返回标量”的契约；默认实现是生产路径，替代实现默认关闭、通过配置启用；策略 trait 不改变流动和结算的顺序，只改变某一步的计算方式。测试要覆盖：每个策略 trait 有默认实现和至少一个替代实现、引擎主流程不变只换策略、ConstantLossModel 与 PipeWeightLossModel 结果不同（证明修正有效）、指标按策略打标签、对照实验按策略分组、策略切换只改配置不改代码。 |

| **诊断规则** | 诊断规则是确定性的、可配置的规则集合，把可观测性指标映射为结构化的调参建议，不依赖 ML、不自动执行——它回答“当前指标异常，可能是哪个参数偏了、往哪个方向调”，第一版只“建议”，由开发者或用户确认后变更配置。规则结构：每条规则包含 rule_id、监控的 metric（可带标签过滤，如 injection_confidence_tier{label=clear}）、比较操作（</>/ratio）、阈值、window（观察窗口，如 7d/3d/1d）、min_samples（样本不足不触发）、suggestion（建议方向，如“考虑降低 flow_loss_rate 或提高 max_supplement_ratio”）、severity（严重程度）。典型规则：path_supplement_loss_ratio 中位数长期 < 0.5 → 建议降低 flow_loss_rate 或提高 max_supplement_ratio；pipe_blocked_rate 持续 > 0.6 → 建议降低 pipe_stability_growth 或提高 blocked_discount；注入 token 长期贴预算上限或注入球数长期顶满 → 建议收紧 strengthen_threshold_X 或重新校准判别器；settle_version_conflict_rate 异常升高 → 建议检查多客户端并发或调整 busy_timeout；size_saturation_rate 过高 → 建议调高 size_max 或降低 size_strengthen_factor；judge_parse_failure_rate > 5% → 告警，建议检查判别器后端或 prompt。输出格式：每条触发的规则输出 {rule_id, metric, current_value, threshold, suggested_direction, severity, window, timestamp}，写入 diagnostics.jsonl，供开发者或用户查看、确认后手动变更配置；不自动改配置、不自动回滚、不自动调参。安全边界：建议器不能建议超出 min/max 范围的值，越界拒绝；单次变更幅度 ≤ 当前值的 20%（可配），超出需显式确认；同一参数在 cooldown（默认 24 小时）内不接受第二次自动建议，防止反复建议、反复调参；所有规则带 window 和 min_samples，样本不足不触发，防止冷启动阶段误报。和“动态调参闭环”的关系：诊断规则是闭环的“诊断”环节——信号采集（指标）→ 诊断规则（结构化建议）→ 配置热更新（arc-swap）→ param_change_log 审计 → 按 config_version 回滚；规则只负责“诊断”，不负责“执行”，执行由开发者或用户确认后手动完成，第一版不引入自动执行。和“纠正审计”的同构：参数变更走 param_change_log，记录 {change_id, parameter, old, new, reason, trigger_metric, trigger_value, config_version, reversible}，和 correction_log 遵循同一套“审计先行、原值快照、可追溯、可回滚”的模式——系统对“自身状态的修改”和“记忆的修改”都保持可审计。为什么用确定性规则而不是 ML：第一版不需要强化学习调参，确定性规则可解释、可审计、可回滚；规则本身可配置、可增删、可调整阈值，不需要改代码；如果未来数据显示某类规则的误报率过高，可以调整阈值或 window，而不是重新训练模型。边界：规则输出到 diagnostics.jsonl、不自动改配置；规则本身进 TOML 配置、可增删改；severity 分 info/warning/critical，critical 触发告警、warning 进建议列表、info 仅记录；多条规则同时触发时按 severity 排序、不合并。测试要覆盖：规则按 window 和 min_samples 正确触发、样本不足不触发、输出格式完整、建议不超出 min/max 范围、cooldown 内不重复建议、severity 分级正确、规则可配置增删、不自动执行、与 param_change_log 同构审计。 |

## 十、已废弃 / 已修正条目

| 条目 | 状态 | 详细说明 |
|---|---|---|
| **管道健康因子** | **已废弃** | 与水量同类二次计权，形成粗管正反馈——`w_eff` 已在流动阶段决定阻力与损耗，再乘进相关性会让粗管路径被更偏爱、被强化更多、变得更粗，细管和孤岛永远等不到水流。 |
| **相关性含水量** | **已修正** | 水量是动力学量，不是语义相关性乘数——相关性应由语义相似度和路径位置决定，水量反映路径通畅度，两者正交。水量乘进相关性会混淆“路好走”和“语义相关”。修正后相关性 = 语义相似度 × 路径折扣。 |
| **新鲜度乘三次** | **已修正** | 收敛到 `size_effective` 只算一次——原来球自身衰减一次、补充规则乘一次新鲜度、注入排序再乘一次，同一个衰减被重复计算，陈旧球被平方甚至立方地过度沉底。修正后存储只存 `size_stored`，读取时算一次 `size_effective`，所有消费方共用。 |
| **每球各拿满 W₀** | **已修正** | 改为总量守恒按余弦占比分配——原实现每个起始球都拿满 `base_water_amount × significance`，命中 3 个球就是 3 倍水，一个“多义”输入自动获得更强扩散力，这是无意的放大。修正后 `W_i = W₀ × cos_i / Σcos`，总量守恒。 |
| **回边参与分配** | **已修正** | 分配时排除已访问出边——原设计回边和去边各拿 50%，回边那 50% 白费，每经过一个中间球水量腰斩，5 球链只能点亮深度 0。修正后只流向未访问出边，传播能力恢复。 |
| **管道有向权重** | **已废弃** | 改为无向共享——有向权重 `w_ab`/`w_ba` 是过度设计，增加存储和逻辑复杂度，却没有对应的人脑直觉。无向后一根管子一个 `w`、一个 `blocked_count`、一个 `last_flowed`，A↔B 共享。 |
| **管道阈值开关** | **已废弃** | 改为阻力有上限，强线索可突破——原设计管道粗细低于阈值时“流不过去”，相当于永久封死，违背“不能清理短期记忆、确实有可能突然想到”的理念。修正后管道是阻力不是开关，阻力有上限，任何管道在足够强线索下都能被突破。 |
| **流动即写入** | **已修正** | 流动只点亮，结算才强化——原设计在流动过程中每跳写入，把持久化塞进传播路径，复杂且容易竞态。修正后流动纯内存计算、只点亮不写入，结算统一计算强化、一次激活一次事务。 |
| **结算异步** | **已修正** | 结算同步立刻执行——原设计流动结束后异步结算，注入用流动过程中已确定的球，结算只影响下一轮图状态。修正后结算 = 注入决策，同一同步步骤完成，注入排序基于刚强化后的球状态。 |
| **语义粗筛丢候选** | **已修正** | 对话消息全量判别——原设计用 EWMA/SimHash/VADER 对候选片段做显著性粗筛，只把高意外片段送判别器，粗筛有损、漏掉的念永远补不回来。修正后对话消息全量判别，粗筛只保留结构性去重、且只作用于工具结果。 |
| **低于阈值不强化** | **已修正** | 给最低强化值——原设计相关性低于阈值时完全不强化，失去“多次弱相关点亮累积起来也能变强”的可能。修正后未达阈值的球给统一最低强化值（默认 0.05），保留极慢的累积路径。 |
| **原型双层节点** | **已废弃** | 改为球—管—水单层模型——原设计用“念事件”和“念原型”两层节点，复杂度失控，带来碎片化、漂移、合并分裂整类问题。修正后球不区分层级，语义相近的球靠管道连接，不靠归并合并。 |
| **念想命名** | **已废弃** | 改名大禹水利记忆网络——原名字承载了已被推翻的认知分层概念，会误导人以为还有“念/想”分层。模型的核心是水文物理过程，名字要体现“疏而不堵”的设计哲学。 |
| **blocked_count 不随时间衰减** | **已修正** | 改为随时间按曲线速减——原设计是永久累积计数、不随时间变化，会让“年轻时差点通过”的痕迹永久保值，一个管道十年前被阻挡 5 次和昨天被阻挡 5 次不应享受同样折扣。修正后存储 `blocked_count_stored` 和 `last_blocked`，读取时算 `blocked_count_effective = blocked_count_stored × exp(-Δt/blocked_decay)`（建议 30–90 天），结算时先衰减再叠加新增量、封顶 `blocked_cap`，写回“已衰减值 + 新增量”而非原始累积值。 |
| **S 只增不减** | **已修正** | 改为饱和增长 + 长期不活动衰减——原设计 `S` 只增不减（仅饱和增长），会让年轻时反复强化、之后多年不用的球 `S` 永远保值、几乎不淡忘。修正后 `S` 每次结算强化时按注水次数或增量增长、有上限 `S_max`、增长速率递减；同时随时间按曲线速减，存储 `S_stored` 和 `last_watered`，读取时算 `S_effective = S_stored × exp(-Δt/S_decay)`（建议 180–365 天），结算时先衰减再叠加增长量、封顶 `S_max`，写回“已衰减值 + 增长量”。 |
| **管道粗细只决定阻力** | **已修正** | 改为同时决定阻力和损耗——原设计管道粗细只决定阻力、损耗是全局常数 `L`。修正后粗管好过且损耗小、细管难通过且损耗大，损失函数 `loss = min(base_loss × (1 + loss_pipe_factor × (1-w_eff)), loss_max)` 是 `w_eff` 的确定性函数；损失计算和阻力判断共用同一个 `w_eff`，顺序是先扣损再判断。 |
| **嵌入维度固定 384** | **已修正** | 改为由具体嵌入后端决定——早期文档惯性写了 384 维（bge-small/MiniLM 的维度），但实际选型中 `pizza-embed-zh-small-v1` 是 **512 维**、`piccolo-large-zh` 和 `bge-m3` 是 **1024 维**。修正后维度不是固定常量、存储体积随维度线性变化；维度一致性是启动时硬校验，换模型需显式迁移，不能在同一张表里混存不同维度的向量。 |
| **相关性用原始查询嵌入算** | **已修正** | 改为流动逐跳用原始查询嵌入、结算用流动加权语境——原文档没有区分流动逐跳和结算的语境差异。修正后流动逐跳用原始查询嵌入算相关性、判断是否补充；结算时用流动加权语境 `原始查询嵌入 × (1-α) + 路径上各球嵌入的加权平均 × α`，α ≤ 0.3、默认 0.2，原始查询嵌入占主导、路径只做轻微染色。 |
| **SQL 作为查询语言** | **已废弃** | 改为 TriviumDB 的 TQL——早期文档里出现过 `CREATE TABLE`、`UPDATE ball SET ...`、`SELECT`，那只是逻辑数据模型的示意、不是运行时实际执行语句。修正后存储内核是 TriviumDB，查询走 TQL（`SEARCH VECTOR`、`MATCH ... EXPAND`、`FIND`），写入是事务 API 和原子增量操作，**没有 SQL 引擎**；唯一保留 SQLite 的地方是 `StorageBackend` trait 后面的回退逃生舱，不是默认路径。 |
| **旧公式（阈值判断 `sim × 折扣`）** | **已废弃** | 改为方案 A（资格看 `semantic_sim`、幅度和排序用 `sim × 折扣`）——旧设计里 `strengthen_threshold_X` 直接判断 `sim × 折扣`，导致死区：深度 4 折扣 0.6 需要 `sim=1.0` 才能过线、深度 5 折扣 0.5 需要 `sim=1.2`，`max_flow_depth` 默认就是 5，第 4、5 跳的球永远无法成为强化球。旧公式乘 water 时被掩盖，移除 water 后暴露。修正后资格不该被路径长度惩罚，深度 5、`sim=0.95` 的球应该被强化、幅度 0.475。当前系统只有方案 A 一套公式，旧公式不参与任何运行时计算。 |
| **N/A 占位符** | **已修正** | 改为明确表述——早期表格里用 `N/A` 表示“不适用”，但实际语义是“当前不产出、未来可能产出”或“当前版本未启用”，`N/A` 模糊了两者。修正后统一用“当前留空、未来由决策模型填充”“默认关闭、可配置启用”“已废弃、不再作为可选项保留”三种明确表述。 |
| **渲染三级（模糊档）** | **已修正** | 改为 0.7 / 0.3 三档 + 印象档三档措辞（≥0.7 清晰、0.6–0.7 深印象、0.5–0.6 印象、0.3–0.5 模糊印象、<0.3 不注入）——“我好像有关于X的印象”这类无内容空壳已废弃 |
| **强化球 / 最低强化球二分** | **已修正** | 改为三分：≥0.7 强化球（幅度强化 + 注入）、0.3–0.7 印象球（最低强化值 + 注入）、<0.3 最低强化球（最低强化值 + 不注入）；强化资格阈值由 0.6 上调为 0.7 |
| **注入排序乘 size_effective（b>0）** | **已修正** | 改为 b=0、排序只看 semantic_similarity——size_effective 是相关性的历史累积结果、不是独立信号，再乘一次是同一信号算两遍。 |
| **注入排序用含路径折扣的相关性** | **已修正** | 改为只用 semantic_similarity（资格口径）——路径折扣已在强化幅度里起作用，不该在排序里第二次惩罚远处球。 |
| **起始球选择乘 size_effective** | **已修正** | 改为纯余弦 Top-N——size 退出所有“谁更重要”的决策，只保留补充释放的活性（含衰减）与渲染长度估算（不衰减）两个物理角色。 |
| **注入预算按水量估算（tokens_per_water）** | **已修正** | 改为按 ball_stored_size × tokens_per_size（默认 20）估算——预算算的是渲染长度，不随时间衰减。 |
| **最低强化值用绝对量（默认 0.05）** | **已修正** | 改为相对量 base_reinforcement × min_strengthen_value（默认 0.1 × 0.05 = 0.005）——绝对量会与强化幅度量级倒挂（达标球最差 0.03 < 0.05）。 |
