# 大禹水利记忆网络
## 设计说明

**版本**：v8.0（TriviumDB 基准版）
**定位**：单用户、自包含、可跨 dsh / pi-agent 的持久记忆系统
**存储内核**：TriviumDB（纯 Rust、嵌入式单文件、向量+图+文档三模原生融合）
**原则**：疏而不堵——不删除记忆，只调度水流；不硬编码系数，全部可配置；无选择性流入——水管只决定水量与阻力，不存在任何「越健康越偏祖」的分流。

---

## 1. 命名与设计哲学

**大禹治水，疏而不堵。** 记忆系统里没有“删除”这道堤坝，只有球的大小、管道的粗细、水量与阻力这组水文参数。记忆不是被清理，是被调度：纠正靠放水缩球，遗忘靠自然沉底，唤醒靠强线索突破细管。球最小也是一个点，管道最细也有阻力上限；**没有被删除的记忆，只有还没等到足够强水压的记忆。**

---

## 2. 核心概念

| 概念 | 含义 | TriviumDB 对应 |
|---|---|---|
| **球** | 记忆节点，大小 = 记忆强度 | Node（向量 + Payload + 图边） |
| **管道** | 球之间的关联，粗细 = 关联强度；无向，A↔B 共享 `w` | Edge（带属性） |
| **水** | 激活流量，每次对话给定总水量 W₀ | 应用层内存计算 |
| **流动** | 水沿管道传播，只点亮球，不写入 | 内存子图 + TQL 图遍历 |
| **结算** | 流动结束后同步执行，决定强化与注入 | TriviumDB 事务 |
| **内容** | 球里装的文本，多条、可追加、可纠正、有上限 | Node Payload（JSON 文档） |
| **嵌入** | 内容的语义向量，单条、EMA 更新 | Node Vector（QuIVer ANN 索引） |

**核心区分**：流动只点亮、不写入；结算同步立刻执行，**结算就是注入决策**——两者不可拆开。

## 3. 系统结构

```
宿主（dsh / pi-agent）
 ├─ 主模型：正常对话，不感知记忆系统
 ├─ TS 薄适配层
 │   · 注册宿主生命周期钩子（dsh: session/event + agent/pre-step；
 │     pi: turn_end + before_agent_start + session_before_compact）
 │   · 转发本轮事件给内核
 │   · 把内核返回的记忆拼装为尾部消息
 ├─ dayu-core（Rust，napi 原生模块）
 │   · 流动与结算引擎
 │   · 判别后端抽象（嵌入规则 / 决策模型，可替换）
 │   · 纠正、时效、巩固、冷热分层
 │   · rmw-utf8 透明编解码
 ├─ TriviumDB（嵌入式单文件 .tdb）：唯一存储依赖
 │   · Node / Edge / Vector / Payload
 │   · QuIVer ANN 向量索引（高维自动激活）
 │   · WAL + 事务 + 进程级文件锁
 └─ 可选适配器（独立模块）
     · 压缩插件存在时：折叠前补充归档、受保护注入
     · 不存在时：核心流程完全不受影响
```

**依赖方向**：适配器 → 压缩插件；核心绝不 import 压缩插件的代码、事件或存储。

## 4. 数据模型（TriviumDB 映射）

### 4.1 球（Node）

```json
{
  "ball_id": "uuid",
  "vector": [f32; 384],           // 内容的语义 EMA，QuIVer ANN 索引
  "payload": {
    "size": 0.5,                  // 截至 last_watered 的强度（写入时物化衰减，见 §4.6）
    "size_max": 10.0,
    "size_saturation_gamma": 1.0,
    "content_list": [
      {
        "content_id": "uuid",
        "text": "...",             // rmw-utf8 压缩后 base64 或原始
        "encoding": "rmw-utf8",
        "source": "turn_id",
        "injected_count": 0,
        "status": "active"
      }
    ],
    "content_list_max": 5,
    "last_watered": "2025-11-05T10:00:00Z",
    "lit_count": 3,
    "status": "active",           // active / contested / archived / deleted
    "domain": "code",             // 可空
    "created_at": "...",
    "schema_version": 1
  }
}
```

**内容**：多条、可追加、可纠正、有上限（默认 5，可配）。新球创建时挂触发片段原文；球被强化时追加本次语境片段（去重后）；超出上限按“被注入次数”淘汰最不常用的，转入冷存储，不删除。

**嵌入**：单条，EMA 更新 `新嵌入 = 旧嵌入×(1−β) + 本次内容嵌入×β`，β 默认 0.1。内容纠正后嵌入不立即重算，由后续 EMA 自然稀释。

**嵌入存储**：TriviumDB 原生 Vector 字段，f32（内部可 f16 量化）；QuIVer ANN 在向量数超过阈值（约 209–834 视版本）时自动激活，无需额外配置。

### 4.2 管道（Edge）

```json
{
  "edge_id": "uuid",
  "from": "ball_a_id",
  "to": "ball_b_id",
  "payload": {
    "w": 0.35,                    // 粗细，∈(0,1]，A↔B 共享（无向）
    "blocked_count": 2,           // 被阻挡次数，A↔B 共享
    "last_flowed": "...",         // 任一方向流动即刷新
    "source": "new_ball",         // new_ball / co_activation / offline_similarity / manual
    "status": "active"
  }
}
```

**唯一性约束**：`(min(a_id,b_id), max(a_id,b_id))` 唯一，防止重复建边。**管道是无向的：一根管子只有一个 `w`、一个 `blocked_count`、一个 `last_flowed`，A↔B 共享。**

### 4.3 冷存储（Node，独立类型或独立表）

### 4.6 有效值：唯一定义点（懒衰减 + 写时物化）

**两条原则**：

1. **读取只算不写**：`size_effective` / `w_eff` 是视图，读取不产生任何写操作；
2. **写入先物化**：结算强化时，先把衰减落到存储，再在衰减后的值上加增量。

**为什么读取不能写**（与存储引擎性能无关，是语义问题）：

- **衰减次数必须由时间决定**：若每次读取都物化，一个球在一秒内被扫描 100 次就衰减 100 次，衰减量取决于“被查了多少次”而非“过了多久”；
- **读路径必须可重入**：起始球选择、旁路 `recall`、对照实验会重复读同一子图，读有副作用会让结果依赖调用顺序；
- **并发语义**：读走共享锁、写需独占锁，读路径写会让并发 recall 退化为串行。

存储字段的含义：

| 存储字段 | 含义 | 读取时 |
|:--|:--|:--|
| `size` | 截至 `last_watered` 时刻的强度（上次写入时已物化过衰减） | 不改 |
| `last_watered` | 上次注水（= 上次物化）时刻，衰减基准 | — |
| `S` | 稳定性，随注水次数增长 | — |
| `w` | 截至 `last_flowed` 时刻的粗细 | 不改 |
| `last_flowed` | 上次流动时刻 | — |
| `S_pipe` | 管道稳定性，随流动次数增长 | — |

**读取时算一次**（不写回）：

```
球：  size_effective = size × exp(-(now - last_watered) / S)
管：  w_eff          = w    × exp(-(now - last_flowed) / S_pipe)
```

**写入时物化 + 累加**（结算强化，§7.2 / §8）：

```
① 物化衰减：size ← size × exp(-(now - last_watered) / S)
② 算增量：  Δ = 强化值 × (1 - size / size_max)^γ      // 用物化后的值算饱和，不是用历史峰值
③ 累加：    size ← min(size + Δ, size_max)
④ 刷新：    last_watered ← now
```

管道同构：`w ← w × exp(-Δt/S_pipe)` → `w ← min(w + Δw, w_max)` → `last_flowed ← now`。

**为什么必须物化**（反例）：球 `size = 8.0`、一年未注水、`S = 30`，读取时 `size_effective ≈ 8.0 × e^-12 ≈ 5e-5`，几乎为零。若存储永不衰减，一次强化后 `last_watered = now`，立刻变成 `size_effective = 9.0`——等于“衰减从未发生”，沉睡球一被点亮就凭空恢复了全部历史强度。物化保证：强化是在“现在还剩多少”的基础上加，不是往“历史峰值”上加。

**`size_effective` 只在两处使用，且都是“物理量”用途，不参与任何“谁更重要”的决策：**

| 消费方 | 用法 |
|:--|:--|
| 补充规则（§6.2） | 可释放水量 = `size_effective × relatedness`（含时间衰减：久未使用的记忆“活性”低，放不出多少水） |
| 结算强化（§7.2、§8） | 先物化衰减，再加增量，写回 `size` |
| 起始球选择（§5.1） | **不使用**——只用余弦；size 是相关性的历史累积结果，不是独立信号 |
| 注入排序（§7.4） | **不使用**——只用 `semantic_similarity`；理由同上 |

**为什么必须是唯一定义点**：如果 `size` 自己先衰减一次，补充规则再乘一次 `R(t)`，排序又乘一次 `R(t)`，同一个“距上次注水多久”就被计了三次——陈旧球被过度沉底，不是“合理沉底”而是“平方沉底”，沉睡记忆永远等不到强线索。这是历史上真实出现过的冗余（新鲜度被当作独立因子三次引入），必须靠本节锁死。

**禁止事项**（代码审查必查项）：
- 禁止在读取路径写存储——`size_effective` 不落盘，读取必须无副作用；
- 禁止在任何消费方内部再乘 `exp(-Δt/S)` 或任何名为 `freshness` / `R(t)` 的因子；
- 禁止跳过物化直接 `size += Δ`——那样会把衰减抹掉，陈旧球凭空回满；
- 禁止在配置里新增“新鲜度指数”（如已废弃的 `sort_exponent_c`）——新鲜度不是可调指数，它是 `size_effective` 定义的一部分。

**球与管道的新鲜度互相独立，不得混用**：

```
球的衰减：  size_effective = size × exp(-(now - last_watered) / S)      S 随注水次数增长    语义：记忆还牢不牢
管的衰减：  w_eff          = w    × exp(-(now - last_flowed)  / S_pipe) S_pipe 随流动次数增长 语义：联想还通不通
```

一个球可以很大很新鲜，但它与邻居的管道很旧很细——两件事必须分开表达，不共享 `R(t)`、不互相乘。

## 5. 起始球选择与注水

### 5.1 起始球选择

```
1. 当前输入做嵌入 → query_embedding
2. TQL 向量检索：SEARCH VECTOR $query_embedding TOP 10 WHERE {status:"active"}
3. 过滤：余弦 < start_ball_threshold（默认 0.3）的球不作为起始球
4. 剩余按余弦降序，取 Top-N（默认 3）——**不乘 `size_effective`**：size 是“相关性 → 强化 → size 增长”的历史累积结果，是相关性的滞后代理；决策时已能算当前余弦，再乘历史累积值等于把同一个信号算两遍
5. 如果没有任何球超过阈值 → 本轮不注水，无记忆注入（正常状态，非故障）
```

QuIVer ANN 自动处理向量检索；球数少时退化为全量扫描，球数多时自动走索引。

### 5.2 注水量分配

```
W_i = W₀ × cos_i / Σ(cos_j for j in 起始球)
```

余弦越高的起始球分到的水越多。起始注水量只由“当前输入与球的余弦”决定，和球本身大小无关。

**W₀ 是总量，不是每球一份**：命中 k 个起始球时，W₀ 在它们之间分配，**总和恒为 W₀**。若每个起始球各拿一份 W₀，命中多个球的“多义输入”就凭空获得 k 倍水量——等于让模糊输入自动获得更强扩散力，不是设计意图。实现见 `crates/dayu-flow/src/engine.rs` 的 `propagate`（起始注水段）。

**强线索放大**：某起始球余弦 > `strong_cue_threshold`（默认 0.8）时，W₀ 先放大 `strong_cue_multiplier`（默认 3.0）再分配。

> **实现**：`crates/dayu-flow/src/engine.rs` 的 `propagate` 在算总注水量前判断 `starts.iter().any(|(_, sim)| *sim >= strong_cue_threshold)`，命中则 `W₀ × strong_cue_multiplier`。放大的是 W₀ 本身，分配仍按余弦占比，**总水量守恒**。
>
> **判据是“像不像”，不是“重不重要”**：`strong_cue` 用起始球余弦（这句话是不是在指某颗具体的球），不是 `significance`（这段内容值不值得记）。后者在每次普通 `recall` 中都是 1.0，用它会让所有输入都被放大 3 倍——这是实际踩过的坑。

### 5.3 多输入源同时注水

> **实现**：`FlowEngine::flow_multi(storage, &[emb_a, emb_b, ...], significance)`；单源入口 `flow` 内部即 `flow_multi(&[embedding])`，行为不变。

- 各源独立选起始球，空源剔除，合并加载子图；
- **按扩散区域重叠度分组**：重叠度 = |A∩B| / |A∪B|，A/B 为各源在子图上的可达球集合（纯图可达，不含水量判断）；重叠度 ≥ `multi_source_overlap_threshold`（默认 0.3）的源并成一组，重叠关系有传递性；不扩散的源（可达集 ≤ 1）不构成独立区域，与任何源视为同组；
- 总水量 = `W₀ × min(1 + source_bonus × (n−1), source_cap)`（`source_bonus` 默认 0.2、`source_cap` 默认 2.0；单源恒为 1，`source_bonus = 0` 关闭放大）；
- 总水量按“该源最高余弦 / 所有源最高余弦之和”分到各源子预算，组内再按球余弦分到各起始球；
- 同一球被多源命中时，注水量 = `min(各源分配之和, 最大单源分配 × multi_source_merge_cap)`（默认 1.5）；
- 组间独立流动，结果合并去重（同球取水量更大者）；
- 补充资格用 `max over sources of cos(源, 球)`——与任何一个输入相关都算相关。

### 5.4 配置项

```toml
[start_ball]

start_top_n = 3
strong_cue_threshold = 0.8
strong_cue_multiplier = 3.0
multi_source_merge_cap = 1.5

```

## 6. 流动规则

### 6.1 流动（纯内存，只点亮）

```
1. 开 TriviumDB 读事务（共享读锁）
2. TQL 加载起始球及其 N 跳邻居子图到内存
3. 记录全局版本号 V_start（TriviumDB 提供或应用层维护）
4. 结束读事务
5. 在内存子图上纯计算流动（不写 TriviumDB）
```

**水的唯一职责（边界约束，不可违背）**：水只回答一个问题——**这次能不能到达这个球**。除此之外它不参与任何判断：

| 用途 | 允许 |
|:--|:--|
| 分配到下游管道（`1 + w` 加权） | ✅ |
| 判断能否通过阻力（`water_after_loss > 1/(1+w)`） | ✅ |
| 决定是否点亮该球 | ✅ |
| 进入相关性（语义相关度） | ❌ 见 §7.1 |
| 决定强化量（球变大/管道变粗） | ❌ |
| 参与注入排序 | ❌ |
| 乘进任何阈值判断 | ❌ |

**为什么**：水的绝对值是调度量，量纲随 `total_water_budget` / `split_mode` / 损失参数漂移——把 `total_water_budget` 从 1.0 改成 2.0，所有记忆的强化量都会翻倍，但没有任何一条记忆变得更牢，只是单位变了。凡是要与阈值比较、要跨轮累加、要与语义相似度相乘的量，必须是无量纲的（`relatedness ∈ [0,1]`）；否则 `strengthen_eligibility_threshold` 退化成不可校准的魔数（反例：强线索 `W₀×3` 时，语义仅 0.25 相关的球 relevance 也能到 0.75 而被判为“强化球”）。

一句话：**水负责“点亮”，不负责“记账”，也不负责“说话”。**

**流动规则**：
- **铁律（不可违背）**：水管只决定「流过的水量」与「阻力」。一个水球流向所有**未访问的连接水管**，每条水管分得的水量**只由该管粗细决定**（`1 + w_eff` 加权），不存在任何「健康因子」式的选择性流入——不按历史流量、不按连通度、不按任何「越常用越优先」的启发式偏祖某一条出边。
  - **为什么排除已访问球**：回边不是“待探索的方向”，是“已经走过的路”。若回边参与分配，中间球每条来路会分走一半水量，每经过一个中间球水量腾空一半——5 球链在默认参数下永远出不了第 1 跳，`max_flow_depth` 沦为装饰。排除回边是**算法状态**（BFS visited）参与物理规则的唯一例外，且不构成“选择性偏袒”：所有未访问出边一律按 `1 + w` 公平分配，不按语义预判方向。
  - **两条规则的分工（不得混淆）**：
    1. **回边排除**（分配前）：指向已访问球的出边根本不参与分配，不产生水量、也不产生损失。
    2. **首次到达点亮**（到达时）：多条不同路径在分配后同时指向同一个**未访问**球时，第一条到达者点亮它，此后它变为已访问，后续到达的水全部损失。
    ——回边走规则 1，不经过规则 2；规则 2 只用于多路径汇聚。
  - **死路（显式规定）**：球的所有出边都已访问时，没有未访问出边，可分配水量**全部损失**，该球成为死路。**禁止为这种情况加“回流”特例**——回流会把刚排除的浪费重新引入，并使流动结果依赖遍历顺序。
- **多出边水量分配（`1 + w` 加权）**：球的当前可分配水量（流入水量 + 球释放的补充）按
  `water_i = water_available × (1 + w_eff_i) / Σ_j(1 + w_eff_j)`
  分到各条**未访问**出边，**先分配、再判断**：
  - 每条管道用**自己分到的水量**独立判断能否通过阻力；
  - 过不去的管道，其分得的水量按损失规则损失掉，**不回收**给其他出边（“想不起来就是白费力气”）；
  - **权重取 `1 + w` 而非 `w`**：`w = 0` 的管道权重为 1，分到最少但**永不为零**——否则分配规则会把细管永久封死，与「阻力不是开关、强线索可突破」直接冲突；粗管权重最大分到最多水，细管分到最少、通过后剩余也少、联想链更短，管道粗细在**流量分配**与**阻力判断**上语义一致；
  - 与「不封死」自洽：分配规则保证每条管道至少分到非零水量，阻力规则保证水量足够大时能突破，两者叠加使最细的管道在足够强的线索下仍可被点亮；
  - 对照开关：`split_mode = "Weighted" | "Equal"`，默认 `Weighted`；`Equal` 仅供对照实验（若加权与平均的召回质量无差异，说明该规则在当前场景不产生实质影响），不作为生产配置。
- 管道粗细 `w_eff` 同时决定阻力和损耗——粗管好过且损耗小，细管难通过且损耗大；
- 损失是 `w_eff` 的确定性函数：`loss(w_eff) = min(base_loss × (1 + loss_pipe_factor × (1 - w_eff)), loss_max)`；`w_eff=1` 时 `loss=base_loss`，`w_eff→0` 时 `loss→base_loss×(1+loss_pipe_factor)`，被 `loss_max` 截断；
- 逐跳计算顺序：**先扣损、再判断阻力**——损失确定发生，不管通过与否；
- 管道是阻力不是开关：`resistance = 1/(1+w_eff) × 阻挡记忆折扣`，阻力有上限（w→0 时 resistance→1）；
- 水量 > 阻力才能通过；通过后管道变粗（w += η），目标球被点亮；
- 水量 ≤ 阻力：损失照常发生，水不消失，尝试该球其他出边；被阻挡管道记 `blocked_count`，下次有效阻力临时降低；
- 同一次激活中，每个球最多被注水一次；已访问球不参与后续分配（规则 1），多路径汇聚时以**首次到达**点亮、后到的水全损（规则 2）；
- 安全阀：`max_flow_depth`（默认 5）、`max_lit_ball_count`（默认 50），任一触发该方向停止，已点亮球照常结算；
- 深度按 BFS 首次到达算。

### 6.2 补充规则

- **相关性口径 = 原始查询嵌入与球嵌入的余弦**：`relatedness(B) = cos(query, B)`。流动阶段逐跳不做语境更新——水到达每个球都用同一个原始查询嵌入判断，不用“被前面球染色的语境”（结算阶段才用流动加权语境，见 §7.1）。不引入水源球 `S`：水源的语义偏差已通过管道连通性隐含表达，再乘进补充判定会让“从一个语义偏的起点出发”永久压制整条链；
- **资格 + 幅度两段式**：到达球时，若 `relatedness > supplement_threshold`（默认 0.4–0.5，须高于 `flow_continuation_threshold` 0.3），球释放补充：`补充量 = size_effective × (relatedness - supplement_threshold) / (1 - supplement_threshold)`——刚好过阈值时补充接近零，接近 1 时才拿满 `size_effective`。弱相关的大球无法靠历史强度放大水流（线性乘积 `size × relatedness` 已废弃：`size = 8.0`、`relatedness = 0.31` 仍能释放 2.48，等于大球赢家通吃）；
- 可释放水量用 **`size_effective`**（= `size × exp(-(now - last_watered)/S)`，见 §4.6）——补充是流动力学行为，“久未使用的记忆活性低、放不出多少水”，衰减在这里是天经地义的。**不再额外乘新鲜度 R(t)** —— 否则同一个「距上次注水多久」被计两次；
- 补充上限：`补充量 ≤ 扣损前水量 × max_supplement_ratio`（默认 2.0）；
- 补充加在扣损之后：单出边时 `下一跳水量 = water_after_loss + supplement`；**多出边时补充先计入可分配总量再分配**：`water_available = min(water + supplement, water × max_supplement_ratio)`，然后按 `1 + w_eff` 分到各出边，每条管道扣损后独立判断——补充不会对每条出边各加一次；
- **补充 > 损失当且仅当球大（`size_effective` 大）、新鲜（衰减少）、与当前输入强相关（过 `supplement_threshold`）**；
- 维度不匹配（切换模型）时 `relatedness` 无法计算：该球不补充，不报错、不中断水流。

### 6.3 管道在流动中的行为

- 取无向 `w` 算阻力和损耗，不区分方向；
- `w_eff = w × exp(-Δt / S_pipe)`，`Δt = now - last_flowed`；
- 阻力和损耗共用同一个 `w_eff`：`resistance = 1/(1+w_eff)`，`loss = loss_model.loss(w_eff, cfg)`；
- 被阻挡时 `blocked_count += 1`，下次有效阻力 `resistance × (1 - blocked_discount × min(blocked_count, blocked_cap))`；
- 成功通过后 `blocked_count` 不清零、不再增长。

## 7. 结算规则

### 7.1 结算流程（同步，立刻执行）

```
流动结束
  → 对每个点亮球算相关性：
      semantic_similarity = cos(结算语境, 球嵌入)
      结算语境 = (1 - α) × 原始查询嵌入 + α × 路径上各球嵌入的加权平均
                 权重 = 各球在路径上获得的 water 占比；α 默认 0.2、上限 0.3
      path_relevance = semantic_similarity × 跳数折扣
      **不含水量**：水量只作语境权重，不乘进相关性
      （若乘入 water，强线索 `W₀×3` 时语义仅 0.25 相关的球也能过阈值 0.7，
        `strengthen_eligibility_threshold` 退化成不可校准的魔数）
  → 多路径取最大值（不累加）
  → 按语义相似度分三档（`strengthen_eligibility_threshold` 默认 0.7、`impression_threshold` 默认 0.3）：
      ≥ 0.7        强化球    ：按 path_relevance 幅度强化 + 注入
      0.3 – 0.7    印象球    ：给最低强化值 + 注入
      < 0.3        最低强化球：给最低强化值 + **不注入**
      ⚠️ 资格只看 `semantic_similarity`，不看 `semantic_similarity × 折扣`：
         阈值 0.7 > `min_discount` 0.5 时，深度 4/5 的球即使语义完全匹配
         （sim=1.0）也会被路径折扣压到 0.7/0.5，永远过不了资格线——
         远处联想被点亮却永不被强化，等于“只贡献路径、不获得强化”。
         资格由语义决定，路径长度只影响幅度（见下方路径相关性）。
  → 强化球：路径相关性 = 终点球相关性 × 路径长度折扣
      路径长度折扣 = max(min_discount, 1 - discount_per_hop × 跳数)
        默认 discount_per_hop = 0.1、min_discount = 0.5：每跳打九折，最低五折，触底不再降
        跳数 0（起始球本身）折扣 1.0；跳数 5 时 0.5
      多路径：同一球出现在多条路径上时取最大路径相关性强化一次，不累加
      ❌ 管道健康因子（**已废弃**，不保留开关）：曾考虑折扣额外乘
        pipe_health_floor + (1 - pipe_health_floor) × avg_w_eff。
        废弃理由与“相关性不含水量”同源：w_eff 已在流动阶段决定阻力与损耗，
        再乘进相关性是同一信号的二次计权，会形成「粗管→更受偏爱→更粗」的正反馈，
        使细管/孤岛记忆永远等不到水流。若将来要重新引入，须重开一次设计决策
        （连同对照实验与副作用观测），不得作为随手可开的配置项保留。
  → 最低强化球：给统一最低强化值 = `base_reinforcement × min_strengthen_value`（默认 0.1 × 0.05 = 0.005）
      必须是相对量：绝对量会与达标球最小增量（`base × 阈值 × min_discount` = 0.03）量级倒挂，
      导致“语义不达标只是路过”的球比“语义达标但路径最远”的球强化得更多
  → 开 TriviumDB 写事务（写锁，Dry-Run 预检）
  → 校验全局版本号：冲突则重读涉及球/边重算增量
  → 写入球大小增量、管道粗细增量、last_watered/last_flowed
  → 提交事务（WAL 持久化）
  → 从强化球 + 印象球中按注入排序取 Top-K
  → 渲染注入文本（清晰档 + 印象档三档措辞）
  → 注入主模型上下文
```

**结算 = 决定注入什么 + 把强化写进图，同一同步步骤完成，不可异步。**

### 7.2 球与管道的路径级强化

- 路径上**每个球**：`有效增量 = 强化值 × (1 − size/size_max)^γ`，`size = min(size + 有效增量, size_max)`；γ 默认 1.0；
- 路径上**每条被水冲过的管道**：`w += 路径相关性 × pipe_strengthen_factor`（默认 0.05），饱和 `pipe_thickness_ceiling`（默认 1.0）；
  - “被水冲过”由 `LitBall.via_pipe` 精确判定（每个球记录从哪条边到达）。**两端都被点亮但这条边没走过 → 不加粗**——否则两端分别经不同路径到达时，它们之间那条没用的边也会被加粗，等于给“没走过的路”发通行证；
  - 两端相关性取 `path_relevance` 均值，且两端都必须相关性可计算（维度不匹配则跳过）；
- 同一结算中，球或管道出现在多条路径上时，**取最大路径相关性强化一次**，不累加。

### 7.3 注入预算：两种模式

**模式 A：排序 → 内容长度估算 → 球数**

```
1. 按注入排序得到候选球序列 [B1, B2, ..., Bn]
2. 预筛：`est_i = size_effective × tokens_per_size`（默认 20）——只淘汰“明显装不下”的球，避免为它们渲染全文；
   主计数：`est_i = 内容字符数 / chars_per_token`（默认 4），渲染后再用真实 tokenizer 校准
3. 从 B1 开始累加 est_i，直到 est_sum + est_{i+1} > token_budget 时停止
4. 得到候选球数 K
5. 渲染前 K 个球的完整内容
6. 用真实 tokenizer 对渲染结果计数
7. 若 real_sum > token_budget：从 K 开始逐个减球，直到不超
   若 real_sum < token_budget：尝试加入第 K+1 个球，直到下一个会超
8. 返回最终的完整球集合
```

**不得用水量估算 token**：球的 token 数由**内容长度**决定，与水多少无关——水多的球可能只有一句话，水少的球可能有一万字。早期设计曾用 `est_i = 水量_i × tokens_per_water`，已被废弃（违反 §6.1 “水的唯一职责”）。

**模式 B：排序 → 固定球数上限**

```
1. 按注入排序得到候选球序列
2. 配置固定球数上限 K_max（如 5）
3. 取前 K_max 个球
4. 渲染完整内容
5. 可选：真实 tokenizer 校验，若超过 token_hard_cap，减球直到不超
6. 返回完整球集合
```

**统一停止规则**：从排序后的候选球开始，逐个加入完整球；如果加入下一个完整球后，总 token > 预算（模式 A）或球数 > 上限（模式 B），停止，返回已加入的完整球。**不切割、不截断、不部分渲染。**

**为什么是 token 预算**：模型窗口、API 成本、推理延迟全部按 token 计；水量是内部调度单位，token 是外部约束单位。**相关性决定优先级，token 决定截断点**，两者解耦——水量只决定“谁被点亮”，不决定“谁先说话”。

### 7.4 注入排序与渲染

- 排序：对**强化球**按 `semantic_similarity` 降序，取 Top-K。**不乘 `size_effective`、不乘跳数折扣**——
  - 不乘 `size_effective`：它是相关性的历史累积结果、不是独立信号，再乘一次是同一信号算两遍（与“新鲜度被乘三次”“水量乘进相关性”同一类错误）；
  - 不乘跳数折扣：折扣已在强化幅度里起作用（远处球被强化得少），不该在排序里第二次惩罚它。注入要回答的是“这条记忆和用户当前说的话有多像”，路径走了多远不影响它的回答价值。
- `sort_exponent_a`（默认 1.0）作为可调指数保留；`sort_exponent_b` 默认 0，仅作对照实验入口、不作为推荐配置。

**为什么 `b` 默认为 0（只按相关性排序）**：

- **正反馈固化**：若 `b > 0`，注入 → 强化 → `size` 更大 → 更易被注入，形成“强者恒强”的马太效应。老记忆会把新记忆挤出注入预算，而新记忆恰恰最需要被带回上下文以确认是否相关。
- **当前相关性应主导注入**：注入的唯一目的是“让模型看见与当前输入最相关的东西”。历史强度回答的是“这条记忆有多牢固”，不是“这次该不该说”。把一次 0.9 相关的记忆排到一次 0.5 相关的记忆之后，需要很强的理由，而目前没有数据支撑。
- **`b` 仍是待验证假设**：`b > 0` 的价值（用巩固度区分“同样相关但内容更可靠”的记忆）尚未被数据证实，不应作为默认值拍板。

`b` 保留为可调参数，对照实验比较 `b ∈ {0, 0.25, 0.5, 1.0}`：除注入命中率外，**必须同时观测注入内容的新旧分布**——若 `b > 0` 命中率略高但显著压制新记忆，这个提升是用固化换来的，不可取。数据显示 `b > 0` 确有收益后再改默认值。

**实现状态**：`sort_exponent_a/b` 已接入 `crates/dayu-flow/src/settle.rs` 的 `sort_for_injection`，默认 `a=1.0, b=0.0` 等价于只按 `semantic_similarity` 降序；排序候选为**强化球 + 印象球**，最低强化球不参与。`size_effective` 已实现（§4.6），`b` 打开后即可参与排序。

**同等语义相关性下不区分水量强弱**：两个球相关性相同，一个被强水量点亮、一个被勉强点亮，注入排序**不作区分**——语义相关性相同意味着回答价值相同；水量差异反映的是路径通畅度（路好不好走），不是回答价值（该不该说）。

若未来数据显示“同等相关性下强激活的球确实更该被注入”，应作为一个**显式的、有名字的第三因子**（`activation_strength`）加入排序：可配置、**默认关闭**、有对照实验支撑，而不是藏进相关性定义里的隐式乘数。理由与 §6.1 相同——水是调度量，一旦以“乘数”形式潜入语义量，就无法单独关闭、无法单独观测、无法单独对照，只能靠改代码才能验证。
- 渲染（清晰档 + 印象档三档措辞）：
  - `sim ≥ 0.7` → `[记忆] 关于“X”，我记得：Y`（清晰档）
  - `0.6 ≤ sim < 0.7` → `我对“X”有比较深的印象……`（印象档·深）
  - `0.5 ≤ sim < 0.6` → `我对“X”有印象……`（印象档·中）
  - `0.3 ≤ sim < 0.5` → `我对“X”有模糊的印象……`（印象档·浅）
  - `sim < 0.3` → **不注入**
- 总 token 不超过预算。

## 8. 球的大小与饱和

**饱和函数**：线性硬顶 + 边际递减系数，作用在**物化后的 `size`** 上（§4.6）：

```
① 物化：  size ← size × exp(-(now - last_watered) / S)
② 增量：  有效增量 = 强化值 × (1 − size / size_max)^γ
③ 累加：  size = min(size + 有效增量, size_max)；size = max(0.0, size)
④ 刷新：  last_watered ← now
```

用物化后的 `size` 算饱和，陈旧球才有“再强化”的空间——否则放了一年的球 `size` 仍为 8.0，永远卡在饱和边缘，与“强线索可唤醒”矛盾。

- `γ` 默认 1.0；`γ=0` 退化为纯线性硬饱和；越大边际递减越强；
- `size_max` 全局统一，默认 10.0，不按球分类型；长期/短期差异靠稳定性 S 实现；
- 饱和后 size 不再增长，但 `last_watered` 照常刷新、管道照常变粗、内容仍可追加；
- `size` 用 f64 存储，写入时 clamp 到 `[0, size_max]`；写入前先物化衰减（§4.6），保证存储里的值不会因跳过物化而“凭空回满”。

```toml
[ball]
size_max = 10.0
size_saturation_gamma = 1.0
size_min = 0.0
size_init_min = 0.1
size_init_factor = 0.5
```

## 9. 管道完整设计

### 9.1 创建（四条来源）

**① 新球接图**（turn_end，判别器创建新球时）：用嵌入与已有 active 球算余弦，取 Top-2 且余弦 > `new_pipe_threshold`（默认 0.5）的球，建弱管道 `w = 余弦 × new_pipe_initial_factor`（默认 0.5）。没有超过阈值的，新球暂时是孤岛——正常状态。

**② 共激活建边**（结算时，可选，默认关闭）：同一次激活中，两个球都产生补充且都进入注入 Top-K，建弱管道 `w = co_activation_initial`（默认 0.1）。

**③ 离线相似补边**（离线巩固时）：孤岛球或图稀疏区域，余弦 > `offline_pipe_threshold`（默认 0.7）且无管道 → 建管道 `w = 余弦 × 0.3`；已有管道但 `w_eff` 低于 `offline_pipe_min`（默认 0.05）且余弦 > 0.8 → 适度加粗。

**④ 手动建边**（纠正/用户显式操作）：直接建管道或调粗，走纠正审计。

### 9.2 变粗（结算强化）

路径上**被水冲过**的管道：`w += 路径相关性 × pipe_strengthen_factor`，饱和 `pipe_thickness_ceiling`。`via_pipe` 集合之外的管道一律不动；同一结算中出现在多条路径上取最大路径相关性强化一次。

### 9.3 变细（惰性衰减）

```
w_eff = w × exp(-Δt / S_pipe)
S_pipe = pipe_stability_base × (1 + flow_count × pipe_stability_growth)
```

- 流动时用 `w_eff` 算阻力，不写回；只有结算强化时才写回 `w`；
- `w_eff` 低于 `pipe_archive_threshold`（默认 0.01）时**不删除**，只是流动几乎过不去——但阻力有上限，强线索仍可突破；
- `S_pipe` 随流动次数增长，经常流动的管道衰减慢。

### 9.4 阻塞记忆（舌尖效应）

每次水流因阻力不足无法通过：`blocked_count += 1`。下次有效阻力 `resistance × (1 - blocked_discount × min(blocked_count_eff, blocked_cap))`，`blocked_discount` 默认 0.1，`blocked_cap` 默认 5，最多降低 50% 阻力。成功通过后不清零、不再增长。`blocked_count_eff = blocked_count × exp(-Δt / blocked_decay)`（默认 7 天）——长期不再被阻挡，说明那条路已经不再难走，次数应逐渐遗忘。

> **实现状态：部分实现。** `Pipe::blocked_effective`（`crates/dayu-domain/src/types/entities.rs`）已实现衰减；阻力加成与结算时的 `blocked_count += 1` 尚未接入 `crates/dayu-flow/src/engine.rs` / `settle.rs`。

### 9.5 合并与重定向

球 B 被球 A 吸收时：

- 另一端是 A → 删除（自环）；
- 另一端是 C 且 A-C 已有管道 → `w = max(w_ac, w_bc)`，`blocked_count = max(...)`，删除 B-C；
- 另一端是 C 且 A-C 无管道 → 重定向为 A-C，保留 `w` 和 `blocked_count`；
- 删除所有 B 的残留管道。

**不叠加权重**：两条管道合并取最大值，不是相加。球分裂时：新球从原球继承组内管道（复制 `w` 和 `blocked_count`），跨组管道按归属重定向，走纠正审计。

### 9.6 归档

**球归档**：由 `DayuCore::archive_sweep` 执行，定时任务与 `dayu archive` CLI 共用。判定为「距 `last_watered` 超过 `archive_inactive_days` 且 `size_effective` 低于 `archive_size_threshold`」两条同时满足；另有容量兜底——活跃球数超过 `max_active_balls` 时按 `size_effective` 升序强制归档最弱的球。归档只改 `status`，`size_stored`、`S`、`last_watered`、`embedding`、内容列表全部保留，不删除、不进独立表。

**唤醒**：归档球与活跃球共用同一份索引（`search_by_embedding` 只过滤 `deleted`），共用同一个 `start_ball_threshold`。被选为起始球即**直接翻回 `active`**，无临时态、无 TTL、无「未强化则回归」。唤醒在结算之前完成（`recall` 取 `depth == 0` 的球调 `wake_archived`）。

**管道**：不归档。管道是球之间的关系，球被唤醒后路就该能用；单独归档管道会制造“球活着但路断了”的怪状态。`archive_sweep` 只改球状态，管道保持 `active`。

## 10. 时效与遗忘

**不删除，只调度。**

- **衰减**：不注水的球自然变小，但**衰减不因读取而写回**——读取时一次算出 `size_effective = size × exp(-(now - last_watered)/S)`（§4.6），**只在结算强化时物化写回**（先衰减、再加增量）；S 随注水次数增长（间隔效应）：
  ```
  S = ball_stability_base × (1 + lit_count × ball_stability_growth)
  ```
  `ball_stability_base` 默认 30（天）、`ball_stability_growth` 默认 0.1，与管道 `S_pipe` 同构；
- **巩固**：反复注水的球 S 增长、衰减变慢，等效于短期变长期；
- **短期不删**：短期记忆永不清理，只降可提取性；强线索放宽阻力阈值，允许沉睡记忆被唤醒；
- **唤醒**：强线索放大起始水量、放大可释放水量、降低被阻挡管道的有效阻力——三条规则叠加，任何管道在足够强线索下都能突破；
- **饱和上限**：见第 8 节；
- **归档**：距上次注水超过 `archive_inactive_days`（默认 90 天）且 `size_effective` 低于 `archive_size_threshold`（默认 0.2）时归档；活跃球超过 `max_active_balls` 时按 `size_effective` 升序强制归档最弱的球。归档球不删除，仍参与检索，被命中即翻回 `active`。

## 11. 纠正机制

**审计先行**：任何纠正先写 `correction_log`，再改状态。

**纠正类型**：删除内容/球、更新球描述、合并/分裂球、删除管道、忘记球、拒绝召回。

**流程**：同事务内写审计 → 改状态（软删默认，硬删需二次确认）→ 强度按贡献扣减或迁移（不为负、不重复计数）→ 下一轮注入体现更正说明或降低权重。

**对称操作**：用户否定 = 放水缩球；用户确认 = 注水 + 球变大 + 管道变粗。

**可逆性**：软删保留原值与原因；`correction_log` 记录原值，支持反向操作。隐式纠正标记 `contested`，不直接删除，离线巩固再确认。

## 12. 存储与持久化（TriviumDB）

### 12.1 存储位置

- 主库：`~/.dayu/store.tdb`（可配置），dsh 和 pi 指向同一路径；
- 冷存储：同库内独立 Node 类型或独立 `cold.tdb`；
- 配置：`~/.dayu/config.toml`（与数据分离）；
- 备份：`~/.dayu/backup/`。

### 12.2 TriviumDB 特性承接

| 原需求 | TriviumDB 承接 |
|---|---|
| WAL 持久化 | 原生 WAL |
| 原子事务 | Dry-Run 预检 + WAL + COW 隔离 |
| 多进程并发 | 进程级文件锁（Writer 排他，Reader 共享） |
| 线程并发 | 线程级 RwLock / Mutex |
| 快照隔离 | MemTable 读锁，一致的逻辑版本 |
| 崩溃恢复 | 定点 I/O 故障、进程强杀场景已验证 |
| 向量检索 | QuIVer ANN，高维自动激活 |
| 图遍历 | TQL MATCH + EXPAND |
| 文档查询 | TQL FIND，MongoDB 风格 |

### 12.3 持久化保证

- 事务提交即 WAL 持久化；进程被 kill -9 不丢已提交事务；
- 每个写入单元是一个原子事务（结算、新球、归档、纠正），不存在半完成状态；
- 启动时自动重放 WAL、回滚未提交事务；TriviumDB 内置恢复流程；
- 定期备份用 TriviumDB 的原子替换或应用层 `copy` 快照。

### 12.4 原文过大处理

三层处理：
- 写入时 `rmw-utf8` 压缩（中文短文本压至 21%–39%）；
- 内容条数截断（默认 5）；
- 冷热分层（热=注入渲染的代表性内容，温=内容列表完整原文，冷=淘汰内容+归档球，存独立 Node 类型）。单条内容长度上限可配（默认 4000 字符），超出截断为“前 N 字符+摘要”，原文转冷存储。

## 13. 并发与一致性

- 流动开始开 TriviumDB 读事务加载子图，记录全局版本号 `V_start`，结束读事务；
- 结算开 TriviumDB 写事务（写锁 + Dry-Run 预检），校验版本号：
  - 无冲突 → 直接写；
  - 有冲突 → 重读涉及球/边重算增量再写（乐观并发）；
- 强度更新用 TriviumDB 的原子增量 `$inc`，不用读-改-写；
- 非原子结算模式：逐条写入，失败记 `pending_retry`，下一轮或启动时重试；
- 注入不依赖结算成败——结算失败或冲突重算失败，注入照常进行，下一轮重试强化。

```toml
[concurrency]
global_version_check = true
conflict_strategy = "recompute"    # recompute / abort
max_recompute_balls = 50
atomistic_settle = true
```

## 14. 工程边界条件

- **新球接图**：创建时用嵌入与已有球算余弦，取 Top-2 且 > `new_pipe_threshold` 建弱管道；否则孤岛，等强线索直接命中或离线补边。
- **冷启动**：图空时当前输入直接创建新球，注水不扩散；前 N 轮提高新球初始大小或降低阈值，避免碎片。
- **兜底合并**：新球创建前查已有球余弦 > `merge_cosine_threshold`（默认 0.95）→ 不建新球，追加内容 + 强化已有球。
- **球合并**：离线巩固时，内容嵌入余弦 > 0.95 且管道权重 > 0.9 的两球合并，大球吸收小球，管道重定向取最大值。
- **判别器接入**：turn_end 异步判定是否产生新球；新球创建走独立事务；判别器不参与流动与结算。
- **敏感内容**：写入前敏感模式检测，命中则脱敏或标记默认不激活。
- **记忆开关**：支持会话级暂停记忆。
- **可追溯**：注入块携带球/内容引用（不展示给模型，UI 可查）。

## 15. 规模管理

按 **200–500 轮/天、极端 5000 轮/会话** 估算：

- 一年 **1.5 万–6 万球**；两年 **3 万–12 万球**；
- 管道每球 2–3 条，一年 **3 万–18 万条**，两年 **6 万–36 万条**；
- 总存储约 **700 MB–1 GB**；TriviumDB 单文件承载。

**分层策略**：
- **主图（active）**：参与流动和结算，控制在 `max_balls`（默认 30 万）的 80% 以内；
- **归档状态（archived）**：不参与常规流动，但仍参与检索；被检索命中即直接翻回 `active`（无临时态、无 TTL）；归档触发条件：距 `last_watered` 超 90 天且 `size_effective` 低于 0.2；活跃球超 `max_active_balls` 时按有效大小升序强制归档；
- **冷存储（cold_content）**：内容原文，注入回源时按需读取，带球 ID 索引。

**起始球选择优化**：
- TriviumDB 的 QuIVer ANN 自动处理向量检索，球数超过阈值自动激活索引；
- 应用层不再需要嵌入分桶或手写 ANN。

**极端长会话**：
- 每 500 次结算后强制 checkpoint（如果 TriviumDB 暴露该能力；否则由 TriviumDB WAL 自动管理）；
- 监控 WAL 增长，必要时手动触发 checkpoint。

```toml
[archive]
archive_inactive_days = 90.0
archive_size_threshold = 0.2
max_active_balls = 10000
cold_content_max_gb = 10
checkpoint_after_settle = true
checkpoint_interval_settles = 500
```

## 16. 与外部组件的关系

**压缩插件是可选适配器，不是依赖**：
- 有它：折叠前补充归档被折叠区间、高优先球可受保护注入、可通过账本回源；
- 没它：核心在每轮结束已自行归档内容，摘要和抽象由自己的离线巩固产生，全流程完整。

**依赖方向**：适配器 → 压缩插件；核心绝不 import 压缩插件的代码、事件或存储。CI 检查核心依赖树。

| **M4 跨客户端与巩固** | 6–10 周 | dsh/pi 共享存储、离线合并/分裂、归档与回源、可选压缩适配器 | 跨客户端召回；原型收敛；归档球可强线索唤醒；TriviumDB 多进程文件锁验证 |
| **M5 规模验证** | 按需 | 30 万球 / 60 万边压测、QuIVer ANN 索引验证、WAL 增长监控 | 起始球选择 <10ms；结算延迟毫秒级；总存储 <1GB；无性能断崖 |

**核心验收指标**：结算同步延迟毫秒级；注入不切割球内容；TriviumDB 崩溃恢复无需人工；纠正审计完整；配置化覆盖所有系数；管道无向权重共享；30 万球规模下起始球选择与流动加载不退化。

## 19. 设计边界（明确不做什么）

- 不做多用户、多 persona 隔离；单用户，领域标签软加权防串味；
- 不做通用 RAG 知识库；
- 不替代压缩插件，不把压缩插件作为运行时依赖；
- 不保证“注入即被采用”，只保证“该想起时能想起”；
- 不追求实时离线巩固，巩固是离线增量过程；
- 不删除短期记忆，只让其自然沉底、可被强线索唤醒；
- 不设“管道永久封死”，只设阻力上限；
- 不做“流动即写入”，流动只点亮，结算才强化；
- 管道是无向权重，不分上下游；
- 注入不切割半个球，要么完整注入，要么不注入；
- 不依赖 SQLite 或外部向量库；TriviumDB 是唯一存储依赖。

## 20. TriviumDB 集成注意事项

**优势承接**：
- QuIVer ANN 高维向量检索性能是 HNSW 的 2.9–3.8 倍（768–1536 维）；
- 三模原生融合避免多库拼接；
- WAL + Dry-Run + COW 隔离提供原子性与崩溃恢复；
- 进程级文件锁天然支持多客户端并发。

**需要适配的差异**：
- **TQL 替代手写查询**：起始球检索、子图加载优先用 TQL 表达；
- **事务粒度与性能**：结算高频写入需关注 TriviumDB 事务开销，可用分组提交优化；
- **文档查询规模边界**：10 万节点内亚毫秒；百万级节点全表扫描延迟上升至 5–7ms，避免频繁全库属性过滤；
- **图遍历规模边界**：局部子图遍历（5 跳、50 球）压力小；远超设计约束的复杂遍历缺乏公开大规模验证；
- **成熟度**：GitHub 星标约 166，生态早期；长期维护风险、API 稳定性、社区支持需持续关注；
- **数据迁移**：如果已有 SQLite 数据，需编写迁移工具转换为 TriviumDB Node/Edge 格式；
- **版本兼容**：0.9.0-beta 及后续版本迭代中，依赖新特性（如 QuIVer ANN）时关注 API 稳定性。

**回退策略**：如果 TriviumDB 在生产验证中出现不可接受的问题，存储层可替换回 SQLite + sqlite-vec 方案——`dayu-core` 的业务逻辑与存储层通过 trait 抽象解耦，回退只改存储适配层，不改流动/结算/纠正逻辑。

### 21.1.1 qid：跨调用串联的查询标识

`qid` 标识**一轮对话**（一次 `judgeTurn` → `recall` → `archiveTurn` 归为一轮），是插件端与 Rust 端日志对齐的唯一键。

| 规则 | 说明 |
|:--|:--|
| 生成 | 调用方不传时由 Rust 生成：`{毫秒时间戳:013x}{进程内序号:04x}{pid低16位:04x}`，共 21 字符 |
| 透传 | 插件端拿到返回的 `qid` 后，在同一轮内所有调用**原样回传** |
| 不使用宿主 ID | 宿主的 turn id / message id 粒度与本系统不一致，不能替代 `qid` |
| 日志 | 每个入口函数开 `info_span!("recall" | "judge_turn" | ...)`，字段 `qid` |

`QueryId::from_input(Option<&str>)`：传了就用，没传就生成——插件端**不需要预先生成**。

对应 Rust 门面方法（`DayuCore`）：`recall` / `recall_with_qid` / `recall_by_embedding` / `recall_multi` / `recall_multi_with_qid` / `judge_turn` / `create_ball` / `link_balls` / `get_ball` / `list_balls` / `set_ball_status` / `archive_sweep` / `wake_archived` / `stats`。

### 21.3 调用约定

- **不要跨 `await` 持锁**：napi 层先取 `Arc<CoreState>` 快照再 await，`MutexGuard` 不是 `Send`。
- **ID 分配**：`allocate_ball_id` / `allocate_pipe_id` 单调递增，未提交也会消耗（可接受）。
- **多源结算**：`recallMulti` 的结算语义相似度目前取**第一个源**；严格做法是逐球取 `max cos(源, 球)`，待 `SettleEngine::settle` 支持多向量后再改。

### 21.4 日志与指标

`init` 时按 `Config` 的 `[observability]` 段初始化 `tracing` 订阅器，三路物理分离：

| 输出 | 内容 | 过滤 |
|:--|:--|:--|
| 控制台 | 人类可读 | `log_level` |
| `logs/dayu.<date>.log` | JSON 全量（含 span 上下文） | `log_level`，排除 `target = "dayu::metric"` |
| `logs/metrics.<date>.jsonl` | 仅指标事件，一行一条 | 只收 `target = "dayu::metric"` |

分流的意义：日志是给人 `rg` 的证据链，指标是给 `jq` / pandas 聚合的数值流，两者保留周期与采样策略不同，混在一起两边都难用。

指标事件字段固定为 `kind` / `name` / `value` / `labels`，并携带当前 span 的 `qid`：

```bash
# 按 qid 还原一轮的完整指标流
jq -c 'select(.span.qid == "001a1bbce70850002cf7c")' logs/metrics.2026-11-08.jsonl

# 统计每次回忆点亮的球数分布
jq -r 'select(.fields.name == "lit_ball_count") | .fields.value' logs/metrics.2026-11-08.jsonl
```

已埋点的关键量：`flow_trigger_rate` / `lit_ball_count` / `flow_loss_by_pipe_weight` / `flow_supplement_by_pipe_weight` / `path_supplement_loss_ratio` / `injection_token_used` / `reinforced_ball_count` / `reinforced_pipe_count`。

`triviumdb` 的日志默认压到 `warn`（每次 flush 都打 INFO 会淹没业务日志），需要时可写 `log_level = "debug,triviumdb=debug"` 单独放开。

---

**一句话总结**：大禹水利记忆网络以球的大小承载记忆强度、无向管道粗细承载关联、水量承载激活，流动只点亮、结算同步决定注入；管道粗细同时决定阻力和损耗——粗管好过且损耗小、细管难通过且损耗大，损失是 w_eff 的确定性函数；补充加在扣损之后，补充大于损失当且仅当球大、与水源同向、与当前输入相关；多出边时水按 `1 + w` 加权分配（粗管多分、细管少分但保底非零），先分配再判断、过不去的损失不回收，`split_mode` 可配以支持对照实验；管道无向共享权重、四条创建来源、路径级强化、阻塞记忆降阻、永不删除只变细；注入预算两种模式统一遵守"不切割完整球"；短期不删、强线索可唤醒；纠正审计先行、软删可逆；所有系数可配置；LossModel 可替换 trait 支持对照实验；存储内核为 TriviumDB，原生承接向量、图、文档三模与事务、并发、WAL 持久化。疏而不堵——记忆不是被清理，是被调度。
