# 大禹水利记忆网络 · 实施方案规划

**文档性质**：执行规划，不是设计文档，不是算法文档
**核心内容**：阶段顺序、每阶段交付物、可执行的验证标准、进入下一阶段的门槛
**原则**：每个阶段结束都是一个可运行、可回退的稳定状态；不完成验证不进入下一阶段

**当前状态（2026-11-08）**：`MemoryStorage` 已删除，`TriviumStorage`（真实 TriviumDB 0.9.0）是**唯一**存储实现，测试也跑真实 `.tdb`、靠临时目录隔离。下文阶段 2–10 中"纯内存"的表述是**历史规划记录**，保留原样以体现当时的决策路径；阶段 10 的存储接入已完成。


## 一、总体策略

**先把业务逻辑在纯内存里跑通，再接真实存储；先用 Mock 后端跑通判别与嵌入，再接 ONNX 模型；先在一个客户端上验证，再扩展到第二个；先跑通在线路径，再做离线巩固和可观测性。**

这个顺序的理由是：业务逻辑（流动、结算、注入）是系统的心脏，它不依赖 TriviumDB、不依赖 ONNX、不依赖 Node 运行时。把它在纯内存 + Mock 后端里跑通并测试充分，后面的存储接入、模型接入、napi 绑定都只是在已验证的心脏外面加壳，风险可控。

**每个阶段结束都是一个“可运行 + 可测试 + 可回退”的状态。** 回退方式是 `git revert` 到该阶段结束的提交，不需要回滚数据库或模型文件。

### 阶段 2：内存存储与流动引擎（1.5 周）

**目标**：用 `MemoryStorage` 跑通“起始球选择 → 注水 → 流动 → 点亮”的完整流动，不涉及结算和真实存储。

**交付物**：
- `dayu-storage` 的 `MemoryStorage`（`test` feature 下），实现 `StorageBackend` 的全部方法
- `dayu-flow` 的 `FlowEngine`：起始球选择、注水分配、逐跳流动、阻力判断、补充计算、安全阀
- `dayu-flow` 的单元测试：用 `MemoryStorage` + `MockEmbeddingBackend` + `MockClock`
- `dayu-testkit` 的 `build_chain_graph()`：构造一条 N 跳链用于流动测试

**验证标准**：
- `cargo test -p dayu-flow` 全部通过，测试覆盖：
  - 起始球选择：余弦低于阈值不选、Top-N 正确、无球超阈值返回空
  - 注水分配：按余弦占比分配、强线索放大
  - 流动：水量 > 阻力才通过、损失由管道粗细决定（w_eff 函数）、同一次激活每球只注一次
  - 多出边分配：按 `1 + w_eff` 加权、`w=0` 的出边分到非零水量、过不去的损失不回收、`split_mode="equal"` 时等量
  - 补充：补充加在扣损之后、球大且与水源同向且与当前输入相关时补充 > 损失、小球/反向时补充 < 损失
  - 安全阀：`max_flow_depth` 触顶该方向停止、`max_lit_ball_count` 触顶不再点亮
  - 管道：无向权重、`blocked_count` 递增、阻力折扣
- **性能基线**：单次流动（50 球子图、5 跳）在 `MemoryStorage` 上 <1ms（用 `criterion` 测）
- **依赖方向检查**：`dayu-flow/Cargo.toml` 的 dev-dependencies 里不出现 `triviumdb`

**门槛**：流动引擎的单元测试全绿，性能基线达标，可以进入结算阶段。

**下一步**：阶段 3，在流动之上加结算。


### 阶段 3：结算与注入（1.5 周）

**目标**：跑通“流动 → 结算 → 强化写入 → 注入排序 → 渲染”的完整在线路径，仍然用 `MemoryStorage`。

**交付物**：
- `dayu-flow` 的 `SettleEngine`：路径相关性计算、多路径取最大值、强化球/最低强化球划分、路径长度折扣（不含管道健康因子，已废弃）、饱和函数、注入排序、三级渲染
- `dayu-flow` 的注入预算两种模式（token 映射、球数映射），统一“不切割完整球”
- `dayu-flow` 的单元测试：结算后球大小/管道粗细增量正确、多路径取最大值、最低强化值、注入不切割球
- `dayu-testkit` 的 `assert_ball_size_after_settle()` 等断言辅助函数

**验证标准**：
- `cargo test -p dayu-flow` 全部通过，新增覆盖：
  - 结算：强化球增量 = 路径相关性 × 系数 × 边际递减；最低强化球增量 = 固定值
  - 多路径：同一球出现在两条路径上，取最大路径相关性，不累加
  - 饱和：球大小不超过 `size_max`，接近上限时增量递减
  - 注入预算：token 模式下不切割球、球数模式下固定条数
  - 渲染：相关性高/中/低三级文本格式正确
- **端到端测试**：`MemoryStorage` + `MockEmbedding` + `MockClock`，从“用户输入”到“注入块列表”跑通，断言注入块内容
- **性能基线**：单次结算 + 注入 <2ms（含渲染）

**门槛**：在线路径（不含判别器、不含真实存储）端到端跑通，测试全绿。

**下一步**：阶段 4，接入配置系统，让所有系数可配。

  - WAL：进程模拟崩溃后重开，已提交数据不丢

- **端到端切换**：`DayuCore` 从 `MemoryStorage` 切到 `TriviumStorage`，阶段 6 的端到端测试全绿
- **性能基线**：单次流动 + 结算 + 注入 <10ms（含 TriviumDB 读写）
- **多进程测试**：两个进程同时打开同一 `.tdb`，一个读一个写，不冲突

**门槛**：TriviumDB 存储全绿，端到端切换成功，性能达标。

**下一步**：阶段 11，napi 绑定。


### 阶段 11：napi 绑定与 TS 薄适配层（dsh）（1.5 周）

**目标**：把 `DayuCore` 暴露为 napi 模块，在 dsh 上跑通“钩子注册 → 事件转发 → 尾部注入”。

**交付物**：
- `dayu-napi`：`recall`、`judge_turn`、`archive_turn`、`correct_memory`、`get_stats` 的 `#[napi]` 导出
- DTO ↔ 领域类型转换
- 错误映射：`CoreError` → 带 `[CODE]` 前缀的 `napi::Error`
- `nianxiang-dsh-plugin`（TS）：注册 `session/event` 和 `agent/pre-step`，转发事件，拼装尾部注入
- dsh 插件的最小验证脚本

**验证标准**：
- `cargo build -p dayu-napi` 成功，生成 `.node`
- `cargo test -p dayu-napi` 通过（只测 DTO 转换）
- **dsh 端到端**：在 dsh 里装插件，跑一轮对话，断言：
  - `session/event` 触发 `archive_turn`
  - `agent/pre-step` 触发 `recall`，注入块追加在消息尾部
  - 前缀字节不变（用 diff 对比注入前后的 system prompt）
- **错误映射**：模拟 `TriviumStorage` 写入失败，TS 侧收到 `error.message` 以 `[TRIVIUM_` 开头

**门槛**：dsh 插件能装、能跑、注入不破坏前缀。

**下一步**：阶段 12，pi-agent 适配。


### 阶段 12：pi-agent 适配（0.5 周）

**目标**：复用 `dayu-core`，为 pi 写薄适配层。

**交付物**：
- `nianxiang-pi-extension`（TS）：注册 `before_agent_start`、`turn_end`、`session_before_compact`
- pi 扩展的最小验证脚本

**验证标准**：
- pi 端到端：跑一轮对话，断言：
  - `turn_end` 触发 `archive_turn`
  - `before_agent_start` 触发 `recall`，注入块用 `display: false` 不可见注入
  - `session_before_compact` 触发归档（如果启用了压缩插件适配器）
- **跨客户端共享**：dsh 写入的球，在 pi 的 `recall` 里能召回（同一 `store.tdb`）

**门槛**：pi 插件能装、能跑、跨客户端召回成功。

**下一步**：阶段 13，离线巩固 CLI。


### 阶段 13：离线巩固 CLI（1.5 周）

**目标**：摘要、抽象、合并/分裂、归档、管道衰减、诊断规则跑在独立 CLI 里。

**交付物**：
- `dayu-cli`：`consolidate summaries`、`consolidate abstractions`、`merge`、`split`、`archive`、`decay-pipes`、`diagnose` 子命令
- 离线巩固的 LLM 调用（摘要/抽象）走本地小模型或 API，带每日预算上限
- `dayu-cli` 的端到端测试：用 `tempfile` 创建临时 `.tdb` + `MockJudge`，跑一次完整巩固，断言球数收敛、归档球进入归档表

**验证标准**：
- `cargo test -p dayu-cli` 全部通过
- **巩固效果**：构造 100 个球（含 20 个相似球），跑 `merge`，断言球数减少、无数据丢失
- **归档触发**：构造 30 万球（用脚本批量插入），跑 `archive`，断言球数回落到 24 万以下
- **每日预算**：`diagnose` 子命令输出结构化诊断信号（JSON），不自动改配置
- **崩溃恢复**：CLI 中途 kill -9，重开后 `pending_retry` 表有记录，下次巩固重试

**门槛**：离线巩固能跑、能收敛、能归档、诊断输出可用。

**下一步**：阶段 14，可观测性完整接入 + 动态调参。


### 阶段 14：可观测性完整接入与动态调参（1 周）

**目标**：Prometheus exporter 就位，诊断规则输出结构化信号，配置版本化与回滚可用。

**交付物**：

- `param_change_log` 表：记录每次配置变更的 `{version, parameter, old, new, trigger_signal, operator}`
- `diagnostics.jsonl`：诊断规则的输出
- 配置版本化：每次变更生成 `config_version`，指标按版本打标签

**验证标准**：

- **诊断信号**：构造"损失主导占比 >0.6"的场景，`diagnose` 输出"建议降低 `loss_pipe_factor`"的信号；构造"补充不足占比 >0.5"的场景，输出"建议提高 `max_supplement_ratio`"

**门槛**：指标可拉取、诊断可输出、配置可回滚、审计完整。

## 六、执行原则

**每个阶段结束时，必须能回答三个问题**：① 这个阶段的交付物能不能跑？② 验证标准是不是可执行的检查项（不是“看起来对”）？③ 回退到上一个 tag 后，系统是否仍然可用？

**不满足验证标准不进入下一阶段。** 尤其是阶段 2（流动）和阶段 3（结算）——这两个阶段是系统心脏，如果测试不充分，后面接真实存储和模型时，任何 bug 都会被放大到难以定位。

**阶段 8 和 9 的模型接入是风险最高的两个阶段**，因为涉及外部模型文件和环境。如果 ONNX 加载遇到问题，**先停在 Mock 后端，用阶段 6/7 的端到端测试继续推进阶段 10（TriviumDB）**——存储接入不依赖真实模型。模型接入可以并行排查，不阻塞主路径。


## 七、一句话

**先纯内存跑通流动、结算、注入（管道粗细同时决定阻力和损耗，LossModel 可替换），再接配置和可观测性（指标拆分 loss/supplement 两个主导维度），然后用 Mock 后端跑通判别和嵌入，再接 ONNX 模型，最后接 TriviumDB、napi、两个客户端、离线巩固和规模压测。每阶段有可执行的验证标准、明确的回退 tag、不达标不进下一阶段。模型接入是风险最高的两阶段，遇到问题先用 Mock 继续推进存储和客户端，不阻塞主路径。**
